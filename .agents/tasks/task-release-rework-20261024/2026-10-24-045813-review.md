### 结构化准备失败的信任链

```
publish-main.mjs --prepare-only --result-file <packet>/invocations/<uuid>.json
   └─ main() 失败 -> recordPreparationFailure（wx，仅 prepare-only）
runPublisher（仅 args 含 --prepare-only 且非零退出）
   └─ readNativePreparationFailure：路径、键集、三个 false、mainCommit 与包内请求一致、回执哈希
drainPreparationQueue
   └─ validatePreparationTerminal + inspectAttempt 无标记 -> failed（带 dispatch 引用）
      否则 -> unknown（原行为）
```

写死的 `publicationStarted/maintenanceStarted:false` 依赖 `publishPreparedMain` 在 `context.prepareOnly` 时于 STARTED.json 之前返回（publish-prepared-main.mjs 第 247 行起）；deploy 调用 `run(prepared.source,[])` 不带 `--prepare-only`，`runPublisher` 不读结果文件。尝试目录标记检查是第二道闸，同时覆盖原生失败和 `rejected-before-native`。

`rejected-before-native` 不带证据，靠代码位置可信：`beforeNative` 只包住 `once`、指针写入、`inspect` 和复用核对，`run(...)` 及其后的断言未包。副作用是复用路径上任何 `inspect` 或复用核对的失败（包括瞬时 git 错误）都会退休一个可能已有有效 PREPARED 的包，换来一次约 28 分钟的完整重新准备，状态工具对此不知情（第 6 项）。

每次读清单都会重新读盘校验 dispatched `failed` 的结果文件哈希，结果文件因此成为队列与发布入口共同的硬依赖（第 4 项）。

### 放弃资格与准入顺序

```
unresolved dispatch
  ├ 全部票 unknown 且属于该 dispatch
  ├ 无 resolution
  ├ now >= deadlineUnixMs + 15 min
  ├ publish-<t12>/ 只含 preparation、LEASE-WARNING.json（缺目录视为空）
  └ 真实轮换管道可 listen+close
        └─ 全部满足 -> abandoned/<id>.json（consumePermitted:false），原 results 字节不动
```

消费者自身崩溃时没有终态，按 `!terminal` 仍然阻塞，不会被放弃；原生 prepare-only 在 `withRotationLock` 内完成准备，探测管道名与 `worker-local-release-rotation.mjs:67` 相同。生产 a3d53227 只读核对：1 张票 unknown，期限 2026-10-22T08:11:22Z，尝试目录只有 `preparation/PREPARING.json` 与 `source-binding.json`，采用后会被放弃。

顺序问题（confirmed）：

```js
if(unresolved&&abandonment){ ... await durableCreate(path.join(directory,'abandoned',...)) ... if(abandoned)continue; }
if(unresolved){ ...blocked...; break; }
try{await admitPreparation();}   // 普通用户与消费者身份准入在此
```

放弃记录永久保留并解除全局阻塞，比 `blocked` 终态更强，却不经过 `assertConsumerIdentity`/`assertOrdinaryPreparationContext`。资格只看证据，不会产生错误的放弃；但随后被拒绝准备的宿主（例如提升权限的窗口）也能执行这一不可逆写入，与“只有普通用户消费者推进队列”的约定不一致。

### 退休包：发布入口与状态工具

发布与检查入口在 `runLatestMainCliOperation` 中调用 `readRetiredPackets(config)`，与消费者共用 `retiredPreparationPackets`/`preparationPacketSlot`，`prepareLatestMainOnce` 与 `inspectMainPreparation` 各再拒一次退休包。

新依赖（confirmed）：`readRetiredPackets` 走完整的 `readPreparationQueueInventory`。发布模式持队列锁，但 `submitPreparation`（hook 与 准备main.bat）不取队列锁，`durableCreate` 先以 wx 打开再写，读者可能读到空文件并以“Noncanonical, duplicate or partial queue JSON”失败；检查模式完全不持锁。若某个退休包的 `invocations/<uuid>.json` 被移动或改动，此后准备与发布都失败关闭，直到人工处理。这些都不会误发布，但影响可用性，而 REPORT 只写了检查模式。

状态工具 `main-prebuild-status.mjs` 只看 `LATEST-PREPARED.json` 指针与包内文件：被放弃的包在新指针写入前显示“打包尚未完成”，复用路径被退休的包可能显示“打包完成”并弹窗。手册第 6 步让用户用它观察进度。

`-rN` 分支名不被 `preparation-retirement-ref.mjs` 的 ref 栅栏与 `preparation-retirement-collector.mjs` 的 nativeFrozen 正则匹配，REPORT 已列为已知限制并说明进程内由 `assertRetirementAdmission` 把关，不重复计为问题。

### 控制代际的单向性

基线 `ticketResult` 对 `failed` 只允许 `[...base,'error']`（confirmed），新写出的 dispatched `failed` 会让旧代际的 `readPreparationQueueInventory` 整体抛出；旧代际也不读 `abandoned/`，a3d53227 会重新阻塞。手册只写“没有一键回退，未演练”，没有说明出现新形状终态后回退会让准备完全停住。
