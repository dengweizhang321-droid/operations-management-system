## High-level view

追加闭包而不是替换，是这次唯一兼顾两类读者的做法。resolution 的校验用 `closures.some`，写入按 `closures[0]` 的键序收集 packet 自带 `source/tools` 的字节，3 个闭包键与键序相同，所以历史 f641685b packet 和新 packet 都能通过；退休资格与 collector 只看 `closures[0]`，a3d53227 的历史 packet 不受影响。工具、测试里没有代码固定旧资格文件哈希或假设只有 1 个闭包；它在 `operatorNames` 里，但历史 resolution 是对照各自冻结 bundle 的 MANIFEST 校验，不对照当前仓库，只读核对生产队列 9 份历史 resolution 均可读。代价是资格面多了一个只在控制分支存在的 S05d 闭包，它是精确字节匹配，不会放进未审查代码。

夹具改动保住了测试原意：collector 与 integration 模拟的本来就是“历史 packet 由已审查的旧生产者构建”，现在直接读 `tests/fixtures/reviewed-producer-f641685b/`，3 个文件与 a6cc9fcd 的 blob 是同一对象，固定字节断言原文不变，`-text` 防止换行转换改动字节。原先“仓库当前生产者必须等于审查字节”这道绊线由没改的 preparation-resolution 两个测试接管：它们用当前字节构造 packet，以后再改生产者文件仍会失败。superseded、collector、integration、entry 在沙箱内起子进程超时，没有实际跑过；脚本对它们是失败关闭的（基线通过即“新失败”中止）。

脚本的快进逻辑可核对且不破坏：本地分支只在等于 `087a8348`/`d1b60496` 时升级，先取对象到 `FETCH_HEAD` 并核对等于新头与祖先关系，检出中的分支在其工作树里 `merge --ff-only`（要求工作树停在旧提交且无已跟踪改动），未检出的用 `update-ref` 比较并交换；分离头的控制测试工作树 `checkout --detach`；其他任何值中止不覆盖。重跑幂等。PS 5.1 的两个陷阱都处理了：数组元素里的拼接都加了括号，git、robocopy、cmd 的 stdout 都送 `Out-Host` 或显式捕获，新增函数不往管道输出。联接只在 `node_modules` 不存在时新建，删除用不带 `/s` 的 `rmdir`，只删登记过的。缺口在复用联接不登记（Issue 2）。

环境规则收窄本身对那两个测试是对的：fixed-schema-rejection 复制的 `controlFiles` 缺 `preparation-retirement-admission.mjs`、main-publication-readiness 的候选包清单缺 `publish-main-step.mjs`，按代码在 a6cc9fcd 就同样失败，S05d/S16 没有新增工具间 import（只多了 `node:net`），所以名称比对不会掩盖本分支新缺的文件。它重新打开 v1 关心的“两侧同因环境失败当既有问题”的地方在依赖副本：基线工作树现在也联接同一副本（Issue 1）。

文档如实记录了中止、根因、修复和新身份，三处旧说法都在原句处标注更正，fixed-schema-rejection 与 main-publication-readiness 没有被写成通过。两处措辞偏宽（Issue 3、4）；v2 指出的 S09 切换说明不完整在这次改到的同一句里仍未补（Issue 5）。

### 环境规则与基线比较

新规则 `Cannot find package|Cannot find module \\?'(?![A-Za-z]:[\\/]|\.{1,2}[\\/]|/|file:)` 对早上的 4 条日志判得对：`typescript`、`esbuild` 是裸包名，算环境失败；`D:\codex-artifacts\...\preparation-retirement-admission.mjs` 和 JSON 转义的 `C:\\Users\\...\\候选包\\tools\\publish-main-step.mjs` 是绝对路径，进入基线复跑。环境类本身是阻断类，所以收窄只会把原来阻断的情况交给基线判定，风险只在“两侧同因失败”。

```
被测工作树 ──junction──┐
                        ├──> deps-8ec00f\node_modules   (同一份)
基线工作树 ──junction──┘
副本缺 node_modules\pkg\x.js -> 两侧都报绝对路径 Cannot find module -> 同名失败 -> 既有问题
```

早上基线工作树没有 node_modules，这类问题会以 `Cannot find package` 阻断；现在两侧共用副本，规则又按路径形状判定，于是失去这道区分（Issue 1）。`Ensure-Dependencies` 只核对锁文件哈希与 3 个路径，不核对副本完整性；本次用 `robocopy /L` 只读比对，源与副本 3160 个目录、31418 个文件无差异，锁文件一致时脚本不会重新复制，所以这次运行的实际风险低。

### 快进与工作树

没有在沙箱里实测的部分：从草稿仓库的真实 fetch、快进时真实仓库 reference-transaction hook 的运行、robocopy 复制路径（FEAT-003 `not_verified` 已如实记录）。工作树内 `merge --ff-only` 遇到会被覆盖的未跟踪文件会拒绝，新路径只有夹具目录下 3 个文件，与早上测试留下的未跟踪文件冲突的可能很小。
