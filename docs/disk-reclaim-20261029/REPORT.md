# D 盘空间回收：查清与方案（2026-10-29）

只读调查产出。未删除、移动或修改任何文件。

## 0. 结论

**找到 38.66 GB 可回收空间，全部是构建产物与历史发布工作目录，不是生产数据，不需要等备份线修复。**

这比原先盯着的 release 目录更适合先下手：release 的 33.77 GB 需要修好备份才能让工具回收、另 49.96 GB 任何工具都碰不到；而这 38.66 GB 只是缓存。

## 1. 为什么现在查这个

原判断是「56 GB 不紧迫、可以等」。改判的原因是实测到**一小时内 D 盘从 56 GB 掉到 54 GB**，而同期 release 目录数未变（仍 343 个、111 个未瘦身，今日零新发布）。即有别处在持续吃盘，而所有回收机制都停着：

- release 保留清理：等 PG 备份成功才触发，备份自 10-19 起失败
- 链外 release 49.96 GB：按策略永不自动清理
- 本文发现的 38.66 GB：无任何自动清理机制

## 5. 方案

### 方案一：只删 78 个无人引用的发布包（最保守，推荐先做）

回收 **10.88 GB**。只动 `main-release-packages` 下除 `1b02c93791bb-d349107e-99df9f68` 以外的 78 个目录。

**为什么安全**
- 生产两侧清单都只引用那一个，已逐字段核对；
- 全部对应活 git 提交，可重建；
- 不碰 `teruisi-runtime`，不需要停机、不需要维护模式、与备份线无关。

**执行前复核**：重读 Django `deployment.json` 与 Worker 生效头 manifest，确认 `sourceRoot` 仍指向保留的那一个；确认无在飞发布（`state/worker-release-publication-staging` 为空）。

### 3.4 引用核查：两个任务目录名出现在生产快照里，但不是运行时依赖

逐个比对 66 个任务目录名与生产清单后，命中两个：`ai-release-candidate-20261013`、`ai-schedule-repeat-fix-20261015`。

进一步查清：命中位置在 Worker 生效头的 `source-snapshot/docs/ai-release-blockers-20261013/{RELEASE_PLAN,REPORT}.md`，即**历史文档正文里提到了这两个目录名**，属文字提及。两者**都不在 `deployment-manifest.json`**，没有任何运行时路径依赖。

即删除它们不会破坏生产，但会让那两份历史文档里的路径引用失效（文档本身在快照里仍完整可读）。**结论：可删，但在方案二里应单列说明，不要当成"无人引用"一笔带过。**

### 方案二：方案一 + 63 个超 7 天任务目录（回收最大）

回收 **38.66 GB**。

**额外风险**：任务目录里可能有未归档的证据或未提交改动。执行前须逐个确认目录内无未跟踪的有价值文件——63 个目录逐一核对是实打实的工作量，不能只看时间戳。另见 3.4：其中两个目录被历史文档正文提及，删后那些路径引用会失效（不影响生产）。

建议拆成两批：先删 10-16 及更早的，观察一周无异常再处理其余。

### 方案三：暂不处理

空间仍有 54 GB，短期不会满。但回收机制全停、且在持续下降，拖下去只会更被动。不推荐。

## 6. 安全边界

- **绝对不动**：`main-release-packages/1b02c93791bb-d349107e-99df9f68`（生产 Django 制品与 Worker 生效头的共同来源）。
- **不动**：`main-manual-release-20261016`（10-29 仍有写入，可能在用）及另两个近期目录。
- **不碰** `D:/teruisi-runtime/` 任何内容——本方案与 release 目录、备份完全无关。
- 删除前确认无在飞发布与准备流程；删除属生产维护动作，需用户授权（AGENTS.md 第 6 条）。
- 建议删除前先 `Move` 到同盘临时目录、观察一轮再真删，可快速回退（但同盘移动不释放空间，需二次确认后删）。

## 8. 追加发现：这批空间在持续增长，不只是历史遗留（2026-10-29）

调查期间发布包从 79 个变成 **80 个**——有自动化在为 `main` 的提交生成发布包，**纯文档提交也建全量包**。实测最新两个：

| 包 | 对应提交 | 生成时刻 | 大小 |
| --- | --- | --- | --- |
| `93a13d7b4d03-…` | `93a13d7b` 本次文档提交 | 10-29 01:48 | 144 MB |
| `79255ad6c2fc-…` | `79255ad6` 协调会话文档合并 | 10-29 00:14 | — |
| `1b02c93791bb-…` | `1b02c937` 生产在用 | 10-28 20:58 | 146 MB |

按日生成量（实测）：10-17 共 17 个、10-18 共 14 个、10-20 共 12 个，高峰约 **2.5 GB/天**；近几日 1–8 个。

**这改变了结论的性质**：这不是一次性的历史垃圾，而是活跃产物。删掉 10.88 GB 存量只能缓解一次，不治本。

### 由此多出一个候选

**方案四：加保留策略（治本）**

为 `main-release-packages` 加保留规则，例如只保留「生产在用的 + 最近 N 个」，其余自动回收；并考虑**纯文档提交不建包**（本次 `93a13d7b` 只改了一份 md，却生成了 144 MB 全量包）。

- 优点：一次解决，不必反复人工清理。
- 代价：要先找到生成这些包的自动化入口（本轮未查，不在只读范围内），属改发布工具链，范围中等，需单独评估。
- 顺序建议：先做方案一回收存量（立即见效、低风险），再评估方案四（治本）。

### 对执行时机的影响

既然有自动化在写这个目录，删除前必须确认**没有正在生成的包**，否则可能删到半成品或与写入竞争。执行时应：

1. 先确认当前无在飞准备/发布（`state/worker-release-publication-staging` 为空、无 `app.deploy-*` 暂存目录）；
2. 保留清单按「执行那一刻重新读取生产两侧 manifest」确定，不要用本报告里的静态列表——生产在用的包可能已随新发布变化。
