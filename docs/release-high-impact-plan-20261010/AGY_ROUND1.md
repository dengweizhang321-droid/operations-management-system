### 核心立场与现场观测对齐

基于 [`current-observation.json`](file:///D:/.codex/worktrees/release-high-impact-plan-20261010/运营管理系统/docs/release-high-impact-plan-20261010/current-observation.json)（2026-10-10 16:14 截点），当前 AB 批次第 10 步 `actual-readonly-ui` 发生 `nonzero_exit (26.8s)` 后被独立协调判定为 `failed`，批次保持 `active` 且未 `completed`。本轮严格遵循红线：**不对当前执行者换绑、减免、重放或发号施令**。

此前 P0 仅缩减 5～15 分钟边角时间，无法满足用户对“显著提速”的诉求。但提速决不能通过跳过 Python/源码完整散列、TTL 替代现场 Status、活动表白名单或放宽动态门禁来伪造。在严格遵守现行规约的前提下，必须重新排序真正能削减“数十分钟”用户等待的高收益路线。

### 一、首选路线：单前驱多改动精确合并为复合严格批次（如 ABC 替代 AB＋C 串行发布）

* **历史毛成本**：每次独立严格发布包含端到端交付 167～279 分钟，其中 4 数据库阶段占用 50～55 分钟（2 次 Backup + 2 次 Restore）、Worker 排空与切换 3～6 分钟、现场验收（UI/权限/自然观测）15～25 分钟、收尾全库深比较 10～15 分钟；批次间等待历史上曾达 145.1 分钟。若串行执行两批，用户需承受两轮完整停服与交付等待（理论合计 160～240+ 分钟）。
* **替代核验成本（已测/已知）**：合并批次**不降低任何安全等级**，仍为 21 步 STRICT/FULL 门禁。替代成本仅为**发布前的多变更联合回归测试与独立复审**。已测数据：ABC 候选准备用时 11.58 分钟，相较 AB 的 9.27 分钟仅增 2.31 分钟；206 项联合回归已在隔离环境全部通过。
* **日常后台成本与频率**：零日常后台常驻开销。仅在同一代码前驱下存在多个待发布独立特性时按需触发。
* **首次投入与依赖**：已有现成 ABC 候选（[`EXACT_AB_BATCH_PLAN.md`](file:///D:/.codex/worktrees/release-high-impact-plan-20261010/运营管理系统/docs/release-integration-review/EXACT_AB_BATCH_PLAN.md#L16-L18)），依赖各变更独立 review 证据闭合、联合回归通过，以及用户单次严格批次授权。
* **适用范围及回退**：适用于共享同一基线、无合并冲突且各自具备独立证据链的变更集合。回退策略：若联合准入失败，立即回退为逐个单批次发布；切换若异常，触发单批次原子回滚。
* **验证收益算式**：
  $$\text{净省等待} = (T_{\text{DB(4阶段)}} + T_{\text{排空切换}} + T_{\text{现场验收}} + T_{\text{收尾比较}} + T_{\text{批次间等待}}) - \Delta T_{\text{联合准备}}$$
  $$= (50\sim 55 + 3\sim 6 + 15\sim 25 + 10\sim 15 + T_{\text{等待}}) - 2.31\text{分} \approx 75\sim 98+\text{分钟}$$
  这是唯一**不改规约、不降防护、具备完整证据**，且单次直接消除 1 小时以上重复等待的高确定性路线。

### 二、支持路线：准入接缝打通与只读准备身份内存复用（保留每字节与动态门禁）

* **历史毛成本**：历史批次中准入子项单项耗时达 22.9～42.0 分钟（已内含于总交付中，不可与数据库阶段累加），主要开销在于跨阶段反复唤起外部 Python 子进程、重复全量遍历 7918 物理闭包及大树散列。
* **替代核验成本（部分已测 / 生产未知）**：保留 Python/源码完整散列与动态门禁，打通 Node wrapper 与 in-process transport，复用已通过隔离验证的 10分钟/24次私有内存身份；8 有界并发读取已测由 8.16 秒降至 4.11 秒，三阶段准备身份已测节省 21.6～24.2 秒。替代成本为内存失效机制与 Windows 并发句柄保障；生产端到端总交付节省目前为工程预估（8～15 分钟），尚无全包实测。
* **日常后台成本与频率**：零日常后台开销，仅在发布执行期生效。
* **首次投入与依赖**：依赖 wrapper 与 C 接缝完成 ABI 联调，保持安全读取协议，严禁降级物理 walk。
* **适用范围及回退**：100% 适用于所有严格批次与非严格批次。回退机制：任何内存哈希不匹配或超时，立刻降级为原逐文件物理全扫。
* **验证收益算式**：
  $$\text{单批准入节省} = \sum_{k=1}^{M} (T_{\text{重复进程启动}} + T_{\text{重复物理IO}}) - T_{\text{内存核查}} \approx 8\sim 15\text{分钟（假设预估，待生产配对实测）}$$
  可与首选路线完美叠加，进一步压榨单次严格批次内的机器等待。

### 三、延后/不值得路线：现阶段盲目推进“持续恢复资格”或“强扩展示分类覆盖交互UI”

* **历史毛成本**：4 数据库阶段虽耗时 50～55 分钟，但**历史 3 个批次均为严格批次；四文件 UI 因含可执行交互与网络行为，依规约仍判定为严格批次**。
* **替代核验成本与风险**：若强行将可执行 UI 划为展示级，需构建极其复杂的客户端 AST 与全链路无副作用证明。今日 16:14 现场第 10 步 `actual-readonly-ui` 发生 `nonzero_exit` 证明交互在运行时的脆弱性，强行绕过数据库备份极易造成生产数据灾难。
* **日常后台成本与频率**：按 [`DAILY_BACKUP_ADOPTION.md`](file:///D:/.codex/worktrees/release-high-impact-plan-20261010/运营管理系统/docs/release-fastpath-evidence/DAILY_BACKUP_ADOPTION.md#L3-L15)，需将调度 `e` 改为 ACTIVE，每日 22:30 自动备份并紧接调用隔离恢复演练（实测单次演练需 11.77 分钟），每天固定消耗约 25 分钟后台高 I/O，且三份轮换下新点会淘汰旧演练点，维护成本极高。
* **适用范围及拒绝理由**：在现行规约下，纯展示类发布的历史适用率为 **0%**。在缺乏纯静态展示发布样本的前提下，投入重型日常演练换取理论免除，实际单次发布等待减少量为 **0 分钟**。
* **验证收益算式**：
  $$\text{期望净节省} = P(\text{纯展示批次}) \times 50\text{分钟} - (30\text{天} \times 25\text{分钟日常后台开销}) = 0\text{分} - 750\text{分/月} < 0$$
  **结论**：在未出现高频纯展示需求前，明确拒绝将其作为当前提速方案，避免陷入“高运维开销却无落地场景”的空转。
