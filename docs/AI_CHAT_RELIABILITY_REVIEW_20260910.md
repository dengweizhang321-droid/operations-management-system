# AI 无法回复的复盘与稳定性改造建议

## 结论与证据边界

历次故障并非同一个原因。这次新增的 HTTP 400 与凌晨修复引入的参数回归相符：昨天下午已实测确认当前火山方舟 Plan 端点拒绝关闭 GLM 思考，凌晨代码却按模型名称猜测能力，在收尾阶段再次发送 `thinking.type=disabled`。隔离测试用真实端点、模型配置和本次耗时分支复现了该错误；纠正后同一用例通过。此前审计没有保存供应商 HTTP 错误正文，因此不能宣称已取得本次供应商返回的具体拒绝说明。

调查使用本机只读 API 和 AI reader 审计作为 MCP 不可用时的替代来源，仅核验故障、配置和调用状态。本报告不输出经营数据结论。原始用户消息、推理正文和凭据不进入证据文件。

## 本次即时修复

- 删除按 GLM 名称猜测“支持关闭思考”的逻辑，所有轮次统一遵守已保存的端点配置。收尾只改变工具集合与指令。
- 对已完整接收且明确结束的有效空响应，在既有预算内最多收尾一次；该行为不再依赖模型名称，也不新增供应商参数。超时、HTTP 拒绝、未知结束原因、无效 JSON 和内容过滤不自动重发。
- 每次派发记录查询/收尾阶段、实际思考参数是否省略、工具数量；HTTP 拒绝额外保留状态码，不保存上游错误正文或密钥。
- 回归夹具覆盖实际 Ark Plan/GLM 组合、时间触发收尾、空正文触发收尾、其他兼容端点、明确保存的关闭思考配置、Anthropic、HTTP 400/429/503、无重复付费调用、配额和审计拒绝。

本次不改变用户的默认模型、模型额度、业务事实源、数据库结构和角色。正式版本与上线验收结果在本报告末尾补录。即时修复不等于以下长期改造已经完成。

## 建议调整对话处理方式

现有链路让模型在一次最长 260 秒的请求中选择工具、反复查数、分析并生成正文。即使本次参数回归消失，慢响应、输出预算、复杂工具选择或连接中断仍可能使整条问答失败。更稳定的方式是把“可靠拿到数据”和“模型解释数据”拆成有状态的步骤。

1. **常见查数采用固定查询流程。** 日期、指标、商品/店铺身份先解析并核验，调用 Django 已有有界只读 consumer，立即生成带来源、截止日期、筛选及指标口径的数据卡。型号有多个候选时先澄清；不得把含糊型号直接猜成品类。模型随后补充解释，模型失败时仍展示已核验的数据和明确状态。
2. **复杂分析改为可恢复的后台任务。** Django 保存任务、步骤、工具结果引用、租约与派发回执；前端提交后取得任务号，通过状态查询或 SSE 展示进度，刷新后恢复。模型未知结果不得自动再次付费；已完成的只读数据步骤按 revision/有效期复用，不能把旧数据悄悄当作最新数据。
3. **按实际端点验证模型契约。** 配置与“供应商＋完整 API 路径＋协议＋模型”绑定；普通回复、工具返回、收尾、空正文、限流等关键路径都有契约测试。禁止根据同名模型推断另一供应商支持的参数。减少每轮无关工具，但保留按真实权限发现其他业务域的入口。
4. **以固定场景集验收。** 同时覆盖 12 板块入口、单日/多日、型号歧义、多域分析、刷新恢复、超时、400/429、空正文和重复请求。建议先建立至少 20 条固定业务场景、分时运行 3 轮的真实样本，记录成功率和中位数/高分位耗时；这是建议的验收方案，尚未执行，不能拿少数成功样本代替。

暂不建议仅换一个模型名称。当前已配置的多个模型仍使用同一 Ark Plan 服务，不能自动视为独立的容灾线路。后续可用同一场景集比较现有候选，再决定主备；引入另一供应商涉及新配置、数据发送目的地和费用，需在具体方案确定后按授权采用。异步任务改善进度与恢复能力，也不能保证供应商永不故障；可靠数据卡和明确失败状态应始终可用。
