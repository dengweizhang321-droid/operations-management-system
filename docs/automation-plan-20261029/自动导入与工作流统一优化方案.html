01 建议先统一管理与证据，再开放配置

能够做到参考方案的使用效果，但应采用“统一管理界面 + 原有专业执行器 + 各业务域权威回执”的路线。

这五份资料是一段持续演进的设计：先接入数据源与自动导入，再从硬编码链路转向规则，再重做展示，最后拆成模块。TERUISI 已有多店下载、缺口规划、内容幂等、原任务续接和专用浏览器，主要欠缺是这些能力在用户面前还没有形成统一、完整、可信的操作闭环。

看得清同一处查看计划、运行、模块、批次、覆盖和需要处理的异常。
改得准规则有版本、能力边界与生效回执；修改不影响在途任务。
恢复有据根据原任务证据提供可执行动作，保留已完成数据和未知结果。

最终用户体验应是：选择平台和主体 → 看今天应做的事 → 看实际完成的数据 → 点开具体障碍 → 执行系统允许的处理 → 自动关联恢复后的结果。日常操作不必翻多份日志，必要技术排障仍能进入 n8n。

本方案纳入全部工作流的管理边界；导入、AI、通知、运维使用各自的成功标准。统一界面不意味着统一调度器、统一重试次数或统一业务写入方式。

不能直接照抄的冲突

  • 参考系统已转向内置调度与全局串行 worker；本系统仍有 n8n、平台 helper、AI 自有队列及领域写入隔离。照搬会引入第二套任务所有者。
  • 规则化文件 §13.1 的最终决定推翻了前文部分旧建议：改为新规则唯一配置源、不限规则数、关规则不取消 pending 等。它们属于另一用户的决定，本系统须明确自己的开关语义和容量边界。
  • 模块化文件 §6.4 选择 S2“一规则一任务”，后面队列唯一键、runner 字段和跨 runner 示例仍残留 S1。实施前必须确定本系统的身份模型，不能混用。
  • 模块化文件“20 + 2 + 1”与总数 25、表内条目不一致；模块数量应由本系统注册目录生成，不把参考数字当验收要求。
  • “今天生成新批次”不能作为唯一成功条件：无缺口、未到期、内容重复均可能是正确结果；必须返回原因、原批次或权威覆盖证据。
  • 不照搬新旧生产各跑一次的迁移方式，避免重复平台导出与同范围写入。观察接线不授权新业务执行。

03 当前系统已有的基础与真正缺口

本次以仓库主线为事实基础，未查询生产运行状态、未补跑工作流。当前生成目录有 8 类导入链路、17 份工作流配置、13 个主体，这些是源码登记数量，不能解释为 17 条均已在线启用。

能力已存在需要补齐
使用入口主导航“自动化中心”；数据导入含文件、运行记录、链路规则。自动化中心作为运行操作主入口；数据导入保留批次视角并复用同一规则组件，避免另建第三个中心。
规则矩阵按工作流与主体展示；30 秒刷新 n8n 今日状态；详情可进入 n8n。升级日程、按主体、模块覆盖；补模块结果、配置差异、生效版本和失败处理入口，技术链路在详情保留。
运行记录并发读取七个领域最近批次；展开显示文件、行数、告警。后端有界历史检索与分页；关联下载前失败、整条运行、执行尝试和批次。当前前端分页仅限已读取集合。
执行状态Django 只读 n8n 元数据，识别自动执行与有证据的完整手动成功。执行成功、数据完成和通知投递分列；加原计划范围、缺口、部分完成和新鲜度，不能只看 n8n 绿色状态。
恢复操作主线已有吉客云完整重试、新采集、从头采集及一键闭合相关入口。复用已有能力，明确操作条件与当前采用版本；逐平台增加适配。不能把吉客云操作不加区分地复制给所有平台。
策略一致性店铺目录、策略文件、模板、生成目录及页面说明。由有效策略生成展示。现有天猫三日旧说明、客服/物流时点差异需要消歧，先显示“未核实/有差异”，再按采用事实修正。

主线存在某项功能，只证明源码已支持；一键闭合等近期增量是否正式部署须另查采用回执。本方案不将主线、候选和生产混称。

备份、守护、发布准备与上线原运维进程身份、互斥、版本和用户逐步授权继续保留。仅汇总健康或提供原入口链接；不通过通用“重试/运行全部”启动发布、迁移、恢复或终止服务。
导入链路先落地统一契约；非导入流程先做只读登记和跳转。尚无接口或尚未登记的外部任务标为待接入，不能宣称已穷尽所有线上任务。

05 架构：统一记录，不另造事实源

现有 React 页面 / 薄 Worker
真实账号、范围校验、请求解析、展示与受控动作入口。
↓ Django 自动化管理服务（复用 workflow 领域基础）
模块目录、规则版本、逻辑运行、动作请求、证据投影、异常视图与审计；新增能力放 Django。
↓ 原执行所有者
n8n 保持导入定时与完整 execution；平台 helper 做专有登录/下载/恢复；AI、市场与运维仍由原队列负责。
↓ 各 Django 业务域
销售、库存、ERP、网店、市场、客服等保留唯一写入权；权威批次、内容幂等、覆盖与 revision 通过原 consumer 返回。
↑ 脱敏结果回传与有界对账
原任务、文件签收、模块结果、精确批次、覆盖与资源收尾共同形成可查询运行视图。

最小数据模型

对象含义与必要字段
模块定义稳定 moduleKey、适用平台/主体、所属业务域、依赖、日期政策、成功证据要求、允许的恢复能力、契约版本。数据库中的可编辑值不得携带任意脚本、URL 或文件路径。
规则与修订ruleId、revision、subjectKind/subjectKey、modules、schedule/timezone、datePolicy、资源组、enabled、adapterVersion、草稿/待采用/已生效状态及审计。
逻辑运行logicalRunId、规则快照、固定业务范围/计划日、触发来源、原始计划摘要、总体状态。手动重跑新采集与恢复原运行明确区分。
执行尝试attemptId、原生 workflow/executionId、父尝试、恢复原因、阶段、开始/结束、错误分类和原生证据引用。一条逻辑运行可有多次尝试。
模块结果moduleKey + 精确主体 + 数据集 + 日期/快照范围；下载、校验、导入、回查、收尾状态；当前上传文件身份与历史复用批次身份分开。
证据与动作所属域 + batchId、rawFileHash、内容指纹、coverage/snapshot revision、行数/告警；动作 requestId、授权主体、固定目标、阶段、回执及投递结果。优先扩展原有写请求/投递账本，不复制一套业务批次。

控制面只存标识、状态和脱敏摘要，不复制销售明细、客服原文、Cookie、账号密码或浏览器目录。业务完成只能由原领域的证据证明；控制面丢失连接时显示“无法核实”，不能写零或猜成功。每项结果另带证据状态（已核实/过期/缺失/矛盾）、来源和观察时间。

状态必须分成三条轴

  • 执行：未到期、待领取、排队、执行中、失败、待人工、结果未明、已结束。
  • 业务：未开始、部分完成、已提交待核验、已核验、无需新增、剩余缺口。
  • 投递：不需要、待发、已发送、失败、结果未明。

例如“数据已核验，通知未送达”不能退回重跑导入；“n8n 已结束，覆盖未核验”不能标成业务完成。关闭旧任务显示“已闭合，部分数据保留”，不是“已完成”。

观察与写入边界

已有 n8n SQLite 继续只读、白名单、有界读取，不直接修改其表。补充脱敏阶段事件接收或增量对账，按 source + eventId 去重；checkpoint 记录观察进度，保留来源时间与 checkedAt。运行列表由服务端过滤分页，返回 total/returned/truncated，避免浏览器最近 50 条冒充历史全量。事件乱序或来源删档时保持未知，并保留原有证据索引。

06 规则配置与模块拆分

规则应表达“谁，在什么时候，对什么范围，使用哪些已注册能力”，不要让用户配置内部脚本。第一阶段只读；完成计划和回执接线后，才逐项开放编辑。

可配置项约束
主体、平台、模块来自后端注册目录；不适用项隐藏或禁用。依赖模块一起选；不支持单独执行的模块只能作为组合的一部分。新增店铺需先完成注册和凭据就绪，不自动继承其他店会话。
周期与时点Asia/Shanghai，显式“停用/仅手动/定时”；展示实际采用版本。期望规则和 n8n 调度读回一致后才能标生效。漏跑策略与失败重试分开。
数据日期选择已注册政策：滚动 45 天、月内补缺、近七日补缺、实际快照日等。按平台能力允许的边界调整，不能用一个通用“昨天”覆盖全部模块。
重试与资源默认继承适配器的有效政策；不允许任意突破点击未决、次数封顶或平台限额。配置层可降低并发，但不能放宽底层店铺/浏览器根锁。
生效与变更读取 revision → 保存草稿 → 校验依赖/冲突/影响 → 预览未来运行范围 → 显式应用 → 原生读回 → 生效；并发修改用 CAS 拒绝覆盖。

n8n 是导入定时触发的唯一所有者，Django 不再增加一个独立 cron。规则应用通过受控 n8n 管理适配器或既有采用流程完成，页面不接触 n8n 凭据；未接通该能力时只支持草稿和导出待采用配置，必须明确标识。

在途任务固定使用启动时的规则快照；更新规则只影响后续新运行。停用规则仅停止新触发/领取，已有排队或运行中的具体处理单独列出，不默默取消；申请取消必须按原执行器支持处理。旧执行和迟到回调仍受 owner/租约版本约束，不能因规则改名获得新执行权。

同一主体、模块及重叠业务范围不得因多条规则而重复派发。定时槽以稳定规则身份与计划时刻去重，恢复复用原逻辑运行；手动新采集有独立请求身份但仍受资源锁和业务范围锁约束。规则改版不自动补跑旧时点。批量建规则可在 Django 内原子保存草稿，跨多个 n8n 工作流的应用需逐项回执与协调状态，不能冒称跨系统事务一次全成。

不采用“一个规则强制等于一个物理任务”。一条规则对应一次逻辑运行，底层可以是一个 n8n execution、四店串行子步骤或多日循环；只有平台适配器证明可独立执行的模块才允许拆成独立任务。

  • 自动化中心：运行总览、链路规则、运行记录；n8n 画布保留在“高级/原生流程”入口。

08 恢复、重试、漏跑：分别设计

情形系统应采取的动作用户看到的结果
短暂只读/下载网络失败执行器按白名单错误和既有总期限重试已绑定对象；不重新生成报表。原任务仍在恢复，剩余次数与下一时间来自有效政策。
登录、验证码、身份不符停止相关业务动作，保留清单；返回明确人工步骤。身份不符不能回退别店。待人工及受影响范围；必要时按现有规则私人提醒。
导出提交或派发结果未知查询原任务/请求回执；有证据后按专用协议续接，不能换 ID 重发。结果未明；普通重试禁用，显示原因与可核查入口。
部分模块已经入库保持原批次，按平台支持恢复未完成部分并重新核验整链；不存在合法续接时等待处理。部分完成，明确保留数据；不把所有模块清零。
文件内容重复业务域按“域 + 精确范围 + 完整规范化内容”判断；签收本次文件并关联原批次。重复跳过 / 复用批次，新增数为 0，不混淆原文件哈希与内容指纹。
错过定时时点独立检查应运行时间槽、活动尝试和覆盖；按允许政策生成唯一补跑意图，经原生完整入口领取。漏跑或已被后续完整运行满足；不能认为失败重试会补一个不存在的 execution。
作废或闭合只走平台已支持的管理员入口，固定旧任务、保留证据；按原执行器已支持的取消/围栏能力核验旧派发与迟到写入的拒绝。不删除批次，也不声称能撤销已经发生的外部点击。已闭合 / 部分保留；新任务是另一项动作。

资源协调继续遵守“helper 所有者 + 浏览器共享根锁 + 各域写锁”。性能优化先消除重复查询和下载、提前查缺口、独立读取并行；只有资源真正独立的队列才增加并发。不得为了提速让共享 Chromium 四店同时启动。

跨日恢复必须保留原计划日、原文件与原批次身份，不能自动把昨天失败改成今天成功。重试预算按逻辑运行计，恢复产生新 execution 也不能重置次数。采集时间、业务日期和执行日期分别保存。

09 不做站内信，仍然能形成完整闭环

异常处理直接附着在运行记录上。总览给出“待人工 / 持续阻塞 / 无法核实”的筛选与数量，进入对应运行后处理；不建设独立收件箱、已读标记、消息红点和通知中心。

需要的效果本系统实现
知道今天是否完成运行总览显示应执行、已核验、正常无需新增、未完成与无法核实；可直接看到数据截至日期。
知道要自己做什么运行详情显示错误分类、具体操作、已完成部分和允许动作；需要人工时沿用本人钉钉单聊。
完成后有反馈整条工作流达到原业务成功与收尾要求后，按现有规则发送一次完成摘要；不逐节点轰炸。
不重复提醒按逻辑运行与故障事件去重；换 execution 不换完成事实。发送未知先查原回执，不能盲目重发。
消息发不出也能处理业务结果保留；页面记录未投递及原因，只恢复投递部分，不重跑导入。

通知专项文档明确：人工协助发本人单聊，完成和无需人工动作的状态通知保留原群；每次发送前动态核验身份与机器人。导入规范中的旧“全部发群”摘要与之冲突，施工时应统一引用专项规则，不能据旧段改变收件人。本次只提出方案，没有发送任何消息。

10 施工顺序：每一阶段都交付可见能力

P0 · 固定基线与消除配置歧义

交付：工作流/模块/主体完整登记表；仓库模板、有效策略、采用版本和在线观察来源分列；修正页面旧文案；形成原链路能力及依赖矩阵。

完成效果：页面能区分“已登记、待采用、已启用、未知”，不再把模板频率当在线事实。将客服、物流时点和天猫主数据周期差异纳入明确处理清单。

P1 · 打通运行与数据证据，交付统一页面

交付：Django 运行投影、事件/回查适配、服务端过滤分页；逻辑运行→原生尝试→模块→批次/覆盖详情；三视图与异常筛选。先适配吉客云与一个天猫店的两种典型结构，再接现有全部导入家族。

完成效果：登录前失败也有记录；整链成功与数据结果可区分；部分成功、无需新增、结果未明均有准确展示。此阶段不修改原生调度。

P2 · 统一受控操作与通知闭环

交付：已有吉客云动作收口到统一详情；其余平台按能力提供完整运行、原任务恢复、漏跑补齐、显式闭合；requestId、固定目标、权限、回执与操作审计；现有钉钉渠道的投递状态关联。

完成效果：不必到日志里猜该怎么操作；重复点击或刷新仍指向同一请求；通知异常不会触发业务重放。未支持的动作明确禁用并说明。

P3 · 开放规则编辑与模块编排

交付：规则草稿/修订、依赖校验、范围预览、冲突检测、受控应用与原生版本读回。按平台逐条切换规则来源；在途运行保留原快照。

完成效果：用户能在系统调整允许的周期、主体和模块组合，并知道何时生效。n8n 唯一定时所有权不变；执行器不接受未登记脚本。

P4 · 其他工作流汇总与性能收敛

交付：AI、市场标注、运营归档/周报与运维状态适配；失败分类与耗时统计；无变化状态的有界增量观察；老展示和重复监控口径收敛。

完成效果：一个总览覆盖各类工作，点击进入原领域操作；有依据识别耗时和人工介入来源，逐步减少重复扫描与无效下载。

推荐先做 P0 + P1，再推进 P2/P3。只有页面改版不能达到参考方案的施工效果；没有运行证据底座就开放编辑，会把配置混乱扩大。工期应在 P0 核实真实采用版本、接口缺口与改动清单后估算，本次不以文件篇幅推算天数。

预计涉及的代码区域

前端复用 app/import-*.tsx、app/n8n-workflow-view.tsx、现有恢复控件及 shell；后端扩展 backend/workflow/ 的自动化管理与原生适配，领域 consumer 仅提供必要证据。目录生成复用 tools/build-import-chain-catalog.mjs；采集变化仅修改对应 tools/*-n8n-pipeline.ts、lib/平台/ 和 automation/n8n/。具体文件、迁移和发布范围在各施工阶段差异形成后确定。

迁移与交付约定

先增量观察、按来源去重，旧历史能证明到哪一层就展示到哪一层；无法关联的旧记录标“历史未关联”，不伪造 logicalRun。新规则按家族启用，任何时刻只有一个定时/执行所有者。新控制能力故障可关闭新增入口，原执行器继续保留原约束；已提交业务数据不做反向回退。

11 怎样判断实现了参考方案的效果

以下是产品完成标准，供未来施工和用户验收使用，不表示本轮已经执行了功能测试。

  1. 新增一个已支持平台的店铺，通过注册与凭据配置接入后，目录、规则、视图和运行记录自动出现，无须复制整页代码。
  2. 规则、链路、矩阵三视图看到同一版本、同一运行；筛选到单店不会扩大到其他店数据。
  3. 一次任务从计划、下载、导入到回查与收尾完整可追溯；下载前失败也能查到。
  4. 每个“完成”都能展开到精确批次/覆盖或明确的正常无动作证据；只有 n8n success 时不冒称业务完成。
  5. 部分成功后能清楚看到已入库模块和剩余项；系统只提供合法恢复动作，旧失败历史不被改写。
  6. 修改周期后显示待应用与实际生效版本；旧任务仍使用原快照，重复或迟到请求不能覆盖新状态。
  7. 错过定时时点可被识别并按政策补齐；定时重试与人工触发相撞时只有一个执行所有者。
  8. 人工协助、持续阻塞和完成通知各按既定粒度去重；无需站内信仍能完成发现—处理—回查。

用哪些数字评估优化价值

先采集同一观察窗口的基线，再比较首次完整成功率、自动恢复后完成率、人工介入次数、数据覆盖及时率、等待/登录/下载/导入/回查耗时、配置漂移数量和重复提醒次数。正常无缺口、未到期与新导入分别计数；不要把少下载的次数直接当稳定性提升，也不要承诺未经测量的提速百分比。
