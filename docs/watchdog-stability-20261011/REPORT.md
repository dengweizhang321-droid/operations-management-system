## 实现

### 稳定性取证

`tools/operations-system-watchdog.ps1` 记录 control、supervisor、monitor 阶段耗时、完成/失败、整轮完成时间及实际子进程失败元数据。某阶段成功后立即保存本轮结果；后阶段失败保留已经确认的状态、12 个已知组件和精确进程身份。最终期限耗尽单独标记，不再覆盖最先失败的阶段。

HTTP 结果记录状态、原因及耗时，仍使用原 5 秒上限、共同 60 秒预算、禁止代理和重定向、8KiB 正文界限。健康响应要求真实对象、真实布尔 `ok` 和精确标记；错误只保留固定分类，不保留正文或异常原文。新版控制器自带的失败探针摘要也保留；后来独立探针成功不能抹掉先前失败。缺少某个已知组件不能由额外或字符串布尔组件代替。

`tools/django-local-service.ps1` 的核心 Status 增加 reader/writer 原两秒 HTTP 检查的状态、超时/传输/HTTP 分类与耗时，增加核心总耗时。原 HTTP200 就绪判定、进程身份和根 ACL 合同保持。`tools/operations-system-control.ps1` 只把七个固定核心状态、已知探针分类和有界数值传到组合 Status。没有增加生产查询、缓存、重试或自动恢复权限。

同一 incident 增加 `first-failure.json`、`last-failure.json`、发送时快照、恢复尝试回执及恢复确认快照。后续健康只更新兼容的 `latest.json`，不覆盖首个和最近失败证据。恢复操作异常保留固定原因及脱敏进程元数据。

### 通知

- 完整端口采集结果才能显示“未监听”；跳过、失败或迟到的采集显示“未知（检查未完成）”。旧非空结果仍可显示已观察到的监听端口，旧空结果不能证明未监听。
- `alert_only` 改为“已告警，未自动重启”，消息写明失败组件、探针、阶段、可用耗时及北京时间。检查错误显示“待确认”，不笼统声称存在未知进程。日期统一 `yyyy-MM-dd HH:mm:ss`，避免月日顺序歧义。
- 同一事件故障通知与恢复通知采用不同持久化槽和回执文件。原故障通知可能已送达（sent/sending/unknown）且同一 fence 的两轮健康通过后，补发一次恢复事实。unknown 故障消息不重发、不改判 sent；恢复是独立的新事实。持续健康不重复通知；从未进入发送的短暂事件不额外发恢复提醒。
- 发送前仍动态唯一核验原本人和机器人，保留原单聊路由。两类通知都先写持久化 sending，再调用 dws；即使状态丢失，也从对应通知回执阻止重放。没有运行 TestNotification 或任何真实消息发送。
- 本轮只查询当前 dws leaf Schema/Help，未取得真实发送的原始成功回执，不能认定历史 `delivery_unconfirmed` 的结构根因。新增投递布尔、失败计数和结果容器形状的固定元数据，帮助下次自然发送取证；未知结构仍保留 unknown，不猜字段、不重发、不改判 sent。
- 恢复通知的身份核验若失败，留下独立未投递回执并正常关闭健康事件；不为通知失败保留一个假故障事件，不自动重发已进入发送的结果。该次恢复的身份失败没有后台补发队列，需检查回执后人工处理。
