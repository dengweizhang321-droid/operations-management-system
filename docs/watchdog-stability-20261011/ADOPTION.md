本任务的源码已在独立工作树完成修复和验证。按[开发与交付](../规范/开发与交付.md)的“合并不等于上线”和[验证与发布](../规范/验证与发布.md)的生命周期门禁，实际生产安装或部署须在本次方案明确确认后执行。

## 独立看门狗候选

候选保存于 `E:/codex-artifacts/watchdog-stability-20261011/candidate/`，文件及 SHA-256 见 [交付回执](DELIVERY.json)。仅安装独立 `operations-system-watchdog.ps1`，配对当前实际已安装的 `process-deadline.ps1` 与原无控制台 launcher 源；不借用另一份同名 helper。隔离回归从这个精确副本加载候选函数和配对 helper。

采用前重新只读核验已安装脚本/helper/launcher/installation、现有计划任务 Execute/Arguments/WorkingDirectory、运行状态和业务就绪。任何字节或绑定变化均重新审查，不能拿准备时快照代替现场验证。保存精确旧脚本、helper、installation 和任务定义作为恢复材料，保留现有 incident/alert 状态。

等本轮计划任务自然结束后，由候选原 `-Action Install -Execute` 执行受控安装。原安装器会 Enable/Start 现有一分钟看门狗任务，并允许既有安全自动恢复及原单聊故障通知，新版增加一次恢复通知；此项实际外部效果属于待确认范围。操作不重启正常业务服务，不做故障注入或手工 TestNotification。

验收包括安装摘要和任务绑定回读、原全套系统状态、至少两轮自然看门狗完成、正常时不发通知。失败场景已在隔离验证，不能为生产验收人为制造故障。计划任务启用后若自然遇到故障，仍执行原恢复权限和预算；不能把“安装无需重启”理解为停用自动恢复。

安装失败或兼容性回读失败时，按刚保全的精确旧脚本/helper/installation 恢复独立监控，重新核验原任务绑定。不回退已写的通知预留或 incident 审计，否则可能导致重复外发；不杀未知进程或重放未决恢复操作。

## 核心后端细化诊断

完整能力还需要 `django-local-service.ps1` 和 `operations-system-control.ps1` 的新增字段真实采用。当前独立看门狗兼容尚无这些字段的旧控制器，不虚构核心 reader/writer 内部原因；先采用看门狗仍能修复端口状态、保留每次事件和阶段耗时，并补发恢复消息。

这两个核心受控工具不能直接覆盖运行目录或主工作区。必须从实际已部署 Worker/Django 来源建立精确候选，对全部部署包、依赖、原迁移及门禁完整差异核验，确认只引入本任务增量，再走既有 PrepareApp/不可变 release/部署与恢复协议。最新 main 的整文件包含其他任务改动，不能把本任务“三个源文件”冒充生产包恰好三处变化。

本任务已完成完整源码和构建验证；没有生成或批准一个可直接替换当前后端的完整运行包。后续正式发布准备应绑定本报告的精确增量，并在实际切换前提供完整候选/影响/恢复证据。独立看门狗采用不授权这两个核心工具的部署、服务重启、迁移或业务写入。

## 稳定性后续判定

安装后观察真实失败的首个/最近失败快照、阶段耗时、控制器探针摘要和恢复尝试。核心细化字段采用后，再判断 core 失败属于 PostgreSQL、进程身份、reader/writer HTTP 还是 ACL。根因未证实前不提高 60 秒整轮预算、不扩大自动恢复权限、不把后来的健康覆盖原失败。

告警数量减少、两轮自然健康或隔离回归通过，都不能单独证明长期稳定性已经恢复。只有新的失败证据与有针对性的修复、同类场景验证及足够自然观察，才更新根因结论。
