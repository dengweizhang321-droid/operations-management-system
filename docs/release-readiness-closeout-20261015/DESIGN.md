## 交付选择

**本轮采用纯契约和模板，复用现有发布工具；不新建批次框架、不改运行时、不新增生产准入门禁。** 用户“按照上面的建议执行”授权本轮优化实施，并要求所有 agent 后续统一遵守；这不是对未来任意版本的上线授权。

将稳定要求合入 [验证与发布](../规范/验证与发布.md) 的“统一发布交付契约”，作为唯一规范正文；三份填写模板由总控保存到 `docs/运维/部署与启动/release-delivery-templates.md`，只列字段和填法并回链正文，不再维护规范副本。[发布批次协议](../运维/部署与启动/release-batch-workflow.md) 只增加短链接，保留候选／采用状态及现有命令、封存和续接语义。根 AGENTS 只补一条强制入口，建议并入原第 5 条：

> 所有 agent 执行发布时，必须遵守《验证与发布》的“统一发布交付契约”，记录就绪证据、精确异常分支和完整交付计时，并复用现有工具执行。

由执行者将书名换成正文锚点链接。本设计保留为方案与取舍证据，合入后注明正式正文位置，不在本文件维护第二套长期规则。无需另建 `RELEASE_CONTRACT.md`、额外 AGENTS 副本或另一套 JSON 批次 schema。

本轮可完成的是统一所有 agent 的行动顺序、证据字段和报告口径；不能宣称已达到 15 分钟，也不能把规范更新说成发布批次协议或自动 hook 已在生产采用。

目前尚无一个现成 hook 自动将“就绪卡 → 发布 → 离线报告 → 文档推送 → 闲置清理”贯通，也没有机器强制所有 agent 已阅读契约。最小实现由发布负责人按模板连续执行已有入口：自动提取已有结构化证据、生成草稿，再核对、推送和保全清理。这是 agent 工作流约束，须如实写明，不能称为新增机器门禁。

收尾报告工具只适用于真实具有原 batch 和完整 WAL 的发布。最近市场第二轮使用的 `PUBLICATION_STARTED.json`、`PUBLICATION_RESULT.json` 等独立回执，不得伪装成该工具的原 batch／WAL。该类记录按同样计时口径整理；缺原批次链时明确记录“不适用 batch 报告生成器”，不造链、不补写过去的 started，也不因此重跑发布。

## 三个阶段的职责与动作

与现行第 4／5／6 步保持一致，不添加“整体验收”阶段。

### 4. 合并前验证并准备异常分支

执行者验证本次改动和直接受影响功能、权限及失败路径。对于会影响发布、恢复或取证的改动，提前准备精确取证命令和异常分支，在隔离环境验证，并完成符合当前模型分工条件的独立审查。使用原脚本和原协议，允许将可复用事实检查前移，不把生产动态成功结果提前伪造出来。

独审覆盖具体实现／分支和证据条件；未来同一精确分支、入口字节和前提不变时，复用这一审查。现场仍须取得本次独立动态证据，证明该分支确实匹配。复用静态方案审查不等于免除独立零效果／完成确认。

### 5. 冻结完整来源，合并并生成对应制品

在首次最终 Prepare 前完成完整来源核对：应用代码、工具和注释、部署闭包、配置摘要、构建输入及被保全的用户改动均进入对应比较。不能到 Prepare 后才发现工具变化，再把 guard 视为可跳过的耗时。

通过相关验证后合并、推送、核验远端，并在隔离交付树从最终来源准备对应制品。若生产组合来源与 main 不同，逐字节绑定经过验证的本次增量和已采用基线，不夹带其他未上线功能。原工具已证明可复用时直接复用；准备阶段构建只做一次，除非实际来源／依赖／前驱等变化使原证据失效。准备失败报告“已合并、制品未就绪”，不触发发布。

本阶段可在线准备、不得改变生产保护入口。即使用户早已说“上线”，前移发生在本轮授权之后的耗时仍计入原总等待。

### 6. 现场发布、处理异常并连续收尾

由一个负责人串行控制生产切换，默认当前普通用户权限。发布前动态核对精确前驱、原入口、进程、权限、互斥、维护／排空和原资格，交给已安装唯一生命周期引擎执行；不以 Markdown“就绪”覆盖门禁。互斥忙时不抢占、不强停其他合法任务，记录真实等待。

发生异常时先保留原 started、失败、unknown 和回执；不靠非零退出、缺少 dump、没有新日志或看似仍正常就宣称零效果。已审分支只有在本次动态证据完整匹配时，才沿原精确协调入口处理为“零效果失败可重试”或“已完成可跳过”。不匹配、证据冲突或无法判定时保持未知及 owner／gate，先做最小补证；仍需改变分支或恢复路径时定向独审。任何协调均保留最初失败，不重写历史为成功。

部署动作成功、目标版本已切换、必要服务可用后即可报告已上线。若既有封存 batch 还有必需动作，则按原合同完成才可称该 batch completed，不通过新文档删除原步骤。随后立即完成原始证据清单、报告草稿及事实核对，推送应入仓的脱敏资料，保全原始受限证据，清理已合入且无运行／发布依赖的闲置树和分支。清理依赖未解除时保留并记录具体理由；不为了清理已上线来源树而停服务。

这些动作计入完整交付时间，不作为新一轮业务验收。离线草稿要求的事实核对不得触发全量业务复验；旧失败的协调证据、重要结论确需独立检查时按当前审查条件定向完成。

## 可复用模板

以下是交给总控落入稳定模板文件的内容草案；采用后仅在稳定模板处维护填法，规范仍只在统一正文维护。所有模板初始状态为“未就绪”，每批填写具体值；空值写明“待取得”“不适用及理由”，不能用 `true`、`已验收` 或模糊 SHA 替代原证据。模板不是 release-batch 的输入，不直接驱动生产。

### 发布就绪卡

```text
初始状态：未就绪（模板默认值，须以原证据填写）
任务／负责人／目标环境：
最早上线授权：时间、消息来源、动作范围
精确候选批准（若另有）：时间、来源；不覆盖最早授权
版本：生产前驱；最终 main；精确组合来源（如有）
范围：原 scope plan 路径＋SHA；完整差异／输入闭包引用
制品：按 scope 填 Worker plan／manifest；Django prepared／receipt
验证与独审：引用；适用源码／依赖／制品；未解决问题
五项判断：验证／数据库保障／维护／切换／恢复边界的原依据
异常预案：适用分支 ID、取证及独审证据；不适用分支说明
已安装能力：原入口／版本／协议；源码候选尚未采用之处
制品就绪时间：原成功回执时间；不能代替现场准入
现场待核：原前驱、进程、权限、互斥、门禁及原计划要求
收尾输入：原 batch/WAL 路径（若实际存在）；否则独立回执清单
结论：具备现场检查条件／制品未就绪；剩余具体缺口
```

### 精确异常分支卡

```text
分支 ID／适用版本、操作及前驱范围：
已审方案及隔离证据：路径＋SHA；审查结论与限制
触发：原 operation ID、started／错误／unknown 回执
本次动态证据：精确进程身份、owner、gate、前后字节／审计等
判定断言：所有必要条件；相反证据／不可证明项
本次独立核验：人员或独立上下文、时间、观察摘要与原件引用
决议：零效果 failed／精确完成 passed／仍 unknown
允许的后续：原协调入口＋精确参数／只跳已确认项／保持停止
失配或未知：需补证或定向独审的问题；不得执行的重放
原失败与等待：原件保留，首次授权和原开始时间不变
```

例：EnterMaintenance 在实际维护效果未知时，只有已审入口的效果顺序成立，且本次原进程终止、前驱与进程谱系未变、持久 gate／相关审计及后续动作证据完整支持零效果，才可按原协议协调。上述是取证方向，具体必须项由对应版本的已审分支确定；单独“没看到 gate”不成立，也不能把最近一次市场发布的零效果结论套给下一次。

### 发布与交付结果卡

```text
上线结论：部署成功／未完成／结果未知；目标组件与版本
原依据：部署回执、实际版本回读、必要服务结果，原失败及协调
batch 状态（如适用）：原 completed／未决；不可用草稿替代
完整计时：最早授权→最终交付；制品就绪时间；就绪后目标窗口
分项：准备、现场检查、首次动作、异常补证/等待、续接、收尾
覆盖说明：区间并集；无打点部分；实际不可用窗口是否有采样
原始材料：清单＋SHA；自动生成的离线草稿仍保留 draft 标记
交付：文档提交／远端核验；受限证据保全；闲置清理或保留原因
未执行／另需授权：迁移、业务补跑、模型实验等按实际填写

```

## 现有工具的接入方式

未来执行时使用已安装、已授权的对应版本；这里核对接口形状，不执行命令。原范围计划入口和批次入口仍以现协议为准：

```text
npm run release:plan -- --base <实际生产来源提交> --head <最终候选提交>
node tools/release-batch.mjs prepare <request.json> <batch.json>
node tools/release-batch.mjs inspect <batch.json> <batch SHA>
node tools/release-batch.mjs execute <batch.json> <batch SHA> <实际原授权 ISO UTC 时间>
node tools/release-batch.mjs status <batch.json> <batch SHA>
node tools/release-closeout-report.mjs <offline-input.json> <全新输出目录>
```

`prepare` 的 request、原 collector、tests、operations 和 live admission 继续遵循原 schema；本模板不为它们添加字段。`reconcileOperation` 只能通过本次适用的已审调用路径接入，不能臆造 `release-batch reconcile` 命令或临场执行未审写脚本。

报告生成器最小身份输入是 `batchPath`、`approvedSha256`、`journalDirectory`，建议同时绑定原文件的 `batchFileSha256`；按实际持有证据提供 plan、版本、回执、执行日志和 `deliveryEvidence` 引用。输入字段应从当前源码或已有原模板填入，不把本设计的文字字段直接当工具 schema。缺合法 delivery 回执时保留 `missing-document-delivery-completion-time`，先产草稿并在结果卡记录真实收尾，后续具备原格式回执再向新目录生成补充报告；不覆盖原件、不为消除缺口虚构时间。

工具的运行时历史观察会按生成时间披露过期，而且 `establishesCurrentReadiness:false`；这不是要求在文档收尾阶段不断查询生产刷新草稿。现场成功按当时有效的原回读成立，报告只如实标为历史证据。

## 计时与 15 分钟目标

目标适用于**对应版本功能已验证、精确制品已就绪、有上线授权且原门禁允许的常规发布**，包含现场发布和完整交付收尾。用以下两个区间同时报告：

- 用户完整等待：最早真实上线授权至文档推送保全及清理闭合；准备、排队、失败协调、重新准备和收尾均保留。
- 就绪后执行窗口：原授权与制品就绪两者均满足的时刻至完整交付，作为 15 分钟常规目标的观察区间。它是辅助指标，不重置原授权或 batch approvedAt，也不代替完整等待。

迁移、数据库恢复、原门禁要求的首次严格采用或异常协调可能另有窗口；记录原因、实际等待和恢复结果。超过 15 分钟报告实际状态，不能宣告成功、删步骤、强终止合法进程或自动切换权限。部署已成功而文档尚未闭合时可报告“已上线，收尾中”，完整计时继续。
