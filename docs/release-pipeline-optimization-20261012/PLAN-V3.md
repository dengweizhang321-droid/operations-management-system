## 二、WP-B 的判定维度（替换 v2 的三态）

对每项能力**分别记录三个独立维度**，它们不是互斥状态：

| 维度 | 取值 |
| --- | --- |
| 实现程度 | 完整实现 / 部分实现 / 未实现 / 未证实 |
| 采用状态 | 已采用 / 有证据确认未采用 / **未证实** |
| 剩余缺口 | 具体缺口、证据、影响、是否阻塞后续工作 |

**判定规则**：

- **未找到采用记录时标记"未证实"，不得判为"未采用"。**找不到证据不等于证明没采用。
- **历史采用记录不自动证明当前仍在运行**，须注明证据日期、版本与适用范围。
- **已有实现只证明存在相关能力，不证明覆盖全部调用链或历史故障。**

**阅读顺序**：先读 `docs/release-final-closeout-20261012/FINAL_REPORT.md`，再回溯 `docs/release-no-data-policy-20261010/REPORT.md` 等旧报告。核验生产状态前确认观察入口安全，不使用已知可能误清回执的旧普通权限 Status/Panel 路径。

## 三、条件任务（替换 v2 的"重复建设"定性）

**删除**"两包均为重复建设"与"未接入的即为缺口"。**替换为**：

- 未使用 `process-deadline.ps1` 的调用点列为**待核查项**；只有无法满足退出码传播、共同期限、输出消费和进程身份等必要契约时，才判定为缺口。**具备等效保障的实现不强制迁移。**
- **WP-B / WP-5 未发现必要缺口时，允许 WP-3 / WP-5G 以"无需代码改动"结项。**不为完成工作包而新增文件、抽象或测试。

## 四、审批规则（统一，替换 v2 第八章）

> 本方案经用户安排执行后，执行者在已授权范围内完成只读调查、具体设计、隔离开发、验证和必要审查。
>
> 验证通过后，按项目既定交付规范完成集成、提交和推送；多包集成由指定的协调 agent 负责，**不默认要求用户手工运行 Git 命令**。
>
> 生产部署、服务操作、数据写入及超出既有授权的处置，须提交包含影响范围、验证和恢复方案的具体结果，再取得对应授权。
>
> 已明确批准的范围不重复询问；出现范围变化时，只确认新增部分。
>
> Git 清理仍遵守现有长期授权与工具保护；用户改动处置不清楚时，单独提出具体问题。

**删除** WP-4、WP-5G 中"动手前先请求确认、等待后再调查"的条款。调查与设计是已授权范围内的动作，不需要先等一次确认。

## 五、Git 基线与清理判据（替换 v2 相关条款）

- 每包记录创建时的基线提交 `baseSha`。本包改动范围按 `baseSha` 与 `HEAD` 比较；集成前另外核验最新目标分支。
- **本地 main 与 origin/main 的包含关系分别记录。**提交已被经核实的 `origin/main` 包含，可以作为"已合入远端主线"的证据；不能因本地主检出落后而否认该事实。
- 是否清理还须独立核验未提交内容、独有忽略文件、进程和正式启动绑定。受管 worktree 使用应用归档工具。

检查命令（替换 v2 的 `main..HEAD`）：

```bash
git log --oneline <baseSha>..HEAD
```

```bash
git diff --stat <baseSha>...HEAD
```

```bash
git diff --check <baseSha>...HEAD
```

**"worktree 少于 5"改为治理期望**，不得为达到数量目标删除仍有用途的工作树。

## 六、CI 资源与制品来源（补齐 v2 边界）

- **所有级别禁止连接生产 PostgreSQL**；需要 PostgreSQL 语义的测试使用独立实例，纳入相应 L1 / L2 契约或集成测试，**不以 SQLite 结果替代**。
- **L2 浏览器测试使用隔离服务。**若消费预构建制品，必须由独立构建步骤提供，并绑定被测提交、依赖锁文件和制品摘要；**不得复用来源不明或过期的 `dist`**。
- 本包**实际验收 L0 / L1**。L2 / L3 未实跑时标为**"待验证"**，在完成隔离验证前**不作为正式必需门禁，也不计入已完成能力**。
- 未知路径、共享依赖和构建配置变化采用明确的扩大验证规则，**不能默默跳过**。

## 七、执行顺序（替换 v2 第七节）

```
先完成 WP-B 基线与 WP-0 短时盘点
                ↓
并行：WP-1 CI、WP-5 可靠性调查、WP-4 历史计时与设计
                ↓
根据调查结论决定是否实施：
WP-2 规范对齐、WP-3 证据扩展、WP-5G 必要修复
                ↓
同域修改串行集成，完成隔离验证
                ↓
准备具体生产方案，再取得对应生产授权
```

补充两条：

- **WP-4 的调查和设计不依赖 CI 完成**；实施和验收才依赖相应验证能力。
- **WP-0 记录采集时间和范围，不长期冻结其他任务；实际治理前逐项重新核验。WP-0G 不作为发布优化的前置门槛。**

## 八、收益验收（替换 v2 第三节）

| 口径 | 定义 |
| --- | --- |
| **T1** | 批准到完整交付 |
| **T2** | **有证据支持的业务不可用区间。**维护标记时间、进程停止时间和业务就绪时间分别记录；证据不足时报告区间及误差，**不把 Start 或 ExitMaintenance 的单个时间点直接等同于恢复可用** |
| **T3** | 失败、补证和恢复的耗时分类，**通常包含于 T1，并可能与 T2 重叠，不与两者直接相加** |

- **不以单次最短耗时作为稳定目标。**
- 收益比较须注明改动范围、环境和验证要求；**没有可比样本时只报告机制改善，不承诺节省分钟数。**
- **正确性修复按缺陷是否关闭验收；提速改动按对应时间口径验收，两者分别报告。**

**已知不可用依据（来自最新记录）**：普通零 DB 生产配对的净收益**未测**，不能声称净省 50 分钟。任何新方案不得复活这个数字。
