## 1. 目标与完成定义

本轮不是另建一套 Agent 框架，也不是在 Cloudflare Worker 内开放任意代码执行，而是把已经存在的中央工具注册表升级为一套声明完整、按入口可见、风险可执行、结果有界的工具总线，并把所有模型工具调用收敛到同一个请求级 Worker 执行环境。

```text
已认证入口 / 问答 Workflow / MCP
  → 创建请求级执行环境
      principal + scope + surface + requestId（服务端提供）
      totalCalls + cumulativeToolTime + terminalState（请求预算）
  → 从 lib/ai/tool-registry.ts 派生当前入口真正可见的工具
  → 模型 tool_call（providerCallId）
  → 执行环境生成 invocationId
  → 四道闸
      ① role / scope / surface 可见性
      ② risk / executionMode 准入
      ③ JSON Schema 与调用预算
      ④ timeout / result size / audit
  → 有界业务 handler
  → D1/R2/共享业务服务
```

以下条件全部满足才算第 4—5 层在当前系统范围内完成：

1. 工具仍只在 `lib/ai/tool-registry.ts` 声明一次；OpenAI、Anthropic、网页目录、帮助回复、MCP 目录和执行路由不出现第二份清单。
2. 每个工具除名称、描述、严格输入 schema、角色、risk、annotations 和 handler 外，还必须显式声明 scope 策略、允许入口、执行模式、Worker 环境、单次超时、单请求调用次数和最大结果字符数。
3. 工具是否可见和是否可执行使用同一套 `principal + scope + surface` 判定；MCP 的 admin 身份不能越过 surface 或 risk 闸门。
4. 当前 `worker_inline` 环境只直接执行只读工具；write/dangerous 即使误登记也默认拒绝，不能因模型调用直接产生副作用。
5. 每次问答只创建一个请求级执行环境；调用次数、逐工具次数、累计工具时间、外部取消和逐工具超时由同一运行时管理。
6. 非法或超长调用名在进入 runtime Map、响应和审计前归一为固定占位符，未知调用不能放大内存或 D1 审计存储。
7. 超时采用协作取消并等待底层 Promise 收敛；超时后不启动下一工具，不制造失去跟踪的后台工作。
8. 工具结果在成功审计和交给模型/MCP 前完成 JSON 可序列化与大小检查；超限明确返回 `tool_result_too_large`，不静默截断，也不把完整结果写入成功审计。
9. 每次调用由服务端生成 `invocationId`，并保留有界的 provider tool-call ID，使 started/succeeded/failed 审计可以精确关联。
10. scoped principal 可以调用不包含业务行数据的全局 freshness 元数据，再使用真正执行 scope 的搜索工具；不能因规则冲突被迫跳过数据截止日期检查。
11. 不开放任意 SQL、任意 API、任意 URL、任意文件/R2 key、shell 或同进程 JavaScript/Python；不声称已经具备隔离代码沙箱。
12. 专项测试、全量单元测试、页面结构测试、lint 和隔离构建通过；不停止、重启或覆盖当前运行中的本地 Worker。

| 参考原则 | TERUISI 当前事实 | 本轮落地 |
| --- | --- | --- |

| 执行器掌握真实身份与来源 | `AiToolExecutionContext` 已有 principal/surface/requestId/signal | 创建请求级 runtime 闭包，模型只能提供工具名和业务参数 |

不能机械照搬的内容：

- `assistant/tools.py`、`TOOL_SPECS`、`AiPendingAction`、`run_analysis`、`AiReportJob`、`sandbox-net`、`media/assistant` 均不是本仓库接口。

- 当前没有中央报告任务、对话产物或 AI 写动作的真实产品入口；预建无人消费的通用 job/pending 表会增加状态恢复和授权债务，不算能力完成。

## 3. 现状盘点

### 3.1 已具备的第 4 层基础

- `lib/ai/tool-registry.ts` 是模型可调用业务能力的唯一声明点，当前包含 12 个有界只读工具。
- `lib/ai/tool-registry-contract.ts` 已验证工具名唯一、根 schema 为 object、`additionalProperties: false`、required 字段完整、角色、risk/annotation 和 handler。
- 同一注册表已经派生 OpenAI function tools、Anthropic input schema、网页工具目录和 MCP 目录。
- 执行前会使用认证 principal 重新校验 role/scope 和完整参数，模型 payload 中的身份/角色声明无效。
- 审计 preflight 不可用时 handler 不执行；完成审计不可用时不返回 handler 数据。
- `lib/ai/tool-loop.ts` 已限制模型轮数、单轮调用数、总调用数，并在模型/工具前后检查取消。
- `app/mcp/route.ts` 已使用顺序批处理、单项超时与总批次预算，超时后等待底层操作结束。

### 3.2 实际缺口

| 优先级 | 缺口 | 影响 |
| --- | --- | --- |
| P0 | risk 只是元数据，不参与执行准入 | 未来一旦登记写/危险工具，网页或 MCP 可能直接执行 |
| P0 | 工具没有 `allowedSurfaces` | 角色相同即能在所有入口看见，无法做入口级最小权限 |

## 4. 第 4 层目标：中央工具层

### 4.1 注册表契约

每个 `AiToolEntry` 必须显式包含：

```ts
type AiToolScopePolicy =
  | "unscoped_only"       // 有 scope 的 principal 不可见、不可执行
  | "principal_scope"     // handler 使用服务端 principal.scope 过滤数据
  | "metadata_safe";      // 只返回无业务行的全局元数据，可供 scoped principal 使用

type AiToolExecutionPolicy = {
  environment: "worker_inline";
  mode: "direct" | "confirmation_required" | "background_job";
  allowedSurfaces: readonly AiToolSurface[];
  timeoutMs: number;
  maxResultCharacters: number;
  maxCallsPerRequest: number;
};
```

注册表验证必须保证：

- surface 名称来自固定枚举、无重复且至少一个；
- timeout、结果字符数、单请求次数都落在共享常量范围内，声明端和运行端引用同一组常量；
- `read_only` 才允许 `direct`；write/dangerous 不能以内联直接模式注册；
- 当前运行时只执行 `worker_inline + direct`；其它模式返回明确错误且 handler 不执行；
- read_only 的 MCP annotations 必须保持 readOnly=true、destructive=false；dangerous 必须 destructive=true；
- OpenAI/Anthropic schema 不包含 scope、surface、requestId、invocationId、deadline 或任何工作区凭据。

### 4.2 可见性与执行一致性

唯一判定函数接收完整的：

```text
principal.role
principal.scope
surface
entry.allowedRoles
entry.scopePolicy
entry.execution.allowedSurfaces
```

该判定同时服务于：

- `GET /api/ai/tools`；
- 帮助短路回复；
- OpenAI tools；
- Anthropic tools；
- MCP `tools/list`；
- 最终执行前的重新授权。

执行前必须重复判定，不能只依赖“模型没看见”。这可防止模型、客户端或旧工具目录直接伪造工具名调用。

### 4.3 当前 12 个工具的策略

- 12 个工具均为 `risk=read_only`、`environment=worker_inline`、`mode=direct`。
- 当前均允许 `ai_chat`、`codex_mcp`、`test`；市场/客服专用批处理入口不自动继承问答工具。
- `get_data_freshness` 使用 `metadata_safe`：只返回数据截止日期、导入时间、来源和时区，不返回业务事实行。
- `search_system_data` 使用 `principal_scope`，继续以真实服务端 scope 约束数据。
- 其余暂不具备行级 scope 的工具使用 `unscoped_only`，有 scope 的账号看不见也不能直接调用。
- 每个 handler 仍必须自身限制日期、行数、字段和查询范围；运行时结果上限不能替代业务查询上限。

### 4.4 写动作和产出工具的安全占位规则

本轮不虚构写工具，但注册表必须防止未来误接：

- write/dangerous 不允许 `direct`；
- 当前工具目录和两种模型 schema 只下发 `worker_inline + direct + read_only`；尚无适配器的确认/后台工具对模型和 MCP 均不可见，伪造名称执行时仍会再次拒绝；
- `confirmation_required` 只有在具备 D1 pending action、服务器生成的确认凭证、幂等键、过期时间和确认 API 后才能增加执行适配器；
- MCP、后台任务和无人值守入口默认不接受网页确认凭据；
- `background_job` 必须有真实 job 状态机、创建者授权、执行时二次鉴权、取消、租约、重试和幂等完成；
- 产出工具还必须在第 7 层定义 artifact 所有权、MIME/签名/大小/hash 和访问路由，不能把任意路径直接交给模型。

## 5. 第 5 层目标：Worker 执行环境

### 5.1 为什么采用 request-scoped runtime

当前中央工具全部在一次 HTTP 请求内完成，Cloudflare Worker 是实际运行边界。因此本轮实现一个请求级 `worker_inline` 执行环境，而不是预建通用 job 表：

```text
create runtime(context, limits)
  ├─ context：principal / surface / requestId / external signal
  ├─ state：totalCalls / callsByTool / cumulativeDurationMs / terminalErrorCode
  ├─ schemas/catalog：按同一 context 过滤
  └─ execute(name, args, providerCallId?)
       ├─ 生成 invocationId
       ├─ 检查总次数、逐工具次数、累计工具时间
       ├─ 合并 external signal + per-tool timeout
       ├─ 统一 registry 鉴权、参数、risk、handler、结果和审计
       └─ 等 handler settle 后才结束调用或开始下一工具
```

网页问答每次模型工具循环只创建一个 runtime；MCP 每个 JSON-RPC `tools/call` 创建一个单调用 runtime。模型循环原有轮次/调用预算保留，运行时预算形成第二道服务端防线。

### 5.2 超时与取消语义

- 逐工具 timeout 从 registry policy 读取，并与当前剩余累计工具时间取更小值；它覆盖 started 审计、handler 和结果校验，在有界结果就绪后停止。
- runtime 合并外部 `AbortSignal` 与内部 deadline signal；任何一个先触发都向 handler 传播。
- 取消是协作式的：D1 或已有服务函数若不能立即响应 signal，runtime 仍等待 Promise settle，再把调用判定为 cancelled/timeout。
- 不使用 `Promise.race` 提前返回并遗留后台操作；一次调用未收敛时绝不开始下一调用。
- 一旦出现 `tool_timeout`、`tool_cancelled` 或累计时间耗尽，runtime 进入终止态；同一请求的后续工具只记录拒绝审计，handler 不再启动。
- handler 结束后再次检查 signal，避免在 deadline 之后返回数据或写成功审计。
- bounded result 就绪后，完成审计作为 fail-closed 持久化步骤继续等待收敛，不再受 handler deadline 误判；完成审计失败仍不返回数据。调用的累计耗时仍包含审计时间，因此会影响本请求后续工具预算。
- 停止 handler deadline 的内部回调只存在于 registry executor options，不进入 `AiToolExecutionContext`，handler 无法主动关闭自身 timeout。
- 外部取消返回 `tool_cancelled`；逐工具 deadline 返回 `tool_timeout`；累计时间耗尽返回 `tool_time_budget_exceeded`，审计错误码彼此可区分。

### 5.3 结果边界

handler 返回后、成功审计前执行：

1. 必须是可 JSON 序列化的对象；循环引用、BigInt 或无效返回明确失败。
2. 最终 `{ok, toolName, data}` provider 结果信封的序列化字符数不得超过该工具的 `maxResultCharacters`，避免 data 单独合格但协议信封越界。
3. 超限只审计错误码和有界参数摘要，不把完整结果写入审计或交给模型/MCP。
4. handler 自己仍必须返回 `totalMatched`、`returned`、`truncated`、`filtersApplied` 等业务边界；运行时不对 JSON 盲目截半。
5. 工具循环的 40,000 字符兜底继续保留，防止未来非中央执行器或协议拼装回归。

### 5.4 调用轨迹

- runtime 为每次工具调用生成不可由模型覆盖的 `invocationId`。
- OpenAI `tool_call.id` / Anthropic `tool_use.id` 作为有界 `providerCallId` 传入 runtime，仅用于关联，不作为授权凭据。
- `ai_tool_audit_logs` 增加 `invocation_id` 与 `provider_call_id`，started/succeeded/failed 使用同一 invocationId。
- chat 级 `chat_message` 审计没有 provider tool call 时，以请求 ID 作为默认关联值，不保存原问题或推理正文。

### 5.5 明确不是本轮执行环境的内容

- 市场 AI 标注、品牌识别、图片缓存和京东下载仍是各业务模块自己的状态机；本轮不重命名或包装成“通用 Agent runtime”。
- 不在 Worker 内运行模型生成的 JS/Python，不开放 shell、文件系统或任意网络。
- 不新增中央报告 job、定时 Agent、artifact 表或代码工作区，因为当前没有产品入口、调度器、产物权限模型和恢复协议。

当出现“跨越单次请求、服务重启后续跑、进度轮询、取消/重试、产物或后台模型多轮”中的任一真实需求时，第 5 层再增加 D1 持久化 job/step/event/lease/idempotency 模型，并使用 Cloudflare Queue、Cron 或受控 pull worker 驱动。任意代码分析只能由不持有 D1/R2/模型密钥、默认无网、资源受限的独立隔离服务提供，主 Worker 只做授权、数据集导出、编排、审计和产物验收。

## 8. 测试矩阵

### 8.1 注册表与可见性

- 缺少 execution policy、非法 surface、重复 surface、超范围 timeout/result/calls 均使注册表启动失败。
- `ai_chat`、`codex_mcp`、`test` 在 catalog/OpenAI/Anthropic/execute 四条路径使用同一过滤结果。
- MCP admin 看不到仅允许 `ai_chat` 的工具；直接伪造工具名也在 handler 前失败。
- scoped analyst 可见 `metadata_safe` freshness 和 `principal_scope` 搜索，不可见 `unscoped_only` 工具。
- write/dangerous + direct 注册失败；confirmation/background 模式在无专用适配器时 handler 永不执行。
- 额外参数、错误类型、越界 limit、模型伪造的 role/scope/surface 字段均不进入 handler。

### 8.2 执行环境

- 单请求总调用数和逐工具调用数分别生效，达到上限后 handler 不执行且记录失败审计。
- 工具 timeout 会触发 handler signal；runtime 等 handler settle，之后才返回，后续工具不会提前开始。
- timeout/cancel/time budget 后 runtime 进入终止态，即使累计预算仍有剩余，下一工具也不启动。
- handler 看不到停止 deadline 的内部 executor hook，不能绕过自身 timeout。
- 外部取消与 timeout 产生不同错误码；已取消信号不会启动 handler。
- 累计工具时间耗尽后不启动下一工具。
- 循环引用或超大结果返回显式错误；成功审计不会收到完整结果。
- started 与 succeeded/failed 拥有相同 invocationId；provider call ID 正确对应 OpenAI/Anthropic 原始 ID。
- runtime snapshot 只包含次数和耗时，不含业务参数、结果、密钥或模型推理。

### 8.3 集成与兼容

- 网页问答的模型 schema 和 execute 使用同一个 runtime/context。
- 帮助回复与 `/api/ai/tools` 使用 `ai_chat` surface；MCP `tools/list/call` 使用 `codex_mcp`。
- MCP 原有单请求 12 秒、批次 20 项/30 秒和等待收敛语义不回退。
- 0013/0005 基线数据库应用 0041 后历史审计保留，新列默认值正确，索引存在。
- 0041 是既有表增加关联列的唯一变更者；新代码运行在未迁移旧库时使用旧列 INSERT，列就绪后自动切换到新列并创建索引。
- 12 个生产工具仍保持明确日期/行数/字段上限和 `filtersApplied/returned/truncated` 契约。

## 9. 风险、回滚与兼容

- **协作取消不是强制终止。** 已有 D1 handler 未必在查询中途响应 signal；runtime 的安全承诺是超时后不返回数据、不启动下一调用，并等待操作收敛。真正需要强制终止的代码必须进入独立进程/容器。
- **结果上限不能替代查询上限。** 超大数据在 handler 内构造后才可能被拒绝，因此每个业务 handler 的 SQL limit、日期范围和字段白名单仍是第一防线。
- **freshness 是全局元数据。** `metadata_safe` 不代表 scoped 用户获得全局销售/库存事实，只允许看到数据截止与来源健康状态。
- **迁移只向前加列。** 不删除或改写历史审计；旧代码忽略新列仍可读取。回滚应用代码时新列保留，不影响旧 INSERT 的默认值。
- **API 保持兼容。** 不改变聊天 JSON 和 MCP JSON-RPC 形状；工具目录只增加安全元数据并可能因 surface/scope 更准确地减少条目。
- **运行服务不受影响。** 验证不得覆盖当前 `dist`；需要 build 时在隔离 worktree 执行。未获用户明确批准不停止或重启本地 Worker。
