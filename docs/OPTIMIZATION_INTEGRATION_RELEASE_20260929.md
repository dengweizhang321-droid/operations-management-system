## 2. 集成时修正的两处行为冲突

1. **维护中的备份准入冲突。**第 1 项拒绝维护期间备份/恢复，而第 4 项要求应用真正停稳后保留原受控操作能力。现在仅接受同一 ID、requests 阶段、相同维护范围及布尔 `drainedStopped=true` 的记录，并重新检查应用与 Worker 已停止。活动维护、缺证据、跨 ID/范围及伪造布尔值均拒绝。
2. **直接备份退出后的未知结果。**操作进程退出会释放 OS 互斥，但不代表备份结果已确认。维护现在复用第 1 项的持久操作记录读取器，在取得原 mutex 后拒绝未闭合记录；不吞掉 abandoned mutex。PS5/PS7 负向测试先复现旧组合错误，再验证修复和精确闭合后的准入。

修复提交：`a96730e7`、`4fa95986`；容量测试夹具同步提交 `33b5486e`。没有修改正式安装文件或绕过原生命周期锁。

## 6. 一次维护发布的拟议步骤

1. **复查候选与回滚材料。**固定本批提交、Worker 计划/清单、Django 收据和已独立恢复的备份；核对保护项、磁盘空间、权限及正式进程。较久以后才发布时重新检查备份新鲜度，必要时生成并验证更新恢复点。
2. **首次采用使用旧协议。**现有后端/helper 尚不具备新排空协议，不能提前用新协议停旧服务。获批后先临时冻结原有相关定时触发入口，记录原激活状态和期间到期计划，再核对 n8n、helper、导入、备份/恢复、AI 通知及其他后台队列。不得仅凭一次空闲快照认定已排空；未确认执行或结果未知时停止进入维护。
3. **进入一次应用维护。**使用当前已安装的旧版唯一 Worker 维护入口，优先保留 PostgreSQL；n8n 进程保持。按原工具门禁采用已准备的 Django 与 Worker/helper，不手改安装目录或版本凭证。
4. **同步受保护入口及主工作区。**线上主工作区仍承担原 guard 校验，不能在停服授权前直接快进。维护窗口内按发布计划的 before/after 字节绑定完成切换，再将本机主工作区同步到已批准的主线提交。
5. **核验整栈。**按原唯一入口恢复，检查 12 组件、全部原健康端点、精确 release、启动绑定、AI/pandas/渠道及 helper 新协议。第 2 与第 7 项同时检查诊断、启动计时、失败处理与完整就绪；不额外杀正式进程制造故障。
6. **配套采用工作流。**应用能力确认后，在触发入口仍受控冻结的条件下逐项采用送审的 12 份定义，核验 current=published、原 ID、调度和业务节点，再恢复原启用状态。中途失败保持冻结并按精确旧定义回退，不能让混合版本执行真实业务。
7. **分项验收及观察。**用新 operator 验证备份结果、轮换和保护，用自然业务执行验证维护恢复、原计划范围及批次/发送账本。原每日 22:30 备份任务仍为 PAUSED，只有用户明确将恢复调度纳入本次批准才启用原任务。维护期间错过的计划列清单，按原业务规则处理，不自动补发通知或重放未知效果。

## 7. 回滚与停止条件

- **激活前失败：**保留当前正式应用、Worker 和在线工作流，候选留存，不把准备失败标为已发布。
- **应用切换失败：**保留维护及失败证据，使用原工具选择兼容的前驱应用与受控 Worker successor/恢复路径；不直接启动已被 fence 的旧版本，不改 authority，不删除未知回执。
- **工作流切换失败：**先确认在途 execution 和未知派发结果，在入口冻结期间按逐文件核验的原定义恢复；不让旧定义重算新 execution 的历史日期。
- **数据库：**本批无迁移，默认回退代码与定义，不反向恢复业务数据。若确需生产数据库恢复，须另行确认精确恢复点、目标及数据丢失范围，隔离演练不构成该授权。
- **运行验收失败：**组件不就绪、身份不明、helper 协议不匹配、备份未闭合、原版本漂移或队列未排空，均停止推进。不能放宽超时、跳过校验或把服务就绪当作业务成功。
