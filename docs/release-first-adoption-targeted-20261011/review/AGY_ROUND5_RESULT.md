### 二、事件根因定性与必要性边界

1. **真实问题与现象定性**：
   - 在真实 CLI in-process session 运行中，原生文件监视器在进入 `configuration-content` 读取前的 control 观察窗口（约 1.39ms）捕获到 `D:\运营管理系统\.dev.vars` 的 `change` 事件，导致会话直接判定为 `changed = true` 而 fail-closed。
   - 对照实验证实：该事件发生前后，文件的 `dev`、`ino`、`nlink`（283）、`size`（2402）、`mtimeNs`、`ctimeNs` 及内容全字节 `sha256` 均严格不变，**仅 `atimeNs` 发生跳变**。
   - **客观定性**：此现象属于 Windows NTFS 文件系统访问时间更新或延迟元数据通知的典型特征，**不能主观断言为特定第三方进程或杀毒软件触发，亦不能将单次对照没有内容变动夸大为“排除了并发写入者”**。引入针对该单文件的精确状态判定机制具有现实工程必要性。

### 三、本设计能保证与不能保证的安全范围

在评估 Astra 提出的 `pending` 缓冲与同步复核设计时，必须客观界定其防御边界：

#### 1. 本设计能够保证的范围
- **极窄作用域隔离**：仅对规范化路径与 `workerDevVarsSource` 完全一致、且事件类型为纯 `change`、文件名精确匹配的单文件生效。所有其他文件、源码目录、npm 依赖、`null` 事件名、`rename` 或删除操作，依然无条件触发 `changed = true` fail-closed。
- **物理指纹抗伪造**：以监视启动前捕获的初始物理基准（`rawSha256` + `dev`/`ino`/`nlink`/`size`/`mtimeNs`/`ctimeNs`）为不可变锚点。任何实际修改字节（即使通过底层手段伪造 `mtime`）、替换 inode（同字节不同文件）、修改链接数或变更 `ctime` 的操作，在复核时均无法与基准匹配，将被坚决拦截。
- **与 SourceBinding 严格闭环**：该设计不接受新字节，不自动更新基准 SHA，最终消费的仍然是原制品绑定的固定配置内容，未打破既有的不可变制品契约。

#### 2. 本设计在理论上不能保证的固有边界（必须如实披露）
- **“Changed-and-Reverted” 极端理论竞态无法完全排除**：
  若存在外部攻击者或特权进程在监视事件发生到 `assertStable()` 执行的极短间隙内修改了内容，并以纳秒级精度复原了文件原始字节与所有时间戳（`mtimeNs`/`ctimeNs`），用户态的文件系统监视器与 stat 机制在物理上无法证明“未曾发生过瞬时脏读”。
  **审查定性**：这是通用操作系统非独占打开文件的客观物理限制。系统保证的是“构建最终读取并锁定的字节严格等于不可变前驱基准”，而非证明存在全系统级别的绝对时间互斥。
- **无独占写锁保护**：
  因 283 个硬链接在生产环境共享，系统无法对其施加独占写锁（Exclusive Lock），仍依赖无并发写者环境假定。

### 四、具体实现缺口与关键必要实现要求

若要实施该方案，当前设计必须解决以下具体的工程隐患：

1. **【关键缺口】同步 `assertStable()` 与异步 I/O 的冲突**
   - **问题**：在 `createPreparationEvidenceSession` 中，`assertStable()` 必须保持纯同步调用（以维持 `exclusive`、`collect`、`recheck` 等核心流程的调用契约）。然而现有代码中的 `assertNoReparsePoint` 是异步方法（`await assertNoReparsePoint(...)`）。
   - **必要实现要求**：在 `assertStable()` 内部执行针对 `pending` 的复核时，**所有文件系统操作必须全部采用同步 API**（例如 `fs.lstatSync(..., { bigint: true })`、`fs.readFileSync`、同步祖先路径解析与 reparse 属性位检查），严禁在同步函数中调用未等待的 Promise，也不得为了适配而将 `assertStable()` 扩散改造为异步函数。
2. **状态机单向不可逆与优先级倒置防范**
   - **问题**：如果监视器短时间内收到多个事件（例如先收到 `.dev.vars` 的 `change` 进入 `pending`，随后收到无名事件或源码变动）。
   - **必要实现要求**：`changed = true` 必须拥有绝对不可逆的最高优先级。一旦任何非法事件将 `changed` 置为 `true`，`assertStable()` 必须直接抛错终止，`pending` 状态在任何情况下均不得覆盖或清除 `changed = true`。
3. **基准捕获的时序前置与单会话生命周期绑定**
   - **必要实现要求**：基准快照必须严格在调用 `monitor()` 注册句柄之前完成同步捕获；该基准只属于当前 evidence session 实例，生命周期随 `dispose()` 销毁，严禁跨会话或跨批次缓存。

### 五、复审结论与后续状态界定

1. **设计方案评价**：
   在严格遵守“全同步复核”、“单文件白名单”、“不可逆优先级”的前提下，Astra 提出的以基准比对化解访问时间（`atime`）抖动导致误报的设计是合理且必要的最小修改，未扩大 10 个运行工具的文件范围，未改变通用 `safeRead`。
