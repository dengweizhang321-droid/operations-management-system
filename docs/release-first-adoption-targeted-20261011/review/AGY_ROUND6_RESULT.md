### 二、冻结 Helper 源码逐项核验结论

对提供的 `release-preparation-evidence.mjs` 源码进行逐行与控制流核查，确认前轮设计要求的落地状态如下：

1. **纯同步调用与 I/O 契约闭合**：
   - `readFixedRuntimeConfiguration` 内的所有文件系统探测与读取（`lstatSync`、`realpathSync`、`readFileSync`）均已实现为完全同步。
   - `assertStable()` 在处理 `configurationPending` 时，直接在同步上下文中调用 `readFixedRuntimeConfiguration()`，消除了前轮指出的“同步断言陷入未等待 Promise”的根本性缺陷。
2. **祖先路径防重定向（Anti-Junction / Symlink）**：
   - 内部辅助函数 `assertPath` 从盘符根节点向下逐级分解路径，严格核验每级目录的 `!isSymbolicLink()` 以及 `path.resolve(realpathSync(cursor)).toLowerCase() === cursor.toLowerCase()`。
   - 在读取前、后各执行一次完整路径断言，有效防御利用父级目录符号链接或 Junction 点切换底层文件的攻击手段。
3. **白名单判定与不可逆事件优先级**：
   - **极窄单文件匹配**：仅当同时满足 `fixedConfiguration && !source && !treeScope && event === 'change'`、且目标路径、事件绝对路径及相对文件名严格精确等于 `workerDevVarsSource`（小写规范化）时，才触发 `configurationPending = true`。
   - **不可逆 fail-closed 门禁**：无名事件（`!relative`）、目录树事件、删除/重命名或任何其他文件事件均直接置 `changed = true`。
   - **优先级严格锁定**：`assertStable()` 优先执行 `if (changed) throw ...`；且在 `configurationPending` 复核中一旦比对失败，立即在 `catch` 块中执行 `changed = true`。一旦置位，会话不可逆死亡，不存在静默清除或降级绕过的可能。
4. **基准时序前置与单会话生命周期**：
   - `startMonitoring` 在注册任何 `monitor` 监听句柄之前，优先同步执行 `readFixedRuntimeConfiguration()` 完成 `configurationBaseline` 捕获。
   - 基准属于会话实例内部闭包状态，在 `dispose()` 时被显式赋值为 `null`，杜绝了跨会话或跨批次泄漏复用。
5. **元数据比较范围与访问时间隔离**：
   - `fields` 严格锁定为 `['dev', 'ino', 'nlink', 'size', 'mtimeNs', 'ctimeNs']`。
   - `atimeNs` 已按设计安全排除（避免受 Windows 延迟访问通知误报干扰），但物理内容哈希（`hash(raw)`）与关键身份/修改时间（`mtimeNs`、`ctimeNs`）保持全量一致性比对。

> **源码审查结论**：在本次审查的代码实现中，**未发现新的阻断性逻辑漏洞**。此前轮次指出的同步 I/O 冲突、状态机优先级倒置及祖先路径校验等隐患均已闭合。

### 三、真实防御边界（保证与不能保证的客观范围）

为避免安全假设过度放大，独立审查者明确界定本模块的防御边界：

1. **能保证的范围**：
   - 确保从 `workerDevVarsSource`（2402 字节）读取并消费的配置内容与其在会话开始前捕获的物理基准逐字节完全一致；
   - 确保任何内容修改、伪造 `mtime`、替换 inode（同内容不同文件）、硬链接增减或父目录挂载点劫持，在同步复核时均能被立即识别并强制 fail-closed。
2. **客观不能保证的理论边界（必须如实披露）**：
   - **瞬时修改与纳秒级复原（Transient Changed-and-Reverted）**：在用户态非独占监视模型下，若存在特权进程在监视事件产生到 `assertStable()` 复核的微秒间隙内完成了“写脏数据并以纳秒精度复原原字节与全部时间戳”，用户态 stat 无法在物理上证明未发生过脏读。系统提供的是“所消费产物与不可变前驱基准一致”的事实，而非全系统级绝对时间互斥证明。
   - **外部硬链接全量覆盖假象**：`runtimeFile` 仅用于当前环境会话身份复用，本单文件读取不能直接外推替代完整制品三元组对全系统 283 个硬链接的跨目录验证。

### 四、关键现场事实与阻断状态披露

1. **源目录 5653 个变更事件阻断（真实源码级阻断）**：
   - 原生测试已证实：配置读取通过（4.1ms）后，旧源码目录 `adoption-source-v2` 产生了 5653 个普通文件/目录的 `change` 信号（从技能文件到账号目录）。
   - **审查定性**：Helper 正确依据规则拦截了该会话，证明源目录保护处于有效运转状态。该失败属于真实环境阻断，**严禁将配置的 pending 例外泛化至源码目录，亦不得通过人工重试或弱化 guard 来强行放行**。必须在全新的不可变 `SourceV3` 隔离环境下完成无外部干扰的真实验证。
2. **操作预算硬上限校正（ProcessDeadline 30分钟限制）**：
   - 经实测确认，原 872 scope 声明的 DB 操作各 3,600,000ms（1小时）超出了底层 `processDeadline` 的 1,800,000ms（30分钟）硬上限，已在实际函数调用中被物理拒绝。
   - 新批次声明将单次 DB 操作预算调整为 1,800,000ms，planner 保持 600,000ms。该调整属于合规收敛，但历史 706 秒的单次恢复记录仅作为参考，不能推定为生产耗时的绝对承诺。
3. **197 个未知引用进程持续阻断生产准入**：
   - 最新环境快照确认存在 197 个无法读取可执行路径或命令行的进程（含 PID 47936 的 PowerShell）。
   - IG04 守卫规则未变，生产准入保持合规阻断，生产环境保持物理静止。
