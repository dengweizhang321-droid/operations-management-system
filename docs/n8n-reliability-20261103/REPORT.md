## 已实施的源码修复

1. **消除已复现的推广容量错配。** 网店 Worker 客户端默认上限改为 128 MiB，与正式 Django writer 一致；Django 普通启动默认也对齐。仅网店域，原文件 25 MiB、50,000 行和内部 128 MiB 硬顶保持。保留完整 raw、内容指纹和一次发布语义；不拆成多个整日替换请求。大请求会占用更多内存，不保证任意 25 MiB 文件均可规范化导入。
2. **修复长会话被小数量阈值拒绝。** TS 与 Django 导入同步为最多 2,000 条消息，与既有迁移边界一致；仍限制单条 4,000 字符、每通 128 KiB、日规范化资料 16 MiB及来源文件 25 MiB。查询 200 条/64 KiB、AI 24 条保持；不截断消息、不改变匹配或会话统计，不涉及迁移。闭合页面移除过期“导入仍限200条”的说明。
3. **停止对容量拒绝的无效小时重试。** 413、明确 payload/body too large 进入现有人工分支。其他已有瞬态重试语义保持；本次没有设计新的无限通用恢复规则。
4. **纠正错误归因。** 无 retry POST 的终局失败保留 `terminal_manual_action`；真实派发未知保留 `retry_dispatch_result_unknown`。公共停止节点改为“保留人工处理原因并停止”。推广导入错误保留有界机器 code，避免任意响应文本进入日志。
5. **准确报告通知认证失效。** 六次共享错误流的账本均为发送前 `identity_failed`；只读复现 CLI exit 5，要求原 profile 重新登录授权。候选账本明确记 `dws_auth_required`；不自动登录、不改变收件人、不清空账本或重发。

第 4 项纠正误导信息，不把“转人工”强行变成业务成功；共享错误流仍以 StopAndError 结束，须区分人工终局和通知故障。第 5 项不等于通知已经恢复，重新授权需要账号操作者参与。

## 链路整改建议

独立规划见 [DESIGN.md](DESIGN.md)。建议保留 n8n 和既有领域导入服务，把整改集中在恢复能力：

- 按失败阶段展示“可续导、待复验、需登录、提交未决”，复用现有恢复器；减少每次故障编写一个带 execution ID 的脚本。
- 结构化保留 `code / stage / retryable / effectState / logicalExecutionId`，逐步替代错误文案正则；同一逻辑任务设置累计重试时间/次数预算，不随新 execution 重置。
- 页面区分应触发、首次完成、恢复后完成、人工未处理和通知失败；不同模块的部分成功可见，但不冒称整链成功。
- 如文件继续增长，再做“分块接收、完整文件一次发布”的导入会话；不切片调用整日替换、不再复制一套调度或业务事实库。

目前没有证据支持为提高完成率而换掉 n8n、继续扩大 Chromium 并发或增加更多看门狗。上述大改为建议，未混入本次小修，也不承诺修复后达到某个百分比。
