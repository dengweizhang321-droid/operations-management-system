## 批次安排

| 方案 | 范围和保障 | 重新绑定与决定 |
| --- | --- | --- |
| 默认第一批 | A＋B：消除外壳等待/期限缺口、验收误报及报告收尾，保留完整前后备份/隔离恢复、原排空、权限、维护/身份及全部原验收 | 生命周期实现自身首次采用走严格流程；候选只含实际前驱已采用功能和A/B闭包。不得带C或其他未批准功能 |
| 默认第二批 | C：影响证明、恢复资格、原Worker-only及准备身份派生复用 | C机制首次采用仍严格，不能给自己免保障。若第一批已采用，必须从新实际前驱重新准备源码/制品/计划/测试/回滚/批次并另获批准 |
| 合并批替代 | 第一批尚未采用，且A/B/C全部最终组合验证和独立复审闭合时，可准备A＋B＋C严格批 | 比较一次与两次固定成本后由用户确认精确方案。当前不预选、不构建替代候选；节省推算不作实测 |

两批固定成本比较包括两轮候选/准入/完整四项数据库操作/排空切换/自然守护及收尾，与风险集中、重绑/重测成本分别列出。共同子阶段不重复计时，不能只加估算48～55/3～6/10～20分钟宣称收益。A/B本身有完整保障，C首次采用不会立即得到展示数据库减免。

## 回滚与失败续接

1. 切换前：准入/备份/恢复失败保持生产前驱和旧恢复点，不提前轮换删除。只有未开始切换/业务、无unknown，并有独立零效果证明时按原cancelUnswitchedBatch安全闭合；已drain须先按精确owner解除并证明。
2. 动作返回未知：保留started/unknown、active/gate与原代码；对精确操作做独立只读回查，按原reconcile记录观察SHA及不重放声明。没有零效果证明不能重试Start/apply/备份/业务；HTTP健康不替代动作成功。
3. 切换后：使用原受控rollback/兼容代码路径和精确前驱制品、startup绑定与manifest；保留guard/authority/activation fence/successor/audit。schema不兼容或已跨PNR时按前向恢复限制处理，不回到D1。
4. 数据恢复：代码回退不等于数据库回滚；必须另获用户对精确恢复点、目标库及维护窗口的明确批准。不能恢复已被淘汰载荷或用备份元数据冒充可恢复包。
5. 收尾失败：后备份/恢复、完整最终状态/自然守护/原任务验收任一未闭合，报告未完成；保持原阻断与证据，不提前宣布完整交付，不重放已passed步骤。
