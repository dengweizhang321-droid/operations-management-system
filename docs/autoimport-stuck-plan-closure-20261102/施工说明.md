## 必须落实的协议

### 客服失败闭合与来源恢复分开

原 `CustomerServiceRecoveryApproval` 用于短时、同日期窗口的来源恢复；`downloaded_pair` 会复用旧来源。只生成这份许可不能声称旧 active 已闭合，也不能解锁次日滚动窗口。

本次新增的人工失败闭合应保留旧 failed 计划、原文件及失败事实，保存精确绑定店铺、旧 execution、原计划摘要和授权的持久终态回执。后续正常 A 在原锁及身份约束内消费闭合事实，建立当前日期窗口的新计划与空来源，不重放旧执行、不借用旧来源。授权生成、终态提交和新 A 消费必须在文案及回执中可区分。

已有 source-recovery 协议不扩权，不通过延长许可、伪造旧计划时间或放宽日期相等要求实现跨日闭合。重复请求应读回原结果；提交未知不得换请求号盲重试。

### 洗碗机只续接最终 verify

洗碗机 `executed` 是执行段完成但最终复验未完成。续接只作用于磁盘 active 精确指向的原计划，复用来源哈希、分天等价性、日文件及精确批次复验，成功才写 `completed`。

新入口必须补足原内存生命周期提供的授权、helper 互斥和维护排空前提，在店铺 planning 锁内核实身份，并在提交前复验 active 与 plan 字节。对成功后响应丢失的同一请求，应有可核实的 completed 结果读取，不重新导入或重建来源。

“失败执行不标成功”只适用于其余三条 failed 任务；不能禁止洗碗机经复验推进 completed。

### 切肉机闭合证据完整解析，导入限额不变

`parseChatLog()` 内部即校验消息数量，超限时不会返回全量解析结果。不得 catch 超限后认定全文可信。闭合分析必须完整解析所有来源，保留格式、日期、消息内容和资源边界，只将消息数量业务限制与闭合证据判定分开；正常导入的 200 条上限保持。

查询、授权执行与回执消费使用一致的证据口径。错误只返回受控脱敏分类，不能直接暴露任意异常正文、聊天内容或下载地址。

闭合只解除旧任务阻塞。若新的滚动窗口仍包含超限会话，新执行仍可能失败；失败即停止不代表已自动形成下一轮可消费的闭合回执。

### 厨电新增 downloaded_list_only 的完整契约

来源必须恰好只有 list/downloaded；原失败边界为 version 1、browserClosed=true、step=export_messages。仅允许有对应前置控制流证明的失败码。正规来源文件须位于本店本 execution 下载目录，扩展名、大小、摘要及来源数量有效，目录中没有其他条目；无 proofs、分天文件、正在导入、派生或来源恢复等后续事实。

“没有 messages 文件”仅证明未落盘；messages 未提交必须结合导出检查点在提交前持久化的控制流证明。list 本身已完成导出，不能把整个执行描述为从未提交任何导出。

Django 授权白名单、TS 查询与提交判据、回执消费、共享类型与身份校验、既有前端种类展示及操作文案必须同步。

### 物流先核复用资格，再接受冻结目标

保留 9851 原目标兼容，复用原校验主体。11037 目标中的摘要及进程身份由受控只读准备产生，候选不等于授权；执行时必须使用已冻结目标及其精确摘要。

不能预先承诺“只换 target 即可”。原工具除目标摘要外还检查历史/当前 helper 文件一致、激活链关系、工作流冻结版本、历史策略与四个 operation、无在途执行、专用端口及全程进程身份。11037 原 manifest 的首 operation 为 `exporting`，其余为 `planned`；这不是已经提交平台导出的证明，但也不能把四项都写成 `planned`。零导出效果必须依据精确登录失败位置与其他证据联合判定。
