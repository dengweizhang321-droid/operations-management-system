## 一、最关键的一条：我自己注入 bug，验证闸真的会红

执行者声称"交叉反例真的会红"。这是整个单元的核心主张，我不采信，自己做了一遍：

**做法**：往 `judge_gate1()` 函数体开头注入那条典型错规则——

```python
if files_obtained == 0:
    return Gate1Judgment(business_state="no_new_needed", execution_state="finished",
                         reason="INJECTED_BUG", reused_batch_id="INJECTED", ...)
```

即"0 文件就当无需新增、绕过证据检查"。这正是把闸③（0 文件→失败）与 `no_new_needed`（无缺口→正确）混成一条路的典型写法。

**结果**：22 个用例里 **6 个当场失败**。还原后 `git diff` 字节一致。

**这证明闸不是摆设**：将来有人把两条路混起来，测试会抓住。这比"用例全绿"有意义得多——绿只说明当前代码通过了自己的断言，红才说明断言真的在约束行为。

## 五、两处已披露的局限（执行者主动说的，我核实都成立）

### 局限一：区间内部空洞判不出来（我亲自验过）

我造了一个 `date_min=2026-09-10`、`date_max=2026-09-12` 的批次，查询同一区间：

```
判定 business=verified  fully_covered=True
```

即：**只要批次的日期区间名义上覆盖了窗口，就算覆盖完整**。如果区间中间某天实际零行（报表内部有空洞），这个闸会误判为已覆盖。

要修得查 `NetshopRow` 或 `NetshopPromotionProductDaily` 的逐日行存在性，而不是只看批次的 `date_min`/`date_max`。执行者没做，理由是"不扩大业务域查询面、本单元是批次级"——**这个取舍我认同**，但它是真实缺口，B4 观察期要盯住：若出现"判了 verified 但某天没数据"，就是撞上这一条。

### 局限二：「未到期」没有独立的业务信号

B0 已查实 `not_due` 只存在于 n8n 便签文字里，**没有任何可查询的落点**。所以这个闸把"无缺口"和"未到期"**收敛成同一种证据形态**（已有 completed 批次覆盖了区间）。

后果：页面暂时无法区分"因为未到期所以没跑"与"跑了但没有新增"。两者都显示 `no_new_needed`。

要分开报，得有真实信号——例如读 `AutomationLogicalRun.trigger_source`/`plan_summary`，或在某处落一个 `skip_reason`。本单元被明确告知不给业务域加字段，所以留着是对的。**但这件事要记进 B3 的接口设计**：如果页面要显示"未到期"，现在没有数据支撑它。

### 局限三：闸② 的服务端拒绝只到谓词层

`may_rerun_import()` / `may_retry_delivery()` / `may_normal_retry()` 这些谓词函数写好了，但**还没有真实 HTTP 入口调用它们**——`AutomationActionRequest` 与动作 API 属于 P2。

所以"业务 verified + 投递 failed 时服务端也要拒"目前证明在函数层成立，**尚未证明在真实请求路径上成立**。P2 接线时必须把这些谓词接进去，否则就只是前端隐藏。
