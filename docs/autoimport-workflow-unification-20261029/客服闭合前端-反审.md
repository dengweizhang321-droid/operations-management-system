## 一、它故意不复用那个谓词，这个判断是对的，而我上一轮说错了

实现者报告称：**故意不用** `isCustomerServicePreSubmitFailure()` 做 `closeAllowed` 判据，因为真实 plan 验证发现该谓词会放过无 `failureBoundary` 的空源 plan，用它当闸会错告操作员"这些不需要处理"。

我核了 `tools/jd-customer-service-failure-closure.ts:17-22`，**它对我错**：

```js
if ("failureBoundary" in plan && (...)) return false;   // ← 字段不存在时整个检查被跳过
if (!Object.keys(plan.source).length) return true;      // ← 空源直接通过
```

那个检查是**条件式的**：`failureBoundary` 缺失就跳过，不是阻塞。

我按真实语义重算了全部卡住的 plan：

```
exec=7250   PAGE_STORE_IDENTITY_MISMATCH   谓词=通过
exec=8653   PAGE_STORE_IDENTITY_MISMATCH   谓词=通过
exec=7266   CUSTOMER_SERVICE_FAILED        谓词=通过
exec=10432  JD_IDENTITY_RATE_LIMIT         谓词=通过
...全部通过
```

**所有卡住的 plan 都能通过那个谓词。** 我上一轮在诊断修正里写的"卡点一：无 `failureBoundary`"是错的——那不是卡点。

真正的卡点在谓词**之后**的运行期检查：`assertPortAbsent()`（浏览器调试端口必须已关）、下载目录必须为空、`downloaded_pair` 要逐项复验 checkpoint。这些是 I/O 级检查，静态读 plan 文件判不出来。

**所以实现者重新推导那套检查而不是复用谓词，是正确的。** 复用会让 `closeAllowed` 对这些 plan 返回 true，而提交时在运行期检查被拒——正是我提示词里警告的"显示可闭合但提交被拒，比没有按钮更糟"。它避开了这个坑，还是靠真实数据发现的。

## 二、`closeAllowed` 与授权链一致（最关键的一项）

它的做法：`closeAllowed` 完整重算 `generateCustomerServiceRecoveryApproval()` 会做的结构检查（店铺注册身份与启用状态、`pre_export_zero_effect` 的残留下载目录检查、`downloaded_pair` 的 checkpoint 复验与重解析），**然后才返回 true**。

所以"可闭合"不会后接"提交被拒"。它说这一条是提交前靠单元测试发现并修正的。
