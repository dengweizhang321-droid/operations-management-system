# 京东客服四店近两周全败 · 诊断（2026-10-31）

只读诊断：读 n8n 元数据与仓库源码，未改任何东西、未运行采集或导入、未发送消息。

## 一句话结论

**不是登录态、不是凭据、不是平台侧变化。** 是一个**自锁死循环**：某一轮失败后，闭合工具的白名单不认它自己产生的失败码，于是永远闭合不掉，下一轮 A 阶段又被这个未闭合状态挡住，四店同时卡死。

## 错误码分布（37 条可读失败，近 14 天）

| 次数 | 错误码 |
| --- | --- |
| **15** | `PREVIOUS_RUN_UNRESOLVED_MANUAL_ACTION` |
| **10** | `JD_IDENTITY_RATE_LIMIT_MANUAL_ACTION` |
| 7 | （未识别，证据里无明确码） |
| 1 | `PAGE_STORE_IDENTITY_MISMATCH_MANUAL_ACTION` |
| 1 | `CHAT_PAGE_MISMATCH_MANUAL_ACTION` |
| 1 | `PAIR_PARSE_REJECTED_MANUAL_ACTION` |
| 2 | `CUSTOMER_SERVICE_FAILED_MANUAL_ACTION` |

## 因果链（按真实时间顺序）

### 第一步：10-17 各店出现首个失败，原因各不相同

- 设备店：`PAGE_STORE_IDENTITY_MISMATCH`（页面店铺身份不符）
- 洗碗机：`CUSTOMER_SERVICE_FAILED`
- 厨电 / 切肉机：已是 `PREVIOUS_RUN_UNRESOLVED`（说明更早就有未闭合的轮次）

这些**首因失败是正常的失败关闭**，符合 `docs/规范/导入与自动化.md` 的清单（身份不符必须停止自动重试）。

### 第二步：10-18 起全部变成 `PREVIOUS_RUN_UNRESOLVED`

`tools/jd-customer-service-n8n-pipeline.ts:86-88`：新一轮 A 发现上一轮 `stage !== "completed"` 时，尝试调 `closeCustomerServicePreSubmitFailure()` 闭合它；**闭合失败就报 `PREVIOUS_RUN_UNRESOLVED_MANUAL_ACTION`**。

```js
} else if (previous.stage !== "completed") {
  try { await closeCustomerServicePreSubmitFailure(...); }
  catch { reject("PREVIOUS_RUN_UNRESOLVED_MANUAL_ACTION"); }
```

### 第三步：闭合工具的白名单不含它自己产生的码 ← **这是自锁的根源**

`tools/jd-customer-service-failure-closure.ts:56` 的可闭合白名单：

```
PAGE_STORE_IDENTITY_MISMATCH_MANUAL_ACTION
CHAT_PAGE_NOT_READY_MANUAL_ACTION
CHAT_PAGE_MISMATCH
CUSTOMER_SERVICE_FAILED_MANUAL_ACTION
LOGIN_GATE_MANUAL_ACTION
JD_IDENTITY_RATE_LIMIT_MANUAL_ACTION
CUSTOMER_SERVICE_LOGIN_PENDING
CUSTOMER_SERVICE_NAVIGATION_TIMEOUT
CUSTOMER_SERVICE_CONTROL_TIMEOUT
```

**`PREVIOUS_RUN_UNRESOLVED_MANUAL_ACTION` 不在里面。**

于是：一旦某轮以 `PREVIOUS_RUN_UNRESOLVED` 结束，它就成了新的"上一轮"，而下一轮想闭合它时发现这个码不在白名单 → `reject()` → 又产出一个 `PREVIOUS_RUN_UNRESOLVED`。**自我复制，永不收敛。**

这解释了为什么 15 次是同一个码、为什么四店同时卡住、为什么两周都没自愈。

### 第四步：10-20~10-22 叠加了风控

同期出现 10 次 `JD_IDENTITY_RATE_LIMIT`（`tools/jd-customer-service-export.ts:52` 的身份风控闸）。四店每天各跑一次、都在同一时段连续打同一平台，撞限流是预期内的。

这个码**在白名单里**，本来可以被闭合——但此时前置的 `PREVIOUS_RUN_UNRESOLVED` 已经锁死了，风控只是雪上加霜，不是主因。

### 第五步：10-23 ~ 10-27 五天完全没跑

近 14 天数据里这五天零 execution。**本次诊断未能确定原因**（n8n 元数据只能看到"没有记录"，看不到为什么没触发）。可能是 n8n 未运行、机器关机或调度被改，需要另查。**不猜。**

### 第六步：10-28 起有零星成功

设备店 10-28、10-30 成功，厨电 10-28 成功。说明**链路本身是可用的**——不是代码彻底坏了，是状态卡住；某些时刻状态碰巧可闭合就能跑通。

## 为什么两周没人知道

这四条线上 `errorWorkflow` 为 `None`（A1 查实、本次复核仍然是）。所以：

- 不进入 60 分钟等待态创建新的完整 execution
- **不走转人工钉钉提醒那条出口**

失败分类是对的（`MANUAL_ACTION` 标记在），但没有出口把它送出来。这正是主方案第一节那个判断的实证：**缺的不是执行能力，是运行证据与异常处置的闭环。**

## 修复路径：两件事，性质不同

### 一、让异常能被看见（代码已在 main，待发布）

`491c3fef` 已把客服四条与物流接入 `TeruisiHourlyRetry2026` 并加专用 webhook。**发布之后**，这类失败至少会走转人工单聊提醒，不会再积压两周。

但注意：`PREVIOUS_RUN_UNRESOLVED` 属于必须人工处理的失败，**接入重试不会让它自动好转**——重试机制对它只会反复触发同一个自锁。所以发布解决的是"看得见"，不是"自动修"。

### 二、打破自锁（需要改代码，本次未改）

这是独立缺陷，有两个方向，**取舍需要你定**：

**方案 A：把 `PREVIOUS_RUN_UNRESOLVED_MANUAL_ACTION` 加进可闭合白名单**
- 好处：一行改动，自锁立刻解除
- 风险：这个码的语义是"上一轮状态无法核实"，允许自动闭合等于允许系统自己跳过一个它说不清的状态。可能掩盖真实的状态损坏

**方案 B：加一个显式的人工闭合入口**
- 好处：保持"说不清的状态必须人工确认"这条纪律
- 代价：每次卡住都要人工操作一次
- 可复用现成范式：`backend/workflow/jackyun_close_authority.py`（吉客云一键闭合）已经是"绑定精确旧任务 + 摘要校验 + 保留原失败证据"的成熟形态

**我倾向方案 B**，理由是本仓既有纪律一贯是"结果未明不自动推进"（`docs/规范/导入与自动化.md` 的失败关闭清单、`n8n-hourly-safe-retry.md` 的停止条件都这么要求）。方案 A 虽然省事，但它放宽的正是那条纪律，而且放宽后出问题的症状会变成"静默跳过"——比现在的"响亮卡死"更难发现。

另外真正该查的是**首因**：10-17 那次 `PAGE_STORE_IDENTITY_MISMATCH` 为什么发生。自锁只是把一次首因失败放大成两周瘫痪，解除自锁不等于解决首因。

## 对 B4 的影响

B4 的观察对象就是这条链。诊断结果说明：

- 观察期内大概率**仍会继续失败**（自锁未解除）
- 所以 B4 能验的主要是**失败路径**：闸① 对无批次的判定、三轴的 `needs_human` 档、投影是否如实呈现失败

# ⚠️ 诊断修正（2026-10-31，由实现者的质疑引出，我用真实数据复核后确认）

**上文"自锁死循环"那个机制说错了。** 实现者在施工中质疑了我的前提，我用线上真实数据复核，**它是对的**。此处修正，上文保留以便追溯。

## 错在哪

我原说：`PREVIOUS_RUN_UNRESOLVED_MANUAL_ACTION` 成为新的"上一轮"失败码，而白名单不含它自己 → 自我复制。

**实际不是这样。** `tools/jd-customer-service-n8n-pipeline.ts:88` 的 `reject()` 只 `throw`，而新 plan 的写入在第 92 行之后——抛出时**还没有任何新 plan 文件**，所以这个码**从不被持久化**。

真实数据证实（读 `outputs/jd-customer-service-pipeline/*/*.json` 里 `stage=failed` 的 plan）：

```
exec=10432  failureCode=JD_IDENTITY_RATE_LIMIT_MANUAL_ACTION
exec=11039  failureCode=CHAT_PAGE_MISMATCH
exec=7250   failureCode=PAGE_STORE_IDENTITY_MISMATCH_MANUAL_ACTION
```

**没有任何 plan 的 failureCode 是 PREVIOUS_RUN_UNRESOLVED。** 卡住的 plan 一直保留它**原始的真实首因码**。四份先例审批文件批的也都是真实首因（`PAGE_STORE_IDENTITY_MISMATCH` / `CUSTOMER_SERVICE_FAILED` / `PAIR_PARSE_REJECTED`），没有一份是那个码。

所以白名单不含它**根本不是问题** —— 那个码压根不会出现在 `previous.failureCode` 的位置。

## 真正的根因：闭合的其他前置条件不满足

`closeCustomerServicePreSubmitFailure()` 除白名单外还要过 `isCustomerServicePreSubmitFailure()`（第 17-23 行）。我逐个 plan 核了，卡点分两类：

| 卡点 | 哪些 plan |
| --- | --- |
| **无 `failureBoundary`** | exec 7250 / 8653 / 9243 / 7266 / 7482 / 9861 / 7247 等，都是较早的 plan |
| **`source` 非空** | exec 11039（`CHAT_PAGE_MISMATCH`）、11042（`PAIR_PARSE_REJECTED`）、7247 |

而 `JD_IDENTITY_RATE_LIMIT` 那几条（10431/10432/10433/10571/10573/10574/10873）**结构上是可闭合的**。

所以实况是：**老的、结构不合格的 plan 堵在那里闭合不掉**，于是每轮新 A 都撞上它、报 `PREVIOUS_RUN_UNRESOLVED`。不是那个码自我复制，是**一个陈旧的不可闭合 plan 一直没被清掉**。

两类卡点的含义不同：
- **无 `failureBoundary`**：这些 plan 产生于该字段被引入之前（历史格式），自动闭合判不了"浏览器是否已关"，只能人工确认
- **`source` 非空**：失败发生在已经取到部分来源之后，属于 `downloaded_pair` 那条恢复路径，不是 `pre_export_zero_effect`

## 这对方案 B 的影响：方向对，但适用范围变了

人工闭合入口**仍然是对的解法**，而且现在理由更清楚：卡住的是结构不合格的历史 plan，自动判据判不了它们，正需要人工确认。

但有一处必须纠正：**审批不该针对 `PREVIOUS_RUN_UNRESOLVED`**（它不存在于任何 plan 里），而应针对卡住 plan 里**真实存在的那个首因码**。实现者在施工中就按这个做了，并在授权模块里**显式拒绝** `PREVIOUS_RUN_UNRESOLVED_MANUAL_ACTION`，理由是"没有东西可供审批匹配"。

这个判断正确。我原提示词里写"允许的码至少含 `PREVIOUS_RUN_UNRESOLVED_MANUAL_ACTION`"是错的，它没有照着做是对的。

## 这件事本身的教训

我的诊断基于**源码推演**（读 pipeline 与白名单的控制流），没有去读 `outputs/` 下的真实 plan 文件。推演出的机制自洽、能解释现象，但**与事实不符**。

实现者是在真实数据里撞到了矛盾才发现的。这印证了本仓已有的一条教训（`review-advice-needs-real-data-check`）：**"一律阻断"类判断要先用真实数据核影响面，测试全绿发现不了。** 这次是同一类错误的另一种形态——**自洽的源码推演也会错，要用真实数据验**。

# 第二次修正（2026-10-31，由前端实现者的真实数据验证引出）

上节"真正的根因"里那张卡点表**也有错**，再修正一次。

## 错在哪

我写了两类卡点，其中"**无 `failureBoundary`**"是错的。

`tools/jd-customer-service-failure-closure.ts:20`：

```js
if ("failureBoundary" in plan && (...)) return false;
```

这是**条件式检查**——字段不存在时整个检查被跳过，然后第 22 行 `if (!Object.keys(plan.source).length) return true;` 让空源 plan 直接通过。

我按真实语义重算了全部卡住的 plan：**exec 7250 / 8653 / 9243 / 7266 / 7482 / 9861 / 10431–10433 / 10571–10574 / 10873 全部通过该谓词。** 没有一个因为缺 `failureBoundary` 被挡。

## 真正的卡点在谓词之后

`closeCustomerServicePreSubmitFailure()` 在谓词之后还有**运行期 I/O 检查**：

- `assertPortAbsent(registered.browser.debugPort)` —— 浏览器调试端口必须已关闭，否则 `CUSTOMER_SERVICE_BROWSER_STILL_OPEN`
- 下载目录（`<downloadDir>/customer-service/<executionId>`）必须不存在或为空
- `readCustomerServiceFailureEvidence()` 必须能读到与 plan 一致的失败证据
- `downloaded_pair` 形态还要逐项复验 checkpoint

**这些是 I/O 级状态，静态读 plan 文件判不出来。** 所以"为什么闭合不掉"无法只靠读 JSON 确定，必须在真实环境里跑那几项检查。

## 我两次错在同一个模式上

| 次 | 我的说法 | 实际 | 怎么发现的 |
| --- | --- | --- | --- |
| 1 | `PREVIOUS_RUN_UNRESOLVED` 自我复制 | 该码从不持久化 | 实现者读真实 plan 文件 |
| 2 | 无 `failureBoundary` 导致阻塞 | 那个检查是条件式的，缺字段就跳过 | 另一个实现者读谓词源码 + 真实 plan |

两次都是**读源码推演得出自洽结论，但没验证真实数据/真实语义**。第二次更糟——我已经在第一次修正里写了"自洽的源码推演也会错，要用真实数据验"，然后立刻又犯了一次同类错误，而且这次是误读了一行条件判断。

**对后续的实际影响**：诊断"为什么闭合不掉"这件事本身**尚未完成**。已经确定的只有：
- 卡住的 plan 保留真实首因码（不是 `PREVIOUS_RUN_UNRESOLVED`）
- 它们都能通过结构谓词
- 所以卡点在运行期检查，但**具体是哪一项，本次没有查**（需要在真实环境跑，或读 helper 的失败日志）

人工闭合入口不受此影响——它重新推导了那套检查，不依赖我的卡点分类。
