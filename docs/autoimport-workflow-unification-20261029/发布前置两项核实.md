# 发布前置两项核实（2026-10-31）

只读核实。结果**推翻了我上一轮的两个判断**，发布方案要改。

## 第一项：错误工作流为何停用 —— 查到了时间点与原因

### 事实

| 时间 | 事件 |
| --- | --- |
| ~10-22 | **仍在正常工作**，`mode=error` 的 execution 持续产生（10-19/10-21/10-22 共 8 条可见） |
| **10-26 15:44** | 被 `import`（CLI 导入）改过一次版本，`versionId=21377db1` |
| 之后 | **零 execution**，`active=False`、`activeVersionId=NULL` |

所以不是"一直没工作"——**它工作到 10-22，10-26 那次 CLI 导入之后停了**。

### 关键发现：线上与仓库是两套不同的告警实现

| | 线上（12 节点） | 仓库（13 节点） |
| --- | --- | --- |
| 告警节点 | `转人工时发钉钉提醒`、`派发未知时发钉钉提醒` | `转人工发钉钉提醒`、`告警-派发未知`、`收集被丢弃的终局失败` |
| 告警方式 | **`executeCommand` 调 PowerShell 脚本** | `httpRequest` POST `/api/ai/channels` |
| 频道来源 | 脚本内部决定 | `$env.TERUISI_ALERT_CHANNEL_ID` |

**节点名、节点类型、告警机制全都不同。** 这不是版本新旧，是两条不同的实现路线。

线上 `targets` 实际有 **13 条**（我第一次正则没匹配到 jsCode 内的映射，误报 0 条，此处更正），不含客服四条与物流——与我们合并的 18 条差的正好是那五条。

## 第二项：`TERUISI_ALERT_CHANNEL_ID` —— 我的担心不成立

线上告警**不用这个变量**。它调的是：

```
powershell -NoProfile -ExecutionPolicy Bypass -File "D:\teruisi-ops\ding-alert\send-manual-action-alert.ps1"
  -WorkflowName ... -ErrorCode terminal_manual_action -ExecutionId ... -Detail ...
```

该脚本**存在**（`D:\teruisi-ops\ding-alert\send-manual-action-alert.ps1`，17,885 字节，10-25 00:48），且**不在仓库里**——是运维侧独立部署的。

`$env.TERUISI_ALERT_CHANNEL_ID` 只存在于**仓库版**的实现里（`tools/n8n-hourly-retry-policy.mjs:299,425`）。所以"变量未配置"这件事对线上无影响，但**对我们要发布的仓库版有影响**。

## 这对发布意味着什么：原方案不能直接执行

我原计划"先发共享错误工作流白名单 13→18，再逐条更新五条原 ID"。现在看，这样做会：

1. **把线上的 PowerShell 告警实现替换成仓库版的 HTTP 实现** —— 而仓库版依赖未配置的 `TERUISI_ALERT_CHANNEL_ID`，等于**把一个在用的告警通道换成一个不通的**
2. 线上那三个 PowerShell 告警节点会消失（仓库版没有同名节点）
3. 顺带会覆盖 10-26 那次 CLI 导入带来的其他改动（我没有逐项对比完整差异）

**所以不能发。** 现状是：仓库版与线上版在告警这一层已经分叉，且**线上那一版是能用的**（脚本在、10-22 前确实在发）。

## 还有一个更要紧的问题没解决

**错误工作流 `active=False`。** 不管发哪一版，它停用就不接收任何失败——11 条正式流程的重试机制**从 10-26 起一直没在工作**，不只客服四店。

这件事比客服积压严重：按 `n8n-hourly-safe-retry.md`，那 11 条的"60 分钟完整重试"是现行设计的一部分，现在整体失效了 5 天以上。

**为什么停用、是否有意，仍未查明。** 10-26 那次 `import` 是谁做的、做了什么、为什么之后 active 变 false，n8n 元数据只记录了版本变更，看不到意图。

## 建议的新顺序

1. **先查清 10-26 那次 CLI 导入**：改了什么、为什么导致停用、是否有意。这决定后面所有事
2. **决定告警实现以哪一版为准**：线上 PowerShell 版（在用、脚本在仓库外）还是仓库 HTTP 版（依赖未配置变量）。**两版合一之前不应发布**
3. 重新激活错误工作流（让 11 条的重试恢复）
4. 然后才是把客服四条与物流加进白名单

第 2 项是个真正的取舍，需要你定：线上那版不在仓库里管理（改它不走代码评审），仓库那版能被版本管理但依赖缺失配置。
