## 逐条理由

### 1. `TeruisiHourlyRetry2026` —— 进去会出事

它的触发器是 `errorTrigger`：**它本身就是错误工作流**，由别的工作流失败时触发。

把它列入自己的白名单，意味着"错误工作流失败时触发错误工作流"——自引用循环。n8n 不会帮你拦这个。症状是一次失败可能衍生出持续的错误 execution 链，而每条看起来都是"正常的重试"。

**这一条是"所有工作流都进白名单"这个判断最直接的反例。**

### 2. `20ZtTLAAbsx5KvTp`（My workflow）—— 身份不明

1 个节点、只有 `manualTrigger`、名字是 n8n 默认的 "My workflow"。这是个空壳或临时试验件，不是业务流程。

白名单的语义是"这条流程失败后值得自动重建一次完整 execution"。对一个 1 节点的空壳，没有东西可重建。

### 3. `DlSNhk4y5H1e7AJ6`（天猫一次性跳过M恢复）—— 一次性人工操作

名字写明"一次性"，只有 `manualTrigger`，是为某次特定故障做的人工恢复件。

**自动重试一个"一次性人工恢复"是矛盾的**：它的前提是人判断过当时的状况。自动重跑可能在完全不同的状态下执行跳过逻辑。

### 4. `NewProductWeeklyDingTalk2026`（新品销售周报）—— 性质不同，不建议

它是**投递类**流程（发周报），不是**导入类**。

按方案的三轴设计，投递失败属于第三轴，处置方式是"只恢复投递部分，不重跑业务"。而白名单那套机制是"等 60 分钟 → 创建新的完整 execution"，用在投递上会变成重发周报。

另外它历史上有自己的问题：`n8n-hourly-safe-retry.md:68` 记录 n8n v2 默认禁用 `Execute Command` 曾导致这条无法激活，启动器现在只为它恢复所需节点。给它加自动重试会和这个特殊处理纠缠。

如果要做它的失败兜底，应当单独设计投递重试，不复用导入那套。

### 5. `cF7wN8k2pQ5sR1vX`（天猫亿玖生意参谋逐日签收导入）—— 需先定性

这条是真正的导入流程（8 节点、`scheduleTrigger` + `localFileTrigger`），性质上**符合**白名单条件。

但它当前停用，且与在用的 `M4xY8kQ2vR6sT9pC`（天猫亿玖 P/M 直连）是同一家店。要先确认它是已被取代的旧版本，还是另有用途——**同一家店两条导入流程同时激活会撞店铺会话**。

定性之后再决定，不能因为"它看起来像导入流程"就加进去。

### 6–7. 两个旧兼容模板 —— 已在白名单，保持现状

`JdN8nM3uL7tI2026` 与 `JdMarketDaily2026` 已经在 `hourlyRetryTargets` 里（这就是"13 个登记目标 vs 11 条正式流程"的差额）。

`n8n-hourly-safe-retry.md:19` 明确：**兼容模板不得与现行静默版同时激活**。它们在白名单里但保持停用是现行设计，不要动。

## 白名单的准入判据（建议写进规范）

从上面逐条分析里能抽出四条判据，将来新增工作流时照着判：

1. **不能是错误工作流本身**（自引用）
2. **必须有自动触发器**（`scheduleTrigger` / `webhook`）。只有 `manualTrigger` 的，按 `n8n-hourly-safe-retry.md:15`「错误工作流只接收 trigger 和 webhook 模式的失败」本来就不会触发重试，加进去是死条目
3. **必须是导入类**，不是投递类或一次性恢复类。投递失败只恢复投递，不重跑业务
4. **必须能安全重跑整条**。重试机制是"创建新的完整 execution"，不是节点重放；对"一次性跳过"这类带人工判断前提的流程不适用

按这四条，当前 17 条白名单 + 补 `JdLogisticsDaily2026` = 18 条，是正确的收口范围。
