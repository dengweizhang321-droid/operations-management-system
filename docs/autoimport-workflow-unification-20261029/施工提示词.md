## 分工：这是整个施工方案的执行纪律（2026-10-30 用户确认）

**Opus 做策划与反审，Sonnet 执行代码。** 适用于本方案全部单元——已完成的 A1/A2b/A2c/B0/B1/B2/B3，以及尚未写提示词的 P2/P3/P4。

| 角色 | 谁 | 做什么 | 不做什么 |
| --- | --- | --- | --- |
| 策划 | Opus | 定架构取舍、查准事实基线、拆单元、写提示词、定验收判据 | **不写实现代码** |
| 执行 | Sonnet（`model: sonnet`） | 按 E-提示词实现、自测、提交推送 | 不自行合并/准备制品/发布；不扩大范围 |
| 反审 | Opus（未参与该单元实现的上下文） | 独立验证，自己造反例，不采信执行者报告 | **发现问题只报不改**，证据交回执行者 |

为什么必须这样分（`docs/规范/任务模型分工.md` 的独立审查条款）：审查必须是未参与该部分实现的上下文，原执行者不能自称独立审查。Opus 若既写又审就踩了这条。

### 派工的具体做法

- 实现：`Agent` 工具显式传 `model: sonnet`，贴 E-提示词全文
- 反审：新上下文（不复用实现会话），贴 R-提示词全文

### 反审必须自己动手验，不能读报告就签字

本方案已有的实证——这几条都是执行者报告"通过"、我自己重验才确认或纠正的：

### 把提示词整段复制，不要摘要

里面的"已核实的事实"段是防止执行者重新推导（推错的代价见下），"硬边界"段是防止越界，删了就失效。

事实不给全的真实代价：京准通推广的批次身份是 `source=jd_promotion` + `dataset=ad`，**不是** `promotion_daily`（那是天猫的）。如果不在提示词里写明，执行者照 `promotion_daily` 查，闸① 一条批次都查不到，于是把每次正常运行判成失败——一个"看起来在工作、实际天天误报"的闸。

## 所有提示词共用的前置（已写进每条，此处说明来由）

每条 E-提示词都带这三段，原因：

1. **必读规范**：`AGENTS.md` 要求任何任务开始前完整读取它与相关专题，不得只依赖对话或缓存
2. **分支与 worktree**：第 2 条要求从最新 `main` 建独立 `codex/*` 分支与 worktree，不得在生产运行目录开发
3. **三步各自授权**：第 4 条要求合并 / 制品准备 / 发布上线三步分别取得当次授权；提示词里一律写明"做完停下报告，不要自行合并"
4. **工作位置要在提示词最开头单独写一段**（2026-10-31 的教训）：连续两个单元出现动错位置——B3 误动共享 stash、B2b 误在主工作区编辑文件。两次都自己收拾干净并主动报告，但不能靠运气。E-提示词的"工作基点"段必须排在任务描述**之前**，明确写出 worktree 绝对路径、禁止在 `D:\运营管理系统` 编辑、以及主工作区有 18 个未跟踪文件和 3 条保全 stash 不得触碰。
5. **禁止 `git stash`**（2026-10-30 B3 的教训）：**worktree 共享同一 stash 列表**，在 worktree 里 stash 会动到主工作区的保全快照。本仓主工作区有 3 条保全 stash（施工协调 20261027、B项残留、20260928 集成前），动错会丢。B3 执行者误操作过一次，自己 `git reset --hard HEAD` 收拾干净且主动报告，三条 stash 完好——但不能靠运气。以后每条 E-提示词的硬边界都要写明不得使用 `git stash`

# 派工顺序与依赖

```
A1 线上核实（只读）
 └─> A2 修生成器漂移 + 同步检查
      └─> B1 四张表与迁移
           └─> B2 闸① 与三轴判据（核心）
                └─> B3 读接口与服务端分页
                     └─> B4 真机只读观察一周
```

A1 必须最先做,因为它决定 A2 处理哪些条目,也决定日程视图上"计划到点"画在哪。B2 是核心——模型够不够用在这里见分晓;它被证伪的话,回到 B1 改的代价是天级。

**每个单元做完都停下等授权**,不要让执行者连续跑完多个单元。按 AGENTS.md 第 4 条,合并到 main、准备制品、发布上线三步各需当次授权;单元之间的推进也建议你逐个过目。

## 派工时的具体做法

Claude Code 的 Agent 工具支持 `model` 参数。按本项目分工：

- 实现单元：`model: sonnet`，贴 E-提示词
- 反审单元：新上下文（不要复用实现会话），贴 R-提示词

反审发现问题时，把证据交回执行者修，审查者不自己动手改——这样审查才是独立的。

## 这些提示词里刻意写了什么

每条 E-提示词都带了"已核实的事实"段,目的是**防止执行者重新推导**。那些事实是本会话逐条查证过的（带文件行号）,重新推导不仅浪费,还可能推出错的结论——比如把已退役的 `lib/imports/content-fingerprint.ts` 当成当前幂等实现。

每条 E-提示词都带"硬边界"段,其中这几条每个单元都有:
- 不改 n8n、不运行采集或导入、不发送消息
- 做完停下报告,不自行合并 / 准备制品 / 上线
- 只暂存本任务文件

每条 R-提示词都要求**自己构造反例、不采信执行者的报告**。B2 的 R-提示词尤其强调这点,因为"闸是绿的但它检查的不是该检查的东西"是这类工作最常见的失败形态,而测试全绿发现不了。
