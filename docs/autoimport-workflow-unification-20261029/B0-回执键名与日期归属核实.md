## 第一节：回执键名一致性

结论先给：**六条链里没有发现参考方案那种"产出侧 `skip`、消费侧 `skipped`"式拼写分裂。** 原因是本系统的 n8n 工作流 IF/Code 节点**从不解析业务语义键**（不读 `skipped`/`not_due`/`duplicate` 之类字段），只解析两类结构性字段：协调锁状态 `coordinationStatus`（是否拿到 helper 所有权）和循环控制字段 `continueBackfill`/`dailyBackfill.status`（天猫逐日循环专用）。真正承担"跳过/重复/未到期"语义的键，产出侧和消费侧几乎总是**同一个 TypeScript/Python 代码库里的同一次读写**，不存在跨进程、跨语言的键名转译机会。后端 `_complete_manual_run()`（`backend/workflow/import_chain_status.py:25-127`）本身也只核验 n8n 节点执行结构（节点名、类型、`executionStatus === "success"`），完全不解析 pipeline 回执 JSON 里的任何业务字段——这点已逐行读过源码确认，不是沿用文档旧说法。

### 同一语义多拼法并存？

**在跨进程/跨链边界上未发现。** 全仓库搜索 `skip`/`skipped` 字面量，命中的全部在各链内部自产自销（如吉客云、天猫 `tmall-promotion-export.ts`、ERP `erp-sales-automation.ts`、`lib/market/image-cache.ts`），且逐一确认同一条链内部只用一种拼法，未发现两个模块各写一种拼法再被同一消费方误读的情况。`not_due`/`no_gap`/`duplicate_ignored`/`imported`/`duplicate`/`completed`/`skipped`（布尔）这些语义各自在各链内保持单一写法。

### 假绿（消费侧把跳过误读为成功）？

**未发现。** 核实到的所有跨边界消费点（n8n IF 节点、`import_chain_status.py`、各 pipeline 之间的 HTTP 调用）要么完全不读业务跳过类键（多数情况），要么读的键名与产出侧逐字相同（`dailyBackfill.status`、`continueBackfill`、`imported`/`duplicate`）。京东商品/客服/物流链的消费侧用的是**白名单式显式枚举判断**（`=== "imported"` 或 `=== "duplicate"`，否则判失败），这是偏严格的失败模式，天然排除了"未知值被当成成功"的假绿路径。

## 第二节：日期归属

### 跨链共用的"冻结计划时间"机制

五条链（京准通推广、京东客服、京东多店商品、吉客云、京东物流）与天猫 A/B/C/P/N 阶段共用同一个模式：n8n schedule trigger 或 webhook 触发后，第一步由一个专门节点（天猫叫「固定原执行计划时间」，其余链在 helper 服务内部用同样来源的 `scheduledAt`/`planTime`）把触发时刻冻结为 `scheduledAt`，之后通过 HTTP 头（`X-TERUISI-SCHEDULED-AT`）或 helper 内存状态（`SlotIdentity.scheduledAt`，`tools/tmall-isolated-helper.ts:22,82-86`）一路传递，所有下游阶段的"今天/昨天"计算都读这个冻结值，不读各自执行时刻的 `new Date()`。小时级安全重试（`automation/n8n/data-import-hourly-safe-retry.workflow.json`）的恢复路径也显式要求携带 `originalScheduledAt`，缺失即失败关闭（`tmall-yiyong-seven-day-gap-loop.workflow.json` 的「固定原执行计划时间」节点注释："Hourly descendants must carry the original anchor...a new execution must not silently recompute yesterday after downtime."）。

### 数据日期是否随任务下发？

六条链（不含天猫 M 节奏判定）**均确认是**：建计划/plan 阶段一次性计算并持久化到 plan/manifest 文件，run/verify 阶段的子进程通过命令行参数或 HTTP 请求体接收已固化的日期，不在子进程启动时自行调用 `new Date()`/`date.today()` 推算"昨天"。天猫 M 节奏判定是本轮唯一确认"不随任务下发、按执行时刻判定"的点，但如上表所述，这是规范明确定义的行为而非本轮新发现的缺陷模式。

## 第三节：结论汇总

**键名一致性**：六条链里**零处**发现"产出侧 `skip`、消费侧 `skipped`"式的拼写不一致，**零处**发现会导致假绿（消费侧把跳过误读为成功）的键名问题。根本原因是本系统的 n8n 分支逻辑不解析业务跳过语义，只解析协调锁状态和天猫专用的循环控制字段，而这两类字段产出侧与消费侧用的是同一份代码定义，没有分裂空间。参考方案那条 P1 事故的触发条件（脚本层与 agent 层各自独立实现同一语义的键名）在本系统的架构里不成立。

**日期归属**：六条链里**五条半**（京准通推广、京东客服、京东多店商品、吉客云、京东物流、天猫 A/B/C/P/N 阶段）确认为"计划时刻冻结、随任务下发"，有代码注释与跨午夜护栏佐证，**零条链存在参考方案那条 P2 事故的模式**（按执行时刻 `date.today()` 落日导致次日误判已完成、前一天数据静默不取）。唯一的例外是天猫 M（货品主数据）节奏到期判定用执行时刻，但这是规范明文定义的"按实际完成日顺延"设计，且 M 失败不影响已完成的商品日/推广日事实（不会导致数据静默不取），性质与参考方案的 P2 事故不同，闸④落地时仍建议记录在案以便评估是否需要改为固定计划日。

# 独立反审（2026-10-30，未参与本核实的新上下文）

这份结论是"零处假绿风险"。结论越好越要独立验——闸① 如果建在错误假设上，整个试点白做。我自己重查了三项。

## 核查一：产出侧的跳过类键名

```
tools/jackyun-export-first-pipeline.ts  → "duplicate_ignored"
tools/jackyun-n8n-pipeline.ts           → "duplicate_ignored"
tools/jd-logistics-n8n-pipeline.ts      → "duplicate"
tools/jd-promotion-n8n-pipeline.ts      → "no_gap"
tools/tmall-warehouse-n8n-pipeline.ts   → "duplicate"
```

确认存在多种拼法（`duplicate` / `duplicate_ignored` / `no_gap`），但这本身不构成问题——要看消费侧读不读。

## 核查二：消费侧读不读这些键（关键）

逐键查 n8n 工作流定义：

| 键 | 出现在几个工作流定义里 |
| --- | --- |
| `skipped` | **0** |
| `"skip"` | **0** |
| `no_gap` | **0** |
| `duplicate_ignored` | **0** |
| `day_complete` | **0** |
| `not_due` | 20 |

`not_due` 那 20 处我逐个看了——**全部在 `stickyNote`（便签说明文字）里**，不是执行逻辑。例如天猫亿玖那条的"凭证说明"便签写着"未到期时 M 返回 `not_due`"，这是给人看的文档，n8n 不解析它。

再查 `backend/workflow/import_chain_status.py` 真正读什么键：**只有 `"executionStatus"`**（第 94 行），即 n8n 自己的节点执行状态。

**结论成立**：本系统的完成判据走的是 n8n 原生 `executionStatus` + `manualCompletion` 阶段契约，业务跳过语义键止步于 HTTP 响应体，没有被消费侧解析。所以不存在参考方案那条 P1（产出 `skip`、消费认 `skipped` → 假绿）的同类风险。

## 核查三：天猫 M 这个唯一例外

`tools/tmall-product-master-cadence.ts:54` 的 `shanghaiBusinessDate(now = new Date())` 确实支持传入 `now`，而第 172 行 `shanghaiBusinessDate(input.now)` 的调用链没传，走默认值 = 执行时刻。

但 `docs/规范/导入与自动化.md:19` 明文定义：M「每日调用，但只有店铺注册表 `productMasterCadence` 到期、存在未决货品活动清单或手动完整运行显式发送强制标记时才允许产生业务动作」。

**这是设计，不是缺陷。** M 的语义是"按实际完成日顺延"，用执行时刻判到期是正确的；且 M 失败不推进下次日期、不回滚已完成的商品日与推广导入。

## 这对 B2 的闸① 意味着什么

原提示词里"闸④ 键名对拿"那条可以**降级**：本系统不需要防"消费侧误读跳过键"，因为消费侧根本不读。

但闸① 本身**更重要了**，原因正是这个结论：既然 n8n 侧的判据只有 `executionStatus`，那"n8n 说成功"与"业务真的入库了"之间就**完全没有交叉验证**。脚本回报的 `no_gap`、`duplicate` 这些业务语义，现在没有任何自动化消费者在看。

所以闸① 要做的事从"交叉核对两份判据"变成**建立第一份业务判据**——后端自己查业务域的 ScopeHead 与批次，而不是读脚本回报的那些键。这反而让闸① 的设计更干净：不依赖任何脚本自述字段。
