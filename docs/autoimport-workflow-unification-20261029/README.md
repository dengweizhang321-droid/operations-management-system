## 一句话结论

能达到参考方案的施工效果，但**规则不能作为调度源**。本系统已有 n8n 11 条正式工作流、统一错误工作流、本机 helper 协调锁，照搬"内置调度 + 退役外部执行器"会产生第二个任务所有者。正确路线是：**n8n 保持唯一定时所有者，规则表作为"期望声明 + 与已发布调度的一致性核验"，Django 补上缺失的持久运行投影。**

## 本系统的真实缺口只有一个核心项

现有 `read_today_status()` 每次现读 n8n SQLite 产出"今天快照"，所以下载/登录/导入**前**的失败查不到、历史查不到、运行与业务批次无法关联。补上逻辑运行 → 执行尝试 → 模块结果 → 批次/覆盖的持久投影，是 P1 的主体，也是其余三期的前提。

其余四项为：规则不可在系统内编辑且同一事实有三处说法；矩阵 104 格里 81% 为空；受控动作只有吉客云一家；AI 工具枚举缺三个 workflowKey。

## 最要紧的一道闸

**闸①：后端按导入批次独立核对。** 判据不由脚本自述——下发时后端已知要跑哪几个模块，收尾时后端自己查对应业务域的 ScopeHead 与批次。脚本说 ok 而域里没有新批次且无权威"无需新增"证据，判 failed 不判 done。

现状缺这一道：执行结果与业务结果从未交叉核对。
