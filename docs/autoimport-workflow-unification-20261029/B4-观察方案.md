# B4 真机只读观察方案（2026-10-31 定）

## ⚠️ 定方案时发现观察对象本身正在出问题

核实线上 `JdCustomerService2026` 时查到的实况（只读 n8n 元数据）：

| 工作流 | 近 14 天 execution | 成功 |
| --- | --- | --- |
| `JdCustomerService2026` | 10 次 | **2 次**（10-28、10-30） |
| `JdCustomerServiceChudian2026` | 10 次 | **1 次**（10-28） |
| `JdCustomerServiceCutMeat2026` | 10 次 | **0 次** |
| `JdCustomerServiceDishwasher2026` | 10 次 | **0 次** |

**四店 40 次 execution 只有 3 次成功。** 而且 10-23 到 10-27 **整整五天完全没跑**。

失败里能读到 `MANUAL_ACTION` 标记与 `timeout`，说明失败**已被正确分类为"必须人工处理"**（符合 `docs/规范/导入与自动化.md` 的失败关闭清单，没有被错误地自动重试）。

但关键在于：**这四条线上都没绑 `errorWorkflow`**（A1 查实、本次复核仍为 `None`）。所以这些失败：
- 不会进入 60 分钟等待态创建新的完整 execution
- 不会走转人工钉钉提醒那条出口

**结果就是积压了两周没人知道。** 这恰好实证了主方案第一节的判断：现状缺的不是执行能力，而是"运行证据与异常处置的闭环"。

## 这对 B4 的三个含义

### 一、观察的意义变了，而且变得更有价值

原计划是"观察一条正常运行的链，核对投影与业务批次是否一致"。实际拿到的是一条**正在失败的链**。

这反而是更强的试验场：
- 失败路径比成功路径更能检验闸① 与三轴（成功路径只验一条 happy path）
- `needs_human` 这一档有真实样本可核，不用造
- 能验证"投影是否把失败如实呈现"，而不只是"成功时数字对不对"

### 二、"连续一周零未解释差异"这个判据要改

原判据假设每天有一次成功运行可对账。实际可能一周只有 1–2 次成功。

**改为按事件计，不按天计**：
- 观察窗口内发生的**每一次** execution（无论成败）都要能在投影里找到对应记录
- 每一次 `status=success` 都要能核对到业务域的批次与覆盖
- 每一次 `status=error` 都要能在三轴上落到正确的档（执行轴 `failed` 或 `needs_human`）
- **零未解释差异** = 上述三类逐条对得上，不是"连续七天都有记录"

### 三、不要为了拿样本而制造失败或补跑

规范明确：造失败就是制造真实平台点击。观察期内：
- 不手动触发任何 execution
- 不改 n8n
- 不为了"让它跑起来"去修登录态或凭据

如果一周内样本仍然太少（例如 0 次成功），**如实报告样本不足**，不要延长观察期硬等，也不要降低判据。那种情况下结论是"B4 未能验证成功路径"，而不是"B4 通过"。

## 观察什么（逐项）

### A. 投影与 n8n 元数据的一致性

每次 execution 都应在 `AutomationLogicalRun` / `AutomationAttempt` 里有对应：
- `native_execution_id` 对得上
- 恢复链（如果发生）父子关系正确
- 跨午夜的 execution 其 `plan_date` 是计划日而非执行日

### B. 闸① 的判定是否符合业务实况

对每次 `success`：
- 业务轴判 `verified` 时，`CustomerServiceImportBatch` 确实有对应的 completed 批次
- 判 `no_new_needed` 时，确实带了原批次 id 或覆盖证据
- 判 `partial` 时，确实是配对计数非零（`session_only` / `chat_only` / `ambiguous`）

**重点验 B2b 反审里标出的两条未经真实数据检验的判据**：
1. 逐日覆盖检查（查 `CustomerServiceConversation.consulted_at` 分布）能否正确反映滚动 30 天的真实缺口
2. `partial`-for-pairing-gap 映射是否贴合真实的 only/ambiguous 日常取值——如果真实数据里这些计数**天天非零**，那 `partial` 会变成常态，这个映射就需要重新考虑阈值

### C. 三轴有无互相顶替

- 执行 `failed` 时业务轴不得显示 `verified`
- 失败的 execution 不得被标成"已完成"
- `needs_human` 时不得提供普通重试

### D. 已知局限是否在真实数据里暴露

B2 披露的"批次区间内部空洞"在客服链的对应形态是：某天有会话行但数量异常少（报表内部空洞）。观察期要记录是否出现"判了 `verified` 但某天会话数明显偏低"。

## 每天记什么

产出 `B4-观察日志.md`，每天一节：

| 字段 | 说明 |
| --- | --- |
| 日期 | 上海日期 |
| 本日 execution | 编号、status、mode、起止时间 |
| 投影记录 | 对应的 logical run / attempt，有无缺失 |
| 闸① 判定 | 三轴各自的值 |
| 业务域实况 | 该范围的 completed 批次 id、会话逐日分布、配对计数 |
| 差异 | 逐条列，有就写，没有写"无" |
| 证据 | 支撑上述结论的查询结果（脱敏） |

## 前置：观察需要代码在可观察环境里

当前状态：代码在 main，但**迁移 0009/0010 未在任何真实数据库执行、接口未上线**。

所以 B4 开始前需要：
1. 在**隔离的镜像环境**执行迁移并接上只读投影（按 `docs/规范/开发与交付.md`，验证默认使用与生产隔离的镜像库）
2. 或者获得授权在生产执行迁移（strict 级，需制品准备 + 发布两次授权）

**建议走镜像环境**：B4 是只读观察，不需要生产写入；而在镜像里对账同样能验证判据是否贴合真实数据（镜像需保留必要的业务口径和边界条件）。

## 不做什么

- 不改 n8n、不手动触发、不制造失败
- 不修客服链的登录态或凭据（那是另一件事，见下）
- 不发送钉钉消息
- 观察期内发现代码缺陷，只保存最小脱敏证据并提出单独修复任务，不在观察任务里改

## 顺带暴露的一件待决事项

**客服四店近两周几乎全败、五天未跑，且无人知晓。** 这是独立于 B4 的生产问题：

- 失败分类正确（`MANUAL_ACTION`），所以不是误判
- 但因为没绑 `errorWorkflow`，既无自动重试也无转人工提醒
- 修复路径已经在 main 里了（`491c3fef` 已把四条接入白名单并加专用 webhook），**但未发布到 n8n**

也就是说：**发布那次合并，正好能解决这个积压问题。** 这给"发布客服四条与物流的重试接入"提供了实际紧迫性，不只是补一个缺口。

至于那些 `MANUAL_ACTION` 失败本身要怎么处理（登录态、凭据、还是平台侧变化），需要另开任务诊断，不属于 B4。
