## 分页契约与查询范围

新增 Worker 只读聚合 `GET /api/imports/records?page=1&pageSize=20&source=&status=`。`pageSize` 为 1–100（沿用现有领域接口上限），page 为正整数；联合翻阅前 10000 条，超出明确报 400 并要求缩小筛选，不将 10000 当成真实 total。整轮聚合 30 秒 deadline，底层请求沿用各服务既有有界超时及签名 principal。

响应：`items`、实际存在的 `sources`，以及：

```json
{
  "pagination": {
    "page": 1,
    "pageSize": 20,
    "total": 4007,
    "returned": 20,
    "truncated": true,
    "completeness": "truncated_do_not_infer_absence"
  }
}
```

`truncated = offset + returned < total`，与指定范例一致；否则 completeness 为 `complete`。页面明确显示「当前页 20 条 · 匹配总数 4007 条 · 分页结果未全部读取」，顶部同时提示分页面不能用于推断其他记录不存在。没有将页长当总数。`sources` 从数据库实际出现的原有 source 身份派生，与状态筛选独立；不新增无数据伪选项。

七个既有 Django 历史 GET 增加显式 `records=1` 分支，共用 `backend/sales/import_record_query.py`。该分支在原有鉴权之后执行，只查询当前 reader 所属的那张批次表：先按原来源映射、数据类型与状态分组筛选，再 `count()`，最后执行 `rows[offset:offset + pageSize]`。未带 records 参数的既有调用者、默认值、导入和恢复行为保持不变。

查询排序仍是完成时间优先、缺失则创建时间；转成真实时间戳比较，老的无时区文本按上海业务时区解释。相同时间增加 `sourceKey / id` 升序稳定顺序，PostgreSQL 使用 C collation；传输时间规范化为 UTC 六位微秒，避免 JavaScript 毫秒精度吞掉数据库排序差异。

Worker 复用各领域签名读取适配器，并行取得必要的领域前缀；每个 SQL 请求最多 100 行，深页按 chunk 使用真实 offset/limit，再合并取目标页。没有给 workflow reader 增加跨域数据库权限，也没有碰 `automation_run_query.py` 或 P1 表。网店历史仍仅 admin 可读；其他原有无范围限制角色看到获授权的六域，页面提示网店未获授权。受限 scope 仍拒绝，不能用 records 参数绕过。

任何应读取来源失败，整页读取失败，不能将失败域默认为空。跨 chunk 的 total 或领域 revision 改变也拒绝本页并提示刷新；销售原 GET 没有 revision header，因此该分支额外采样既有 `revision_token()`，前后不一致拒绝，并返回 recordRevision 绑定后续 chunk。

## 效率与一致性限制

这是保留七域最小只读权限下的有界合并，不是跨域 SQL UNION 或持久游标。第一页每域最多读取 20 条，浏览器只收 20 条；深页仍会重新读取各域所需前缀，最坏成本随页码增长，受 10000 条联合窗口与 30 秒 deadline 限制。没有给出未经测量的 P95 或数据库扫描成本下降承诺。若以后规模显著增长，应另评估领域 keyset 游标或由批准的聚合 reader 提供跨域查询。

同一域读取期间和跨 chunk 会核 revision，但七个领域没有共同事务快照；两次翻页之间新增/更新记录仍可能改变 offset 分页的成员，这是当前历史列表的活读语义。源读取失败不回退旧数据库、不把缺失当零；同筛选刷新失败可以保留上次成功页并显示错误，新筛选不展示旧范围数据。
