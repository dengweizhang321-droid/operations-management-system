# 京东单店试点落地方案（2026-10-30）

本文是[主方案](REPORT.md)的试点切口。只规划，未改代码、未动 n8n、未运行采集。

## 一、先说一个硬约束：不是每条链都能单店试点

四个京东店与各链的实际绑定（按 `lib/imports/chain-catalog.generated.json` 实测）：

| 链 | 工作流 ID | 覆盖主体 | 能否单店试点 |
| --- | --- | --- | --- |
| 京东 · 商品数据 | `JdN8nSilentCopy2026` | **四店共用一条** | ❌ **不能** |
| 京准通 · AI 推广 | `JdPromotionDaily2026` | 商用设备店独占 | ✅ 能 |
| 京准通 · AI 推广 | `JdPromotionCutMeat2026` | 切肉机店独占 | ✅ 能 |
| 京东商智 · 市场榜单 | `JdMarketSilentCopy2026` | 洗碗机店独占 | ✅ 能 |
| 京东 · 客服聊天记录 | `JdCustomerService2026` 等 4 条 | 各店独占 | ⚠️ 能，但见下 |
| 京东 · 入仓库存 | `JdLogisticsDaily2026` | 事业部主体（非销售店） | ✅ 能 |

**`jd` 商品数据链四店共用同一条工作流、同一个 execution**，整条跑或整条不跑。"只给一个店做试点"在这条链上做不到——它恰恰是三视图里"共用工作流显示整链状态"要表达的东西，试点阶段不要碰。

## 二、推荐切口：京准通推广 · 志高商用设备旗舰店

### 为什么选它

1. **一店独占一条工作流**，范围天然隔离，不影响其他店。
2. **在线正式流程**。按 `n8n-hourly-safe-retry.md`，11 条正式目标含"京准通推广 2 条"；客服四店不在正式目标内，且 4 条里 3 条仍是 `.candidate`。
3. **已有完整的真实故障到恢复样本**（试点最值钱的东西）：
   2026-09-12 13:00 trigger execution `1268` 因报表列表迁移引导遮挡失败 → 错误 execution `1269` 等到 14:00 → 新建完整 webhook execution `1287` → 同处再失败 → `1288` 等到 15:01 → `1303` 于 15:01:58 成功，精确导入 2026-09-11 商用设备店 **9,496 行，批次 completed、告警 0、重复 0，落库覆盖零缺口**。
   **闸①、三轴状态、恢复链展示这三件事可以直接拿这条历史样本回放验证，不必等新故障。**
4. **A/B/C 三阶段边界清晰**，正对应模块结果的阶段字段：
   - `A·固化京准通目标日期与店铺` → `/jd-promotion/plan`
   - `B·生成下载校验导入并回查` → `/jd-promotion/run`
   - `C·独立复验文件与精确批次` → `/jd-promotion/verify`
   另有 `领取共享 helper`（`/coordination/claim`）、`helper 领取成功？`、`等待前序流程释放 helper`、`失败后每小时安全重试入口`（webhook）。
5. **业务域证据字段已齐**，闸① 不需要新增任何业务域字段。

### 业务域证据路径（闸① 的输入，全部已存在）

`backend/netshop/models.py` 的 `NetshopImportBatch` 已有：`raw_file_hash`、`content_hash`、`scope_key`、`published_state_token`、`status`、`row_count`、`inserted_count`、`duplicate_count`、`warning_count`、`date_min`/`date_max`、`snapshot_date`、`totals_json`、`completed_at`。
配套 `NetshopImportScopeHead`、`NetshopImportAttempt`、`NetshopImportFingerprint` 提供范围锁与尝试审计。

闸① 因此可直接写成：**本轮计划的业务日期范围内，该店该数据集有没有 `status=completed` 的新批次，或权威的"无需新增"覆盖证据；两者都没有而脚本回报 ok → 判 failed。**

### 不选其他链的理由

- **客服链**：不在 11 条正式目标内、3/4 是候选模板，且双文件（Excel + LOG）配对导入是本系统最复杂的证据形态之一。试点要验证模型够不够用，别同时引入最难的边界。
- **市场榜单**：主体是"市场类目"不是销售店，现行为静默 n8n 入口、来源未开放。
- **入仓库存**：主体是事业部，不是销售店。
- **商品数据链**：四店共用，见第一节。

## 三、试点范围：P0 的一条切片 + P1 的一个垂直切面

**不要在试点里做完整 P0 或完整 P1。** 试点的目的是**证伪模型**——用最小代价回答"这套数据模型和闸够不够用"。

### 第 1 步 · 修目录漂移并钉死（半天）

1. 重跑 `node tools/build-import-chain-catalog.mjs`。当前目录里物流是 `0 8`、客服是 `0 9`，而 n8n 定义在 2026-10-28 已改为 `50 8` 与 `10 12`——**页面此刻显示的时点是错的**。
2. 跑 `tests/import-monitor.test.ts` 的一致性检查。
3. 加一条"目录与定义同步"检查，使生成器漏跑会被 CI 或发布前置发现，而不是靠人记得。

> 与试点店无关，但是试点的前置：**基线自身不对，试点结论不可信。**

### 第 2 步 · 为这一个店建最小投影（2–3 天）

只实现主方案 §4.1 的四张表，且**只接推广链一条**：

- `AutomationLogicalRun`：`plan_date` + `subject_key=jd-yiyong-director` + `chain_key=jd_promotion`
- `AutomationAttempt`：挂 n8n `execution_id`，支持父子（1268→1287→1303 要能表达成一条逻辑运行下的三次尝试）
- `AutomationModuleResult`：阶段 `download/validate/import/verify`，证据指向 `NetshopImportBatch.id`
- 三轴状态字段

**此期规则表只读**，从现有目录生成，不做编辑功能。

### 第 3 步 · 用历史样本回放验证（2–3 天，试点核心）

不需要等新故障：

| 验证项 | 用什么验 | 期望 |
| --- | --- | --- |
| 恢复链能表达 | 9-12 的 1268/1287/1303 | 一条逻辑运行、三次尝试、父子正确；重试预算按逻辑运行计不重置 |
| 闸① 能抓假绿 | 构造"脚本 ok 但域里无新批次、无权威无需新增证据" | 判 failed，不判 done |
| 闸① 不误伤 | "无缺口 / 未到期 / 内容重复"三种正确结果 | 判 `no_new_needed`，带原批次或覆盖证据，**不判失败** |
| 三轴不顶替 | 业务 `verified` + 投递 `failed` | 不提供"重跑导入"，只允许恢复投递 |
| 结果未明保护 | 已提交但远端结果未知 | 普通重试禁用，给可核查入口 |
| 跨午夜日期归属 | 该链完成标记取 `plan_date` 还是执行时刻 | **须先核实**（主方案第十一节第 5 项） |

### 第 4 步 · 真机只观察，不改调度（1 周日历时间，不占人力）

试点期间 **n8n 一个字都不改**。投影只做增量只读观察，跑满一周：
- 每天的逻辑运行、尝试、模块结果与批次是否对得上
- 有无"投影说完成、域里没批次"或反向的不一致
- 自然发生的失败能否被正确分类

## 四、验收判据

1. 这一个店的一次推广运行，从计划、下载、导入到回查与收尾**完整可追溯**；**下载前失败也查得到**（现在查不到）。
2. 9-12 的三次尝试回放后显示为**一条逻辑运行的三次尝试**，不是三条独立失败。
3. 闸① 对假绿判 failed，对"无需新增"判 `no_new_needed` 并带证据——**两个方向都要验**。
4. 三轴状态的互不顶替用例全过。
5. 连续一周投影与业务批次零未解释差异。
6. 期间未修改 n8n、未新增业务写入源、未制造平台点击。

**第 3 条两个方向都验过才算模型够用。** 只验单向会得到一个过严或过松的闸。

## 五、工期

编码 **4–6 天**，加一周只读观察，**合计约 2 周**。

比主方案 P0+P1 的 4–6 周短，因为只接一条链、不做三视图完整前端、规则表只读。但它能回答最关键的问题：**这套模型和闸是否够用。** 模型被证伪，在这里改是天级代价；等铺到 8 条链再改就是周级。

## 六、试点之后的扩展顺序

1. **第二条推广链**（切肉机店）——验证"同链多店各自独立"
2. **吉客云五表**——验证"模块依赖顺序"与已有恢复动作收口

"四店共用"放靠后，因为它的展示语义依赖前面几条把模型坐实。

## 七、试点前须先核实

1. `JdPromotionDaily2026` 的**实际采用版本与当前启停**（仓库 `active: false` 是安全导出默认值，不构成线上停用证据）。
2. 该链完成标记的**日期归属**取 `plan_date` 还是执行时刻。
3. 该链"跳过/未到期/完成"回执的**键名**与消费侧是否一字相同。
4. 1268/1287/1303 的 execution 明细**只在 n8n 自己的库里**。仓库里 `docs/evidence/jd-promotion-migration-guide-production-20260912.json` 是发布证据（releaseId、备份、回读），**不含这三条的阶段明细**；叙述只在 `docs/自动化/通用/n8n-hourly-safe-retry.md` 第 70 行。回放前须确认 n8n 库里这三条未被保留策略清掉。

## 八、核查中发现：这两条推广链的仓库定义落后于线上

| 来源 | 商用设备店 | 切肉机店 |
| --- | --- | --- |
| `automation/n8n/*.workflow.json` 定义 | `40 10 * * *` | `50 10 * * *` |
| `lib/imports/chain-catalog.generated.json` 目录 | `40 10 * * *` | `50 10 * * *` |
| **9-12 生产回读证据** | **13:00** | **13:10** |

证据原文（该 JSON 的 `readback.promotionWorkflows`）：
`both unique active/published; Asia/Shanghai 13:00 and 13:10; hourly retry unchanged`

**这与物流/客服那处漂移性质不同，更严重：**

- 物流/客服：n8n 定义已更新（`50 8` / `10 12`），只是生成器漏跑 → **重跑生成器即可修**
- 推广两条：定义与目录自身一致，但**双双落后于线上** → 重跑生成器**修不了**，只能查线上才知道哪个对

仓库里这两条的 cron **不能当作线上事实**。这实证了主方案第十一节第 1 项要扩展一句：**仓库里的 cron 表达式同样不构成线上调度证据**，和 `active=false` 一样。

对试点的影响：第 1 步除重跑生成器外，还必须**从线上读回这两条的真实 cron**，再决定是以线上为准改仓库，还是以仓库为准改线上（后者属于改 n8n，须单独授权）。这件事做完前，日程视图上的"计划到点"会画错位置。
