# 一、客服四店时点错位：到底会出什么问题

## 现象

仓库定义与线上实际的 (店, 时点) 对应关系错了一轮：

| 店 | 仓库定义说几点跑 | 线上实际几点跑 |
| --- | --- | --- |
| 商用设备 | 12:10 | **13:10** |
| 切肉机 | 12:50 | **12:10** |
| 商用厨电 | 12:30 | **12:50** |
| 商用洗碗机 | 13:10 | **12:30** |

两组值是**同一个集合** `{12:10, 12:30, 12:50, 13:10}`，只是配错了店。

## 会出什么问题

**现在不会出业务问题。** 四条工作流在线上各自按自己的时点正常跑，数据照常导入。四个时点都还在，没有重叠、没有遗漏。

问题出在**人根据仓库信息做判断的时候**：

1. **排障时找错对象。** 洗碗机店 12:30 跑失败了，你去看仓库记录，它说洗碗机是 13:10——于是你会以为"还没到点，再等等"，而实际上它已经失败了 40 分钟。反过来，13:10 真正跑的是设备店，你却以为那是洗碗机的。

2. **页面会显示错的计划时间。** 当前 `lib/imports/chain-catalog.generated.json` 里这四条还是更早的 `0 9 * * *`（9:00），连错位后的值都不是。三视图的日程视图要画"▲ 计划到点"，画的就是这个错值——条形图上实际运行的位置和计划三角会差三四个小时，看起来像"每天都严重延迟"，其实是基线画错了。

3. **改时点会改错店。** 如果以后想把洗碗机挪开避免和别的流程撞车，照仓库定义去改 `13:10` 那一条，改的其实是设备店。

4. **这类错误会自我掩盖。** 逐条单看，每个值都是"一个合理的时点"，没有任何一条看起来可疑。只有把四条并排对照线上才看得出来。这就是为什么它在仓库里存了至少两天没人发现。

## 怎么修

**不能按仓库值回填**——四个值都在，照着填只会再错一轮。

正确做法：
1. 以**线上**的 (店, 时点) 对应关系为准，重建仓库四份定义文件的映射
2. 重跑 `node tools/build-import-chain-catalog.mjs` 同步目录
3. 增加一条检查：同一条链下各主体的时点必须**唯一**，且必须与线上读回值**逐条相符**。这条检查就是 A2 单元里"目录与定义同步"的扩展版，现在有了真实用例

修完的判据：四条的 (店, 时点) 在线上、定义文件、生成目录三处完全一致。

# 二、六条工作流没有重试兜底：原因与补绑方案

## 原因：从未绑定，不是被覆盖

按 `workflow_entity` 的创建时间排列，界限非常清楚：

| 分组 | 创建时间 | errorWorkflow |
| --- | --- | --- |
| 11 条正式流程 | 2026-08-03 ～ 08-21 | **全部已绑** |
| 客服四条 | 2026-10-07 ～ 10-08 | 未绑 |
| 京东入仓 | 2026-10-15 | 未绑 |
| 天猫入仓 | 2026-10-17 | 未绑 |

`docs/自动化/通用/n8n-hourly-safe-retry.md:68` 记录 2026-09-11 做过一次受控发布，给"11 条现行正式流程"统一加了 errorWorkflow 与专用 webhook。这六条都是**那次发布之后**才创建的，没有人补这一步。

所以不是某次操作把 settings 覆盖掉了，是新增工作流时漏了这道工序。`workflow_history` 显示这几条 10-26 由 `import` 创建、10-28 由本人在界面编辑过，但两次都没有涉及 errorWorkflow。

## 补绑不是一件事，是三件

查到一个关键事实：`TeruisiHourlyRetry2026` 的机制是**失败 → 等 60 分钟 → 回调目标工作流的专用 webhook → 创建新的完整 execution**（不是节点重放）。

而这六条：

- 线上**没有** webhook 节点（逐条查实，`webhook=[]`）
- 仓库定义里**也没有**
- `TeruisiHourlyRetry2026` 定义里的目标白名单写死 13 个 ID，**这六条一个都不在**

**只绑 errorWorkflow 会得到一个半截的链条**：错误工作流被触发、等满 60 分钟、然后找不到回调入口。看起来"有兜底"，实际不会产生新的 execution。

所以补绑要做三件：

1. 给六条各加一个仅本机可达的专用 webhook 节点，只连到各自的"领取共享 helper"入口
2. 把六条加进 `TeruisiHourlyRetry2026` 的目标白名单
3. 给六条的 `settings.errorWorkflow` 绑 `TeruisiHourlyRetry2026`

三件都要**先改仓库定义，再受控发布到 n8n**。

## 建议的执行顺序

照 `n8n-hourly-safe-retry.md` 第 74 行起已验证的受控发布序列：

1. 只读备份 n8n 数据库与这六条的当前版本、active、owner、settings、nodes、connections
2. 先更新共享错误工作流的目标白名单并发布，确认 Error Trigger、60 分钟 Wait、同 owner 调用策略正确
3. 逐条更新六条原 ID（**不新建同名副本**），保留各自 owner、调度与既有 active 状态
4. 回读验证：`activeVersionId == versionId`、专用 webhook 已注册、errorWorkflow 已绑
5. 用隔离的可逆失败验证一次"失败 → 等待态"，**不制造平台业务点击或生产导入**
6. 保存脱敏采用证据

## 两个取舍要你定

**① 天猫入仓（`TmallWarehouseDaily2026`）这次要不要一起补。**
它 `active=false`、节点名写着"待启用"、`triggerCount=0`，现在没有失败风险。一起补的好处是一次做完；分开的好处是这次只动五条在跑的，范围更小。

**② 客服四条的错位要不要和补绑同一批做。**
两者都要改这四条的定义文件。同一批做可以只走一次受控发布；分开做则每次范围更清楚、更容易回退。

我的建议：**客服四条的错位与补绑同一批**（反正都要改这四份定义、都要重新发布），**天猫入仓单独留到它真正启用时再做**（现在补了也没有验证机会，而未验证的兜底不算兜底）。
