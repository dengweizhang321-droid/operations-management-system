## 前提纠正及事实来源

派工单的“全局单锁”“没有任何释放方式”“只能重启”不是当前源码的完整描述：

- `tools/tmall-isolated-helper.ts:79–88`：天猫以 storeKey 为 slot key，其余工作流共用 `legacy`。不同天猫店可同时存在；`:124` 使 legacy 与所有其他槽位互斥。因此本方案保护的是原资源隔离约束，不承诺全机只有一个 Chromium。
- `:159–180` 已有 `closeCoordinator`，并分别服务吉客云和京东客服的受控闭合。存在匹配槽位时，要求唯一匹配 Worker 已真实退出、inFlight 为零；也允许无匹配槽位。两种情况均须无其他槽位、无并行闭合，且业务侧证据满足；成功才清理存在的匹配槽位。它不是任意请求都可调用的通用解锁。
- Map/retired 在内存中；没有通用 release/force-unlock 或 TTL。重启会丢内存状态，但不证明浏览器、平台任务、下载或未知业务提交已经清洁。
- 10-29 四次 409 的直接阻断是领取阶段已有 quarantine；不是四次已证明的独立 quarantine 根因。首次进入 quarantine 的 owner、退出原因和浏览器状态仍需对应生命周期证据，当前六条错误不能补出这些事实。

源码、频率分类及查询边界见 [状态机事实](E6-状态机事实.md)、[脱敏证据](E6-evidence.json)、[只读取证脚本](e3-e6-readonly-evidence.py)。旧主工作区派工单及处置手册仅作问题输入；不据其“只需重启”表述执行恢复。

## 当前状态机

1. **空闲 → starting**：claim 同步登记 owner（workflow/executionId/storeKey/scheduledAt）、随机 instanceId，然后异步启动 Worker，避免并发领取竞态。维护排空、已退役 execution、跨店身份与计划锚点不符继续拒绝或等待。
2. **starting → running**：Worker ready 后变更；相同 owner 可以继续整条链。其他 execution 按现有店铺和 legacy 互斥规则等待。
3. **完成请求 ≠ 槽位释放**：Worker 的 finished 消息只记录 clean 并请求 terminate；只有真实 Worker.exit 回调才设置 exited 并退役该 execution。clean=true 时删除槽位；clean=false 时进入 quarantined/failed。
4. **异常 → quarantined**：spawn Promise 拒绝、Worker 错误或非清洁退出均可进入。30 秒启动超时会请求 terminate，但不能以超时发生代替真实 exit 见证。Promise 拒绝时 exited 也可能仍为 false。
5. **quarantined → 后续 claim 被拒绝**：同 key 触发 `helper_slot_cleanup_requires_manual_action`（`:107`），HTTP 层将 rejected 转为 409（`:421`）。其他 key 还受 legacy 互斥规则约束；不能把等待与本 key 的 409 混为一类。
6. **域内受控闭合**：观察/授权及业务证据满足后，freeze 建立全局闭合 reservation；匹配槽位进入 closing。complete 再核验退出见证，登记 retired 并删除槽位；finally release 清 reservation，未 complete 时恢复旧状态。源码允许无匹配槽位的闭合协调，是否可闭合仍由域协议决定，不能泛化成“空 Map 即安全”。

`forward` 对在途请求计数（`:254` 起）；请求结束和 Worker 退出是不同事实。n8n execution 为 error/stopped、端口暂时不响应、健康阶段未变化，均不足以单独证明可清理资源。

## 三个候选方案

| 候选 | 做法与收益 | Chromium 并发及误中断风险 | 仍需人工介入的情况 |
| --- | --- | --- | --- |
| A：保留机制，完善可发现性及原域内处置 | 将 quarantine owner、instance、退出/在途状态与既有闭合入口纳入只读说明；复用现有脱敏生命周期日志和人工告警，不另造发送链。已支持的域继续原审批/闭合；不支持的状态保留证据后单独制定恢复 | 不新增释放行为，不扩大原并发；不得在告警后自动重启或终止浏览器 | 所有不满足现有闭合条件的对象；helper 不可达；原 owner/提交效果未知 |
| B：复用闭合协调器，增加受控资源清理能力 | 在确有未覆盖场景时扩展原域协议，明确区分“资源已清理”与“业务已闭合”；精确 owner/instance 绑定、原子 freeze/recheck、审计后退休原 execution。可以避免为单个失效槽位重启整个 helper | 只有真实 exit、零 inFlight、受控浏览器资源已关闭且业务未决由原门禁保留时才允许；不杀活跃任务。任一证据缺失仍锁住，禁止客户端 finally 无条件 release | 活 Worker/请求、其他槽位占用、浏览器归属不明、平台提交未决、领域无安全恢复协议、已重启导致见证缺失 |
| C：持久所有权/退休记录，TTL 只触发复核 | 将 ownership、实例代际、退休记录及清理回执持久化；重启先对账；TTL/heartbeat 过期只触发检查，满足与 B 同等证明才释放。改善重启后的连续审计与防重 | 心跳过期绝不是死亡证明；自动释放若无跨进程 fencing，会允许旧 owner 晚到请求或孤儿 Chromium 与新 owner 重叠。需要在所有业务入口贯彻代际拒绝，工程面最大 | 时钟漂移、进程/实例身份不明、存储损坏、平台效果未知、旧协议缺 fencing，均须人工处理 |

### B 的最小设计边界

这部分是未来采用前的设计要求，本单不新增端点或实现。

1. 优先复用客服/吉客云已有查询、审批、freeze/complete/release；支持名单由真实案例决定，不创建通用 `/force-unlock`。客服九码自动闭合白名单保持；旧来源恢复审批的≤2小时与failureCode精确匹配保持，人工v2闭合继续其独立authority/目标证据契约，不混用两类审批。新增资源清理适用条件不能借本方案越过域内闭合判据。
2. 只读查询给出固定原因码及目标身份，授权绑定 helper 生命周期、slot instanceId、workflow、storeKey、原 execution、计划锚点、关键证据摘要和有效期；不用 PID 单独作身份，不接受调用方任意端口/路径。
3. 首先证明 Worker exited=true、inFlight=0，并按当前 coordinator 保留“无其他槽位”和闭合互斥条件；不能因为天猫原本支持不同店并行就顺带放宽本轮闭合隔离。核验该 owner 的受控浏览器已退出、无可能复活的原执行主体。不可核验则返回拒绝。
4. 资源清理和业务许可分开：未知提交、已有下载或导入不是“无效果”。保留原 manifest、文件、任务绑定和失败事实，原业务恢复/幂等门禁继续阻止新执行绕过未决任务；只有领域协议证明后继执行仍安全才可采用资源释放。
5. freeze 后重新核验所有身份和证据。持久记录清理 intent，再做原内存 retire/delete，最后写完成回执；过程中失败或崩溃不得报告成功或盲目重放，下一次以原 intent 和实际状态对账。完成回执描述资源结果，不将旧 n8n execution 改成 success，不触发完整 workflow。
6. 新请求只允许重新从原 n8n 完整入口按原协议开始；原 execution 永久拒绝重放的业务约束继续生效。helper 重启后旧授权失效，须重新查证，不能因内存槽位消失把旧授权升级为成功。

## 推荐及失效条件

**当前选择 A，下一步开发优先 B，暂不选择 C。** 留存中已确认多店受阻，值得补齐准确处置入口与可见性；但原始故障 owner 未还原，现有域闭合的覆盖率未查清，不足以证明必须新增通用机制。A 可立即作为处置原则；B 只在发现原域确有安全清理缺口且用户决定实施后开发，并由独立审查核验并发/未知状态边界。此选择不授权本轮修改监控或执行清理。

推荐会在以下条件下失效，需要重新选择：

- 同类 quarantine 高频复发、人工等待超过实际容忍度，且已取得充分生命周期证据：仅 A 不够，应提高 B 优先级；不能因频率高而降低安全证明。
- 失败完全落入现有客服/吉客云闭合能力：新增 B 是重复建设，应直接使用原路径和审批。
- 根因是 Worker 未退出、浏览器孤儿或平台提交未知：B 的准入条件无法满足，应修复原生命周期/领域恢复，不能通过释放资源掩盖问题。
- 重启频繁、进程间并行或旧 owner 重放成为已证实主要风险：内存协调不足，才考虑 C 的持久 ownership 和 fencing；不能只新增落盘 Map 或 TTL。
- 原始故障主要为 ECONNREFUSED/服务启动故障：槽位释放不是主修复点，应按现有服务启动协议查证。
- 业务要求改为全机严格单 Chromium：当前每店天猫并行的前提已改变，须单独确认调度/吞吐取舍，不能在 E6 里默默恢复全局锁。

本轮交付仅本方案。没有 helper 实现变更、生产资源清理、服务重启、业务补跑或真实通知；历史频率和源码语义可供 lead 的独立反审直接核对。
