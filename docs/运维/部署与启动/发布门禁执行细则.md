# 发布门禁执行细则

本页从基线 `f641685b` 的验证与发布规范迁出当前工具操作细节，仅调整位置。通用规则以[验证与发布](../../规范/验证与发布.md)为准；**适用动作前必须读取并完整执行本页对应门禁，不得用规范摘要代替。** 文档不修改执行器、不授予生产操作、不改变已封存批次。事故和旧协议限定资格另见[历史索引](../../规范/验证与发布.md#历史限定资格索引)。

反引号中的工具路径相对仓库根；命令只是原入口说明，本轮未执行。原参数、数值、身份/权限、锁序、新鲜度、失败关闭和未知保护均保持。原文在进入本页前的事故细节已替换为必须查阅的历史资格链接。

## 在线准备、维护前检与唯一生命周期引擎

- 已采用的 `plan --prepare-online` 只准备候选，必须复验原生效链、已安装入口与前驱精确进程，不能提前改生产保护入口或发放启动许可。Django `PrepareApp` 收据绑定前驱和完整候选指纹；`DeployApp` 仍在维护中复验并切换。应用维护仅通过唯一 Worker 的 `EnterMaintenance -KeepPostgres` 持久声明，普通维护继续完整停机；同域 reader 延迟等待必须由 stack 清理新进程并保留最终完整就绪屏障。后续使用仍需对应生产操作授权。见 `docs/运维/部署与启动/startup-release-optimization.md`。

- 候选改变控制器或 supervisor 时，发布前核对实际控制器、看门狗绑定和持久状态的版本兼容性，提前准备配套诊断及必要受控迁移。旧状态归档和监控窗口的完整条件见[Q01](../../规范/历史记录/发布限定资格-20261022.md#q01)。
- 维护前的静态只读准入应绑定实际前驱与适用恢复代码，并在 STARTED 前拒绝未知控制代际。静态通过不替代现场身份、互斥、排空和新鲜事实。有限续接只能保留原意图/ID/失败，使用独立进程的有界新鲜观察、原 token/进程与原生身份门禁；不把 Windows absence 当作 Linux 停止证明，不允许无原完成凭据的已完成状态冒充成功，也不从有限前驱桥推导通用 unknown 重试。
- 冻结发布以批准的完整提交、HEAD/tree/干净来源和同一请求/制品绑定为准；目标选定后的共享 `origin/main` 推进不替换或否决该目标。`assertFrozenSource` 在实际准备、发布和制品观察入口复用，进入维护前再次核验；获取最新目标仍只在原固定入口选择阶段执行。
- 维护前检绑定精确工具、来源及进程身份，在 STARTED 前只读检查、双锁内复核并保持原新鲜期限；前检不证明停止。具体代际、两分钟证据及有限桥条件见[Q02](../../规范/历史记录/发布限定资格-20261022.md#q02)，缺身份字段保持 unknown。

- 发布前只做[上述必需程序代码检查](../../规范/验证与发布.md#发布检查与功能验收分工)，相关功能及其代码的业务行为由用户上线后检测。只改文档或离线工具且没有应用载荷变化时无需生产应用构建；文档只检查本次差异和引用。
- 新发布先执行 `npm run release:plan -- --base <当前生产来源提交> --head <候选提交>`，由 Git 完整差异生成绑定提交的范围计划。前端改动只准备 Worker；仅后端改动只准备 Django；只有 Django migration 变化才执行迁移。共享运行库、依赖、配置、发布工具或未知路径升级为完整组件流程。代码检查按[发布检查与功能验收分工](../../规范/验证与发布.md#发布检查与功能验收分工)执行，不把计划中的旧功能验证标签当作 AI 必须执行的验收；打包、实际数据保护和部署动作仍按适用工具执行。有效且绑定同一提交与制品的结果直接复用。
- 数据库保护与代码回滚分开判断。后续结构迁移按[备份与恢复约定](../../规范/验证与发布.md#后续结构迁移的备份与恢复约定)取消迁移前后全库备份和隔离恢复，不因存在 migration 自动追加这些步骤。无持久化影响的前端 Worker 改动不要求本次数据库备份；其他后端或 Worker 持久化路径按实际数据影响核验当前有效备份。普通无迁移发布不执行迁移命令，也不为了形式重复生成发布后备份或隔离恢复。
- 历史审查证据保持原字节，不为 lint 改写已归档脚本；语法和范围外规则保持。批次/生命周期夹具显式区分只读和私有写上下文，不降低身份、取消或期限断言。有限 lint 适配范围见[Q03](../../规范/历史记录/发布限定资格-20261022.md#q03)。
- 十工具无迁移闭包与 CF 缓存有限差异的完整限定资格见[Q04](../../规范/历史记录/发布限定资格-20261022.md#q04)；适用时必须逐项核验，归档不构成减免。
- `npm test` 会先执行生产构建。生产构建会改写 `dist`，而本地预构建 Worker 会监听该目录；构建前必须检查 `127.0.0.1:3000` 是否被本项目服务占用。
- 未经用户在当前对话中明确批准，不得停止、重启或中断本地服务，也不得在运行中的 Worker 监听构建产物时原地构建。当前本机正式 Worker 只能由 `tools/worker-local-service.ps1` 解析并管理不可变 effective head；禁止直接运行 Wrangler、旧 release、`dist` 或 `tools/start-local-worker.mjs`。
- 日常人工启动、`运行项目.bat`、`npm start`、`npm run dev`、登录启动项和桌面控制面板必须统一汇聚到 `tools/worker-local-service.ps1 -Action Start` 这一唯一启动引擎。该引擎先只读核验已部署 Django/PostgreSQL 的全部已启用 reader/writer 与 BI reader；仅在状态明确未就绪时调用既有 Django `Start`，全部回读 ready 后才进入原不可变 Worker release/进程身份门禁。`tools/operations-system-control.ps1` 只提供组合状态、外层非阻塞互斥、日志和最终 HTTP 回查，启动时不得复制 Django 或 Worker 的写入/生命周期逻辑。只有 Worker 内部状态明确为 `stale_or_invalid_receipt`、受保护回执可验证且 supervisor 不存在时，唯一引擎才可通过既有精确回执删除函数清理该回执，并必须回读为 `stopped`；端口占用、身份不明、回执损坏、状态错误或健康异常均失败关闭。
- 一次顶层 Django `Start` 或 `Stop` 中，完整 runtime 后代 ACL 审计只执行一次；同进程子域只能使用临时、不落盘、有界且同时绑定 PID、runtime 路径和部署清单的本轮证据复用完整审计结果，并必须重新验证根 ACL 与应用树。单独子域操作、跨进程、超时、绑定变化或上下文损坏必须回退到完整 ACL 审计，不得使用持久缓存跳过生命周期安全门禁。Worker release 完整性验证可以对文件元数据和内容读取使用有界并发，但不得改变已发布 tree-hash 的 ordinal path/length/content 协议、减少校验文件或放宽重解析点和硬链接门禁。
- 不得为了测试而覆盖本机 PostgreSQL/Django runtime、Worker release runtime、D1/R2、浏览器 profile、下载目录、备份、审计或 `.dev.vars`。测试优先使用临时目录、内存/临时 SQLite 和夹具。
- 未经明确要求，不执行生产部署、远程 D1 迁移、生产数据导入或外部平台真实发送。涉及这类动作时，应先说明目标环境、影响范围和验证/回滚方案。
- 用户另行明确要求功能验证时，按指定范围考虑注册表、鉴权、导入、迁移、缓存或自动化的失败、重试、重复、跨范围和并发交错场景；不因这些改动自动追加功能测试或验收。

## 合并前发布兼容与证据分类

### 合并前发布兼容性验证

- 在最新 main 基础上冻结干净候选提交，合并前使用实际候选字节验证受影响的发布入口、参数传输、包内依赖、迁移代际及启动准入。发现问题在任务分支修复，相关字节改变后重验受影响部分。合并只改变元数据且实际输入不变时复用有效证据；不能把普通分支测试包直接当作绑定最终 main 和真实前驱的正式制品。
- `package-lock.json` 变化时，同次交付准备匹配精确锁文件的离线依赖，包含项目安装脚本及其直接依赖；不能只交付成功构建记录后删除唯一可用依赖，把固定打包配置留在旧锁。普通权限安装成功的目录、锁文件和安装回执通过固定控制安装器的 `--dependency-update` 材料一并采用，只替换依赖目录与锁摘要，保留原配置 CAS 和旧依赖。派发前检查冻结 Git 对象的锁摘要；不匹配直接 failed，不先产生 source/schema/native 准备操作。
- 发布入口和完整性工具的固定验证入口为 `node tools/verify-release-candidate.mjs --base <最新main提交> --out <工作树外的新目录> --dependencies <node_modules绝对路径>`。它从完整 Git 差异选范围，在独立干净候选树执行受审的 Node/PS5/PS7 检查及私有真实 Django DeployApp/HardenAcl/manifest/Wrangler 闭包，自己生成绑定候选树、载荷、工具、命令、退出码及原始输出摘要的 `REPORT.json`。候选脏、未知适配器、步骤失败、载荷漂移或清理失败均不通过；不接受手填 passed，也不执行合并或发布。
- 当前适配器仅用于发布控制和字节完整性所需检查，不作为追加业务功能验证的入口。新业务/迁移/未知运行工具只补实际构建、部署和启动必需的代码及工具兼容材料，不新增功能验收或以全仓单测替代。发布状态未知、部分成功及重放保护继续按原协议处理。
- 机器证据区分 `packageIntegrity`、`nativeEntryBoundary` 和 `nativeColdStart`。真实参数入口在首个副作用边界停止、library-only 函数及编排替身都不能证明完整冷启动。真实 Start/Stop 路由或生命周期语义发生变化时，需要专用隔离环境完成原生冷启动及必要就绪；缺能力时保持候选未合并。已审窄例外的全部条件见[Q05](../../规范/历史记录/发布限定资格-20261022.md#q05)和[Q06](../../规范/历史记录/发布限定资格-20261022.md#q06)，不扩展到其他 helper、路由或业务行为。

- 合并前证明与最终制品准备分开。正式发布必须先取得对应目标的原生 `PREPARED.json`，再执行即时身份、锁、前驱、权限、在途任务及就绪复验；提前检查不能替代这些动态事实。

## 固定入口、自动准备与发布续接

### 发布执行方式

- 固定 main 发布 CLI 及其可选 `.bat` 包装器跨任务使用。每次执行先获取远端 `refs/heads/main`，记录并冻结本次完整目标提交，再生成独立来源与发布请求；单次执行中不再漂移目标。不得让旧任务的 `completedTask`、固定旧 source、旧续接模式或历史 `SUCCESS` 截断新提交。远端获取失败即停止，不静默回退旧 main。
- 显示状态必须区分：检查/准备不等于发布；目标提交已与当前实际组件、真实完成回执及就绪状态一致时，只显示“当前已是目标版本，本次没有发布”；只有本次实际部署完成、对应目标的原生成功回执及版本/服务确认通过后，才显示“发布成功”。有 `STARTED` 无成功结果、维护/排空未退出或半切换状态必须先协调，不能按已安装的版本元数据直接视为完成。

- 发布负责人完成合并前验证、main 合并推送及制品准备后，按本次生产授权调用原生入口；不再默认交付 BAT 并等待用户点击。没有生产授权时完成具体就绪材料后再取得授权，不把 main 更新或准备成功视作自动部署授权。
- 普通 `publish-main.mjs` 调用默认仅发布就绪包；准备明确使用 `--prepare-only`，发布使用 `--deploy-only`，两种模式互斥。缺少原生 PREPARED 时，在构建、STARTED 和维护之前拒绝。旧非冻结来源不接收新的构建并发布请求；已封存精确恢复入口保持原协议。保留必要版本与前驱、普通权限、唯一生命周期入口、排空、互斥及未知结果保护，不增加全量测试或全库备份/恢复。
- 手动入口显示进度和成功/失败状态，保存原始步骤日志。重复点击已成功的同一包不再部署；已有开始记录但结果未知时停止并给出日志位置，不自动重放。交付“准备就绪”与用户实际“上线成功”分别报告。

### 标准入口、完成判据与受限续接

标准入口：负责人通过固定 main CLI 执行准备和已授权发布；`准备main.bat`、`发布main.bat` 是可选包装器，底层沿 `tools/publish-latest-main.mjs` → 冻结包 `tools/publish-main.mjs` → `tools/publish-prepared-main.mjs` 执行，不要求用户手动点击。状态与续接从**原冻结包**运行 `node tools/publish-main-status.mjs --config <固定配置> --attempt <原发布目录>`；默认只读，显式 `--resume` 才申请原队列和 rotation 锁执行受限续接。源码已交付、已合 main、控制入口已采用与生产执行分别记录，不能凭文档存在视作已安装。

完成判据：本次目标与实际组件绑定的 `SUCCESS.json` 必须为 `status=deployed_and_ready`，原 `VerifyStartup` 回执中 `startupVerified=true`，原 ready 门禁通过，维护/排空已退出，发布目录指向真实完成回执。单个进程退出0、组件元数据或已有历史成功不单独证明本次完成；已完成服务切换而目录更新中断时只协调发布索引，不再执行发布步骤，不追加功能验收。

异常恢复原则：先核原 STARTED、FAILED、准备包、intent、持久回执、原进程退役及现场来源/前驱，再仅续接尚未执行的步骤；有 started 而缺可信完成结果仍是 unknown，不按“未执行”重发。原失败和原始输出/真实退出证据保留。首版范围、最多一次 Reconcile 及历史一次性入口完整限制见[Q07](../../规范/历史记录/发布限定资格-20261022.md#q07)，不由本原则授予新恢复能力。

### 自动提前打包与发布执行

- `查看打包状态.bat` 是独立只读观察窗口：每5秒查看本机已获取的origin/main、对应冻结请求和原生准备记录。用户打开后可最小化等待，完成或需处理时显示本地弹窗；关闭观察窗口不影响后台准备，也不再接收该窗口提醒。查看器不fetch、不触发准备、不获取发布锁或执行部署。准备开始记录可能因中断保留，不能把其存在当作进程仍在运行；未知发布优先提示处理，准备完成不等于上线或原生现场准入。
- 固定控制入口升级先用 `node tools/install-main-prebuild.mjs --config <固定入口配置绝对路径> --out <新的隔离材料目录>` 从干净提交生成完整不可变控制包；这一步只准备材料。采用须在对应授权内用 `node tools/install-main-prebuild.mjs --adopt <材料目录>`，按原 v1 队列、新 v2 队列、原 native rotation 的顺序持锁，核旧进程及子进程退出后发布唯一 `CONTROL-INSTALLATION.json` adopted 记录。中断后仅显式同意图 `--resume`，未知状态或指针漂移拒绝；源码合入、材料生成、控制入口采用和应用上线分别报告。
- Git 触发仅监听 committed 的非删除 main 远端引用更新；自动与人工准备共用普通用户串行队列，不使用模型或定时轮询，不进入维护、排空、切换、迁移或启动。尚未获取到本机的远端更新不会触发；排队不等于准备成功。首次桥接和未 adopted 拒绝条件见[Q08](../../规范/历史记录/发布限定资格-20261022.md#q08)。
- `准备main.bat` 可手动执行同一准备流程。固定 `发布main.bat` 仍每次 fetch 并冻结最新 main，但只消费对应的已准备包；尚未准备好时明确停止，不使用旧包、不现场重新打包。一次执行冻结后不随之后的 main 更新漂移。原迁移/依赖变更的专用准备边界保持。
- 准备的 `preparation/PREPARING.json`、原子发布的 `PREPARED.json` 与部署 `STARTED.json`、`SUCCESS.json` 分开。准备结果绑定请求、完整提交和源码树、真实前驱、原生 Worker plan 与 Django PrepareApp 凭证；正式发布前复用原 Worker 完整验证及 Django `VerifyPreparedApp`/`DeployApp` 检查。准备中断或发布结果未知保留原记录，不自动重放；无成功回执不能显示发布成功。
- v2 触发票据按原始 SHA、配置和不可变控制代际绑定。consumer 先在队列锁内仅 fetch/read 观察目标，完整 create-only 写入并 fsync 精确 DISPATCH 后，才创建来源/worktree 或调用原生准备；once 不再 fetch 改目标。只合并尚未 dispatch 的同语义 latest-main 请求，旧目标记 superseded，不给旧目标写 prepared；已 dispatch 的目标不取消。两个人工请求和自动 hook 通过同一随进程退出释放的命名管道串行，退出锁后重查新事件。结果及其 ticket/dispatch/native PREPARED/request 依赖缺失或篡改均拒绝，不能把依赖 ENOENT 当成“尚无结果”。
- 冻结目标后、DISPATCH 前，实际已安装控制须检查相同提交的有限能力；已知不支持在任何 source/schema/native 效果前记 failed，普通身份准入先于 fetch。已有 unknown 不据错误文案降级；历史终止仅适用[Q09](../../规范/历史记录/发布限定资格-20261022.md#q09)及原完整资格，跨 token 只读 witness 不授予高权限控制或通用重试。
- 同目标仅在完整前驱/链/packet 与 config/bundle 代际一致、原 queue 完成结果及全部绑定有效时复用原 PREPARED 完成事实，避免物理 ref 事务重复触发原生准备；发布仍即时执行原生完整性门禁。发布调用在 fetch 前取得同一 queue lease，保持 queue→rotation 顺序，释放后再消费期间新票据；不以新 request 或代际绕过 unknown。
- 准备在真正 native rotation 的 listen 点，沿同一调用期限有界等待最多 30 分钟；只有 callback 尚未进入的 EADDRINUSE 允许退避，部署默认仍立即拒绝锁忙，不抢锁、不重放整轮。native 零 callback 超时有独立证据；当前跨进程准备调用未传递这项恢复资格，队列保守记 unknown，不靠 stderr 推断未执行。DISPATCH 后失败、丢回执或残片保留 unknown 并阻断后续重放，不能换 requestId 绕过。
- 多任务合入按最终组合版本准备。例如 A 已准备而 B、C 后合入 main，发布 A+B+C 只需等待包含三者的最终 main 原生 PREPARED，不要求所有历史中间包都完成。尚未 dispatch 的过时请求可合并，已经开始的准备保留原目标和结果；准备就绪不等于上线。
- 同一精确准备包复用其已经安装并完整验证的依赖，不再次运行 npm ci。新准备包继续使用既有离线 tarball cache 和原 npm ci；不增加需要跨包完整扫描及复制 node_modules 的目录缓存。构建末尾在私有 staging 中复制已验证的依赖并完整复验目标树，Windows 依赖目录 rename 不作为打包完成前提。
- 准备和发布通过同一固定实际环境启动，移除 Git 本地变量及 shell 注入差异，原生完整环境哈希规则不变。准备包及必要原生收据仍按既有完整性与 ACL 规则处理。预打包缩短正式发布阶段的等待，减少重复读取、复制和过时候选构建才减少总准备工作；具体收益按分项日志实测，不预设分钟数。
- 固定入口安装时保存有限白名单Windows基底，后续升级复用；自动准备与人工发布不重新继承各自窗口的基底值。显式覆盖libuv的Windows必需变量（包括LOGONSERVER及其空值），用真实子进程验证一致性，不只比较传给spawn的对象。基底不包含全量shell、秘密或NODE_OPTIONS；原生仍核完整实际环境指纹。
- Windows PATH条目使用系统规范分隔符；PowerShell命令发现与COM快捷方式可能保留或规范不同的路径表示，不能把斜杠表示差异当作不同程序，也不能据此放松原快捷方式身份门禁。新输入在准备时绑定；已封存包的环境/工具不热改，异常续接须走原精确恢复分支及独立审查。
- 结构迁移使用有限 recipe，绑定唯一迁移字节、前后代际、真实隔离 PostgreSQL 证明及安装器摘要；未知、新增或改写迁移须由对应任务补齐并审查，不能自动放行。负责人随合并交付材料；首个精确代际案例见[Q10](../../规范/历史记录/发布限定资格-20261022.md#q10)。
- 自动准备只读核验对应结构父链和当前应用清单，生成冻结来源专属 evidence，再经原 `PrepareApp` 准入；不连接生产数据库、不执行迁移。正式发布时先复核同包及证据，按原同ID维护执行对应 Plan→DeployApp/HardenAcl→Install/Finalize→Worker apply→Start。成功回执保留同operation/maintenance及原生结构安装结果；未知保留原意图、维护及日志，不重放或自动反向迁移。
