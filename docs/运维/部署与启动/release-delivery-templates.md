# 发布交付工作单模板

所有代理先阅读[统一发布交付契约](../../规范/验证与发布.md#统一发布交付契约)。这里提供可复制的材料结构和现有工具接入点，规则正文只在该契约维护。复制到本次 `docs/<任务目录>/RELEASE.md`，替换占位内容并保留原证据；空白、勾选、状态文字和模板本身均不证明授权、验证或上线。

纯文档等非生产交付按实际范围填写，不为填工作单运行应用构建、维护、迁移或无关验证。以下生产工作单初始状态为 **未就绪**，不存在默认通过项。

仅在已确认的干净工作树中，使用现有离线范围工具：

```text

```

占位命令不能原样执行。主工作区已有改动保留；不得将未审用户改动夹入组合来源。

## 4. 现场准入与运行记录

由原发布器在其锁/有效lease及动态边界核对前驱、原进程创建身份、权限、owner、维护/排空和制品。只读预检结果记录真实观察时间；互斥可能在预检后变化，预检不代替原动作内加锁。

| 原操作ID/意图与协议 | 原argv/工具摘要的受限引用 | started时间/证据 | 原回执/输出摘要及进程证据 | 当前结论 |
| --- | --- | --- | --- | --- |
| 待实际生成 | 不填写凭据/环境秘密/任意原始模型内容 | 未执行 | 无 | 未执行 |

原记录只追加/保全，后来的协调不改写首次exit code。故障后另记录精确原操作、观察时间/工具摘要、观察人/原协议所需独立性、证据、缺口和允许分支；不能只填 `independent:true` 或“无新文件”充当证明。

原批次需要协调时使用其**已审精确适配器**和原导出接口；`tools/release-batch.mjs` 没有通用reconcile CLI。本模板不授予生产写入、清owner、解除门禁、重放、任意终止进程或变更解析器的权限。

## 5. 必要上线确认与原格式收尾

完成条件按契约与[原规范](../../规范/验证与发布.md#发布完成的判定)，只核本次部署成功、目标版本及必要服务。证据至少关联原操作和对应候选；不只看后来running或HTTP200。准备/未执行/失败/未知均与实际采用分别列示。

### 已具备受支持原batch和连续WAL

可先离线检查原封存范围：

```text
node tools/release-batch.mjs inspect <原封存批次JSON> <批准批次SHA>
```

发布前准备下列收尾输入骨架（**全部null仍未具备，不能作为完成输入**），用真实原文件路径及精确摘要填入。字段格式以当前工具为准，不生成假batch、WAL或收据；额外验证/版本/现场/交付证据应来自原观察。

```json
{
  "batchPath": null,
  "batchFileSha256": null,
  "approvedSha256": null,
  "journalDirectory": null,
  "receipts": [],
  "planEvidence": null,
  "versionsEvidence": null,
  "runtimeEvidence": null,
  "deliveryEvidence": null
}
```

真实输入齐全时，使用已存在的输出目录以外的新目录生成草稿：

```text
node tools/release-closeout-report.mjs <真实离线输入JSON> <尚不存在的本次输出目录>
```

工具仅生成 `report.json`、`REPORT.md`、`evidence-manifest.json`；其 `acceptancePassed:null` 和历史运行观察不证明验收/当前健康，不关闭批次、不提交Git、不推送、不清理工作树。证据不足时保留缺口，不能补写“passed”。

### 既有入口只有独立操作回执

保留该入口原started/result/failure、PID/创建身份、门禁/owner、manifest/plan/consumption及必要回读等适用证据，按本工作单记录同一原操作的关系、原时间和摘要。现有batch报告工具不接受这种输入时，按预备文档骨架填原事实；不伪造批次/WAL，也不把专用包装器声明当独立验收。本轮契约不新增这个格式的自动适配器。

## 6. 计时与15分钟目标

| 边界 | 原实际时间与来源 |
| --- | --- |
| 原始用户上线授权 | 未记录；未知时标缺口，禁止从较晚就绪时间重置 |
| 开发/验证，main合并/制品准备开始与完成 | 未记录 |
| 完整发布材料就绪 | 未记录 |
| 首次实际发布尝试、失败及每次协调/续接 | 未记录 |
| 本次部署与必要可用性确认 | 未记录 |
| 文档/Git/保全/记忆/合格清理实际完成 | 未记录；未完成不得填过去时间 |
| 整轮原授权至交付、就绪后发布、异常/等待和收尾 | 按原边界计算，父子/并行区间不重复加总 |

常规就绪版本参考预算为发布及必要确认13分钟、必要收尾1分钟、余量1分钟；这是待实测的目标，不是杀进程deadline或缩减门禁许可。原授权总等待继续保留；长在途、迁移、恢复或超出预审的异常另报原因和窗口，仍计原时间。HTTP精确停服需要真实可用性采样，不能从整个切换跨度倒推。

## 7. 聚焦提交、保全与归档

发布前准备本次允许暂存路径和聚焦提交正文；发布后填真实结果，核 `git diff --cached`、推送并核远端。只对本次任务的已合并/已停用检出，按原清理规则先核进程/启动绑定、忽略文件和可恢复保全，再用受管归档或Git原工具清理；不在通用报告工具中偷偷执行Git/删除。

收尾清单未完成时如实列剩余项。所有自动化只复用本次绑定仍有效的原结果，不重新打包、备份、恢复演练或追加无关综合验收。材料缺口、未覆盖和失败原件随本次任务保留。

## 8. 最终对用户报告

填写实际已采用的提交/制品/范围、必要确认、各时间边界、原失败及协调、未执行/未完成项和原因、是否有待业务决定。纯文档交付说明没有应用载荷变化及无需生产部署；候选与代理行为契约生效不能说成生产执行协议已切换或15分钟已达标。
