## 用户需求

系统设置 › 货品细分映射：
1. “吉客云未找到”的货品名称按表格准确归类，可通过吉客云过往销售明细查找；
2. 供应链名称在吉客云明细数据里可以找到。

## 只读比对（替代来源：用户桌面《7-9月至今直饮机.xlsx》）

- 表格中只有名称的条目共 508 条，其中 291 条在这 3 个月的销售明细中能按规范化名称精确找到货品编号。货品档案里的名称多半后来改过，所以之前查不到。
- 模糊匹配会配错型号，例如 30L 配成 60L、BJZK-30S 配成 60S，因此**不采用**。只认规范化后完全一致的名称（NFKC、去空白、忽略大小写）。

## 变更

- **归类顺序**：手动归类 → 表格代码 → 名称在吉客云货品档案中找代码 → **名称在吉客云全部历史销售明细中找代码（新增，`sales_name_to_code`）** → 仍找不到的按名称兜底计入。这一步才是真正的“吉客云未找到”。品类细分分析会按找到的代码计入。
- **供应链名称**：优先取货品档案的供应商；为空时，取销售明细中该代码最近一次的非空“货品默认供应商”。
- **设置页**：销售明细补找到、但档案里没有的代码，单独列为已归类行。匹配方式新增文案“名称转代码（销售明细）”，说明文字和品类细分脚注同步更新。
- **性能**：
  - 销售明细名称索引每次导入后才重算一次，按销售数据修订号缓存在进程内；
  - 这次计算的查询时限单独放宽到 60 秒，完成后恢复原值；
  - 计算失败后，同一修订号 60 秒内不再重试；
  - 设置页每次计算只取一次索引。
- 无迁移，无数据写入。

## 已知限制

- 导入新的销售明细后，第一次打开两个页面时要扫描一遍全部历史明细。若超过 Worker 的 8 秒读取时限，这一次会提示失败，后台计算会继续完成，刷新即可。
- `set_config` 的作用范围是按 PostgreSQL 语义判断的，没有在真实 reader 库上实测。
- 名称不完全一致的条目不会自动归类，需要在“编辑”里手动补规格代码。
- 还开着旧页面的浏览器第一次可能提示“响应不完整”，刷新即可。
