# Bounded recovery scope draft — not executed

The original f15 source/spec/19-operation sequence and unresolved Start remain fixed. No new Backup, Restore, arbitrary port takeover or Start replay follows from this development work.

First contain repeated unsafe diagnostics only within a separately approved, bounded recovery plan. The existing watchdog Get-Admission validates the desired-state binding and maintenance record; Get-WatchSnapshot returns before status while admission is maintenance. However the same marker makes all new Django business HTTP except /health/live and /health/ready return503 Retry-After300. New protected background activity and system_backups job admission also reject. Existing requests/jobs/diagnostics are not terminated, there is no drain proof, and the schedule is unchanged. Creation and exact abort-only retraction are now developed as a pair, but neither is approved or executed. The pair alone is a containment/plan-observation experiment, not a complete repair; it must not begin an indefinite outage while later steps remain unknown. The ordinary EnterMaintenance/ExitMaintenance lifecycle is not a harmless setter/remover and cannot substitute for this paired contract.

Second, actual administrator metadata now correlates23 live service instances to original launch intervals/parent56560, but their historical configFingerprint inputs and deleted complete records are not recoverable from the reviewed evidence. Do not reconstruct old fingerprints from current bytes or timestamps. The preferred next proposal is a separately scoped controlled stop of those exact current instances and verified descendants, followed by the original lifecycle producing new receipts from explicit current inputs. Ordinary Stop alone is insufficient: with missing receipts it returns without stopping them. Such an operation needs fresh native same-instance identity, approved termination/drain boundaries and a concrete failure/exit plan; no executable package for it exists yet. A listening port is not ownership authority, and a new repair is not a no-effect replay of the old Start.

Third, the new native read-only diagnostic candidate d0e9… can bind actual717 and unchanged backend/controller/transport without adopting new formal application bytes. Merely changing the old binding was insufficient; this candidate supplies the reviewed read-only metadata adapter. Original PlanInstall currently rejects a running watchdog task. Even after natural idle, Install-WatchdogSafely requires Get-WatchSnapshot.healthy=true, while an active maintenance marker yields unprobed/false. The marker must not be removed solely to bypass that assertion, nor may the assertion be deleted. A later integrated repair must resolve service readiness and safe watchdog exclusion/maintenance exit ordering before installation. The current abort-only exit requires the unchanged49-event tuple and cannot act as a general post-restart exit. The existing installer changes only the Action target of an existing task while retaining its triggers/RunLevel; this exact additional scope needs approval. The immutable add91 version/binding must not be overwritten.

Finally, after containment, exact ownership and a safe diagnostic route are independently established, capture the original Start completion predicates under the correct host/role. Require current Worker identity and all enabled backend components, health contracts, exact manifests and inactive gates. Only a finite original reconciliation proof can confirm an achieved postcondition without replaying Start; the old failure must remain. Resume must still execute the original remaining acceptance operations and release ownership only through the normal closeout.

The new permanent Django and watchdog source is not adopted into f15 by this draft. Adopting a future corrected Django package would require a separately prepared exact artifact/manifest and corresponding original deployment process; a Git merge alone cannot change the currently approved runtime.
