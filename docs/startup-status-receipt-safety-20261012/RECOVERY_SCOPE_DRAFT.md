# Bounded recovery scope draft — not executed

The original f15 source/spec/19-operation sequence and unresolved Start remain fixed. No new Backup, Restore, arbitrary port takeover or Start replay follows from this development work.

First contain repeated unsafe diagnostics. The existing watchdog Get-Admission validates the installed desired-state binding and the maintenance record's version, ID and runtime root; Get-WatchSnapshot returns before invoking status whenever admission is not running. A valid, same-batch maintenance intent can therefore suspend this path without changing the task schedule or launching a guest. This is a proposed production write, not a read-only observation. It requires its own exact owner/WAL/gate CAS, safe path/ACL/bytes checks and evidence that an already-running diagnostic has finished. A gate must not assert drainedStopped=true when services have not been drained/stopped. Do not fabricate a successful original EnterMaintenance receipt or silently replace its existing lifecycle with a file write. The ordinary EnterMaintenance action itself stops services; it is not a harmless gate-only setter. Root must resolve and approve this concrete containment seam before any receipt restoration.

Second, collect under the approved administrator identity without invoking the unsafe legacy status consumer. Capture the exact23 missing service records' trustworthy original startup sources, configuration fingerprints, executable/launcher/argument bytes and current same-instance CIM/native creation identities. Evidence must establish both the original ownership and its continuing identity; listening ports or process names alone are insufficient. Access denied, missing startup provenance, reused PID, ambiguous child lineage, mismatched configuration or concurrent receipt appearance must reject the affected reconstruction. Any actual restoration should be create-only under the existing protected run root, bind a before/after owner/gate/current-process observation, and preserve every failed/unknown history entry. The draft does not grant a generic record-adoption API.

Third, a separately reviewed exact diagnostic bundle can bind the actual717408 Worker plus unchanged controller/backend/transport bytes. Use the existing prepare-watchdog-status-driver.mjs and original PlanInstall/Install contracts; do not overwrite the old driver-binding.json or immutable add91… version. Existing watchdog installer preserves an existing task's triggers and RunLevel by setting its Action only, but a new immutable bundle changes the Action executable/script paths. Consequently preserving the schedule is supported; preserving every TaskAction byte while using a new bundle is not supported by this installer. An absolute prohibition on Action changes blocks adoption until that scope is explicitly resolved. No runtime substitution or symlink workaround is proposed.

Finally, after containment, exact ownership and a safe diagnostic route are independently established, capture the original Start completion predicates under the correct host/role. Require current Worker identity and all enabled backend components, health contracts, exact manifests and inactive gates. Only a finite original reconciliation proof can confirm an achieved postcondition without replaying Start; the old failure must remain. Resume must still execute the original remaining acceptance operations and release ownership only through the normal closeout.

The new permanent Django and watchdog source is not adopted into f15 by this draft. Adopting a future corrected Django package would require a separately prepared exact artifact/manifest and corresponding original deployment process; a Git merge alone cannot change the currently approved runtime.
