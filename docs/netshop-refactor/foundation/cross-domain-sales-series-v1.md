No production source, deployment, migration, business replay, new grant or model call is included. It remains a candidate until I's SDK allowlist and independent Q review are complete.

The request must provide both `seriesGrain: day|week|month` and `seriesOutlets`, containing 1–4 exact `{platform,rawShopName,rawChannel}` objects. Raw strings and original grant rules remain unchanged. Duplicate, malformed, unauthorized, foreign, absent-from-both-periods or outside-explicit-rawOutlets identities fail closed. Selected objects come from the full authorized two-period candidate union, independent of search/pagination. Empty selection does not implicitly choose the first page. Native resolved_category cohorts apply to the same parent and series scope; P category labels are not ERP taxonomy evidence.

Without these two fields the owner adds no series-related requestScope/response fields; the original canonical full response remains identical to the existing actual PG fixture. With them, requestedScope includes `seriesIntent:{grain,rawOutlets}` and the parent scopeKey/snapshot token binds that intent. q/page remain outside the whole-scope identity. Selecting four plot objects does not shrink parent periodTotals, candidate counts, candidate union or source facts. One object absent in the current period but present in baseline remains valid; its empty current buckets return no_records/null.

The extra top-level `series` has schemaVersion `netshop-sales-period-series-v1`, projection `native-period-tuples-v1`, parent scopeKey, intent, unchanged independent current/baseline windows, closed basis declarations, identical metricMetadata and the same complete typed sales/ERP pair vector. Ordered items contain exact identity/canonical key and full current/baseline arrays of compact native tuples. Strict header columns are windowColumns `[startDate,endDate,endExclusive,days]`, metricColumns the eleven original salesPeriodMetrics in their declared order, and pointColumns `[window,values,rowCount,trustedOrderCount,missingOrderNoRows,netAmountPerOrderValue,observedDateCount,observedDateRanges]`. Each observed range is `[startDate,endDate]`.

`restore_period_point` / `restoreSalesPeriodSeriesPoint` restore the original `{window,facts}`. They preserve all original values, safe integer counters, trusted ERP order groups, original mean value and imported-date evidence. Fixed basis/unit/unknown-completeness strings and uniquely determined rowPresence/status/reason/mean numerator=netSales/denominator=trusted count are restored, then the full original period decoder validates every field. This is a lossless transport projection, not a new average/aggregation: the original mean value is separately stored and is never replaced by a newly calculated value. Constant metadata at the series header also retains unverified_source/unknown cost/profit proof; plot zero does not certify a primary cost/profit card.

Day means a calendar business date. Week means Monday–Sunday, with the first and last bucket clipped to the original period; it is not rolling seven-day grouping. Month means the natural calendar month clipped at original endpoints. The independent original windows each remain 1–366 days and can differ in length or overlap. No pro-rata scaling, latest-data cutoff, fabricated date pairing or derived 367-day request is introduced. Missing buckets are emitted with no-record null facts, never interpolated or replaced by zero. Imported observed dates remain completeness unknown, even when every bucket is present.

The owner groups actual authorized rows by exact raw identity and native calendar bucket, using the original `sales.analysis.expressions`. Each bucket's order denominator is SQL DISTINCT of trusted ERP order_no inside that exact raw identity and bucket. It never sums daily order counts or falls back to online order/source-line IDs. Multiple product lines and dates of one order within one natural week/month count once. This is shipped-business-date ERP order-group net amount, not payment-customer AOV.

All queries and serialization stay inside the existing owning call/transaction, one 65-second monotonic deadline and one signed UTC expiry. Single-SQL limits remain min(original,7s,remaining). Every participating actor/version is checked before and after the complete result. No per-bucket RPC or fresh time allowance exists.
