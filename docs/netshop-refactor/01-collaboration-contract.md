# 网店分析多 Agent 协作契约

本契约适用于方案二的隔离开发与合并。业务目标是丰富单店认识；网店总览 01 保留既定设计，其余栏目组织为店铺全景、店铺与平台对比、商品表现、推广分析。

## 授权与范围

- 当前仅生成契约及提示词，不启动实现 Agent 或任何生产操作。
- 执行提示词由用户明确发送后，按其核心范围推进隔离开发、验证、提交与约定合并，不重复询问已授权的常规实现细节。
- [内容清单](04-content-scope.md)中的核心内容为本期候选；用户派发时可按编号增删。条件内容只有在来源、覆盖、身份和口径证据齐备时才启用数值，否则交付准确缺失态并继续其他内容。
- 自动下载、真实补跑、生产数据写入、外部消息、真实付费模型调用、服务启停、迁移和上线不包含在本工作包中。生产采用须另走本次明确授权及原发布流程。
- 不增加客户CRM、独立库存账、独立财务账或另一套任务系统。人工映射维护、备注、任务派发、自动调价和停投列为可选后续事项。

## 角色与产物

| 角色 | 职责 | 必交产物 |
| --- | --- | --- |
| I 集成负责人 | 范围、分工、共享文件变更、合并队列、整体交付 | 任务清单、基线表、接口冻结记录、合并证据 |
| O 总览负责人 | 既有01完成与交接、新旧视图兼容 | 01精确提交、接口契约、原设计验收、在途修改清单 |
| F 公共底座 | 统一身份、日期、数据状态、查询边界、共享组件、旧页兼容 | 类型与校验器、共享服务、合成夹具、契约测试、消费示例 |
| P 商品负责人 | 商品经营表现、详情、档案及专属只读服务 | 独立栏目、查询与负向测试、钻取接口 |
| A 推广负责人 | 推广概览、趋势、对象诊断与专属只读服务 | 栏目、店日配对、范围限制、测试与报告兼容 |
| S 全景负责人 | 单店八章节、多领域只读聚合、专业页联动 | 栏目、各来源能力矩阵、多源一致性证据 |
| C 对比负责人 | 店铺与平台比较、可比集合与结构拆解 | 栏目、对比算法及边界测试 |
| Q 独立复核 | 复核最终代码与证据，验证回归和数据语义 | 带严重度的问题、复验记录、通过或未通过结论 |

同一人员可分时承担角色；同一改动的最终独立复核应由未编写该改动的 Agent 或人工完成。没有独立复核条件时明确标注未完成，不自称已独立通过。

## 工作树与资源隔离

每个工作角色使用独立 `codex/*` 分支和工作树。先检查已有工作树及在途任务，适合继续的原任务优先复用；不得复制用户未提交修改。新分支从当前已验收的最新 `origin/main` 建立；依赖尚未合入时仅做设计和夹具，不以未审分支充当主线。

分支建议为 `codex/netshop-foundation`、`codex/netshop-products`、`codex/netshop-promotion`、`codex/netshop-panorama`、`codex/netshop-comparison`、`codex/netshop-integration`。既有总览继续使用原分支，不抢占或强制重建这些名字。

生产目录不得安装依赖、构建、迁移或用于测试。独立 worktree 不复制生产 `.dev.vars`、凭据、数据库连接、浏览器 profile 或对象存储状态；依赖不得用指向生产目录的链接代替安装。

I 给每个运行中的预览登记端口。沿用 `TERUISI_PREVIEW_PORT` 的3100至3900范围，后端为前端端口加15000/15001，控制端口加10000。分配前核验三类端口未占用，不得杀占用者。例如前端3120对应后端18120/18121、控制13120。测试数据库、临时目录和存储命名空间也必须按角色隔离；演示数据库不等于PostgreSQL验收。

## 文件所有权

下列新目录为建议划分。F 可根据已有结构选择等价路径，但必须一次冻结并通知所有角色，不能让每个栏目自行选一套公共类型。

| 建议新增 `app/netshop/shared/**`、`lib/netshop/insights-contract.ts`、`backend/netshop/insights_common.py` | F；底座合入后由I串行维护 |

| 建议新增 `app/netshop/promotion/**`、`backend/netshop/promotion_insights.py`、推广专属API及测试 | A |
| 建议新增 `app/netshop/panorama/**`、`backend/netshop/store_panorama.py`、全景专属API及测试 | S |

| `app/page.tsx`、`app/shop-module-view.tsx`、`app/shell/**`、共享日期控件、全局CSS/tokens | O在01交接前；F在底座阶段；之后仅I |
| `backend/netshop/query.py`、`views.py`、`urls.py`、`consumers.py`、`lib/django/netshop-service.ts`及现有公共API | 同上，按阶段转交；不允许角色并写 |

| 公共验收测试、集成证据与本工作包契约 | I维护；Q提供独立审查结果 |

阶段转交必须记录精确提交、文件清单、未完成事项及当前持有人。文件所有权限制写入，不限制只读检查。它不允许绕过权限或访问敏感运行材料。

栏目需要公共路由或旧查询修复时，提交简短变更请求：用途、精确文件/符号、入出参、兼容影响、测试、依赖。I合入对应公共变更后回告SHA，栏目更新基线继续。禁止多个Agent复制整份`shop-module-view.tsx`后各自重写；也不要为了避免协调而复制指标算法。

## 拆分与兼容

先建立可测试的组件边界，保留旧页面入口和指标语义，再逐栏目接入。建议保留 `view=analysis|outlets|platforms|products|promotion` 的既有值，只调整用户可见名称，避免旧书签失效。新的页内章节和商品身份参数由共享导航解析器处理。

网店总览的 `overviewView=classic|balanced` 及其默认规则按01契约保留。全景的新共享指标不得强迫01更换DTO或改变视觉；需要复用时采用适配器和等价测试。旧接口可加向后兼容字段或新版本入口，不能静默改变旧字段定义。

子页只挂载活动视图所需读取；重型明细按需分页，独立分区允许显示自身错误。不能用某一分区失败阻止整页其他可信数据，也不能把错误降格为无数据。

## 协调与变更请求

共享契约按版本冻结。新增可选字段需兼容读取；字段改名、单位、来源、分母、状态或时间语义变化必须升级协议并迁移所有消费者。I发布契约变更及影响列表后相关角色再开发；不得各自口头约定。

发现缺源或未知业务定义时，列明字段、来源候选、影响的内容编号和最小补证据条件，继续完成不依赖它的功能。不因等待一个字段阻塞整页，也不填模拟数值。新的业务范围取舍由I汇总为一次明确问题交用户，不让各角色重复询问。

进度分为 `设计完成`、`隔离实现`、`本角色验证`、`待复核`、`可合并`、`已合主线`、`已生成候选`、`已生产采用`。阶段不得混称“完成上线”。

## 验证与交付

各角色先跑直接相关测试，再按影响范围运行单元测试、lint、后端边界检查和隔离生产构建。仅文档变更不运行生产构建。不得在正式服务监听的产物目录构建；未知基线失败须对前驱复现并单列，不能改断言、忽略错误或删测试宣称通过。

涉及查询、权限、聚合或多源关联时，要在独立PostgreSQL环境验证，而非只凭SQLite或模拟API。UI应验证典型桌面与窄屏、筛选/返回/深链接/空态/缺数/失败/版本变化；不缩小字体挤内容。性能在相同环境和有代表性的规模下比较，并记录范围、数据规模、执行计划、响应大小及耗时，不虚构固定性能承诺。

每个角色交付使用如下记录，字段不得空称通过：

```text
角色与内容编号：
契约版本与经用户派发的范围：
工作树、分支、基线SHA、依赖SHA、提交SHA：
修改文件与共享文件变更请求：
接口、来源、字段能力、缺数与未实现项：
测试命令、退出码、失败与基线对照：
隔离UI/后端验证及证据路径：
旧功能兼容与调用方影响：
待用户决定的新增范围：
提交/推送状态；生产操作未执行项：
```

集成只由I进行。其他角色提交自己的变更并按仓库规范推送分支，不自行更新main、不强推。合并前更新最新main并复验组合，冲突按语义处理；共享文件由持有人修改，不使用整文件ours/theirs覆盖。

本轮存在他人正在使用的01工作树。即使其分支已合入，也须等负责人交接、确认无未提交独有内容、预览/构建/发布依赖后才清理。其他已完成工作树亦遵守项目归档与保全规则。
