## 三、两侧时间去向：都已测清

### 准备侧 1770 秒（不停站）

「前驱完整自校验」五次合计 **609 秒、占 42%**。三个削减方向全部关闭：

1. **缓存校验结果** —— 不行。`rotation.mjs:1155` 在首段后**主动释放服务锁**（注释写明不阻塞构建期间的服务恢复），锁释放期间别的进程可改 worker 状态，所以三次回调是**重新取证**而非重复取证。缓存会掩盖这五次校验本要防的东西。
2. **减少校验次数** —— #1 与 #2 之间隔整个构建、都必要；#2 与 #3 窗口最短但只省 96 秒、论证成本更高。
3. **缩小哈希范围** —— 不行。`node_modules` 全树哈希是该目录完整性的**唯一**证据（`validateTree` 重算全树而非读 manifest），`dist` 仅 187 个文件而 `node_modules` 有 31420 个、`workerd.exe` 在后者内，两者是独立输入。

### 发布侧 180.4 秒（真实停站的主体）

S17 结论：那三次重复核验（37 秒）技术上可削，但只值 **3.4% 停站**，代价是改钉死字节、两处绊线、一个隐蔽陷阱、削薄一层防御。**不划算，不改。**

## 四、本专项最重要的发现：瓶颈不在代码

`candidate-stopped#1` 的 79.9 秒与准备侧 609 秒**同源**——都是 **31420 个文件的全树哈希在 6–11 MB/s、IOPS 受限的磁盘上重算**。

两侧合计约 763 秒受此支配。所以：

| 路径 | 作用范围 | 风险 |
| --- | --- | --- |
| **换 NVMe** | 同时作用于准备侧 609 秒与发布侧 154 秒 | **零代码风险**，不动钉死字节、不触发门禁、不削防御 |
| 缩小 release 本体 | 直接减少被哈希文件数 | 发布架构改动，风险高 |
| 削那 37 秒 | 占停站 3.4% | 需改钉死文件 + 承担隐蔽陷阱 |

**609 秒 + 154 秒是这套 immutable release 设计的固有成本。** 要降只有换硬件或改架构两条非「削减」路径，**推荐优先评估换 NVMe**。

## 六、方法层面的教训（本专项反复出现）

同一形态出现四次以上，**可检验的那一面都通过了，而决定结果的是没被检验的那一面**：

| 形态 | 实例 |
| --- | --- |
| 测试全绿，但代码在死路径上 | 第三步落点错误：六个用例 + 三个变异全绿，而拦截器从未被执行 |
| 指标全优，但窗口不洁净 | (c) 方案 profile 三项优于最终采用的 (b2)，若只按指标选就会选错 |
| 结论对，但推理错 | 授权路由：推断的理由不成立，答案恰好同向 |
| 读过文档，但没用上 | 判断「这次拿不到数据」时，规划第十节已写明执行器从冻结源码取字节 |
| 查了一处，用在另一处 | 从仓库 grep 脚本参数，而实际执行的是控制包里旧代际那份 |

**可操作的三条**：

1. 遇到「都对了」的判断，先问「有什么没被这个判断覆盖」。
2. 涉及生产的判断（尤其授权与范围）要把依赖的前提一并记下，**执行前回核前提是否仍成立**——「已上线/未上线」这类状态会变，而依赖它的结论不会自动失效，只会悄悄变错。
3. 「另一个会话也这么认为」不构成交叉验证；只有各自回到原始证据才算。本专项有一次两个会话共享同一个过期前提，推了好几轮。
