## 二、为什么没走固定发布验证入口（`tools/verify-release-candidate.mjs`）

这一节由并行的发布优化会话（"Worker JSON 失败原因窄资格验证"）实测澄清，
记录在此备查。

### 事实

该验证入口有一个 `supported` 集合，变更文件不在集合内就会 `unsupported` 非空、
在所有 check 之前失败关闭。实测：

```
lib/sales/import-service.ts        → unsupported: ["lib/sales/import-service.ts"]
tools/release-scope-plan.mjs       → unsupported: ["tools/release-scope-plan.mjs"]
```

**`lib/` 下的业务代码同样不在 `supported` 集合里。**

### 为什么这不是缺陷、也不是绕过门禁（三条，缺一条就容易被质疑）

**第一条：职责范围。** 那个验证入口是为**发布机制本身**设计的——生命周期
控制器、准备队列、发布工具、制品完整性、启动门禁。它检查的是"构建/部署/启动
这条链路会不会被这次改动弄坏"，不是"业务功能对不对"。业务代码路径本来就不在
它的职责范围内，不是漏掉了。

**第二条：规则依据。** `AGENTS.md` 规则 4/5 明确：发布前只检查**影响构建、
部署和启动的必需程序代码**；相关功能及其代码的业务行为、业务口径、接口业务
结果，**上线后由用户自行检测判断**，AI 不新增功能测试或综合验收作为发布前提。
所以业务代码不进那个入口，是规则规定的分工，不是省略了步骤。

**第三条：实测事实（这条最容易被想错）。** 不是"`tools/` 下就一定被覆盖、
`lib/` 下就一定不被覆盖"——**路径前缀不决定是否被覆盖，集合归属才决定**：

| 文件 | `unsupported` | 原因 |
|---|---|---|
| `lib/sales/import-service.ts` | **非空** | 不在 `supported` 集合里 |
| `tools/release-scope-plan.mjs` | **非空** | 同样不在 `supported` 集合里（`tools/` 也会撞） |
| `tools/jackyun_audit_addition.py` | 空 | **因为它在 `proofFiles`（结构证明工具）集合里**，不是因为它在 `tools/` 下 |

所以"改了 `tools/` 就有门禁、改了 `lib/` 就没门禁"这个理解是错的。真正的判据
是文件在不在那几个精确集合（`supported`、`proofFiles`、各窄资格 flag）里。

> 以上三条由并行的发布优化会话（"Worker JSON 失败原因窄资格验证"）实测澄清。
> 本会话最初的理解（"因为没改 tools/ 所以不撞门禁"）**是不准确的**，已据此更正。

### 一个技术约束：做不到"只发其中一笔"

发布优化会话查明：`publish-latest-main.mjs` 的目标提交是硬编码取
`origin/main` 当前 HEAD（`git rev-parse refs/remotes/origin/main`），
**没有指定目标提交的参数**。而 `846d15b8`（销售修复）已经是 main 的 HEAD。

所以现在只有两种可能：**一起发，或者都不发**。要做到"只发 C 项不发销售"
就得回退 main 历史，那是不该做的事。

如果用户选择暂不发布，销售修复会跟着一起等——这不是本任务能单方面推进的。
