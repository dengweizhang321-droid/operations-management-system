## 一、重要更正：之前判断"不能直接清"是过于保守了

### 之前的判断（第1步排查时）

看到清单里前3个数据集有 `rowCount`（352、906、427），就判断"有已验证的真实业务产物，
按规范不能直接删，需要受控归档入口"，而那套工具不在 main 上（在禁区目录里），
所以结论是"这轮不处理"。

### 现在查清的事实

逐字段核对4个数据集，**没有一个有 `batchId`**：

| # | 数据集 | 阶段 | rowCount | **batchId** | export字段 |
|---|---|---|---|---|---|
| 0 | flow（流水） | `validated` | 352 | **无** | 有 |
| 1 | shop_products（店铺商品） | `validated` | 906 | **无** | 有 |
| 2 | realtime_inventory（实时库存） | `validated` | 427 | **无** | 有 |
| 3 | inventory_snapshot（库存快照） | `exporting` | — | **无** | **无** |

从线上 helper（`releases/20261027T005508Z`）核实阶段序列：

```
browser_ready → export_intent → exporting → downloading → downloaded
→ validated → import_intent → imported → completed
```

**`validated` 之后还有 `import_intent` 和 `imported` 两个独立阶段。**
前3个停在 `validated`，意味着：下载完了、校验过了，但**从未进入导入阶段**。
`batchId` 是入库后才会有的字段，4个都没有，所以**都没写进业务库**。

第4个连 `export` 字段都没有，说明连导出请求都没发出去，**平台侧没有未决任务**。

### 所以

| 判断项 | 结论 |
|---|---|
| 有没有数据进了业务库 | **没有**（4个都无 batchId） |
| 有没有平台侧未决任务 | **没有**（第4个无 export 字段） |
| 属于规范里"禁止直接删"的状态吗 | **不属于** —— 那条针对的是
`export_submitted`/`downloaded`/`importing` 这类已发生业务点击或已有落库的状态 |
| 需要受控归档工具吗 | **不需要**，和客服4店、吉客云11010 同性质，可常规清理 |

本次更正的依据是逐字段核对 + 线上 helper 的阶段序列，不是推测。

## 二、但真正的问题不是清单，是那个失败原因

清掉清单只是让它**能重新跑**，不保证**跑得通**。10-16 那天的记录说明了真实难度：

| 13:59 | 批次回执变了（`BATCH_RECEIPT_CHANGED`） |
| **14:36** | **成功** |

| **10-17 11:18** | **条数不稳定（`SOURCE_COUNT_UNSTABLE`）** ~~← 现在卡住的这个~~ **【已更正：这是修复前的最后一次失败，`e07fbe64` 于当天 13:46 修复】** |
