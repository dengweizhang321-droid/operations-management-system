# 销售表失败根因（execution 11012）

- 日期：2026-10-27
- 性质：**只读排查，没有改动任何东西**
- **本文件已修正**：第一版把"毛利率为 null"误判为根因，经对比验证后推翻。见下文第三节。

## 一、结论：唯一的失败原因是 1 行销售数量是小数

| 项 | 值 |
|---|---|
| 行号 | 2492 |
| 字段 | `quantity`（数量） |
| 值 | **1.5** |

`lib/sales/import-service.ts:197-201` 的 `validateRows()` 要求 `quantity` 必须是
`Number.isSafeInteger`，`1.5` 不满足 → 产生 parserErrors → Django 后端
（`write_service.py:1161`）见到 parserErrors 就拒绝整批 39081 行。

**一行小数，让整批销售数据进不去** —— 和 10-24 库存表（3325.5）是完全同一个模式。

## 二、失败链条

```
D·统一导入 → 销售表 → chunk_upload_and_import
  → validateRows() 发现第2492行 quantity=1.5 不是安全整数
  → parserErrors 非空
  → Django write_service.py:1161 拒绝整批
  → 「文件校验未通过，未创建规范化导入会话」
```

## 三、【重要修正】"毛利率为 null"不是根因，我第一版判断错了

### 第一版的错误推理

我用解析器原始输出跑 `validateRows`，发现 7344 行 `grossMarginBps` / 
`untaxedGrossMarginBps` 是 `null`，而校验要求必须是安全整数，于是判断
"7344 行合法数据被误判，这是校验代码缺陷"。

### 推翻它的两个证据

**证据1：10-23 成功那次，null 更多**

| | 11006（10-23 **成功导入 39331 行**） | 11012（10-27 失败） |
|---|---|---|
| 毛利率为 null | **7370 行** | 7344 行 |
| 数量是小数 | **0 行** | **1 行** |

10-23 那次 null 比现在还多，照样成功。**所以 null 不可能是失败原因。**

**证据2：null 在校验之前就被转成 0 了**

`lib/sales/import-service.ts:325` 校验的不是解析器原始输出，而是
`mapAnalysisSafeRow()` 转换后的数据，而该函数第 29、31 行：

```ts
grossMarginBps: row.grossMarginBps ?? 0,
untaxedGrossMarginBps: row.untaxedGrossMarginBps ?? 0,
```

**`?? 0` 把 null 变成了 0**，所以 null 从来不会到达 `validateRows`。

### 我犯错的原因

我直接拿解析器输出去跑校验函数，**跳过了真实流程中间的 `mapAnalysisSafeRow` 转换**。
这和之前"只测裸解析器、漏掉预处理"是同一类错误 —— 用简化的调用链代替真实链路做判断。

顺带说明：数据库字段 `gross_margin_bps` 是 `BigIntegerField()`（不允许 null），
后端 `write_service.py:441` 也不接受 null —— 三层都不允许 null，而 `?? 0` 正是
为了满足这个契约而存在的设计，不是缺陷。

## 四、排查时排除的其他可能

| 怀疑 | 核实结果 |
|---|---|
| 销售文件解析有问题 | **否**，原始 42951 行 / 处理后 39081 行，都是 0 错误 |
| 警告数量超 200 上限 | **否**，`sanitizeSalesIssues` 已有 `slice(0,200)` |
| 成本源依赖断了 | **否**，库存 runner 正常留下 `salesCostSourcePath`，SHA 匹配 |
| 毛利率为 null | **否**，见第三节 |
| 唯一标识/重复行/日期/单号/业务类型 | **全部 0 问题** |

## 五、怎么处理

**你已决定：自己去吉客云把那一行的数量改掉。** 这是最直接的办法——
源头数据修正，不动代码。

改完之后手工跑一次，销售表应该就能通过（其余校验全部 0 问题）。

### 如果以后还想从代码层面根治

销售数量和库存数量不同：**库存 3325.5 四舍五入影响不大，但销售数量 1.5 变成 2
会直接改变销售额、成本、毛利的计算结果**。所以不建议照搬库存那套"四舍五入+告警"，
更合适的做法是"遇到小数数量就明确拒绝并指出行号"（现在就是这个行为，只是
错误消息不够直白，没有告诉你是哪一行、什么值）。

**建议的小改进**：让错误消息带上行号和实际值（比如"第2492行 数量=1.5 不是整数"），
这样你一看就知道去吉客云改哪一行，不用像这次一样要排查一轮。
