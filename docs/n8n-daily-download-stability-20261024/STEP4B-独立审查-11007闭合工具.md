## 二、必须修（阻断）

### M1 `audited11007.error` 写错，是 n8n 的 `message` 而不是解码出的 `description`

`lib/jackyun/closure-11007.ts:24` 写的是 `"The service was not able to process your request"`。

但 `decodeN8nPreflightEvidence`（`n8n-preflight-decode.ts:56`）取的是 `error.description`，
不是 `error.message`。实测 11007 的 n8n error 对象两个字段都存在且不同：

| n8n 字段 | 实际值 |
| --- | --- |
| `description`（解码器实际读取） | `文件校验未通过，未写入任何库存数据` |
| `message`（常量里写的） | `The service was not able to process your request` |

后果：`assertClosure11007Evidence` 第 73 行 `e.error !== a.error` 永远成立，`plan`
第一步就抛"不是已审计的 11007 导入失败"。**工具 100% 跑不通**。

实测证据（`/d/codex-artifacts/review-jackyun-closure-20261025/decode.ts`，用真实
n8n 库解码后与常量逐字段比对）：12 个字段 11 个 MATCH，唯一 MISMATCH 就是 `error`。

修法：常量改成 `文件校验未通过，未写入任何库存数据`。
注意这个值同时也是 `run-manifest.json` 里 inventory 模块的 `error` 字段值，
可以顺手加一条交叉核对（参考 `fresh-restart.ts:144` 的
`evidence.source.error.includes(rejected.error.message)` 做法）。

### M2 `audit/inventory.json` 的错误明细层级写错，少了一层 `details`

`closure-11007.ts:140-147` 按 `error.httpStatus` 和 `error.errors` 读。
真实文件是 `error.details.httpStatus` 和 `error.details.errors`：

```
"error": {
  "stage": "chunk_upload_and_import",
  "message": "文件校验未通过，未写入任何库存数据",
  "details": { "httpStatus": 422, "status": "rejected", "errorCount": 2,
               "errors": [ {...row:1735...}, {...row:1735...} ], "warnings": [] }
}
```

后果：`inventoryAudit.error?.httpStatus` 是 `undefined`，`errors` 取到 `[]`，
`inventoryErrors.length !== 2` 成立 → 抛"库存导入失败证据已变化"。即便 M1 修好，
这里仍然挡住。

实测：把真实 inventory 审计的 `details` 拍平成工具期待的结构后，`inspect` 立刻通过
（`iso.test.ts`，输出 `inspect SUCCEEDED`）。这证明 M1+M2 是**仅有的两处事实层面
的拦路问题**，其余核对项对真实数据全部成立。

顺带：既有先例 `import-recovery.ts:92` 用的是
`audit.error?.details?.httpStatus`，`fresh-restart.ts:143` 也是
`rejected.error?.details?.httpStatus`。本工具没跟上这个已有结构，说明常量是
按文档推的而非按真实文件核的 —— 这正是本次审查最该抓的那类错误。

### M3 漏核 `import-checkpoints/`，里面有一条未决上传记录（`complete_intent` + 非空 `uploadId`）

真实 `outputs/jackyun-import-runs/n8n-export-first-11007/` 下有 6 个条目：

| 条目 | 工具是否核对 |
| --- | --- |
| `run-manifest.json` | 核对 |
| `api-controller-state.json` | 核对 |
| `audit/`（恰好两文件） | 核对 |
| `import-checkpoints/` | **未核对** |
| `processed/` | **未核对** |
| `raw/` | **未核对** |

工具只做了 `readdir(formal/audit)` 的清单核对（第 153 行），**没有对 `formal` 本身
做清单核对**。这与审查要点 2 提到的先例不等同：`import-recovery.ts:92-95` 核的是
`readdir(p.formal)` 必须恰好等于 `["audit","browser-controller-state.json","processed","raw","run-manifest.json"]`，
是对**上一层目录**的完整清单，本工具缺这一层。

这不是洁癖问题。`import-checkpoints/inventory.json` 的真实内容是：

```
"stage": "complete_intent",
"uploadId": "ecb398a8-cfd0-4ea8-b1c4-d9f0d4a70d31",
"batchId": null
```

按 `import-coordination.ts:11,66` 的语义，`complete_intent` 表示
**分片上传已完成、complete 请求意图已持久化，但服务端批次号尚未回执**；
`fresh-restart.ts:180` 对同一状态的处理是必须向 Django
`/api/imports/recovery` 查到 `uploadStatus === "ready"` 且 `uploadId` 精确匹配，
才算"确认未提交"，否则抛"旧库存存在未知提交或 processing，禁止从头采集"。

也就是说：现有代码里，这个 `uploadId` 对应的上传会话**是不是真的未提交，是一个需要
向 Django 查证才能确定的事**，不能从本地文件单独推断。本工具直接跳过，等于把
"库存没写进去"这件事只建立在 `audit/inventory.json` 的 422 记录上。

规范依据：`导入与自动化.md` 第 54 行"**部分文件/导入**、跨日、其他消费者、身份异常、
**提交未决**和证据变化不得借此自动闭合"；第 33 行也强调闭合入口"不适用于任何导出点击
未决、超时、部分文件或**已开始导入**的情况"。11007 恰好是"已开始导入 + 一条提交未决
上传会话"，正中禁止项。

实测该缺口的可利用性（`crash.test.ts` 的 EXTRA DIRS 用例）：在 fixture 里额外塞入
`import-checkpoints/sales.json`（`complete_intent`）和
`import-checkpoints/combos.json`（`stage:"committed"`、带 batchId），
再塞一个 `processed/mystery.xlsx`，`inspect` **全部接受**。
也就是说：如果后三表真的有过提交痕迹，这个工具看不见，照样闭合。

修法建议（任一或组合）：
1. 加 `readdir(p.formal)` 必须恰好 `["api-controller-state.json","audit","import-checkpoints","processed","raw","run-manifest.json"]`；
2. 加 `readdir(formal/import-checkpoints)` 必须恰好 `["inventory.json","products.json"]`，并逐个核对 `stage`（products=`committed`、inventory=`complete_intent`）、`identityDigest`、`batchId`（inventory 必须 null）；
3. 加 `readdir(formal/processed)` 必须恰好只有那个预处理后的库存文件、`readdir(formal/raw)` 恰好两个文件；
4. 对 inventory 那个 `uploadId` 的未提交性，给出明确处置：要么比照 `fresh-restart.ts:180` 做一次 Django 只读查证，要么在回执里显式记录"该 uploadId 未经查证"并由用户在批准时承担这一判断（见待确认 Q2）。

## 三、建议改（非阻断）

### S1 半成品状态：两个崩溃窗口，一个会把工具永久卡死

实现里的真实顺序是三步，不是你提到的两步：

```
1. writeFile(activeArchive, flag:"wx")     ← 先留副本
2. rename(active → active.json.closed-11007)
3. create(receiptPath, flag:"wx")          ← 后写回执
```

我独立实测了两个窗口（`crash.test.ts`）：

| 崩溃点 | active.json | 回执 | 再跑 apply | 新 execution 能否跑 |
| --- | --- | --- | --- | --- |
| 第 1 步后、第 2 步前 | **仍在原位** | 无 | **永久失败**：`EEXIST ...11007-archive\active.json`（`wx` 撞上自己留的副本） | 不能，被 active 挡住 |
| 第 2 步后、第 3 步前 | 已移走 | 无 | 失败：`ENOENT ... active.json`（inspect 要求 active 存在） | **能**，走新建计划路径 |

两点评价：

**第二个窗口是可接受的降级**，而且比你的担心要好。我核了 A 节点逻辑：
`tools/jackyun-export-first-pipeline.ts:351` 用
`readJsonFileOr(activePath, null)` 读，ENOENT 得到 `null`；
第 456 行 `if (!unifiedResume && active && active.executionId !== executionId)`
在 `active` 为 null 时整块跳过，直接落到第 548-556 行的新建计划路径
（`plan` 为 null → `createExportFirstPlan` → 写新 plan → 写新 active）。
所以"丢审计记录、不卡业务"这个判断成立，而且副本还在
`preflight-closures/11007-archive/active.json` 里，审计并没有真丢。
再跑 apply 会被 ENOENT 拒绝，不会重复归档、不会制造不一致 —— 这是对的。

**第一个窗口是实打实的缺陷**：`wx` 副本先写、rename 后做，一旦在这中间崩，
工具就被自己留下的副本永久锁死，而业务也仍然被 active 挡着，两头都不通，
只能人工手删那个副本才能继续。注释（第 178-181 行）宣称"a crash between the two
steps never leaves active.json both present and claimed to be archived" —— 这句对
第 2/3 步成立，但它没覆盖它自己新引入的第 1/2 步窗口。

建议：把 `rename` 直接当作归档动作（`rename(p.active, p.activeArchive)`，
目标在 `11007-archive/` 下），去掉"先 copy 再 rename 到 `active.json.closed-11007`"
这个双份设计。`rename` 本身在同一卷上是原子的，一步到位既保留了字节又腾空了 active，
崩溃窗口从两个减到一个，而且剩下那个是良性的。既有先例
`close-jd-logistics-known-flow.ts:217` 用的就是单次 `io.moveNoReplace`，没有预先 copy。
或者退一步：把第 1 步的 `wx` 改成"若已存在且字节相同则视为已完成、继续走 rename"的
幂等写法。

### S2 `apply` 的 `proposalPath` 没做路径身份校验

`tools/jackyun-11007-closure.ts:55` 直接
`JSON.parse(await readFile(proposalPath, "utf8"))`，没有过 `assertEntityPath`、
没有大小限制。虽然 `approvedSha` 和随后的 `inspectClosure11007` 全等比较把危害封住了
（伪造的 proposal 过不了 sha + 全等双闸），但既有工具对所有证据文件都走
`bytes()`/`readRegular()`，这里破例了。建议统一。

### S3 `publishClosure11007` 的 `root` 重解析顺序别扭

第 171 行先用**未解析**的 `root` 调 `inspectClosure11007`（里面自己会 `path.resolve`），
第 173 行才 `root = path.resolve(root)`。结果能对，因为 inspect 内部解析过且 proposal
里的 `root` 是解析后的值，全等比较会把不一致的情形拦住。但读起来像 bug，
建议把 `path.resolve` 提到函数第一行。

### S4 `assertClosed11007` 是孤儿代码，没有任何调用方

全仓搜索确认：`closure-11007.ts` 的三个导出里，`assertClosed11007` 只被它自己定义，
**没有任何生产代码调用**，连测试都没覆盖它。整个 `lib/jackyun/closure-11007.ts` 在
pipeline 里也完全没有接线点（`grep -rn "closure-11007|assertClosed11007|audited11007"`
除自身和测试文件外零命中）。

这带来一个需要想清楚的后果：对比
`preflight-recovery.ts` 的闭合回执会被 A 节点第 513 行的
`assertClosedPreflight(root, active.executionId, executionId)` 读取和复验，
本工具写的回执**没有任何消费者**。它写在
`preflight-closures/n8n-export-first-11007.json`，而 A 节点在 active 已被移走的情况下
根本不会走到读 11007 回执的分支，所以它纯粹是一份给人看的审计记录。

这本身不一定是错 —— 一次性闭合工具只需要"腾空 active + 留痕"。但要注意
第 545 行有个检查：`if (await stat(preflightClosurePath(root, executionId)))` 抛
"原登录失败运行已经闭合，禁止重放"。这个 `executionId` 是**当前**新 execution 的 ID，
不是 11007，所以不会误伤。确认过，无风险，但 `assertClosed11007` 建议删掉或
至少加测试，否则是没人维护的死代码。

## 四、待确认（需要用户决定）

### Q1 "row=1735 的两条 INVALID_NUMBER 就是我们已修的那个小数"这个信任链条

工具核的是：`stage=chunk_upload_and_import` + `httpStatus=422` + 恰好 2 条错误 +
`code=INVALID_NUMBER` + `row===1735` + `field∈{onHandQuantity, availableQuantity}`。
它**不核**错误 `message`，也无法读真实 XLSX 去确认那一行的值确实是 `3325.5`。

风险评估：**低，但不是零，而且有一个便宜的加固办法没做。**

低的理由：
- 这些文件现在就在磁盘上、内容已固定，工具每次都重算 sha 并写进 proposal；plan→apply 之间任何改动都会被全等比较拦住。真正的风险窗口不是"被篡改"，而是"原始事实本身就被误读"。
- 组合约束相当窄：同一行、同时两个数量字段、恰好 2 条、无其他错误、422。小数值被 Django 判为"不是有效整数"是最自然的解释。
- 真实 `audit/inventory.json` 里的 `message` 是 `库存数量不是有效整数` / `可用库存不是有效整数`，与小数假设一致。

不是零的理由：**同样的 `code`/`row`/`field` 可以由别的根因产生** —— 空值、
文本、科学计数、超出 int 范围的大数，都可能被同一个 `INVALID_NUMBER` 分支拒绝。
我实测把两条错误的 `message` 换成 `库存数量为空`（空值根因，小数修复完全治不了），
`inspect` 照样接受（`crash.test.ts` 的 FORGED FACTS 用例）。

便宜的加固：把 `message` 也纳入常量核对
（`库存数量不是有效整数` / `可用库存不是有效整数`），再把
`error.details.status === "rejected"`、`errorCount === 2`、
`warnings` 为空数组一起断上。这不需要读 XLSX，纯粹用已有的审计文件就能把
"是否同一根因"的证据面从 4 个字段扩到 8 个。**我建议做，但归在待确认而非必须修**，
因为即使不做，闭合的安全性也不依赖它 —— 闭合本身不恢复导入、不写数据，
万一根因判断错了，后果只是下一次完整 execution 在同一个地方再失败一次，
而不是写入脏数据。请用户确认是否接受这个"判断可能错、但错了也只是白跑一轮"的性质。

### Q2 `import-checkpoints/inventory.json` 那个 `complete_intent` 上传会话怎么处置

`uploadId=ecb398a8-...` 这个分片上传会话，在 Django 侧现在是什么状态？
- 如果是 `ready`（已上传、未提交）—— 那库存确实一行没写，闭合安全。
- 如果是 `processing` 或已变成某个批次 —— 那就是"提交未决/部分导入"，按

但本工具的设计前提是"纯文件系统操作、零网络请求"（CLI 注释明确这么写，

1. **加一次只读 Django 查证**（比照 `fresh-restart.ts:180`）。最严谨，但破掉"零网络"的干净性，且需要 Django 在线。
2. **只核本地、在回执里显式声明未查证**。保持零网络，把判断责任放在批准动作上。考虑到 `audit/inventory.json` 明确记了 `httpStatus:422` + `status:"rejected"` + `文件校验未通过，未写入任何库存数据`，而 422 是服务端在校验阶段拒绝、按定义不会进入提交，这个判断有相当强的本地证据支撑 —— `complete_intent` 只说明"complete 请求发出过"，422 说明"它被拒了"。我倾向这个选项够用。
3. **人工在 PG 侧核一次库存批次**，确认 2026-10-24 没有新库存批次，然后走选项 2。

不管选哪个，M3 里"核对 `formal/` 完整目录清单 + `import-checkpoints` 文件集合与
stage"这部分是**必须加的**，和这个选择无关 —— 那是防"后三表悄悄有过动作"，
与 inventory 这条未决会话是两件事。

## 五、补充审查：`fresh-restart.ts` 是否是更合适的现成机制

协调方在核实 M3 时发现了 `lib/jackyun/fresh-restart.ts`（main `299f9764`），
并提出假设："它第 143 行要求 `httpStatus===400`，而后端 `importExecutionHttpStatus`
的返回类型只有 `200|201|409|413|422|503`、不含 400，所以这套机制是针对更早期
返回 400 的后端版本设计的，现在悄悄失效了。"

**这个假设不成立。我独立核实后的结论相反：这套机制没有过时，它要求 400 是因为
它是为另一个真实事件量身定做的，而且已经被消费过一次。**

### 5.1 时间线证伪了"400 时代"的说法

| 事实 | 证据 |
| --- | --- |
| `importExecutionHttpStatus` 返回 422、不含 400 | 至少自 `132940d2`（2026-08-20）起就是这个签名；`63c78c19`（2026-10-13）再次确认 |
| `fresh-restart.ts` 引入时间 | `299f9764`，**2026-10-18** |

`fresh-restart.ts` 比"422 已成定局"晚了两个月。它不可能是为 400 时代写的 —— 
写它的时候 `importExecutionHttpStatus` 早就不返回 400 了。作者是明知 422 的情况下，
**故意**写了 `httpStatus !== 400` 这个条件。

### 5.2 400 是可达的，而且来自另一条代码路径

协调方只查了 `importExecutionHttpStatus`，漏了路由层。
`app/api/imports/inventory/chunks/route.ts` 里有 5 处 `reject(400, ...)`：
请求内容无效、缺快照日期、未知上传操作、缺分片标识、分片为空。
这些是**请求/绑定层面的拒绝**，不经过 `importExecutionHttpStatus`。

所以 400 和 422 在这条链路上代表两类完全不同的失败：
- **400** = 请求本身或上传会话绑定不成立（路由层挡掉）
- **422** = 文件进了校验、被逐行规则拒绝（`importExecutionHttpStatus` 默认回退）

### 5.3 `fresh-restart.ts` 真正的服务对象是 10037/10039，不是某个"早期版本"

我在生产目录里把所有 `*/audit/inventory.json` 按 httpStatus 筛了一遍：

| httpStatus | 命中运行 |
| --- | --- |
| 400 | `n8n-export-first-10039` |
| 422 | `n8n-export-first-11007` |

10039 的那条审计内容（只读查看）：

| 字段 | 10039 | 11007 |
| --- | --- | --- |
| `details.httpStatus` | **400** | **422** |
| `details.status` | rejected | rejected |
| `details.errors` | **`[]`（空数组）** | **2 条 INVALID_NUMBER / row 1735** |
| `details.errorCount` | 无 | 2 |
| `error.message` | 约 7075 行仓库映射/可用不一致 | 文件校验未通过，未写入任何库存数据 |
| 失败性质 | 仓库映射整体不成立 | 单行小数值越界 |

而且 `outputs/jackyun-export-first/fresh-restarts/` 下**已经有一个 `10037` 目录** —— 
这套机制已经被 10037→10039 这组逻辑运行消费过一次了。

函数自己的注释写得很清楚：
`/** Intentionally supports one audited serial prefix only. */`
它和 `auditedImport891`、`audited843` 是同一类东西 —— 参数化只是形式，
`httpStatus===400` + `errors` 必须能被 `evidence.source.error.includes(rejected.error.message)`
匹配这些硬条件，把它锁死在那一个已审计事件上。**不是通用机制。**

### 5.4 所以"一套机制悄悄失效"这件事不存在，不需要单独告知用户

协调方问"要不要单独告知用户：一套曾经可用的恢复机制因返回码变化悄悄失效了"。
**我的判断是：不要告知，因为这个结论是错的，报上去会制造一个假缺陷。**

真实情况是：`fresh-restart.ts` 服务于 400 类的仓库映射拒绝（10039），
11007 是 422 类的行值拒绝，两者本来就是不同失败类别，它拒绝 11007 是
**设计意图内的正确行为**，不是失效。

顺带说明 11007 走不通这条路的，不只是 400 这一条。我核了它的其余前置条件：

| `fresh-restart.ts` 的前置要求 | 11007 实际 | 是否满足 |
| --- | --- | --- |
| `httpStatus === 400`（第 143 行） | 422 | 否 |
| `rejected.error.message` 须被 n8n `evidence.source.error` 包含（第 144 行） | 11007 的 n8n description 恰好等于该 message，这条**反而满足** | 是 |
| `control.record.decision === "resume"`（第 106 行） | 实读 `recovery-control/11007/0001.json`：`decision = "collect"`、generation 1、attemptExecutionId 11007 | **否** |
| `BoundHumanAuthority` 且 `authority.kind === "new"` + `supersedes`（第 190 行） | 不存在 | 否 |
| `publication-baselines/<runId>.json`（第 152 行） | `n8n-export-first-11007.json` 存在 | 是 |
| 后三表在 `import-checkpoints`/`audit` 无痕迹（第 147-150 行） | 真实目录两处都只有 products/inventory | 是 |

即便把 400 改成接受 422，还卡在 `decision` 仍为 `collect`、以及缺人工授权这两道上。
协调方选项 C 里提到"由另一个人工决策入口先把 decision 从 collect 推进到 resume" —— 
这个推进本身要经过 `human-retry.ts` 的授权链（`readJackyunRecoveryTarget` 计算目标、
`BoundHumanAuthority` 带 `authorizationId`/`expiresAt`），是一套独立的、比本次闭合
重得多的流程，而且它的终点是"从头重新采集五表"，不是"释放锁让 n8n 正常跑"。

### 5.5 关于那个只读 GET：确实现成，而且 CLI 真的调得通

协调方说对了一件重要的事：`fresh-restart.ts:167-180` 的查证做法是现成的，不用新发明。
我补充核实了可行性（这是选项 B 成立的前提）：

- `app/api/imports/recovery/route.ts` **只有 GET**，注释明确
  `/** Read-only, authenticated status query. Never init/claim/complete an upload. */`，
  内部只向 Django writer 发 `method: "GET"`。确认是纯查询，不会推进任何上传状态。
- 提交动作在**另一个文件** `app/api/imports/recovery/finish/route.ts`，只有 POST。
  两者物理分离，调 GET 不可能误触 finish。
- 鉴权：`requireAppPrincipal(["admin"])`，但有
  `TERUISI_LOCAL_DIRECT_ACCESS` 回环直连通道（`lib/auth/authorization.ts:86-96`，
  非回环 host 一律 403）。既有 CLI 工具正是靠这条路访问 `localhost:3000`。
  所以从闭合工具里发这个 GET 技术上可行。

### 5.6 三个选项的评估与我的建议

**我建议 A + Q1 加固，不建议 B，明确不建议 C。**

| 选项 | 评估 |
| --- | --- |
| **A. 继续修 M1-M4，保持"纯释放锁"语义** | **推荐。** 语义最小、影响面最窄、与规范第 33 行"闭合不是跨 execution 接管"一致。11007 要的就是让 11010 能正常从 A 跑一遍完整五表，不是恢复旧任务。M3 要求的目录清单核对（`formal/` 完整清单 + `import-checkpoints` 文件集合与 stage）在 A 里照样要加，这部分与选项无关。 |
