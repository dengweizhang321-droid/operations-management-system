# 吉客云根因 + 你那个"重试3次再提醒"的方案评估

- 日期：2026-10-25（上海）
- 性质：**只读排查与评估，没有任何改动**
- 证据：`scan_history.mjs` 输出（19轮历史库存文件逐一解析）、`parse_inventory.mjs`、`row1928b.mjs`

## 第一部分：吉客云根因（已查清）

### 一行小数，卡死两天

10-24 失败的真正原因：库存文件第 **1928** 行，广东仓某货品的数据是

| 字段 | 值 |
|---|---|
| 库存数量 | **3325.5** ← 小数 |
| 可用库存 | **3325.5** ← 小数 |
| 单位 | PCS（件） |
| 仓库 | 广东仓 |

解析器要求库存数量必须是整数（`lib/imports/inventory-stock.ts:377` 用 `Number.isSafeInteger`），
小数直接判为"不是有效整数"→ 整个文件校验不通过 → **26451 行一行都进不去**。

### 这是全新变化，不是老问题

我把 10-05 到 10-23 全部 19 轮的库存文件都重新解析了一遍：

| 日期 | 小数库存行数 | 结果 |
|---|---|---|
| 10-05 ~ 10-22（**18轮**） | **0** | 全部成功 |
| **10-23**（11007） | **1**（第1928行） | **失败** |

**小数是 10-23 第一次出现。** 吉客云那边有人把某个货品的库存改成了 3325.5。

### 顺带排除一个误判

我之前以为"51行缺成本价"是问题。**不是。** 这51行从 10-05 起每轮都有，18轮全部成功导入 ——
解析器对缺成本价是**容错**的（只报 warning 不阻断）。真正阻断的只有那1行小数。

### 为什么不能简单改成"接受小数"

| 环节 | 现状 |
|---|---|
| 解析器 | 要求 `Number.isSafeInteger` |
| 后端导入 | `backend/inventory/import_service.py:202` 用 `int()` 转换 |
| **数据库字段** | **`BigIntegerField`（整数）** |

整条链路从解析到入库都是整数设计。改成支持小数要动数据库结构，是大工程，而且会影响
库存、备货、可用量所有相关计算。**不建议。**

### 修复方案（三个，要你选）

| | 做法 | 风险 | 多久 | 能不能防下次 |
|---|---|---|---|---|
| **A（推荐）** | **到吉客云后台把那个货品的库存改成整数**，然后手工跑一次吉客云 | 低。源头修正，不改代码 | 10分钟 | **能**，但如果以后又有人填小数还会再犯 |
| B | 改解析器：小数库存**按四舍五入处理并记警告**，不再阻断 | 中。要改代码+审查，但不动数据库 | 第4步一起做 | **能**，永久免疫 |
| C | 改解析器：**跳过**个别坏行，其余正常导入 | 中高。会静默丢数据，违反规范"零行必须失败关闭"的精神 | — | 不建议 |

**我的建议：A + B 一起做。**
A 先让吉客云今晚能跑通（不然还要多丢一天库存快照）；B 从根上让这类单行问题不再拖垮整批。

**但 A 有个前提**：11007 那个未闭合记录还在。就算库存数据修好了，手工跑还是会被
"原运行尚未闭合"挡住（我上一轮验证过）。所以顺序应该是：

1. 你到吉客云改那个货品的库存为整数
2. 我处理 11007 未闭合（需要你批准具体做法，见 [STEP2-方案.md](STEP2-方案.md) C-3）
3. 手工跑一次吉客云验证

## 第二部分：你那个"9点后 + 重试3次 + 钉钉提醒"的方案

### 先说结论

| 你的想法 | 我的评估 |
|---|---|
| **都调到9点后** | **合理，而且数据强力支持** |
| **首次失败后重试** | **已经有了**，不用新建 |
| **重试3次还失败就钉钉提醒** | **方向对，但"3次"这个数字对67%的失败是浪费** |

### 1. "都调到9点后"——数据完全支持你

我按启动时间分组统计了14天的定时执行：

| 启动时间 | 成功 | 失败 | 成功率 |
|---|---|---|---|
| **9点前** | **0** | 6 | **0%** |
| 9点后 | 108 | 60 | 64% |

**9点前启动的定时执行，14天一次都没成功过。**

而且京东物流那条（08:00启动）是唯一排在9点前的，它14天唯一那次成功是
**10-16 14:34**，在9点之后。当天它上午跑的 09:04、10:03、11:25 全失败，下午才成。

更有说服力的是 10-16 那天物流跑了6次，**每次报不同的错**：

| 时间 | 错误 |
|---|---|
| 09:04 | 事业部对不上 |
| 10:03 | 日期控件有歧义 |
| 11:35 | 商品状态控件有歧义 |
| 13:05 | 实时数据粒度不符 |
| 13:59 | 批次回执变了 |
| **14:36** | **成功** |

这正是"平台数据还没刷新完"的典型表现：页面控件和数据在变，每次撞到不同的不一致。

**所以你的判断是对的，而且我原来排的定时表是错的**（我把客服排到了 08:00/08:20/08:40、
物流 07:30，全在刷新之前）。

### 2. "首次失败后重试"——已经有了，不用新建

那条"数据下载导入工作流每小时安全重试"已经在做这件事，而且结构比我以为的完善：

| 它的节点 | 作用 |
|---|---|
| 捕获下载导入工作流失败 | 任何流失败自动触发 |
| **筛选安全自动重试的失败** | **区分能不能重试** |
| 等待一小时 | 退避 |
| 读取原执行计划时间 | 核对身份 |
| 原计划已完成？ | 避免重复 |
| 启动新的完整业务 execution | 真正重试 |
| 不可派发或结果未知转人工 | 转人工 |
| 还有需要继续退避？ | 继续等 |

它14天的实测战绩：**自己触发43次成功42次**（几乎从不出错），
派发下游20成功18失败，另有 **21次被它正确拦下没派发**（判定为要人工处理的不重试）。

**所以筛选机制是有效的，不需要重做。缺的只有"连续失败N次后钉钉提醒"这一环。**

### 3. "重试3次再提醒"——这里我建议改一下

问题在于：**67%的失败重试是无用的**，等3次纯属浪费时间。

14天失败分类实测：

| 失败类型 | 次数 | 占比 | 重试有用吗 |
|---|---|---|---|
| 要人工处理（掉登录、验证码、京东限流、上次没处理完） | **70** | 67% | **没用** |
| 临时性（网络、超时、页面没跑完） | **34** | 33% | 有用 |

按你的方案，一个"掉登录"的失败要等 **3小时**（重试3次×1小时）才提醒你，
而这3小时里重试必然全部失败 —— 因为登录态不会自己好。

**我建议分两类处理：**

| 失败类型 | 做法 | 提醒时机 |
|---|---|---|
| **要人工处理** | **不重试，立即钉钉提醒你** | **马上** |
| **临时性** | 重试，最多3次 | 3次都失败才提醒 |

好消息：**那条重试流已经会区分这两类了**（"筛选安全自动重试的失败"节点，14天正确拦下21次）。
所以只要在它现有的"转人工"分支上接一个钉钉通知，就能实现。

而且这符合你记忆里的既有偏好和项目规范：
- 规范第27条：「人工协助立即提醒；同一卡点连续3次检查或30分钟无实质进展时知会」
- 你2026-09-14 的要求：异常通知只发你本人钉钉单聊，不发群

**项目规范里早就是"立即提醒 + 连续3次"的双轨设计，和我的建议一致。**

### 4. 但钉钉提醒要能真正帮到你，还缺一样东西

你说"钉钉提醒我，我找AI修"。要让这个闭环真的省事，提醒里必须写清**你要做哪一步**。

现在的失败信息是这样的：

| 实际错误文本 | 你看了能知道做什么吗 |
|---|---|
| `PREVIOUS_RUN_UNRESOLVED_MANUAL_ACTION` | ✗ |
| `JD_IDENTITY_RATE_LIMIT_MANUAL_ACTION` | ✗ |
| `The service refused the connection` | ✗ |
| `JD_LOGISTICS_SOURCE_COUNT_UNSTABLE` | ✗ |

第4步要做的就是把这些翻译成人话，比如：

> 【京东客服-商用厨电】今天没下载成功
> 原因：上一轮（10-21）卡住没清理
> 你要做的：回复"清理厨电客服卡住任务"，我来处理
> 影响：客服聊天记录缺 10-22 至今

这个在你原任务的第4步里已经列了（"卡住当天发钉钉提醒，写清楚我要做哪一步"），
方向完全正确。

## 第三部分：要不要"换一种方式"——我的回答

你问的是有没必要换方式让它们更稳定。**我的判断：不用换架构，但要改三处设计。**

### 不建议换的（现在的设计是对的）

| 项 | 为什么保留 |
|---|---|
| 单个 helper 排队 | 这是规范明确要求的设计，避免多浏览器抢同一账号。14天实测排队机制正常工作 |
| 失败就停、不自动重放 | 保护数据正确性。138次成功全部真实落库、零脏数据，这个严格性是有价值的 |
| 卡住清单拦截下一轮 | 防止重复导出。虽然造成死循环，但根因是"没人清"，不是机制错 |

### 建议改的三处

| # | 改什么 | 为什么 | 收益 |
|---|---|---|---|
| **1** | **全部挪到9点后** | 9点前成功率 0% | 直接消除一类必然失败 |
| **2** | **要人工的失败立即钉钉提醒**（不等重试） | 67%的失败重试无用，而且卡住清单会让第二天继续失败 | 把"卡一周"变成"卡一天" |
| **3** | **单行坏数据不要拖垮整批** | 吉客云26451行因1行小数全部进不去 | 这类问题从"全军覆没"变"记个警告" |

这三处里，**第1和第2是改配置和加通知，不动核心逻辑**；第3要改解析器，但只改容错策略。
