# 京东 POP 库存流水与 ERP 建单核对规划

日期：2026-10-15。状态：独立规划草案。请求角色 `decision`，模型 `gpt-6-astra`、强度 `high`；实际后端模型未独立确认。本文没有实施生产接口、迁移、自动下载、导入、ERP 写入或真实推送。

## 1. 当前范围

用户最新明确：“先按‘京东POP：流水与ERP建单核对；京东自营/C仓，不需要处理’”。本轮在“库存管理 → 京东入仓监控”现有页面新增京东 POP 子版块，仅处理：

- 来源1库存流水：`https://wl.jdl.com/bsc-inventory/flow`。
- 来源4店铺商品：`https://wl.jdl.com/supplychain-bbi/esg`，作为销售平台与店铺商品归属辅助来源。
- 商品对照表 C/D 对应的 ERP 编号/名称人工维护。
- 调拨单 C 对应的 ERP 调拨状态人工维护。
- 全部受控京东账号可登记使用，新店物流能力与自动采集默认关闭。

原“三类物流接口”被最新指令收窄为一个物流事实来源、一个商品归属辅助来源和系统内人工维护接口。实时 C 仓、快照 C 仓、区域库存/销量/周转、在途补货计算、缺货阈值和缺货推送均不在本轮接口、表、页面或实施阶段中。

本轮交付 demo 与结构/下载方案，不代表真实链路已接通。后述 `/api/inventory/jd-pop/*` 均为拟议 TERUISI API，不是京东后台地址。

## 2. 已核实事实

详细证据见 [表格结构分析](表格结构分析.md) 与 [下载调研](下载调研.md)。

| 对象 | 已核实事实 | 设计约束 |
| --- | --- | --- |
| 库存流水 | 事业部编码、仓编码、各商品/单据编码、类型、库存状态/类型、实际与可用期初-变动-结存分别存在 | 不合并编码；负变动不等于负库存或销售出库 |
| 店铺商品 | 已观察实际 iframe `https://scsw.jdl.com/storeGoods/list`，同事业部可见多个店铺、导单店及一商品多店关系 | 事业部不是店铺；映射允许一对多，不能重复累计共享流水 |
| 商品对照 | A事业部商品编号、B商家商品标识、C人工ERP编号、D人工ERP名称、E京东名称参考 | 人工值绑定事业部＋商品键，不绑定Excel行号 |
| 调拨单 | 现行行粒度为 L京东单据编码＋H事业部商品编号，C人工ERP调拨状态 | 加来源事业部隔离；人工已调拨不能冒充ERP回查 |
| 人工状态证据 | 原簿没有ERP单号、ERP仓代码、ERP建单数量、审核/过账状态或ERP库存快照 | 本轮只能提示待确认，不能证明真实缺单或倒挂 |

原簿自动列随首次时间排序，人工 C/D 和 C 留在原单元格；补历史或重排可能使其错配。将人工值绑定稳定业务键是本轮系统化的首要价值。

## 3. 页面设计

既有“京东入仓监控”保持原功能，新增“京东 POP”子版块：

| 区域 | 展示与动作 |
| --- | --- |
| 调拨与 ERP 确认 | 京东单据、事业部商品、ERP货品、出入仓、调出/实收、京东进度、ERP人工状态、首次/最近业务时间；展开源流水、维护人工状态与备注 |
| 商品映射 | 事业部商品、商家标识、店铺销售平台编码、ERP C/D值、冲突；人工维护与历史查看 |
| 来源与采集设置 | 账号、来源事业部、授权店铺、最近成功批次、导入/核对状态；独立开关、未就绪原因 |

卡片使用“待维护商品映射”“京东已出库，ERP待确认”“部分入库”“人工已确认”。京东进度与ERP人工状态分列。来源不可用、范围不完整、映射冲突分别显示，旧数据必须带上次成功时间；不能把读取失败显示成零待办或核对通过。

京东状态建议：待出库、已出库在途、部分入库、已完成、数量异常、待核对。实收大于调出单列异常，不能沿用原Excel `实收≥调出` 全判完成。人工状态建议：未确认、未调拨、人工确认已调拨、需复核；未知原文本保留并进入需复核，不能只因非空视为完成。

demo 使用明确合成数据，保存仅改变演示状态。禁止演示按钮调用真实 helper、京东、ERP 或外部发送。

## 4. 领域与身份

新权威逻辑建议放 `backend/inventory/jd_pop/`，沿用 inventory reader/writer 与 PostgreSQL。Worker仅做真实principal、输入解析、有界传输与稳定响应。ERP主数据继续由 `erp_reference` 拥有，店铺引用既有受控注册/网店身份，不造竞争事实源。

现有 [公开路由](../../app/api/inventory/inbound-monitor/route.ts) 要求 unrestricted data scope；[库存查询](../../backend/inventory/query.py) 当前基于ERP库存与销售，返回 `nativeComparisonAvailable=false`。新增demo不能改变此真实能力声明。[库存模型](../../backend/inventory/models.py) 的批次、范围头、回执与revision模式可复用，新流水不能塞入旧stock数据集覆盖库存快照。代码检索未找到可直接作为本需求ERP建单事实的现成调拨接口。

身份链为“采集账号 → 来源事业部授权 → 流水/事业部商品”，另以“来源事业部＋平台＋店铺＋店铺商品 → 事业部商品”关联销售归属。账号不等于店铺，商智shopId不等于物流事业部。多个账号能看同事业部时，来源事实只存一份，访问授权和采集尝试分别留存。

店铺筛选只能过滤关联商品；未有逐事件店铺证据时标为“事业部共享流水”，不声称某店独占。同一事业部商品关联多店，汇总仍按来源事件或调拨商品键去重，不能按店复制求和。来源未证实相同不自动合并。初版延续unrestricted scope；后续受限店铺角色须同时验证事业部与店铺权限。

## 5. 表与唯一键（拟议）

编码为字符串，保留前导零；规范键清理尾部制表符/首尾空白，原值保留证据。时间按Asia/Shanghai解释。源行号仅为追溯位置，不作业务键。

| 模型 | 关键内容与唯一约束 |
| --- | --- |
| JdPopSourceBinding | 账号、来源系统、事业部编码、核验名称/时间、授权范围与状态；唯一(account,system,department)；不存凭据秘密 |
| JdPopShopProductLink | 来源事业部、平台/店铺、事业部商品、店铺商品、销售平台编码、ISV编码、商家标识、组合装标志、批次/有效期；完整关系身份待真实导出固定，保留一对多 |
| JdPopProductMapping | 唯一有效(system,department,departmentProduct)；ERP编号/名称、单位/换算、核验状态、人工版本与修改历史 |
| JdPopImportBatch | dataset=flow/shop_products、事业部、精确时间/仓/类型范围、raw/content hash、契约版本、行数/完整性、账号/run/execution、状态/发布时间 |
| JdPopImportScopeHead | 稳定基域锁、owner/fencing、固定长度范围令牌与发布版本；重叠日期范围不能各拿互不相斥的锁 |
| JdPopFlowEvent | 完整源字段、规范身份与证据批次；源稳定事件ID优先。当前源序号未证实稳定，单据号不能单列去重 |
| JdPopTransferProjection | 唯一(system,department,jdDocument,departmentProduct)；流水范围/版本、映射版本、规则版本、出入量、进度与冲突 |
| JdPopTransferManualState | 同一调拨商品键唯一；人工状态/备注、actor/time、CAS版本、确认时流水摘要；新增流水后标为需复核 |
| JdPopAudit | 对象键、真实actor、requestId、前后摘要、版本与结果；流水替换不删除人工历史 |
| JdPopCollectionPolicy | 账号/事业部/数据集范围、物流能力与自动采集开关、版本；默认false，新店不继承true |

稳定事件ID尚待实证。没有ID时，不能把“单号＋商品＋时间”宣称绝对唯一，也不能折叠完全相同的合法重复事件。优先以完整范围版本集合替换：指纹保留完整规范业务行及其多重次数；重叠窗口原子替换，禁止简单追加。只有事件身份与源修订规律验证后才采用事件增量更新。

人工映射和人工调拨状态与源集合分离。排序、筛选、补历史不得改变归属；当前范围未出现的旧调拨保留人工历史。数量精度依据实际源契约选择整型或Decimal，不盲目截断。

## 6. API合同草案

以下是系统合同。读用inventory reader，写用writer；导入与人工维护仅operator/admin，并由服务端复核scope。写入有真实actor、requestId、幂等回执、expectedVersion；冲突409。未知参数、跨来源身份和不完整数据拒绝。

通用返回包含 `contractVersion,mode,revision,source{system,departmentCode},coverage{start,endExclusive,warehouses,complete},batchId,observedAt,mappingRevision,warnings,items,pagination`。mode区分demo/live；默认每页50、最大100，范围/筛选数/响应量/时限有界。缺失为null而非0。

| 拟议接口 | 合同要点 |
| --- | --- |
| GET /api/inventory/jd-pop/flows | 参数来源事业部、起止左闭右开时间、仓、商品、业务类型、分页；返回完整库存分量、单据与证据 |
| GET /api/inventory/jd-pop/transfers | 增加京东状态、ERP人工状态、映射状态、店铺筛选；返回稳定调拨商品键、出入量、仓、覆盖与异常 |
| GET /api/inventory/jd-pop/transfers/{id} | 授权内有界源流水、人工历史与规则版本；不泄露其他事业部 |
| POST /api/inventory/jd-pop/imports | dataset仅flow/shop_products；账号引用、核验事业部、精确范围、契约版本、受控文件引用、任务证据；服务端重算SHA与内容指纹 |
| GET /api/inventory/jd-pop/imports/{batchId} | 精确批次身份、范围、行数、完整性、告警、发布版本与落库回查结果；上传成功不等于发布成功 |
| GET /api/inventory/jd-pop/product-mappings | 商品各编码、ERP C/D值、可见店铺、歧义与版本 |
| POST /api/inventory/jd-pop/product-mappings/validate | 预检工作簿或人工候选，报告重复/冲突；不覆盖已确认数据 |
| PATCH /api/inventory/jd-pop/product-mappings/{id} | 维护ERP编号/名称/备注及版本；名称仅核验；修改后使相关投影失效 |
| GET /api/inventory/jd-pop/shop-products | 有界辅助关系；保留一事业部商品多店/多销售编码，不自动展开未确认套装 |
| PATCH /api/inventory/jd-pop/transfers/{id}/manual-state | status、notes、expectedVersion、expectedFlowRevision；物流已变409要求重看；返回人工确认，不生成ERP单据 |
| GET/PATCH /api/inventory/jd-pop/collection-policies | 独立能力/自动采集开关、范围、版本；身份未核实不得启用，新店全关 |

导入事业部须同时核对受控账号授权、实际来源身份、文件事业部字段；客户端填值不构成证明。本轮无真实ERP写接口。未来若接ERP只读证据，应增加独立erpVerifiedState并绑定ERP单号、货品、来源/目标仓、数量、业务时点、核验批次，不把人工状态直接升级为真实核验。

## 7. 核对与防倒挂边界

本轮可表达：“有调拨出库回传，ERP人工状态为空/未调拨 → 京东已出库，ERP待确认”。人工修改后显示“人工确认已调拨”。不能表达“ERP缺单已核实”或“倒挂已发生”。

实际负库存检查源结存V/Y；U/X负变动不是负库存。ERP账实差异仍需要ERP同口径证据。京东实际库存、可用库存、锁定和在途分量分别保存，预占/取消/回传不能按正负净额归零来判一致。

调拨聚合以已核验工作簿规则起步：负向出库回传计调出，正向入库回传计实收。多出仓、多入仓、多商家单据、实收超调出或未知类型单列异常，不取第一个仓静默掩盖。跨日期窗口只见半边调拨时，需补同单历史或披露首次接入边界；证据不全保持待核对。

## 8. 自动下载、幂等与时序

复用 [导入与自动化规范](../规范/导入与自动化.md) 及下载调研列出的京东注册表、全局Chromium锁、n8n execution owner和任务清单模式。物流使用独立协议，不照搬商智shopId、任务标题或日期策略。

1. 新店默认关闭；原商品/商智enabled不构成物流授权。先按已核验事业部去重计划，再关联店铺，避免四账号下载并重复计同一事实。
2. 计划固定runId、executionId、账号、事业部、dataset、exactScope、policyVersion；按来源串行。登录/验证码/身份异常停止，不跨profile回退。
3. 导出前持久化baseline与intent；仅接管本轮唯一精确任务。提交未决保留，不重发、不选最新一条、不跨店复用文件。
4. 文件验证身份、表头、日期边界、数量/编码、全部分页、完整筛选范围、重复语义及raw/content hash。页面观察不能代替下载验证。
5. 幂等身份为inventory域＋dataset＋事业部＋精确范围＋完整规范内容；文件名/行顺序/元数据不产生新批次，业务变化产生新版本。同事业部多账号同内容只增加尝试审计。
6. 流水在已证明完整的时间/仓/类型范围原子替换；店铺商品在精确授权事业部/店铺集合全量替换。移除的旧源关系退出当前版本，人工映射与状态独立保留。
7. 零行只有权威完整空集合证据才可替换；误空、缺页、权限不足、来源失败不清空旧事实。非法预检只记尝试，不占业务指纹。
8. 重叠范围按稳定事业部基域串行锁，独立尝试owner；发布事务续验fencing与版本。迟到旧任务不能覆盖新版本、释放新owner或完成其他尝试。
9. 回查批次身份、行数、范围、指纹与实际选用版本后才报导入成功。下载、导入、投影、人工确认分别记状态；响应丢失按原尝试协调，不重做导出。
10. 业务时间与导入时间分开；较新导入时间不代表较新业务事实。映射有版本/有效期，历史核对绑定当时版本；人工修正重新投影，不改写源证据。

## 9. 默认关闭与通知边界

本轮不实现缺货或待确认通知，不设计推送API或迁移。来源登记、人工映射和演示开关都不构成真实采集/外发。

若未来明确增加ERP待确认通知，另行设计事件/投递账本：事件绑定事业部＋调拨商品键＋规则身份，投递绑定事件＋目标＋消息类型；区分pending/sending/sent/failed/unknown/suppressed，未知外发不自动重发。新流水/人工确认更新事件，停用取消待发候选。这里只保留未来约束，不是本轮实施项。

## 11. 未决与范围外记录

实时C仓和快照C仓已被用户排除；此前只读观察保留在下载调研，不进入本轮接口、表、指标或采用阶段。真实导出请求/附件、事件稳定ID、范围上限、分页导出、零行语义和源修订规律尚未下载实测；两个页面可读不代表自动链路可运行。

事业部多店关系已观察，但精确店铺/平台编码语义、组合装与单位换算仍须实证，不按名称、前缀或值相同合并不同编码。本轮目的是减少漏确认与人工值错位，不声称已解决全部ERP倒挂。
