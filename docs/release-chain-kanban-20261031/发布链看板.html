优先级 3

清理 按用户要求搁置

最小收益。对发布成功率的影响：零。

能删的只剩 1 个文件
  • publish-main-completed.mjs — 无生产 import，不在任何 代码引用 行里，唯一干净的删除项
  • pi150-forward-recovery.mjs — 可达性判断成立，但它是 Q07 点名的 代码引用，删了会让规范失真，须同一次改动更新 Q07
差点误删的三处
  • publish-main-resume.mjs — 唯一的续接实现（有 STARTED 无 SUCCESS 靠它收敛）
  • publish-main-pi-reconciliation.mjs — 保全 Pi 升级失败原因

真正的结论：这份清点九天前已做过并归档在 Q01–Q14，裁决是「下一步应泛化、本轮不改代码」。此后七天该文件又加四次常量，32 → 42。缺的是机制，不是清单。
两条教训
  • 注释不是死活证据。deliberately limited / one exact 描述的是某次受审改动的授权范围，不是代码死活。按注释判死会命中三处唯一的恢复能力
  • 退役 pin 是审核记录，不是当前期望。落后是设计如此 —— pin 出生时就已失配，而被钉文件此后零改动。不该补；退役链连 INTENT 目录都不存在，今天不阻塞任何事
