## 对现方案的判断

| 内容 | 判断与理由 |
| --- | --- |
| AB先采用、之后按新前驱准备C | 合理：先验证完成协议及验收工具，缩小首次采用的定位范围。代价是C首次仍需另一轮严格流程。当前AB已执行，不能换成旧ABC计划；未来未执行批次可另比较组合方案的成本和集中风险。 |
| 严格21步、前后2次备份＋2次隔离恢复 | 首次修改生命周期/备份相关控制链有依据；隔离恢复、业务保全、版本与权限就绪各有独立证明对象。不能把页面200或单次恢复通过当作全流程通过。 |
| Django包未改仍维护停启 | 本批修改控制链，沿用已批准严格维护有依据；摘要未变不足以证明Worker不会改变权限、签名转发、导入/helper或生命周期。不能称现批应自动Worker-only。 |
| watchdog安装、两次自然观察、历史审计保全 | 首次采用需要核验安装副本/配置与新release/fence/PID，保护旧失败/未知不被抹去。未来无变更的重复安装可研究省略条件，自然观察和完整性仍须现场证明。 |

## 优化路线与交付要求

### 第一阶段 P0：使验收目标可证明，减少可预防返工

**工作包1：UI错误与环境证据。** 复用现有A的进程完成协议、B的审计分类及D的运行副本绑定，提前核对浏览器、Python、Playwright、fixture、实际安装来源和版本。每个步骤记录脱敏阶段/断言码、准确进程及后代身份、期限、输出完成状态、请求终态与资源摘要；按具体页面就绪条件等待，避免只依赖笼统networkidle。正常导航主动取消与真正未完成业务请求需不同证据，但不扩大任意ERR_ABORTED白名单。

- 改动入口：[UI审计](../release-integration-review/batch-v2/ui-audit.mjs)、[适配器](../release-integration-review/batch-v2/adapter.mjs)、[只读重试](../../tools/release-readonly-retry.mjs)及当前日志接缝。
- 验收：版本/资源错配、权限失败、业务请求失败、导航/输入替换取消、迟到响应、输出丢失、残留浏览器等负例可被区分；未授权请求和业务写入始终阻断。
- `productionWrites:0`固定输出本身不是独立效果证明。证据不足保留unknown；只有精确零效果或完整完成证据才经原协调入口闭合。现工具仅对封存Status与有限瞬态码重试，UI未知不能直接加入自动重试。独立UI容错协议是另一个待审候选。

**工作包2：前后数据保全目标。** 先将“两个时刻完全相等”“各自可恢复”“合法业务变化”“未授权历史变化”分开。复用B的完整行级身份/内容指纹与原拥有方回执，不在发布工具里另建业务鉴权系统。新增、修改、删除、自然重导以及人工/AI标注都需相应身份、内容与实际来源回执证明；不能按created_at过滤旧内容、忽略活动表或用LSN/WAL独立证明授权。

- 改动入口：[完整比较验证器](../release-integration-review/batch-v2/validators.mjs)，复用 [B已有机制](../release-acceptance-closeout/REPORT.md)。现批仍按原断言，不追写基线、不自动豁免。
- 先验证两个候选：**A：完整快照＋逐项来源差异说明**；**B：另行批准、覆盖整个比较区间的全写入静默窗口**。B必须盘点后台/外部/独立写入口、冻结新请求并排空，不假定现EnterMaintenance已覆盖全部入口和前后快照区间。
- 推荐先复用已有回执与指纹作小范围验证，测量覆盖率、验证成本及静默窗口对业务的影响，再选路线。任一未解释差异仍阻断，不能把“无法证明”包装为合法增量。
- 验收：合法新增/重导可准确归因；未授权修改/删除、标注改变、伪造/缺失回执、截点交错及静默覆盖缺口均拒绝。减少误报不能增加漏报。

### 第二阶段 P1：打通真实准入接缝，改善排期与收尾

**工作包3：C接缝和分项计时。** 当前AB/ABC wrapper每轮复验7918个Python文件后启动外部collector；[封存终审第44行](../release-integration-review/BATCH_V2_FINAL_INDEPENDENT_REVIEW.md)明确没有启用C内存transport。标准transport只接受精确入口及闭包，不能简单加一个参数就缓存任意wrapper。

- 在 [collector wrapper](../release-integration-review/batch-v2/collector.mjs)、[标准准入](../../tools/release-batch-admission.mjs)与 [批次transport](../../tools/release-batch.mjs)之间设计受控接缝；保持Python及源码/工具/环境完整字节核验，研究有界读取、解析/归一化及派生身份复用。原制品、动作前检查、动态身份/权限/就绪/排空保持。
- 验收：编辑器外部改字节、增加启动hook、短期变化后恢复、角色/fence/进程变化、并发、过期或跨批复用均拒绝。记录wrapper、Python、源码/工具、制品、Status、恢复资格各层成本，子项不重复累计。
- 同源码、同制品、同数据规模、同保障做配对测量。C的既往身份阶段秒数不能乘21步当生产收益，也不保证单步毫秒级。

**工作包4：排期和交付组织。** 复用原queue审计，在准备期明确前驱依赖、在途任务、下一cron和排空预算，展示当前阶段/阻塞原因。版本改变后重绑并重新批准，不让多个聊天竞争同一准备目录或生产通道。候选源逐步使用独立、受保护且有生命周期的固定来源，避免跨任务位移。

复用B的离线报告生成，提前固定模板，原journal及回执自动填事实，完成状态由独立核查确定。分开记录“入口可用、必要验收闭合、全部交付完成”；锁外文档收尾仍计入总等待。不能从633毫秒生成样本推导完整交付秒级。未测负载时不规定21点或其他固定最佳时段。

### 第三阶段 P2：持续恢复资格与合格展示路径

**工作包5：日备份＋精确同点演练。** 按 [现有前置方案](../release-fastpath-evidence/DAILY_BACKUP_ADOPTION.md)，在对应工具严格采用后，另行授权更新原唯一调度，不新增第二套备份/轮换。等待自然调度实际成功；选定仍保留且26小时内的点及7天内同点完整恢复，目录/权限/软件/角色/序列等全部有效。

三份策略及两个保护点可能导致已演练的新点次日被淘汰；需要对新的自然点建立绑定演练闭环。新失败/未知不能被旧成功覆盖，不能以手工备份冒充计划成功。本轮没有实时调度资格核验或启用操作。

**工作包6：风险分级和切换矩阵。** 仅完整行为闭包证明的展示改动才考虑Worker-only及恢复证据复用。复用原 `BeginWorkerDrain→StopForRelease→apply→Start→EndWorkerDrain`，gate覆盖全过程，确认新helper/无在途才解除。数据、权限、导入、自动化、生命周期、备份或未知改动仍保持严格保障；旧四文件交互修复在现分类仍strict。

未来可研究“安装/配置未变只复验”及无依赖只读验收与自然等待交叠，先证明无顺序依赖、资源争用及失效竞争；当前21步与重资源串行不变。涉及R2/n8n定义、字节或业务补数时单列证据、恢复和授权，PG备份不代表覆盖它们。

这份方案交付用于后续开发决策，不是生产上线审批、当前未知协调回执或恢复授权。源文件/调用轨迹/实际交换材料已保全；文档链接、原输出与result一致性、JSON、当前批次摘要及截点日志链已核查，没有执行实现回归或生产构建。
