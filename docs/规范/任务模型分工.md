# 任务模型分工

本规范用于本项目 AI 助手的任务选型、子代理派工与独立审查。根 [AGENTS.md](../../AGENTS.md) 是唯一规范入口；这里维护模型分工正文，不另建同名入口。用户当前明确指令优先，工程交付、权限和生产边界仍遵守 [开发与交付](开发与交付.md) 与对应领域规范。

## 当前模型映射（模型变化时优先更新这里）

映射版本：`2026-10-15-v3`。下表是用户确认的选型基线，不是账户可用性保证，也不自动修改当前聊天、自动化或 TERUISI 内置 AI 的模型配置。

执行与审查默认使用 High；表中的 XHigh 角色仅供满足明确条件时局部升级，不是所有复杂任务的默认门槛。默认列与升级条件同时适用：命中条件的相关部分使用升级角色，其余部分继续默认强度。独立审查必须保持新上下文并直接核对证据，不因强度改为 High 而减少必要验证。

| 角色代码 | 职责 | 当前模型 ID | 思考强度 | 已指定备选 |
| --- | --- | --- | --- | --- |
| `routine` | 常规执行与实施步骤细化 | `gpt-6.1-sol` | `high` | 未指定 |
| `complex` | 按条件局部升级的复杂实现与分析 | `gpt-6.1-sol` | `xhigh` | 未指定 |
| `repeat` | 已验证流程的重复执行与固定监控 | `gpt-6-luna` | `high` | 未指定 |
| `decision` | 独立规划、提示词及其他模型未解决事项的咨询 | `gpt-6-astra` | `high` | 未指定 |
| `deep` | 上述职责内特别复杂且仍未解决的推演 | `gpt-6-astra` | `xhigh` | 未指定 |
| `review` | 独立事实或常规逻辑复核 | `gpt-6.1-sol` | `high` | 未指定 |
| `critical-review` | 独立关键逻辑、方案与结论审查，默认 High | `gpt-6.1-sol` | `high` | 未指定 |
| `deep-review` | 按条件局部升级的独立审查 | `gpt-6.1-sol` | `xhigh` | 未指定 |

相同模型承担不同角色不代表必须重复调用。`review`、`critical-review` 与 `deep-review` 表示未参与该部分实现或方案制定的独立审查上下文；只有下文审查条件满足时才创建审查代理。工作类别表只引用角色代码，型号和强度集中在本表维护。普通文案由执行者自行核对；日志需要独立复核时使用 `review`，不设规划咨询角色的例行审查例外。

### 职责范围

- `decision` / `deep` 只负责需要独立产出的规划或方案、提示词，以及其他执行或审查模型解决不了的具体事项。交付规划、提示词或难题结论后，把实施与验证交回执行角色；不承担常规编码、数据整理、普通文案、发布、监控或例行审查。
- 常规与关键审查分别由 `review` / `critical-review` 独立完成；需要局部深度推演时按条件使用 `deep-review`，不因任务重要就自动调用规划咨询角色再审一遍。审查中仍有无法解决的明确问题，才向 `decision` 定向咨询；咨询结论返回原审查者核验，不替代审查完成条件。
- “写规划”指需要目标、路线、边界和取舍的独立方案。执行者整理实施步骤、列简短计划不必另开规划代理。普通文案归执行角色；用户要求生成或实质改写提示词时，使用提示词角色。

### 读取与实际调用

1. 每次任务开始，以及重新派工、恢复中断任务或准备使用新的角色时，读取当前映射与对应类别；同一版本已在当前上下文中读取的内容可复用，不反复加载整份历史。发现规范或映射版本变化时重新读取。工作树落后于最新主线时按根入口读取最新规范，保留已有改动。
2. 派工前核对当前工具/客户端实际允许的模型 ID、思考强度和所需工具。请求中明确传递目标模型与强度，不依赖默认继承；根据调用回执或可见配置如实记录“请求模型”和可确认的“实际模型”。工具未返回实际模型时标明未独立确认，不冒称已切换。
3. 主代理已符合目标角色时直接执行。主代理型号不匹配且工具支持模型指定时，可按本规范创建一名目标执行子代理，主代理仅负责必要协调和交付；不为维持主代理参与而重复完成子任务。客户端限制需要新上下文时，使用精简交接，并保留适用规范的必读要求。
4. 文档不能自行切换当前主聊天的底层模型。工具不支持指定模型、目标模型不可用或强度不支持时，明确报告差异；仅使用表中已指定且适用的备选。未指定备选时继续不依赖该模型的工作，将需要选型决定的部分交用户处理，不静默降级、不声称等效，不通过开启额外用户聊天绕过限制。
5. 本规范明确要求：在类别表的独立审查条件或升级条件满足时，调用相应角色的子代理；常规低影响任务保持单代理。派工授权仅涵盖当前任务范围，不扩展生产操作、数据写入、外部发送或跨聊天联系权限。子代理不得擅自继续转派。

## 按工作类别选择角色

先按工作类别选择默认安排，再根据实际不确定性、耦合范围、错误代价与验证难度升级。混合任务只升级需要更强判断的部分，不把整项任务机械套用最高档。固定计算、数据校验和轮询优先程序执行。

“方案同执行”表示同一代理细化已有方向并连续完成；确需独立规划时，规划部分交 `decision`，实施仍由执行角色负责。“按条件审查”在条件未满足时由执行者完成必要核对和验证，不额外派工。下表非规划、非提示词事项中的咨询均须满足“执行或审查模型仍无法解决”的条件，不能仅凭出现风险关键词就调用。

| 工作类别 | 方案 | 执行角色 | 审查角色与触发条件 | 升级条件与范围 |
| --- | --- | --- | --- | --- |
| 资料整理与工作日志 | 无需独立方案 | `routine` | `review`：重要事实、工作归属或对外材料需要独立核对时 | 先补充来源证据；独立复核后仍有重要矛盾，交 `decision`。不再重复把任务交给另一执行代理 |
| 文案与提示词 | 普通文案同执行；独立规划用 `decision` | 普通文案 `routine`；提示词 `decision` | `critical-review`：复杂开发任务提示词在正式派工前；普通文案由执行者核对 | 提示词的复杂约束冲突仍未解决时升 `deep`；普通文案仅在执行者无法解决具体难题时咨询 `decision` |
| 数据查询与导出 | 同执行 | `routine` | `critical-review`：新口径、关键多表关联或异常结果影响决策时 | 缺数据先补证；指标定义或关联规则冲突交 `decision`。固定查询核对范围、日期、行数和汇总 |
| Excel 与报告制作 | 同执行 | `routine` | `critical-review`：复杂新公式、匹配逻辑或重要经营结论交付前 | 成本匹配冲突、复杂计算或决策依据不清交 `decision`；固定模板先程序核验值、公式和范围外变化 |
| 经营分析与归因 | 实施分析同执行；需独立分析规划时用 `decision` | `routine` | `critical-review`：重要结论交付前，重点审因果推断、证据缺口和行动建议 | 因果解释冲突先由执行与审查角色核验；补证后仍无法解释的具体问题咨询 `decision`，不因涉及投入就自动追加咨询 |
| 选品与业务规划 | 独立业务规划用 `decision` | `routine`：取数、计算、方案支撑与落地 | `critical-review`：重要方案交付前，核对销量基础、成本假设、利润与资源约束 | 重大投入、两店定位和供应链取舍纳入规划；实施或审查未解决的问题再咨询 `decision`，最终业务取舍由用户决定 |
| 前端与交互开发 | 同执行 | `routine` | `critical-review`：关键业务、金额口径、权限或请求竞争行为改变时 | 复杂口径或并发判断交 `decision`；纯布局和文案调整自行验证 |
| 后端与业务计算 | 实施细化同执行；独立技术方案用 `decision` | `routine` | `critical-review`：业务计算、事务、权限、迁移或历史兼容等关键逻辑变更时 | 复杂事务、金额口径、历史兼容或结构迁移，实现升 `complex`；其中无法解决的具体问题再咨询 `decision` |
| 自动化下载与导入 | 成熟日常流程无需独立方案 | `repeat`，仅限已经验证的流程执行 | `review`：检查规则或一般流程变更；涉及跨店隔离、幂等、写入规则变更时，相关部分用 `deep-review` | 新建或修改流程、导入异常处理改用 `routine`；跨店、重复写入或结果未知时先查证，仍无法解决才咨询 `decision`。此行不把流程开发分给重复执行角色 |
| 恢复重试与任务调度 | `decision` | `routine` | `critical-review`：每次恢复、幂等、并发或调度关键机制变更；审查者独立于方案与实现 | 并发交错、部分成功恢复等需要更深推演时，相关实现用 `complex`、相关审查用 `deep-review`；仍未解决再咨询 `decision`，特别复杂咨询用 `deep`。`repeat` 仅运行已验证步骤，不设计恢复规则；日常运行不重审 |
| 故障排查与性能优化 | 同执行 | `routine` | `critical-review`：重大修复或复杂根因结论，结合复现与前后测量独立核验 | 证据矛盾、跨系统根因，或两轮有实质验证的修复仍未解释同一问题时交 `decision`；缺权限、缺数据先解决证据问题 |
| 发布部署与运行维护 | 实施细化同执行；需独立恢复规划时用 `decision` | `routine` | `critical-review`：异常恢复方案、未知状态下的继续操作或不明确回退路径 | 结果未知、实际前驱冲突或恢复路径不明时先停止相关重放，由执行与审查角色查证；仍无法解决再咨询 `decision`。正常发布一个负责人串行切换 |
| Git 与工作区清理 | 同执行 | `routine` | `critical-review`：删除范围、归属或恢复可靠性存在不能直接排除的疑问时 | 未合并内容、归属冲突或保全不完整先核查，复杂冲突交 `decision`。模型意见不能替代保全与身份核验 |
| 架构设计与系统重构 | `decision` | `routine` | `critical-review`：关键设计采用前及最终关键实现；复审只覆盖增量与直接影响 | 跨模块契约、兼容边界等需要更深推演时，相关实现用 `complex`、相关审查用 `deep-review`；仍未解决再咨询 `decision`，特别复杂咨询用 `deep`。让规划角色提前参与，不等实现结束才找设计问题 |
| 日常监控与固定检查 | 无需独立方案 | 程序检查，`repeat` 汇总 | `review`：检查规则变更或重要完成判定有歧义时 | 异常交 `routine` 排查；未知业务效果、复杂恢复或矛盾证据交 `decision`。状态无变化时不重复升级或提醒 |

新增工作类别先匹配最接近的现有类别；确有不同执行或审查需求时再增加。未填写类别、占位文字或无语义数字不构成新分工。

## 升级判断：区分事实、推理与用户决定

- **事实缺失**：先查权威数据、日志、源码或适用规范；没有资料、没有权限、下载排队、服务不可达本身不是升级模型的理由。强模型也不能补出不存在的事实。
- **推理困难**：已有必要证据，执行或独立审查角色仍无法解决关键规则冲突、状态矛盾、未知写入结果、复杂并发等具体问题，才交 `decision` 定向咨询。应说明已做的查证与尝试，或已有证据为何表明无法解决；不为凑次数重放危险操作，不因一次不确定就升级。不要求普通实施细节、措辞和例行工具选择逐次请示。
- **用户决定**：目标偏好、重大业务取舍或超出当前授权的动作由用户决定，模型提供依据与选项；已授权范围内不重复确认。
- 升级交接应带上明确问题、已查事实、证据位置、已排除假设、候选方案和待决定点。同一未变化问题复用已有结论；新证据或前提变化时才再次咨询，不形成“拿不准就逐级转交”的循环。

## 独立审查与执行边界

1. 审查使用未参与该部分方案或实现的新上下文。型号可以相同，不能让原执行者自称“独立审查”；若关键方案也由审查角色对应模型制定，最终审查仍另开上下文。
2. 审查者默认只读，可在隔离环境做必要验证，不同时修改被审文件、运行生产操作或接管发布。发现问题先返回证据，由明确的执行负责人修复，避免双方争写。
3. 给审查者原始需求、适用规范、目标提交或文件摘要、完整相关差异、直接依赖及验证证据入口。执行者摘要只是线索，审查者必须自行读取必要源码和证据；精简交接不得省略必读规范与关键事实。
4. 每项发现说明触发条件、文件或证据位置、实际影响和建议修复。区分已复现缺陷、证据支持的风险、一般建议与待确认事项；不把假设自动升级成阻断。
5. 修复后复用原审查上下文做增量复审，检查原问题及直接影响。范围或关键假设变化时才扩大审查；真实阻断未解决不能以达到轮数限制为由通过。双方意见冲突用源码、反例或测试协调，不靠投票或“两个模型都同意”。
6. 审查不替代测试、业务回查或用户授权。只覆盖本次改动和直接影响；不把无关问题扩入当前任务，不默认追加全仓审查、全量测试或生产发布后的综合验收。具体交付仍以 [验证与发布](验证与发布.md) 为准。

## 控制协作与 Token 消耗

- 普通任务一个负责人连续完成。复杂任务通常增加一名必要审查者；只有互不依赖、边界明确且确有收益的工作才增加执行子代理。不为查一个文件、跑一条命令或等待同一个外部操作创建新代理。
- 每个子任务明确目标、输入、可改范围、输出、完成条件及资源归属。主代理负责协调与最终交付，不再完整重复子代理的工作；子代理返回结论和证据入口，原日志保留在任务目录，不把全部日志灌入主对话。
- 独立读取和分析可以并行；共用文件、数据库、浏览器会话、运行锁或生产发布操作应串行或明确隔离。遵守宿主实际并发上限，不以增加代理绕过能力或权限限制。
- 保留当前用户选择的强度，不为了表面省 Token 自动改低，也不默认把所有任务开到最高档。只有映射更新、类别升级或用户明确要求才调整。
- 衡量整个任务的主代理与子代理合计用量、总耗时、返工、漏检与人工介入。无法取得用量时如实注明，不估造节省百分比；模型单价下降、缓存命中或并行提速不等于总 Token 下降。

## 更新模型与保持规则一致

1. **确定变更范围**：替换型号或默认强度只改顶部对应角色；工作类别、审查条件或职责改变时才改类别表。多个角色当前使用同一模型，更新时逐项决定是否同步，不按名称全局替换。
2. **核验新能力**：检查当前官方资料及本机工具实际可用性，包括模型 ID、强度、所需工具和账户访问。新型号出现不自动采用，“更新”不代表已在本项目验证更好。
3. **代表任务比较**：选择拟替换角色的一两个代表性任务，在同等输入、验证标准和隔离条件下比较结果、总耗时与可获得用量。关键角色覆盖对应失败或边界情形，不为试模型触发生产写入、外部发送或额外业务补跑。
4. **更新与交付**：在用户已授权的调整范围内更新映射版本、日期、模型 ID、强度和明确的备选；按 [开发与交付](开发与交付.md) 交付。变更理由与验证证据放 `docs/<任务目录>/`，本页只保留当前有效规则。
5. **实际生效核对**：后续派工明确使用新映射；若还维护客户端角色配置或自动化配置，应在对应授权范围内同步并核对实际调用。未接通的配置如实报告，不把文档变更称为运行配置已切换。
6. **在途任务与回退**：进行中的执行或审查不因文件更新突然换模型；在安全交接点记录所用映射版本并决定续接。新方案不满足质量要求时保留证据，恢复已验证映射；业务代码和数据不会因模型映射回退而自动回滚。

Excel 用于收集与审阅选择，确认后的本规范是项目正式依据。后续修改 Excel 须明确合入本规范才成为新规则；记忆仅保存定位和决定，不另存长期竞争版本。本次规则只约束项目助手派工，不自动改 TERUISI 产品内的供应商模型或定时工作流配置。
