# 验证、服务生命周期与发布

路径约定：反引号中的代码、配置和工具路径均相对仓库根目录；Markdown 链接相对本文件。

- 按实际影响分级、绑定完整源码与制品、恢复证据复用及统一批次编排按[发布批次协议](../RELEASE_BATCH_WORKFLOW.md)执行。该协议首次生产采用仍需明确授权并走严格流程；采用前不得提前改变已安装门禁。展示级必须有完整闭包与独立行为证明，冻结／排空原任务后才可 Worker-only 切换；未知影响进入严格级。

- 已采用的 `plan --prepare-online` 只准备候选，必须复验原生效链、已安装入口与前驱精确进程，不能提前改生产保护入口或发放启动许可。Django `PrepareApp` 收据绑定前驱和完整候选指纹；`DeployApp` 仍在维护中复验并切换。应用维护仅通过唯一 Worker 的 `EnterMaintenance -KeepPostgres` 持久声明，普通维护继续完整停机；同域 reader 延迟等待必须由 stack 清理新进程并保留最终完整就绪屏障。后续使用仍需对应生产操作授权。见 `docs/STARTUP_RELEASE_OPTIMIZATION.md`。

- 功能验证只覆盖本次修改及直接受影响的功能、接口和权限路径，运行对应测试和 `git diff --check`；lint、类型和边界检查按改动需要选择，不默认追加 `npm run test:unit`、全仓 `npm run lint` 或无关模块验收。只改文档或离线工具且没有应用载荷变化时无需生产应用构建；文档必须检查链接、命令和当前代码一致。
- 新发布先执行 `npm run release:plan -- --base <当前生产来源提交> --head <候选提交>`，由 Git 完整差异生成绑定提交的范围计划。前端改动只准备 Worker；仅后端改动只准备 Django；只有 Django migration 变化才执行迁移。共享运行库、依赖、配置、发布工具或未知路径升级为完整流程。计划中的验证、打包、数据库保护和部署动作均为必需项，不能人工删减；有效且绑定同一提交与制品的结果可以复用，不重复测试或打包。
- 数据库保护与代码回滚分开判断。无持久化影响的前端 Worker 改动不要求本次数据库备份；后端或 Worker 持久化路径至少核验当前有效备份；真实 migration 必须生成迁移前备份。普通无迁移发布不执行迁移命令，也不为了形式重复生成发布后备份或隔离恢复。
- 历史审查证据保持原字节，不为 lint 改写已归档脚本。`eslint.config.mjs` 对明确列出的 CommonJS 审查夹具采用 CommonJS 语义，仅调整 ESM 风格的 require 导入规则；固定 Node 诊断脚本仅豁免不适用的 Next.js `module` 命名规则。证据仍在扫描中，语法和其他规则保留；应用及范围外脚本保持原规则，范围边界由 `tests/lint-evidence-scope.test.ts` 验证。批次/生命周期夹具必须声明当前协议并显式区分只读和私有写上下文，不能通过降低进程身份、取消或期限断言适配旧测试。
- 验证类别应与实际源码及部署影响匹配。`tools-no-migration-v1` 支持 v3 strict/full 与显式 v4 targeted-first-adoption 的精确十文件发布控制差异、执行工具自身字节及完整 Django 前后清单/库存；它把迁移测试类别替换为迁移闭包核验，不宣称已执行 PG 恢复。v3 保留四数据库阶段；v4 的一次前备份及一次新已安装消费链隔离恢复由独立协议约束，不用于减免旧批准。CF 缓存仅接受逐次封存的精确 hash 与受限传输叶子差异，现场核全部其他字段不变；不设置通用忽略。原限定资格见[限定契约](../release-no-data-adoption-20261011/VALIDATION_QUALIFICATION.md)，新范围见[本次方案](../release-first-adoption-targeted-20261011/DESIGN.md)。
- `npm test` 会先执行生产构建。生产构建会改写 `dist`，而本地预构建 Worker 会监听该目录；构建前必须检查 `127.0.0.1:3000` 是否被本项目服务占用。
- 未经用户在当前对话中明确批准，不得停止、重启或中断本地服务，也不得在运行中的 Worker 监听构建产物时原地构建。当前本机正式 Worker 只能由 `tools/worker-local-service.ps1` 解析并管理不可变 effective head；禁止直接运行 Wrangler、旧 release、`dist` 或 `tools/start-local-worker.mjs`。
- 日常人工启动、`运行项目.bat`、`npm start`、`npm run dev`、登录启动项和桌面控制面板必须统一汇聚到 `tools/worker-local-service.ps1 -Action Start` 这一唯一启动引擎。该引擎先只读核验已部署 Django/PostgreSQL 的全部已启用 reader/writer 与 BI reader；仅在状态明确未就绪时调用既有 Django `Start`，全部回读 ready 后才进入原不可变 Worker release/进程身份门禁。`tools/operations-system-control.ps1` 只提供组合状态、外层非阻塞互斥、日志和最终 HTTP 回查，启动时不得复制 Django 或 Worker 的写入/生命周期逻辑。只有 Worker 内部状态明确为 `stale_or_invalid_receipt`、受保护回执可验证且 supervisor 不存在时，唯一引擎才可通过既有精确回执删除函数清理该回执，并必须回读为 `stopped`；端口占用、身份不明、回执损坏、状态错误或健康异常均失败关闭。
- 一次顶层 Django `Start` 或 `Stop` 中，完整 runtime 后代 ACL 审计只执行一次；同进程子域只能使用临时、不落盘、有界且同时绑定 PID、runtime 路径和部署清单的本轮证据复用完整审计结果，并必须重新验证根 ACL 与应用树。单独子域操作、跨进程、超时、绑定变化或上下文损坏必须回退到完整 ACL 审计，不得使用持久缓存跳过生命周期安全门禁。Worker release 完整性验证可以对文件元数据和内容读取使用有界并发，但不得改变已发布 tree-hash 的 ordinal path/length/content 协议、减少校验文件或放宽重解析点和硬链接门禁。
- 不得为了测试而覆盖本机 PostgreSQL/Django runtime、Worker release runtime、D1/R2、浏览器 profile、下载目录、备份、审计或 `.dev.vars`。测试优先使用临时目录、内存/临时 SQLite 和夹具。
- 未经明确要求，不执行生产部署、远程 D1 迁移、生产数据导入或外部平台真实发送。涉及这类动作时，应先说明目标环境、影响范围和验证/回滚方案。
- 修改注册表、鉴权、导入、市场迁移、缓存或自动化状态机时，必须增加针对失败、重试、重复、跨范围和并发交错的负向测试，不能只验证成功路径。

## 常规发布的三个交付步骤

范围计划确定组件后，后续只保留以下三个交付步骤；`release:plan` 的 `workflow` 按第 4、5、6 步输出对应动作，计划工具只生成清单，不执行合并、构建或生产发布。

4. **验证修改功能**：在隔离 worktree 验证本次修改及直接受影响路径，记录具体功能、测试命令和结果。新增功能覆盖主要成功与失败路径；权限、导入、自动化等变化按其实际影响补充负向检查。共享或未知变化先查明依赖范围，再选择受影响功能验证。没有 migration 变化不运行迁移 dry-run；备份或恢复工具本身变化时，其恢复功能属于本次验证范围。源码和依赖不变时复用有效结果。
5. **合并并生成对应制品**：验证通过后同步最新 `main`；若出现新的相关改动或冲突，只复验受到影响的部分。完成合并、推送并核验远端，在隔离交付树从最终合并提交准备相应 Worker immutable release 或 Django PrepareApp，生产构建在制品准备中只执行一次。准备失败时保留已合并提交并报告“制品未就绪”，不得发布。纯文档、测试或离线工具交付没有应用载荷变化时不生成生产应用包。记录最终提交、制品摘要及可复用验证来源；合并仅改变提交元数据、受测源码与依赖未变化时，不因提交 SHA 变化重跑功能测试。
6. **发布**：有本次明确上线授权且对应制品就绪后，使用既有唯一生命周期入口执行计划中的排空、必要维护和组件切换。只在迁移变化时执行已批准迁移；备份按实际数据影响处理。上线检查限于版本、必需服务就绪及本次修改功能，不重跑开发阶段的完整测试或重新打包。验收通过即完成发布；日志、记忆和闲置工作树清理随交付收尾，不另开业务验收轮次。异常保留原审计和失败状态，按对应恢复流程处理。

上述合并与制品准备属于同一次连续交付，不承诺 Git 推送与构建在技术上原子完成。应用实际部署仍使用现有已安装入口的制品完整性、权限、进程身份及任务排空检查；本流程调整不修改旧已批准批次或旧运行包。

## 发布影响、验证与恢复策略

本节是发布分类与保障的唯一规范正文。具体批次命令、封存与续接见 [发布批次协议](../RELEASE_BATCH_WORKFLOW.md)，在线准备和原生命周期步骤见 [启动与发布](../STARTUP_RELEASE_OPTIMIZATION.md)。已合并源码、已准备候选、实际安装采用和验收通过分别记录；不得用 Restart 代替候选 plan/apply。日常热重启只恢复同一 effective head，不产生新候选采用。

### 事实来源与五项独立判断

先绑定实际生产前驱 source-snapshot、最终组合源码的完整成员集合与所有增删改字节、运行依赖闭包及原前后 preparation receipt 的非源码输入，再独立复审真实构建、启动、部署、观察和消费链。main、分支名、文件名、HTTP GET 或“前端／筛选／只读”标签均不能替代这些证据。缺完整前驱、候选或部署输入时，写“无法据现有证据判定”，保留 full，不做纸面减免。

每个精确候选分别写明：验证强度、数据库保障、维护范围、切换方式、恢复边界。`release-impact.mjs` 的 `requirementsForImpact` 产生测试和验收要求；`recoveryDecision` 决定数据库动作。严格验证可以与经精确资格证明的无迁移闭包并存，维护保留 PostgreSQL 也不代表免备份。它们不得混成一个高／中／低风险标签。

下表的检查类别按本次实际影响选择，常规交付执行上面的三个步骤，不据类别名称追加无关全量测试。已有封存批次的精确检查和数据库操作合同继续保持原语义；新常规范围计划只生成交付清单，不自动改写已安装批次的准入要求。

| 影响与验证 | 数据库保障 | 维护范围与切换 | 恢复边界 |
| --- | --- | --- | --- |
| v2 display：有限展示结构证明＋完整独立闭包复审；impact/UI/权限回归/边界/构建及全部任务验收 | 默认 full；仅全部旧 v2 复用资格有效时 reuse | 原 Worker 排空、精确停止、apply、唯一 Start、解除排空；Django/PG 保持的资格须现场核验 | 兼容应用；旧包已 fence 时走原 successor/恢复入口，不直接启动旧包 |
| 普通 business：经闭包证明的领域行为；domain/contract/negative/permissions/boundary/build及业务深比较 | full 前后备份及同点隔离恢复 | 已安装能力允许时 PrepareApp＋KeepPostgres 应用维护；新旧部署与启动按原门禁 | 兼容前向/应用回退；生产数据恢复须另批精确恢复点、目标和窗口 |

表内 full 表示封存的完整前后 Backup/Verify及同点隔离 Restore 保障，实际操作顺序必须依据该候选依赖与已安装合同批准，不能只按表格自行移动维护内恢复步骤。恢复点的 dump/manifest/SHA、profile、角色/权限、迁移、序列及隔离清理分别核验；生产数据恢复是独立动作。E盘最多三份和保护项规则不因模式变化而改变；数据库备份不覆盖R2附件或整机。

### 常规 full / reuse / not-required

- **full**：未知数据/部署效果、备份机制或受保护路径变化默认走完整保障；缺资格不是“无需保障”。`Start` 未就绪时可能 migrate、复位权限及启动渠道，Worker-only也须在这些原调用前证明后端已就绪，不能因切换名称宣称无副作用。
- **reuse**：仅旧 v2 display。当前唯一日备份 ACTIVE、最近原 installed Backup及E归档/轮换成功且≤26小时；同一仍现存恢复点≤26小时、原Verify通过；同manifest/dump的完整受保护隔离恢复≤7天，内容/角色/权限/迁移/清理与owned序列健康通过；环境、schema、roles、operator、retention、schedule等摘要精确一致。批准前、切换边界、收尾复验；手工备份、旧JSON、被淘汰点或未知最新调度不能替代。资格失效保原批次，安全闭合后重新准备/批准full，不执行中删改步骤。不会为取得reuse自动启用调度或解除保护。
- **not-required**：仅完整 v3 机器证明和精确独立副作用原报告闭合。首版支持既有CSS同选择器/属性/规则结构的受限展示值，以及完整静态、零参数、无导入/事件/表达式/自定义祖先的被动use-client TSX原生文本和有限布局类。新增/删除、自定义组件、局部事件、PNG、Markdown、查询/API、权限、迁移、依赖、启动钩子和备份工具不在v3证明边界内。还需原前后全部非源码环境/运行配置/npmrc/工具链输入相同、Django不变、备份机制不变及精确source/artifact/plan/closure副作用报告，包含布局观察器和文本消费者。声明effects:false不能取得资格。

合格v3不查询日备份、26小时点或7天恢复资格；日调度PAUSED不阻塞这个模式。它只证明本次变化及封存动作没有新增持久效果，允许原正常业务自然写入，不要求全库静止。v3未知效果仍full，不能用reuse填补证明。v2较宽的静态PNG/局部布尔交互边界不能移植为v3 not-required。

### 精确批准的首次采用策略

`teruisi-release-batch-v4` / `teruisi-first-adoption-targeted-v1` 是显式、限定的首次工具采用资格，不是常规第五种风险等级。默认batch仍v3；旧v1/v2/v3批准、WAL和数据库步骤保持原语义。v4维持strict，完整tools-no-migration必须绑定双Django原manifest/全部库存、Worker精确十工具字节闭包、原PG operator/consumer；业务、配置、迁移、依赖不变。完整无迁移资格可将migration-rehearsal替换为migration-closure，但须按`requirementsForImpact`增加targeted-recovery-negative与installed-recovery-consumer，不减其他严格检查。

该限定顺序恰为一次前Backup → 原维护/停止 → Worker apply → Django DeployApp/HardenAcl → 新installed消费链只读规划 → 同一前点的installed隔离Restore → 同ID ExitMaintenance → 唯一Start → 全部原验收/收尾。不能复用此前恢复证据、用prepared旧operator或他点恢复替代。失败/unknown保留原owner、WAL与维护，不自动回放或换不兼容解析器。新候选只有实际满足原精确白名单与闭包才可另提该策略，不能沿用f15的历史批准给任意工具新增改动减免。

采用事实：f15于2026-10-12完成v4限定批次；v3 not-required工具支持随该次采用，普通零DB完整生产周期及净收益尚未实测。永久Status安全修复、全维护Stop选路修复的源码与原冻结运行字节不同，仍须兼容候选采用；旧普通权限Status/Panel不能据源码已合并用作现场诊断。看门狗e033安全wrapper只覆盖其限定路由。原证据见 [基线](../release-pipeline-optimization-20261012/WPB-BASELINE.md)与[最终采用报告](../release-final-closeout-20261012/FINAL_REPORT.md)，不授未来生产操作。

### CI候选规则与证据新鲜度

候选`verify:l0/l1`仅验证已审安全切片，其原完整lint和覆盖缺口保留；候选规则将共享组件/传输至少扩大至L2，将依赖/构建/配置/类型或未知路径扩大为全域L3。候选L2/L3实验基础设施已有局部实测，真实业务HTTP/角色PG/完整应用冷启动仍未验收，保持pending，不作为已完成门禁。合成SQL/静态CSS探针不能替代完整业务或冷启动。

当前main继续适用本页首部的按真实改动范围最小充分验证及[开发与交付](开发与交付.md)原门禁。这里说明候选尚未交付，不是豁免子集实际需要的高级别、生命周期或数据验证；真实影响/依赖要求更强检查时必须在隔离环境完成，无法完成就保留对应候选，不凭拆分或命令名称减免。声明完整、SHA一致或草稿生成时间不证明执行、采用或现场就绪。每动作完整字节/物理路径、精确进程/权限、维护/排空及原新鲜窗口保持；watch只失效。离线报告始终`acceptancePassed:null`，保原失败、未测、未知及reconcile，不用最终成功追认旧exit0。

## 发布包与数据库备份保留

- 发布包保留最近 7×24 小时的完整包；当前运行版本、必要回滚版本及显式保护版本即使超过七天仍保留。历史启动校验依赖的 manifest、successor、activation fence、guard、authority 和审计凭证不按日期删除。仅清理经验证且无进程引用的精确旧包载荷，禁止整目录按时间通删。
- PostgreSQL 使用既有 `pg_dump` custom 格式与一致性快照备份，不新增备份密码或恢复密钥。一个恢复点包含 dump、manifest、SHA-256 校验文件；角色、权限和迁移证据继续按现有归档版本验证。数据库备份不代表已备份 R2 附件或整机配置。
- 备份脚本包含中文路径时使用 UTF-8 BOM，并同时验证 Windows PowerShell 5 和 PowerShell 7 的实际路径、根权限及子文件继承。E 盘归档根使用独立受限 DACL，不得绕过仅限 D 盘 runtime 的权限函数。备份后台启动 Windows PowerShell 5 时固定使用其系统内置模块目录并清除继承的 library-only 标志，不修改全局 `PSModulePath`。加载运维脚本库时隔离参数作用域，避免覆盖调用者的 `Execute`、`Json` 等变量；跨旧代码页传输路径时使用无损的 ASCII 转义 JSON。
- 正式数据库备份保存到 `E:\运营管理系统业务数据`，最多 3 个已验证恢复点；D 盘只作生成和导入校验的临时区。发布前后备份均占名额，必要的迁移前备份作为保护项占其中一个名额，其余按完成时间保留最新。新备份成功、E 盘归档复验完成后才淘汰旧份，过程中允许短暂第四份；失败不提前删旧，不因达到上限解除关键备份保护。保护项占满或证据异常时停止轮换并报告。
- 系统备份管理仅允许无数据范围限制的管理员使用，复用既有备份/Verify/隔离恢复工具。导出交付完整备份包；导入先上传、校验并在独立 PostgreSQL 环境恢复验证。上传或校验不等于生产恢复，恢复生产必须另获用户对精确恢复点、目标与维护窗口的明确确认。
- 发布流程以 `docs/STARTUP_RELEASE_OPTIMIZATION.md` 为准：开发、测试、生产构建及候选准备期间保持生产正常，不修改当前生效入口或运行包。正式切换可在用户批准的短时应用维护窗口进行；不得把在线准备描述为全程零停机。优先保留 PostgreSQL 的应用维护，沿用唯一生命周期引擎和全部原验证/恢复门禁。
- 上述原能力与[批次协议](../RELEASE_BATCH_WORKFLOW.md)组合使用。旧 v2 恢复复用须满足 26 小时恢复点、7 天同点演练、持续日备份及现场目录／权限／软件／保留条件。新 v3 可由完整字节差异与受限部署操作独立证明无新增持久数据影响，封存 not-required 与零 Backup/Restore，不查询上述复用资格；验证强度、组件切换、数据／部署效果和备份机制分别判定。服务端查询、权限、迁移、依赖、启动、备份及未知改动尚无受支持的无数据证明时保持 full，并列明缺口；v2/v3 新规则自身首次采用仍走严格/full；显式新 v4 仅在完整十工具／双 Django 库存资格闭合时使用一次前备份、一次新已安装消费链隔离恢复，严格分类与原生命周期／恢复断言保留，详见批次协议。旧已批准批次和 WAL 不减免、不换绑。完整字节／路径／权限／进程／ready／互斥／排空／动作前验证及业务补数、原任务验收仍计入收尾，不因页面先恢复可用就宣称发布完成。
