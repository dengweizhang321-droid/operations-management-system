# 验证、服务生命周期与发布

路径约定：反引号中的代码、配置和工具路径均相对仓库根目录；Markdown 链接相对本文件。

- 按实际影响分级、绑定完整源码与制品、恢复证据复用及统一批次编排按[发布批次协议](../运维/部署与启动/release-batch-workflow.md)执行。该协议首次生产采用仍需明确授权并走严格流程；采用前不得提前改变已安装门禁。展示级必须有完整闭包与独立行为证明，冻结／排空原任务后才可 Worker-only 切换；未知影响进入严格级。

- 已采用的 `plan --prepare-online` 只准备候选，必须复验原生效链、已安装入口与前驱精确进程，不能提前改生产保护入口或发放启动许可。Django `PrepareApp` 收据绑定前驱和完整候选指纹；`DeployApp` 仍在维护中复验并切换。应用维护仅通过唯一 Worker 的 `EnterMaintenance -KeepPostgres` 持久声明，普通维护继续完整停机；同域 reader 延迟等待必须由 stack 清理新进程并保留最终完整就绪屏障。后续使用仍需对应生产操作授权。见 `docs/运维/部署与启动/startup-release-optimization.md`。

- 候选改变 Django 控制器或 supervisor 脚本时，发布前同时核对已安装看门狗 driver 绑定和持久 supervisor 状态的版本兼容性，提前准备配套诊断候选及必要的受控状态迁移。旧 stopped 状态只有在精确前驱、无原进程/回执、原生命周期互斥及已完成维护条件下才能原样归档，由原构造器创建新状态；不得泛化接受 `app.previous` 摘要或直接改旧绑定。自然监控观察应从原任务已结束、下一轮尚未开始的窗口启动，避免把窗口前开始、窗口内才写出的样本误当作新观察；原失败证据与新鲜度断言保持。

- 功能验证只覆盖本次修改及直接受影响的功能、接口和权限路径，运行对应测试和 `git diff --check`；lint、类型和边界检查按改动需要选择，不默认追加 `npm run test:unit`、全仓 `npm run lint` 或无关模块验收。只改文档或离线工具且没有应用载荷变化时无需生产应用构建；文档必须检查链接、命令和当前代码一致。
- 新发布先执行 `npm run release:plan -- --base <当前生产来源提交> --head <候选提交>`，由 Git 完整差异生成绑定提交的范围计划。前端改动只准备 Worker；仅后端改动只准备 Django；只有 Django migration 变化才执行迁移。共享运行库、依赖、配置、发布工具或未知路径升级为完整流程。计划中的验证、打包、数据库保护和部署动作均为必需项，不能人工删减；有效且绑定同一提交与制品的结果可以复用，不重复测试或打包。
- 数据库保护与代码回滚分开判断。后续结构迁移按[备份与恢复约定](#后续结构迁移的备份与恢复约定)取消迁移前后全库备份和隔离恢复，不因存在 migration 自动追加这些步骤。无持久化影响的前端 Worker 改动不要求本次数据库备份；其他后端或 Worker 持久化路径按实际数据影响核验当前有效备份。普通无迁移发布不执行迁移命令，也不为了形式重复生成发布后备份或隔离恢复。
- 历史审查证据保持原字节，不为 lint 改写已归档脚本。`eslint.config.mjs` 对明确列出的 CommonJS 审查夹具采用 CommonJS 语义，仅调整 ESM 风格的 require 导入规则；固定 Node 诊断脚本仅豁免不适用的 Next.js `module` 命名规则。证据仍在扫描中，语法和其他规则保留；应用及范围外脚本保持原规则，范围边界由 `tests/lint-evidence-scope.test.ts` 验证。批次/生命周期夹具必须声明当前协议并显式区分只读和私有写上下文，不能通过降低进程身份、取消或期限断言适配旧测试。
- 验证类别应与实际源码及部署影响匹配。`tools-no-migration-v1` 支持 v3 strict/full 与显式 v4 targeted-first-adoption 的精确十文件发布控制差异、执行工具自身字节及完整 Django 前后清单/库存；它把迁移测试类别替换为迁移闭包核验，不宣称已执行 PG 恢复。v3 保留四数据库阶段；v4 的一次前备份及一次新已安装消费链隔离恢复由独立协议约束，不用于减免旧批准。CF 缓存仅接受逐次封存的精确 hash 与受限传输叶子差异，现场核全部其他字段不变；不设置通用忽略。原限定资格见[限定契约](../release-no-data-adoption-20261011/VALIDATION_QUALIFICATION.md)，新范围见[本次方案](../release-first-adoption-targeted-20261011/DESIGN.md)。
- `npm test` 会先执行生产构建。生产构建会改写 `dist`，而本地预构建 Worker 会监听该目录；构建前必须检查 `127.0.0.1:3000` 是否被本项目服务占用。
- 未经用户在当前对话中明确批准，不得停止、重启或中断本地服务，也不得在运行中的 Worker 监听构建产物时原地构建。当前本机正式 Worker 只能由 `tools/worker-local-service.ps1` 解析并管理不可变 effective head；禁止直接运行 Wrangler、旧 release、`dist` 或 `tools/start-local-worker.mjs`。
- 日常人工启动、`运行项目.bat`、`npm start`、`npm run dev`、登录启动项和桌面控制面板必须统一汇聚到 `tools/worker-local-service.ps1 -Action Start` 这一唯一启动引擎。该引擎先只读核验已部署 Django/PostgreSQL 的全部已启用 reader/writer 与 BI reader；仅在状态明确未就绪时调用既有 Django `Start`，全部回读 ready 后才进入原不可变 Worker release/进程身份门禁。`tools/operations-system-control.ps1` 只提供组合状态、外层非阻塞互斥、日志和最终 HTTP 回查，启动时不得复制 Django 或 Worker 的写入/生命周期逻辑。只有 Worker 内部状态明确为 `stale_or_invalid_receipt`、受保护回执可验证且 supervisor 不存在时，唯一引擎才可通过既有精确回执删除函数清理该回执，并必须回读为 `stopped`；端口占用、身份不明、回执损坏、状态错误或健康异常均失败关闭。
- 一次顶层 Django `Start` 或 `Stop` 中，完整 runtime 后代 ACL 审计只执行一次；同进程子域只能使用临时、不落盘、有界且同时绑定 PID、runtime 路径和部署清单的本轮证据复用完整审计结果，并必须重新验证根 ACL 与应用树。单独子域操作、跨进程、超时、绑定变化或上下文损坏必须回退到完整 ACL 审计，不得使用持久缓存跳过生命周期安全门禁。Worker release 完整性验证可以对文件元数据和内容读取使用有界并发，但不得改变已发布 tree-hash 的 ordinal path/length/content 协议、减少校验文件或放宽重解析点和硬链接门禁。
- 不得为了测试而覆盖本机 PostgreSQL/Django runtime、Worker release runtime、D1/R2、浏览器 profile、下载目录、备份、审计或 `.dev.vars`。测试优先使用临时目录、内存/临时 SQLite 和夹具。
- 未经明确要求，不执行生产部署、远程 D1 迁移、生产数据导入或外部平台真实发送。涉及这类动作时，应先说明目标环境、影响范围和验证/回滚方案。
- 修改注册表、鉴权、导入、市场迁移、缓存或自动化状态机时，必须增加针对失败、重试、重复、跨范围和并发交错的负向测试，不能只验证成功路径。

## 常规发布的三个交付步骤

范围计划确定组件后，后续只保留以下三个交付步骤；`release:plan` 的 `workflow` 按第 4、5、6 步输出对应动作，计划工具只生成清单，不执行合并、构建或生产发布。

4. **验证修改功能**：在隔离 worktree 验证本次修改及直接受影响路径，记录具体功能、测试命令和结果。新增功能覆盖主要成功与失败路径；权限、导入、自动化等变化按其实际影响补充负向检查。共享或未知变化先查明依赖范围，再选择受影响功能验证。没有 migration 变化不运行迁移 dry-run；备份或恢复工具本身变化时，其恢复功能属于本次验证范围。源码和依赖不变时复用有效结果。
5. **合并并生成对应制品**：验证通过后同步最新 `main`；若出现新的相关改动或冲突，只复验受到影响的部分。完成合并、推送并核验远端，在隔离交付树从最终合并提交准备相应 Worker immutable release 或 Django PrepareApp，生产构建在制品准备中只执行一次。准备失败时保留已合并提交并报告“制品未就绪”，不得发布。纯文档、测试或离线工具交付没有应用载荷变化时不生成生产应用包。记录最终提交、制品摘要及可复用验证来源；合并仅改变提交元数据、受测源码与依赖未变化时，不因提交 SHA 变化重跑功能测试。
6. **发布**：有本次明确上线授权且对应制品就绪后，使用既有唯一生命周期入口执行计划中的排空、必要维护和组件切换。只在迁移变化时执行已批准迁移；备份按实际数据影响处理。发布后只确认本次部署成功、目标版本已切换及必要服务可用，完成即报告上线；不另设“整体验收”阶段，不重跑发布前的功能验证或重新打包。日志、记忆和闲置工作树清理随交付收尾，不另开业务验收轮次。异常保留原审计和失败状态，按对应恢复流程处理。

上述合并与制品准备属于同一次连续交付，不承诺 Git 推送与构建在技术上原子完成。应用实际部署仍使用现有已安装入口的制品完整性、权限、进程身份及任务排空检查；本流程调整不修改旧已批准批次或旧运行包。

### 默认人工点击发布

- 固定 `.bat` 是跨任务使用的 main 发布入口。每次点击先获取远端 `refs/heads/main`，记录并冻结本次完整目标提交，再生成独立来源与发布请求；单次执行中不再漂移目标。不得让旧任务的 `completedTask`、固定旧 source、旧续接模式或历史 `SUCCESS` 截断新提交。远端获取失败即停止，不静默回退旧 main。
- 显示状态必须区分：检查/准备不等于发布；目标提交已与当前实际组件、真实完成回执及就绪状态一致时，只显示“当前已是目标版本，本次没有发布”；只有本次实际部署完成、对应目标的原生成功回执及版本/服务确认通过后，才显示“发布成功”。有 `STARTED` 无成功结果、维护/排空未退出或半切换状态必须先协调，不能按已安装的版本元数据直接视为完成。

- 用户要求合并当前任务时，负责人完成本次必要验证、main合并和推送，再交付直接构建发布main的一键 `.bat`，由用户手动点击上线；不默认执行生产切换，也不要求用户再次召回 Codex 执行发布。只有用户当前明确要求 Codex 代为发布时，才使用该次授权执行。
- 默认针对合并后的 `main` 生成手动入口，允许用户双击时按冻结的 main 提交直接构建、部署、执行必要结构迁移并启动；不再默认采用多任务组合或在交付 BAT 阶段添加全量测试、多轮重复复审、全库备份与恢复演练。已通过的相同范围验证复用。保留编译/部署失败即停、必要版本与前驱、普通权限、唯一生命周期入口、排空、互斥及未知结果保护；这些必要检查不泛化为额外综合验收。
- 手动入口显示进度和成功/失败状态，保存原始步骤日志。重复点击已成功的同一包不再部署；已有开始记录但结果未知时停止并给出日志位置，不自动重放。交付“准备就绪”与用户实际“上线成功”分别报告。

### 自动提前打包、人工切换

- `查看打包状态.bat` 是独立只读观察窗口：每5秒查看本机已获取的origin/main、对应冻结请求和原生准备记录。用户打开后可最小化等待，完成或需处理时显示本地弹窗；关闭观察窗口不影响后台准备，也不再接收该窗口提醒。查看器不fetch、不触发准备、不获取发布锁或执行部署。准备开始记录可能因中断保留，不能把其存在当作进程仍在运行；未知发布优先提示处理，准备完成不等于上线或原生现场准入。
- 本机安装 `tools/install-main-prebuild.mjs --config <固定入口配置绝对路径>` 后，Git `reference-transaction committed` 只监听 `refs/remotes/origin/main` 的非删除更新。成功推送或获取远端 main 后，由普通用户的隐藏 Node 进程执行 `--prepare-only`；不使用模型或定时轮询，不进入维护、排空、切换、迁移或启动。远端由其他机器更新、尚未 fetch 到本机时不会触发。
- `准备main.bat` 可手动执行同一准备流程。固定 `发布main.bat` 仍每次 fetch 并冻结最新 main，但只消费对应的已准备包；尚未准备好时明确停止，不使用旧包、不现场重新打包。一次执行冻结后不随之后的 main 更新漂移。原迁移/依赖变更的专用准备边界保持。
- 准备的 `preparation/PREPARING.json`、原子发布的 `PREPARED.json` 与部署 `STARTED.json`、`SUCCESS.json` 分开。准备结果绑定请求、完整提交和源码树、真实前驱、原生 Worker plan 与 Django PrepareApp 凭证；正式发布前复用原 Worker 完整验证及 Django `VerifyPreparedApp`/`DeployApp` 检查。准备中断或发布结果未知保留原记录，不自动重放；无成功回执不能显示发布成功。
- 本机触发票据按原始 SHA 与终态结果关联，由随进程退出释放的命名管道串行消费，合并同一轮更新，退出锁后重查新事件。队列不授予生产切换权限；准备失败保留日志，手动发布不会把失败状态转成成功。
- 同一精确准备包复用其已经安装并完整验证的依赖，不再次运行 npm ci。新准备包继续使用既有离线 tarball cache 和原 npm ci；不增加需要跨包完整扫描及复制 node_modules 的目录缓存。构建末尾在同一私有 staging 卷转移依赖目录，省去重复复制，目标树仍完整复验。
- 准备和发布通过同一固定实际环境启动，移除 Git 本地变量及 shell 注入差异，原生完整环境哈希规则不变。准备包及必要原生收据仍按既有完整性与 ACL 规则处理。预打包缩短点击后的等待，减少复制才减少总准备工作；具体收益按分项日志实测，不预设分钟数。
- 固定入口安装时保存有限白名单Windows基底，后续升级复用；自动准备与人工发布不重新继承各自窗口的基底值。显式覆盖libuv的Windows必需变量（包括LOGONSERVER及其空值），用真实子进程验证一致性，不只比较传给spawn的对象。基底不包含全量shell、秘密或NODE_OPTIONS；原生仍核完整实际环境指纹。
- 已注册的结构迁移随包自动纳入：`config/main-schema-releases/` 保存有限 recipe，绑定唯一迁移字节、前后代际、真实隔离 PostgreSQL 证明及安装器摘要。当前支持 `inventory.0016_jd_product_monitoring` 的精确147→148；未知、新增或改写的其他迁移仍须由对应任务补齐并审查其有限安装器与 recipe，不自动放行任意 migration。任务负责人将这些材料随合并交付，不需要用户跨聊天传话。
- 自动准备只读核验147父链和当前应用清单，生成本次冻结来源专属 evidence，再经原 `PrepareApp` 准入；不连接生产数据库、不执行迁移。正式手动点击时先复核同包及证据，按原同ID维护执行 Plan→DeployApp/HardenAcl→Install/Finalize→Worker apply→Start。成功回执保留同operation/maintenance及原生结构安装结果；未知保留原意图、维护及日志，不重放或自动反向迁移。后续普通启动允许用户保存非空监控配置。

### 发布完成的判定

- 常规发布以本次部署动作成功、目标组件版本正确、必要服务可用为完成条件。代码审查和本次修改功能验证在发布前完成；同一源码、依赖及制品的有效结果直接复用。
- 不把全量公开资源摘要比对、全权限复验、全业务接口深比较、无关 n8n 工作流核对、全组件综合状态扫描或等待自然看门狗轮次列为每次上线的固定完成条件。相关领域发生实际改动时，按影响范围在发布前完成对应验证，不扩为发布后的独立综合验收。日常监控继续按既有配置运行。
- 真实业务补跑、五表导入及其批次、日期和数据归属核验按独立业务任务处理，须有对应授权；不得用“已上线”表示这些业务已成功，也不以补跑成功作为常规发布完成的前提。
- 本规则用于常规发布流程和新范围计划，不通过文档更新删改已封存批次、跳过既有执行入口的内部检查或把失败／未知状态标为成功。若工具仍按旧合同执行综合验收，应如实说明工具行为与新规范的差异；文档变更本身不修改正在执行的批次。

## 统一发布交付契约

契约版本 `release-delivery-contract-v1`。本项目所有主代理、实施代理、审查代理及发布负责人均须遵守；用户当前明确指令优先。契约规定交付动作与证据，不创建新的生产执行协议，不改写已封存批次、旧批准、已安装入口或权限边界。[工作单与工具接入模板](../运维/部署与启动/release-delivery-templates.md)只引用本节，不另存竞争规则。

### 职责与发布就绪

一个负责人串行集成和发布；实施者交付其范围的源码与验证证据，独立审查者不得把自审称为独审。其他代理不得并行操作同一生产锁、队列、部署目录或批次。已有本次范围授权且就绪时直接执行，不重复询问；缺少生产授权时，先完成可审查的就绪材料，再一次提出精确范围的确认。

发布按下表推进，工作单的“已就绪”是证据完整性声明，不是生产授权、动态健康证明或新的启动许可。缺项仅暂停依赖它的动作，其余独立工作继续；对不适用项记录范围计划和理由，不为填表增加无关测试。

| 阶段 | 必须完成的动作与产物 | 未满足时 |
| --- | --- | --- |
| 合并前验证 | 按实际影响验证修改和直接受影响路径，完成所需独审；提前核对发布入口/控制器/看门狗兼容性，准备适用的异常分支、只读取证脚本及续接/回退边界 | 不以合并、制品生成或历史运行快照代替功能验证 |
| 异常预案审定 | 使用已有已验证流程时核其源码、调用参数及候选兼容性并复用有效证据；本轮新增或改变恢复机制时，在隔离环境验证成功、提交丢回执、确定未提交、未知、部分切换及适用的取消/迟到响应分支，由独立角色审查 | 不把通用try/catch、重发POST、后来版本看似正确或延长超时当恢复方案；不得为演练中断生产 |
| 合并并准备制品 | 按原第5步完成main合并/推送与对应制品准备；先核完整组合来源和受保护入口差异，冻结源码/依赖/配置/工具及字节，再生成制品、发布/回退计划和必需的数据保障证明 | 制品未就绪就报告缺口，不进入维护；不在准备后临时加入注释、行尾或配置变更并沿用旧收据 |
| 最终就绪包 | 记录实际生产来源、合并的应用提交、最终组合发布来源、完整差异范围、对应Worker/Django制品/收据摘要、适用测试和独审、异常预案及工具摘要、精确操作顺序、数据策略与预备收尾清单 | 缺失或绑定不一致不能声明就绪；main后续纯文档/元数据变化不自动要求重建字节未变且原绑定仍有效的候选 |
| 现场准入与发布 | 授权后通过既有唯一入口即时核实际前驱、进程创建身份、权限、互斥、owner、门禁、排空及原新鲜度要求；只执行范围计划对应组件、迁移及数据保障动作 | 现场事实与已审前提冲突时不沿用旧成功；忙/未就绪等待照实计时，不能删除owner或改身份抢占 |
| 必要上线确认 | 原操作成功回执、目标组件版本和必要服务可用均满足原完成判定，明确已采用与未采用内容 | HTTP200、running或静态摘要本身均不证明某个原操作成功；未知不能报告完成 |
| 必要交付收尾 | 发布前预备输出目录、文档骨架、证据文件清单、精确Git路径与闲置工作树清理范围；成功后填入真实回执/计时，核查原始证据，完成聚焦提交推送、保全、记忆及符合清理条件的归档 | 未完成/仍被占用的清理如实列为未完成；不以稍后完成时间回填更早的“全部完成” |

生产构建只在制品准备中执行一次；原源码、依赖、制品和验证绑定仍有效时直接复用结果。任何候选实际内容或前驱变化按原规则失效并补充相应准备/审查，不因赶时限忽略差异。前端只处理Worker，后端只处理Django，只有migration变化才执行迁移；共享/未知变化按既有完整流程，不用拆文件、改路径或声明“离线”绕过范围计划。纯文档、测试或没有应用载荷变化的离线交付按原非生产规则完成，不为其重启服务或构建应用。

### 异常后的事实核对与安全续接

合并前审定的是取证方法、判断条件和分支；某次故障的真实结果只能在故障后确认。预审结论可在精确前提不变时复用，**原执行协议要求的独立现场只读观察/协调仍须执行**，不能用预审替代新鲜事实或冒称任何人的独立观察。

| 观察结果 | 必需依据 | 允许动作 |
| --- | --- | --- |
| 原操作已完成、回执曾丢失 | 原请求/操作与批次身份、精确任务或组件、目标状态/版本、原回执与审计/消费记录相互关联 | 按原协调入口复用精确完成结果，跳过已确认步骤；保留原失败/unknown原件 |
| 确定未产生本次作用 | 满足预审的本阶段零效果条件和原协议要求；关联原操作、进程退出及其可能的迟到效果、前驱/完整入口与activation fence、owner/门禁、审计及后续步骤等适用证据 | 经原协议协调后，才按同一意图和原身份进入已审重试分支；次数/间隔按已批准方案，不泛化自动重放 |
| 未知、证据缺失或相互矛盾 | 原started/unknown、已保存输出/进程证据及缺口 | 保留owner、门禁、原日志与未完成状态，停止依赖该结果的新写入；完成定向查证，超出已审分支时追加相应独审 |
| 已开始切换但未闭合 | 完整入口/fence、原前驱与successor、consumption、回执和持久owner等本阶段适用证据 | 走原协调/恢复协议；旧head仍在不能单独证明零效果，不手工写回受保护入口或再apply |

取消等待不证明服务端取消；不能盲目结束身份不明的子进程、删除记录、创建新任务/操作身份或切换解析器来掩盖unknown。现场新增问题先查清其与目标功能、数据正确性或恢复的关系，只处理真实阻断，不把无关重构、监控完善或一般建议插入交付。

### 计时、预算与完成报告

同时记录原始上线授权、开发/验证、合并/准备、发布就绪、实际发布尝试、异常/续接、上线确认和交付完成时间。用户在开发前已授权时，原授权至完整交付的总等待一直保留；不得把较晚的“就绪”时间改成原授权时间。另列就绪后的发布执行跨度，准备前移、等待互斥、人工协调和收尾均如实呈现。并行阶段按区间并集合计，父子耗时不重复相加，未采样空档不补成执行或停服。

**15分钟是已验证且制品就绪版本的常规发布交付优化目标，包含该次发布的必要收尾；不是强制终止时限、稳定性能承诺或门禁豁免。**参考预算为现场发布/必要确认13分钟、必要收尾1分钟、波动余量1分钟，须以实际测量验证。迁移、真实数据恢复、长在途任务或超出预审范围的异常应另报窗口与原因，实际等待仍保留在原总计时。预算超出时及时报告当前阶段、状态、剩余动作及原因，不以吞错、缩减验证、自动重试或先报“全部完成”达标。

只核对本次部署成功、目标版本正确和必要服务可用，不另加全组件综合验收或重复功能测试。自动报告必须区分已采用、准备就绪、候选、未执行、失败与未知；实际采用事实来自原操作和必要观察，报告生成本身不产生成功。性能优化先细分Worker校验/切换、服务启动等剩余成本，已存在的在线准备、同域读写重叠、同次ACL复用及有界并发不重复算作新增收益；跨域并行、跨进程权限缓存和放宽校验不因本契约获得采用授权。

### 现有工具与自动化边界

优先复用 `tools/release-scope-plan.mjs` 的完整差异范围、适用版本 `tools/release-batch.mjs` 的原封存/检查/执行/状态及导出的协调接口，以及 `tools/release-closeout-report.mjs` 的离线证据草稿。先核实际已采用能力；候选协议不能仅凭文档存在而当生产入口。批次工具没有通用reconcile CLI；需要原已审适配器调用其导出接口，不编造命令或现场编写未经审查的恢复实现。

收尾工具要求其支持的原batch、连续原WAL及精确回执绑定；其他发布入口只有独立操作回执时，按模板保留原格式生成交付说明，不伪造batch/WAL来凑输入。工具生成的 `acceptancePassed:null`、草稿及历史观察不变成生产验收、当前健康或关闭批次的证明。Git提交/推送和工作树归档仍走原工具与精确范围；本契约没有声称现有报告工具会自动执行这些动作。

本节和模板对代理行为生效；其额外准备项、独审适用判断及跨工具收尾完整性，当前由负责人/审查者据证核验，**不宣称新增字段已被底层执行器自动强制**。后续确有高收益工具缺口时单独实施、隔离验证、审查及按实际范围准备/采用，不为本轮契约改写运行包或另造发布系统。

## 发布影响、验证与恢复策略

本节是发布分类与保障的唯一规范正文。具体批次命令、封存与续接见 [发布批次协议](../运维/部署与启动/release-batch-workflow.md)，在线准备和原生命周期步骤见 [启动与发布](../运维/部署与启动/startup-release-optimization.md)。已合并源码、已准备候选、实际安装采用和验收通过分别记录；不得用 Restart 代替候选 plan/apply。日常热重启只恢复同一 effective head，不产生新候选采用。

### 后续结构迁移的备份与恢复约定

- 后续数据库结构迁移发布取消迁移前、迁移后的全库备份及全库隔离恢复，不再将这些动作作为默认发布步骤、准入条件或完成条件；不因 migration、models/SQL 或 strict 分类重新追加。结构变更具有持久效果，取消这两类动作不等于证明“零数据影响”，也不套用旧 v3 无持久效果资格。
- 仍在隔离环境使用独立结构和合成数据验证本次结构变更、兼容性、权限及直接受影响功能；不为结构迁移验证复制正式业务数据或执行全库 dump/restore。业务数据处理范围按[数据存储与迁移](数据存储与迁移.md)单独安排。
- 日常备份、既有恢复点的保护与保留、单独授权的备份或生产恢复继续独立管理。本约定不关闭备份调度、不删除已有恢复点，也不自动授权业务数据处理或生产恢复。
- 此约定适用于后续新发布；不通过文档修改追改在途或已封存批次的步骤、审计和结果，也不直接改变已安装工具门禁。新发布准备时应核对执行工具与此约定的一致性，提前处理旧工具仍强制全库备份/恢复的兼容问题，不能现场伪造证据、绕过门禁或静默补回已取消的默认步骤。

### 事实来源与五项独立判断

先绑定实际生产前驱 source-snapshot、最终组合源码的完整成员集合与所有增删改字节、运行依赖闭包及原前后 preparation receipt 的非源码输入，再独立复审真实构建、启动、部署、观察和消费链。main、分支名、文件名、HTTP GET 或“前端／筛选／只读”标签均不能替代这些证据。缺完整前驱、候选或部署输入时，写“无法据现有证据判定”，保留 full，不做纸面减免。

每个精确候选分别写明：验证强度、数据库保障、维护范围、切换方式、恢复边界。`release-impact.mjs` 的 `requirementsForImpact` 产生测试和验收要求；`recoveryDecision` 决定数据库动作。严格验证可以与经精确资格证明的无迁移闭包并存，维护保留 PostgreSQL 也不代表免备份。它们不得混成一个高／中／低风险标签。

下表的检查类别按本次实际影响选择，相关功能验证在发布前完成，常规交付执行上面的三个步骤，不据类别名称追加无关全量测试或发布后的独立综合验收。后续结构迁移优先适用上节的新约定，表内既有 full 要求不覆盖该范围；其他范围仍按实际影响判断。已有封存批次的精确检查和数据库操作合同继续保持原语义；新常规范围计划只生成交付清单，不自动改写已安装批次的准入要求。

| 影响与验证 | 数据库保障 | 维护范围与切换 | 恢复边界 |
| --- | --- | --- | --- |
| v2 display：有限展示结构证明＋完整独立闭包复审；impact/UI/权限回归/边界/构建及全部任务验收 | 默认 full；仅全部旧 v2 复用资格有效时 reuse | 原 Worker 排空、精确停止、apply、唯一 Start、解除排空；Django/PG 保持的资格须现场核验 | 兼容应用；旧包已 fence 时走原 successor/恢复入口，不直接启动旧包 |
| 普通 business：经闭包证明的领域行为；domain/contract/negative/permissions/boundary/build及业务深比较 | full 前后备份及同点隔离恢复 | 已安装能力允许时 PrepareApp＋KeepPostgres 应用维护；新旧部署与启动按原门禁 | 兼容前向/应用回退；生产数据恢复须另批精确恢复点、目标和窗口 |
| strict：工具、生命周期、权限、导入、自动化、迁移/models/SQL、依赖/构建配置或未知可执行变化；另核并发、迁移、生命周期、备份恢复与原写路径 | full；不得靠布尔声明或维护参数减免 | 精确审查 Worker/Django/PG 范围，复用唯一引擎；迁移保护和集成 gate 保持 | 迁移兼容、PNR与前向恢复按原合同；代码回退不回滚数据库，也不恢复退役D1事实源 |
| 合格 v3 无本次新增持久效果：保持原展示测试并增加 no-data-negative，不降低验证强度 | not-required；封存零 Backup/Restore，恢复证据为空 | 只允许原固定 Worker 排空切换及受限观察；Django保持 | 兼容应用；unknown保 owner/WAL/gate，不自动重放或数据库恢复 |

表内 full 表示封存的完整前后 Backup/Verify及同点隔离 Restore 保障，实际操作顺序必须依据该候选依赖与已安装合同批准，不能只按表格自行移动维护内恢复步骤。恢复点的 dump/manifest/SHA、profile、角色/权限、迁移、序列及隔离清理分别核验；生产数据恢复是独立动作。E盘最多三份和保护项规则不因模式变化而改变；数据库备份不覆盖R2附件或整机。

### 常规 full / reuse / not-required

- **full**：除按上节约定执行的后续结构迁移外，未知数据/部署效果、备份机制或受保护路径变化默认走完整保障；缺资格不是“无需保障”。`Start` 未就绪时可能 migrate、复位权限及启动渠道，Worker-only也须在这些原调用前证明后端已就绪，不能因切换名称宣称无副作用。
- **reuse**：仅旧 v2 display。当前唯一日备份 ACTIVE、最近原 installed Backup及E归档/轮换成功且≤26小时；同一仍现存恢复点≤26小时、原Verify通过；同manifest/dump的完整受保护隔离恢复≤7天，内容/角色/权限/迁移/清理与owned序列健康通过；环境、schema、roles、operator、retention、schedule等摘要精确一致。批准前、切换边界、收尾复验；手工备份、旧JSON、被淘汰点或未知最新调度不能替代。资格失效保原批次，安全闭合后重新准备/批准full，不执行中删改步骤。不会为取得reuse自动启用调度或解除保护。
- **not-required**：仅完整 v3 机器证明和精确独立副作用原报告闭合。首版支持既有CSS同选择器/属性/规则结构的受限展示值，以及完整静态、零参数、无导入/事件/表达式/自定义祖先的被动use-client TSX原生文本和有限布局类。新增/删除、自定义组件、局部事件、PNG、Markdown、查询/API、权限、迁移、依赖、启动钩子和备份工具不在v3证明边界内。还需原前后全部非源码环境/运行配置/npmrc/工具链输入相同、Django不变、备份机制不变及精确source/artifact/plan/closure副作用报告，包含布局观察器和文本消费者。声明effects:false不能取得资格。

合格v3不查询日备份、26小时点或7天恢复资格；日调度PAUSED不阻塞这个模式。它只证明本次变化及封存动作没有新增持久效果，允许原正常业务自然写入，不要求全库静止。v3未知效果仍full，不能用reuse填补证明。v2较宽的静态PNG/局部布尔交互边界不能移植为v3 not-required。

### 精确批准的首次采用策略

`teruisi-release-batch-v4` / `teruisi-first-adoption-targeted-v1` 是显式、限定的首次工具采用资格，不是常规第五种风险等级。默认batch仍v3；旧v1/v2/v3批准、WAL和数据库步骤保持原语义。v4维持strict，完整tools-no-migration必须绑定双Django原manifest/全部库存、Worker精确十工具字节闭包、原PG operator/consumer；业务、配置、迁移、依赖不变。完整无迁移资格可将migration-rehearsal替换为migration-closure，但须按`requirementsForImpact`增加targeted-recovery-negative与installed-recovery-consumer，不减其他严格检查。

该限定顺序恰为一次前Backup → 原维护/停止 → Worker apply → Django DeployApp/HardenAcl → 新installed消费链只读规划 → 同一前点的installed隔离Restore → 同ID ExitMaintenance → 唯一Start → 全部原验收/收尾。不能复用此前恢复证据、用prepared旧operator或他点恢复替代。失败/unknown保留原owner、WAL与维护，不自动回放或换不兼容解析器。新候选只有实际满足原精确白名单与闭包才可另提该策略，不能沿用f15的历史批准给任意工具新增改动减免。

采用事实：f15于2026-10-12完成v4限定批次；v3 not-required工具支持随该次采用，普通零DB完整生产周期及净收益尚未实测。永久Status安全修复、全维护Stop选路修复的源码与原冻结运行字节不同，仍须兼容候选采用；旧普通权限Status/Panel不能据源码已合并用作现场诊断。看门狗e033安全wrapper只覆盖其限定路由。原证据见 [基线](../release-pipeline-optimization-20261012/WPB-BASELINE.md)与[最终采用报告](../release-final-closeout-20261012/FINAL_REPORT.md)，不授未来生产操作。

### CI候选规则与证据新鲜度

以下分级命令和扩大规则属于**完整CI候选分支的待采用方案**，固定代码见[215b8f0c](https://github.com/dengweizhang321-droid/operations-management-system/tree/215b8f0cc03dfd8e737c1ae92f4838c808a45fb6/tools/ci)，交付材料见[dc94e649](https://github.com/dengweizhang321-droid/operations-management-system/tree/dc94e6492ce34457529581239f2b682bb6d36264/docs/release-pipeline-optimization-20261012)。当前资料/工具子集不包含package验证脚本、tools/ci、tests/ci或工作流，不提供`verify:l0/l1/l2/l3`命令，不启用默认CI或分支保护，不能据本节把候选入口当作当前可运行能力。

候选`verify:l0/l1`仅验证已审安全切片，其原完整lint和覆盖缺口保留；候选规则将共享组件/传输至少扩大至L2，将依赖/构建/配置/类型或未知路径扩大为全域L3。候选L2/L3实验基础设施已有局部实测，真实业务HTTP/角色PG/完整应用冷启动仍未验收，保持pending，不作为已完成门禁。合成SQL/静态CSS探针不能替代完整业务或冷启动。

当前main继续适用本页首部的按真实改动范围最小充分验证及[开发与交付](开发与交付.md)原门禁。这里说明候选尚未交付，不是豁免子集实际需要的高级别、生命周期或数据验证；真实影响/依赖要求更强检查时必须在隔离环境完成，无法完成就保留对应候选，不凭拆分或命令名称减免。声明完整、SHA一致或草稿生成时间不证明执行、采用或现场就绪。每动作完整字节/物理路径、精确进程/权限、维护/排空及原新鲜窗口保持；watch只失效。离线报告始终`acceptancePassed:null`，保原失败、未测、未知及reconcile，不用最终成功追认旧exit0。

计时分别记录T1精确批准到完整交付、T2维护/进程停稳/HTTP与认证业务恢复、T3失败执行/未知补证/故障恢复/正常恢复验证/收尾。区间并集和父子关系防止重叠累加；离散采样空档不回填。未经同源码/载荷/门禁/负载配对测量，不承诺净省分钟数。

## 发布包与数据库备份保留

- 发布包保留最近 7×24 小时的完整包；当前运行版本、必要回滚版本及显式保护版本即使超过七天仍保留。历史启动校验依赖的 manifest、successor、activation fence、guard、authority 和审计凭证不按日期删除。仅清理经验证且无进程引用的精确旧包载荷，禁止整目录按时间通删。
- PostgreSQL 使用既有 `pg_dump` custom 格式与一致性快照备份，不新增备份密码或恢复密钥。一个恢复点包含 dump、manifest、SHA-256 校验文件；角色、权限和迁移证据继续按现有归档版本验证。数据库备份不代表已备份 R2 附件或整机配置。
- 备份脚本包含中文路径时使用 UTF-8 BOM，并同时验证 Windows PowerShell 5 和 PowerShell 7 的实际路径、根权限及子文件继承。E 盘归档根使用独立受限 DACL，不得绕过仅限 D 盘 runtime 的权限函数。备份后台启动 Windows PowerShell 5 时固定使用其系统内置模块目录并清除继承的 library-only 标志，不修改全局 `PSModulePath`。加载运维脚本库时隔离参数作用域，避免覆盖调用者的 `Execute`、`Json` 等变量；跨旧代码页传输路径时使用无损的 ASCII 转义 JSON。
- 正式数据库备份保存到 `E:\运营管理系统业务数据`，最多 3 个已验证恢复点；D 盘只作生成和导入校验的临时区。发布前后备份均占名额，必要的迁移前备份作为保护项占其中一个名额，其余按完成时间保留最新。新备份成功、E 盘归档复验完成后才淘汰旧份，过程中允许短暂第四份；失败不提前删旧，不因达到上限解除关键备份保护。保护项占满或证据异常时停止轮换并报告。
- 系统备份管理仅允许无数据范围限制的管理员使用，复用既有备份/Verify/隔离恢复工具。导出交付完整备份包；导入先上传、校验并在独立 PostgreSQL 环境恢复验证。上传或校验不等于生产恢复，恢复生产必须另获用户对精确恢复点、目标与维护窗口的明确确认。
- 发布流程以 `docs/运维/部署与启动/startup-release-optimization.md` 为准：开发、测试、生产构建及候选准备期间保持生产正常，不修改当前生效入口或运行包。正式切换可在用户批准的短时应用维护窗口进行；不得把在线准备描述为全程零停机。优先保留 PostgreSQL 的应用维护，沿用唯一生命周期引擎和全部原验证/恢复门禁。
- 上述原能力与[批次协议](../运维/部署与启动/release-batch-workflow.md)组合使用。旧 v2 恢复复用须满足 26 小时恢复点、7 天同点演练、持续日备份及现场目录／权限／软件／保留条件。新 v3 可由完整字节差异与受限部署操作独立证明无新增持久数据影响，封存 not-required 与零 Backup/Restore，不查询上述复用资格；验证强度、组件切换、数据／部署效果和备份机制分别判定。除按[后续结构迁移约定](#后续结构迁移的备份与恢复约定)执行的范围外，服务端查询、权限、迁移、依赖、启动、备份及未知改动尚无受支持的无数据证明时保持 full，并列明缺口；v2/v3 新规则自身首次采用仍走严格/full；显式新 v4 仅在完整十工具／双 Django 库存资格闭合时使用一次前备份、一次新已安装消费链隔离恢复，严格分类与原生命周期／恢复断言保留，详见批次协议。旧已批准批次和 WAL 不减免、不换绑。部署入口内部的完整字节／路径／权限／进程／ready／互斥／排空及动作前验证保留；常规发布收尾按[发布完成的判定](#发布完成的判定)执行，真实业务补数及其结果核验作为独立任务处理。
