## 常态发布路径（一页入口）

先按实际生产来源到候选的完整差异确定范围：前端只处理 Worker，后端只处理 Django，仅 migration 变化执行已批准迁移；共享运行库、依赖、配置、发布工具或未知变化保持完整组件流程。无应用载荷的文档交付只核差异与引用。文件是否被应用包收录，以应用准备工具的复制清单为准，不以文件看起来是否"离线"判断；Django 侧以 `tools/django-local-service.ps1` 的 `Prepare-Application` 复制清单为准，Worker 侧以 release 清单的 `keyFiles` 及 `tools/worker-local-release.mjs` 的 guard 入口清单为准。

## 发布入口与记账边界

实际上线只走 `tools/publish-latest-main.mjs`；已准备制品的续接入口同样是不带模式参数的 `tools/publish-latest-main.mjs`（从已采用的控制包以固定入口 `--config` 调用）。`tools/publish-prepared-main.mjs` 是发布器内部执行已准备制品的库，没有独立命令行入口，不得当作续接入口直接调用；`--consume-preparation` 是准备队列的消费者，不是上线。发布器负责自建冻结来源 `D:\codex-isolated\main-release-packages\<commit>-…\source`，并在成功后写 `publish-<12hex>/SUCCESS.json` 与状态目录下的 `PUBLISHED-MAIN.json`（含 `workerRelease`、`workerManifestSha256`、`djangoManifestSha256`、`receiptPath`/`receiptSha256`）。这两份记录是下一次发布判断"现役是哪个已发布版本"的唯一依据。

下列动作是发布器内部调用的底层动作，**不得作为发布手段单独调用**：`tools/django-local-service.ps1` 的 `PrepareApp`、`DeployApp`、`HardenAcl`，以及 `worker-local-service.ps1` 的 `EnterMaintenance`、`ExitMaintenance`、`Start`。单独调用它们时，制品完整性、身份、权限、互斥、排空和启动门禁**仍会逐项放行且不报错**，应用也确实切换并可用，但本次上线不写任何发布记录，因此不被发布记账承认。**门禁放行不等于流程正确**：这些门禁校验的是"这次动作本身安全"，不校验"这次动作是否属于一次被记账的发布"。

绕过后的后果是累积的，且由下一个发布者承担：

- 现役 `D:\teruisi-runtime\django-sales\app\deployment.json` 的 `sourceRoot` 会指向执行准备的源码树（例如某个 worktree），而不是冻结发布包。
- 下一次发布在 `publish-latest-main.mjs` 的来源一致性断言处失败，报"前后台来源不同且没有匹配发布记录，不能推定已发布版本"。
- 唯一的放行旁路是目录记录分支，要求 `PUBLISHED-MAIN.json` 的 `workerRelease`、`workerManifestSha256`、`djangoManifestSha256` 与现役**三值同时相等**；任一不等即进入该断言。
- **该断言在自建冻结来源之前执行**：`observeLatestMain`（含断言）先于 `prepareLatestMainOnce`（建来源）被调用，二者在同一调用链内保持此顺序。所以"让发布器自己建来源"不能解除来源不一致，发布器根本走不到建来源那一步；`bootstrapSuccess` 兜底也在该断言之后，同样救不了。
- 于是形成死锁：写目录记录要先有一次成功发布，成功发布要先有匹配记录。

因此缺口不能用"再按底层方式发一次"弥补——那只会把来源换成另一个非发布包路径，记录依旧不写，死锁不解。受控修正 `PUBLISHED-MAIN.json` 属于改发布记账，风险高于常规发布，须单独授权并在专题中记录依据，不得由代理自行决定。

维护窗口有两种开法，不要混为一谈：`worker-local-service.ps1` 的 `EnterMaintenance` 只需 `-MaintenanceId` 与（按停机范围）`-KeepPostgres`，不校验 `rotationOwnerPid`，也不要求发布器在运行；而 `publish-prepared-main.mjs` 自己开的窗口会把 `rotationOwnerPid` 写成发布器进程 PID，并要求 admission 落在 `<packet>/publish-<12hex>/maintenance-admission.json`。前者能开窗口这一事实，不表示它是合规的发布路径。

停机范围按本次差异决定：无 Django migration 时用 `-KeepPostgres`（只停 Worker 与 Django，PostgreSQL 不停）；有 migration 时 PostgreSQL 必须保持运行以执行已批准迁移。旺季停机代价高，停机方式须先与用户确认，不默认整栈停。

## 常规发布的三个交付步骤

范围计划确定组件后，后续只保留以下三个交付步骤；`release:plan` 的 `workflow` 按第 4、5、6 步输出对应动作，计划工具只生成清单，不执行合并、构建或生产发布。

4. **检查必需程序代码**：在隔离 worktree 检查本次差异中影响构建、部署和启动的程序代码，记录必要检查及结果；共享或未知变化先确定代码依赖和组件范围，不追加业务功能或相关代码业务行为的验证。已有且仍有效的检查结果直接复用，功能检测由用户上线后负责。
5. **合并并生成对应制品**：必需代码检查通过且获得本次合并授权后，同步最新 `main`；若有冲突或实际代码变化，只补受影响的必需代码检查。完成合并、推送并核验远端，在隔离交付树从最终合并提交准备相应 Worker immutable release 或 Django PrepareApp，无需再次请求制品准备授权，生产构建只执行一次。准备失败时保留已合并提交并报告“制品未就绪”，不得发布。纯文档、测试或没有应用载荷变化的离线交付不生成生产应用包。记录最终提交、制品摘要及有效检查来源，不重跑功能验证。
6. **发布**：单独取得用户对本次上线的明确授权且对应制品就绪后，使用既有唯一生命周期入口执行计划中的排空、必要维护和组件切换。只在迁移变化时执行已批准迁移；备份按实际数据影响处理。发布后只确认本次部署成功、目标版本已切换及必要服务可用，完成即报告上线；不另设“整体验收”阶段，不重跑发布前的功能验证或重新打包。日志、记忆和闲置工作树清理随交付收尾，不另开业务验收轮次。异常保留原审计和失败状态，按对应恢复流程处理。

授权判定统一见根 [AGENTS.md](../../AGENTS.md) 第 4、5 条；上述三个步骤不代表三次授权，也不承诺 Git 推送与制品构建在技术上原子完成。实际部署仍使用现有已安装入口的制品完整性、权限、进程身份及任务排空检查，不追改旧已批准批次或旧运行包。

准备失败、绑定不一致或结果未知时，不进入依赖它的下一步。生产授权与制品就绪缺一不可；合并、准备、上线分别报告。原生版本/完整性、身份/权限、互斥、排空、必要迁移和启动门禁保持，功能由用户上线后检测。事故及旧协议资格按[历史限定资格索引](#历史限定资格索引)查阅。

## 源码摘要的字节来源

- 修改或复算 `code_digest`、recipe 和来源绑定时，复用对应 gate 对最终冻结来源 `root` 的计算，不能另造“统一按 Git 字节”或“全部转 LF”的算法。`tools/check_schema_code_digest.py` 调用实际 `gate.code_digest(root)`；例如 `tools/sales_preflight_addition.py` 通过 `tools/bi_app_addition.py` 的 `sha()` 读取文件原始字节。
- Git blob 只有在与该冻结来源的实际字节对应时才可用于离线复算；先核 `.gitattributes` 与实际取字节路径，`core.autocrlf` 不代表所有文件都保存为 LF。迁移摘要另由既有 `python_source_sha256()` 等函数处理，不能把它的换行规范化规则套到代码摘要上。摘要一致性检查不产生打包或发布授权。

## 发布检查与功能验收分工

- 每次发布上线只由 AI 检查影响本次构建、部署和启动的必需程序代码，按必要性选择语法、类型、依赖、构建、发布入口及调用参数检查；不默认运行全仓检查或增加多轮复审。
- 相关功能及其代码的业务行为、业务口径、接口业务结果、权限业务场景和使用效果，上线后由用户自行检测判断。除非用户另行明确要求，AI 不新增或执行功能测试、业务回查、浏览器验收、业务数据演练或综合验收，也不以这些结果阻塞合并、制品准备或已授权发布。
- 必需代码检查无阻断、对应制品就绪且已有上线授权后，直接执行发布，不再要求功能验证或再次确认。发布工具内置的版本/制品完整性、身份/权限、互斥、排空、必要迁移和启动门禁继续随发布执行；成功后读取原生完成回执报告上线，不另开 HTTP、SQLite、业务接口或独立健康扫描来做功能验收。
- 本节是后续每次发布的默认分工，优先于下文、关联专题和模板中的旧功能验证要求；旧验证类别、测试清单及历史资格不是新增功能验收的授权。文档更新不伪造旧证据、不修改已封存批次，也不直接改写已安装执行器；既有工具内部检查与 AI 额外功能验证分别说明。

- 按实际影响分级、绑定完整源码与制品、恢复证据复用及统一批次编排按[发布批次协议](../运维/部署与启动/release-batch-workflow.md)执行。该协议首次生产采用仍需明确授权并走严格流程；采用前不得提前改变已安装门禁。展示级必须有完整闭包与独立行为证明，冻结／排空原任务后才可 Worker-only 切换；未知影响进入严格级。

### 准备、维护与服务操作边界

在线准备只生成候选，不能改生效入口或授予启动许可。冻结来源与请求/制品保持绑定，维护前只读准入不能替代现场身份、互斥、排空和新鲜事实；未知控制代际在 STARTED 前拒绝。服务操作须有当前明确授权，所有入口复用唯一生命周期引擎，故障按原有限协议处理。构建不得覆盖正在监听的产物；验证不得覆盖正式环境、凭据或数据。

本节具体前置、精确回执清理、ACL/完整性复用及隔离要求完整见[执行细则 G01](../运维/部署与启动/发布门禁执行细则.md#g01)，适用动作前必须逐项执行。数据库保护见下文策略，历史状态/维护桥/夹具/闭包限定另见 Q01～Q04。

### 合并前发布兼容性验证

用冻结干净候选的实际字节检查受影响的发布入口、参数、包依赖、迁移代际及启动准入；字节变化只补受影响检查。正式制品绑定最终合并提交及真实前驱，取得原生 PREPARED 后仍须即时动态复验。锁文件变化须同次交付匹配离线依赖，不匹配在准备效果前拒绝。

包完整性、真实入口边界、完整原生冷启动分别报告；前两项不证明第三项。真实生命周期语义变化须完成隔离原生冷启动及必要就绪，缺能力保持候选未合并。固定检查入口、拒绝条件及 Q05/Q06 窄资格见[执行细则 G02](../运维/部署与启动/发布门禁执行细则.md#g02)，不接受手填通过、不扩大有限资格或新增功能验收。

### 发布执行方式

负责人通过已采用的固定入口执行本次合并授权所包含的制品准备，单独取得本次发布上线授权后再串行执行发布，BAT 仅为可选包装器。目标只在选择阶段获取并冻结；缺原生 PREPARED 在构建、STARTED 和维护前拒绝，不回退旧包、不在发布时补建。准备与发布分开，未知不重放，同目标复用仍核完整绑定与动态门禁。

固定入口、自动准备、环境/依赖、锁序/派发、结构安装和受限续接的完整操作条件见[执行细则 G03](../运维/部署与启动/发布门禁执行细则.md#g03)，适用时逐项执行；历史首版范围及一次性分支见 Q07～Q10。源码、准备、采用及实际上线分别报告，历史成功不替代本次成功。

### 标准入口、完成判据与受限续接

完成判据：本次目标与实际组件绑定的 `SUCCESS.json` 必须为 `status=deployed_and_ready`，原 `VerifyStartup` 回执中 `startupVerified=true`，原 ready 门禁通过，维护/排空已退出，发布目录指向真实完成回执。单个进程退出0、组件元数据或已有历史成功不单独证明本次完成；已完成服务切换而目录更新中断时只协调发布索引，不再执行发布步骤，不追加功能验收。

异常先核原 STARTED/FAILED、准备包、intent、持久回执、进程退役及现场来源/前驱，仅续接已证明尚未执行的步骤。有 started 缺可信结果仍为 unknown；保原失败、输出及真实退出。具体支持范围、最多一次原 Reconcile 及原锁/身份要求见 G03 和 Q07，不授予通用重试。

### 自动提前打包与发布执行

自动准备仅限本次合并授权包含的制品准备，发布上线仍须单独授权；二者共用普通权限受控环境及串行队列。触发、排队、来源冻结不等于 PREPARED，PREPARED 不等于上线或上线授权。只合并尚未 dispatch 的过时同语义请求，已派发不取消；未知保留原件并阻断重放。控制采用与应用发布分别授权，队列、rotation、派发/复用及新鲜度的原完整门禁见[执行细则 G03](../运维/部署与启动/发布门禁执行细则.md#g03)。

### 发布完成的判定

- 常规发布以原生发布动作及其内置版本切换、启动门禁完成为条件，依据真实成功回执报告上线；必需程序代码检查在发布前完成，同一源码、依赖及制品的有效结果直接复用。功能及相关代码业务行为的检测判断由用户上线后负责，不作为 AI 的发布完成条件。
- 不追加全量公开资源比对、全权限复验、业务接口深比较、无关 n8n 核对、全组件健康扫描或等待看门狗轮次；即使相关领域有改动，也不据此自行增加功能验收。日常监控按既有配置运行。
- 真实业务补跑、五表导入及其批次、日期和数据归属核验按独立业务任务处理，须有对应授权；不得用“已上线”表示这些业务已成功，也不以补跑成功作为常规发布完成的前提。
- 本规则用于常规发布流程和新范围计划，不通过文档更新删改已封存批次、跳过既有执行入口的内部检查或把失败／未知状态标为成功。若工具仍按旧合同执行综合验收，应如实说明工具行为与新规范的差异；文档变更本身不修改正在执行的批次。

## 统一发布交付契约

契约版本 `release-delivery-contract-v1`。本项目所有主代理、实施代理、审查代理及发布负责人均须遵守；用户当前明确指令优先。契约规定交付动作与证据，不创建新的生产执行协议，不改写已封存批次、旧批准、已安装入口或权限边界。[工作单与工具接入模板](../运维/部署与启动/release-delivery-templates.md)只引用本节，不另存竞争规则。

### 职责与发布就绪

一个负责人串行集成和发布；实施者交付其范围的源码与验证证据，独立审查者不得把自审称为独审。其他代理不得并行操作同一生产锁、队列、部署目录或批次。已有本次范围授权且就绪时直接执行，不重复询问；缺少生产授权时，先完成可审查的就绪材料，再一次提出精确范围的确认。

发布按下表推进，工作单的“已就绪”是证据完整性声明，不是生产授权、动态健康证明或新的启动许可。缺项仅暂停依赖它的动作，其余独立工作继续；对不适用项记录范围计划和理由，不为填表增加无关测试。

| 合并前代码检查 | 只检查影响本次构建、部署和启动的必需程序代码及发布入口/参数，复用有效结果 | 必需代码问题先修复；不要求 AI 功能验证，功能由用户上线后检测 |
| 异常预案准备 | 复用既有恢复流程和有效证据，只检查本次发布必需的恢复入口代码、调用参数和适用身份；不默认新增隔离业务演练或多轮复审 | 不用重发、换身份或延长超时掩盖未知；不得为演练中断生产 |
| 合并并准备制品 | 取得本次合并授权后，按原第5步连续完成main合并/推送与从该最终合并提交准备对应制品，无需另行取得制品准备授权；先核完整组合来源和受保护入口差异，冻结源码/依赖/配置/工具及字节，再生成制品、发布/回退计划和必需的数据保障证明 | 未获合并授权不执行合并或制品准备；制品未就绪就报告缺口，不进入维护；不在准备后临时加入注释、行尾或配置变更并沿用旧收据 |
| 最终就绪包 | 记录实际生产来源、合并提交、最终发布来源、差异范围、对应Worker/Django制品/收据摘要、必需代码检查、适用恢复入口、操作顺序和数据策略 | 缺失或绑定不一致不能声明就绪；功能检测不作为就绪前提，纯文档/元数据变化不要求重建有效制品 |
| 现场准入与发布 | 单独取得本次发布上线授权且对应制品就绪后，通过既有唯一入口即时核实际前驱、进程创建身份、权限、互斥、owner、门禁、排空及原新鲜度要求；只执行范围计划对应组件、迁移及数据保障动作 | 未获单独上线授权不得发布，合并授权和制品就绪不能代替上线授权；现场事实与已审前提冲突时不沿用旧成功；忙/未就绪等待照实计时，不能删除owner或改身份抢占 |
| 发布完成报告 | 依据原操作成功回执及工具内置版本/启动结果报告已上线，功能由用户自行检测判断 | 不追加功能或独立健康验收；失败、未知不能报告完成 |
| 必要交付收尾 | 发布前预备输出目录、文档骨架、证据文件清单、精确Git路径与闲置工作树清理范围；成功后填入真实回执/计时，核查原始证据，完成聚焦提交推送、保全、记忆及符合清理条件的归档 | 未完成/仍被占用的清理如实列为未完成；不以稍后完成时间回填更早的“全部完成” |

生产构建只在制品准备中执行一次；原源码、依赖、制品和验证绑定仍有效时直接复用结果。任何候选实际内容或前驱变化按原规则失效并补充相应准备/审查，不因赶时限忽略差异。前端只处理Worker，后端只处理Django，只有migration变化才执行迁移；共享/未知变化按既有完整流程，不用拆文件、改路径或声明“离线”绕过范围计划。纯文档、测试或没有应用载荷变化的离线交付按原非生产规则完成，不为其重启服务或构建应用。

### 异常后的事实核对与安全续接

合并前审定的是取证方法、判断条件和分支；某次故障的真实结果只能在故障后确认。预审结论可在精确前提不变时复用，**原执行协议要求的独立现场只读观察/协调仍须执行**，不能用预审替代新鲜事实或冒称任何人的独立观察。

| 观察结果 | 必需依据 | 允许动作 |
| --- | --- | --- |
| 原操作已完成、回执曾丢失 | 原请求/操作与批次身份、精确任务或组件、目标状态/版本、原回执与审计/消费记录相互关联 | 按原协调入口复用精确完成结果，跳过已确认步骤；保留原失败/unknown原件 |
| 确定未产生本次作用 | 满足预审的本阶段零效果条件和原协议要求；关联原操作、进程退出及其可能的迟到效果、前驱/完整入口与activation fence、owner/门禁、审计及后续步骤等适用证据 | 经原协议协调后，才按同一意图和原身份进入已审重试分支；次数/间隔按已批准方案，不泛化自动重放 |
| 未知、证据缺失或相互矛盾 | 原started/unknown、已保存输出/进程证据及缺口 | 保留owner、门禁、原日志与未完成状态，停止依赖该结果的新写入；完成定向查证，超出已审分支时追加相应独审 |
| 已开始切换但未闭合 | 完整入口/fence、原前驱与successor、consumption、回执和持久owner等本阶段适用证据 | 走原协调/恢复协议；旧head仍在不能单独证明零效果，不手工写回受保护入口或再apply |

取消等待不证明服务端取消；不能盲目结束身份不明的子进程、删除记录、创建新任务/操作身份或切换解析器来掩盖unknown。现场新增问题先查清其与目标功能、数据正确性或恢复的关系，只处理真实阻断，不把无关重构、监控完善或一般建议插入交付。

### 计时、预算与完成报告

同时记录原始上线授权、开发/验证、合并/准备、发布就绪、实际发布尝试、异常/续接、上线确认和交付完成时间。用户在开发前已单独明确授权本次上线时，原上线授权至完整交付的总等待一直保留；不得把开发授权、合并授权或较晚的“就绪”时间当作原上线授权时间。另列就绪后的发布执行跨度，准备前移、等待互斥、人工协调和收尾均如实呈现。并行阶段按区间并集合计，父子耗时不重复相加，未采样空档不补成执行或停服。

**15分钟是已验证且制品就绪版本的常规发布交付优化目标，包含该次发布的必要收尾；不是强制终止时限、稳定性能承诺或门禁豁免。**参考预算为现场发布/必要确认13分钟、必要收尾1分钟、波动余量1分钟，须以实际测量验证。迁移、真实数据恢复、长在途任务或超出预审范围的异常应另报窗口与原因，实际等待仍保留在原总计时。预算超出时及时报告当前阶段、状态、剩余动作及原因，不以吞错、缩减验证、自动重试或先报“全部完成”达标。

只核对本次部署成功、目标版本正确和必要服务可用，不另加全组件综合验收或重复功能测试。自动报告必须区分已采用、准备就绪、候选、未执行、失败与未知；实际采用事实来自原操作和必要观察，报告生成本身不产生成功。性能优化先细分Worker校验/切换、服务启动等剩余成本，已存在的在线准备、同域读写重叠、同次ACL复用及有界并发不重复算作新增收益；跨域并行、跨进程权限缓存和放宽校验不因本契约获得采用授权。

### 现有工具与自动化边界

优先复用 `tools/release-scope-plan.mjs` 的完整差异范围、适用版本 `tools/release-batch.mjs` 的原封存/检查/执行/状态及导出的协调接口，以及 `tools/release-closeout-report.mjs` 的离线证据草稿。先核实际已采用能力；候选协议不能仅凭文档存在而当生产入口。批次工具没有通用reconcile CLI；需要原已审适配器调用其导出接口，不编造命令或现场编写未经审查的恢复实现。

收尾工具要求其支持的原batch、连续原WAL及精确回执绑定；其他发布入口只有独立操作回执时，按模板保留原格式生成交付说明，不伪造batch/WAL来凑输入。工具生成的 `acceptancePassed:null`、草稿及历史观察不变成生产验收、当前健康或关闭批次的证明。Git提交/推送和工作树归档仍走原工具与精确范围；本契约没有声称现有报告工具会自动执行这些动作。

本节和模板对代理行为生效；其额外准备项、独审适用判断及跨工具收尾完整性，当前由负责人/审查者据证核验，**不宣称新增字段已被底层执行器自动强制**。后续确有高收益工具缺口时单独实施、隔离验证、审查及按实际范围准备/采用，不为本轮契约改写运行包或另造发布系统。

## 发布影响、验证与恢复策略

本节是发布分类与保障的唯一规范正文。具体批次命令、封存与续接见 [发布批次协议](../运维/部署与启动/release-batch-workflow.md)，在线准备和原生命周期步骤见 [启动与发布](../运维/部署与启动/startup-release-optimization.md)。已合并源码、已准备候选、实际安装采用和验收通过分别记录；不得用 Restart 代替候选 plan/apply。日常热重启只恢复同一 effective head，不产生新候选采用。

### 变更分级与验证强度

验证强度、数据库保障、维护范围、切换方式、恢复边界是五项独立判断，不合并成一个风险标签。下表只归纳阅读顺序，不新增功能验收或替代工具/批次门禁。

| 变更或证据范围 | 通用规则 |
| --- | --- |
| 纯文档 | 只核本次差异与引用，不构建或启停生产应用 |
| 测试或无应用载荷且未被任何应用包收录的离线工具 | 按影响完成必需代码检查，原测试/交付要求保持；不生成生产应用包、不启停生产应用 |
| 被应用包收录的离线工具 | 虽无业务载荷，但只能随对应应用包安装，按完整组件流程准备与部署；判定依据是该文件是否出现在应用准备工具的复制清单中，而非它看起来是否"离线" |
| 展示或领域业务变化 | 完整闭包判范围；AI 只做构建/部署/启动必需代码检查，功能由用户检测；旧协议完整类别条件仍见 Q11 |
| 工具、生命周期、权限、导入、自动化、迁移/models/SQL、依赖/构建配置或未知可执行变化 | strict；共享/未知保持完整组件流程，原迁移保护和集成 gate 保持 |
| 包完整性、真实入口边界、完整原生冷启动 | 分项报告，前两项不证明第三项；真实生命周期语义变化须完成原隔离冷启动，缺能力保持候选未合并 |
| 未执行、部分验证、失败或未知 | 保留原状态、失败及缺口；不由 SHA 一致、旧成功、草稿或报告生成推定执行/采用/通过；符合窄资格也只声明已证明范围 |

### 后续结构迁移的备份与恢复约定

- 后续数据库结构迁移发布取消迁移前、迁移后的全库备份及全库隔离恢复，不再将这些动作作为默认发布步骤、准入条件或完成条件；不因 migration、models/SQL 或 strict 分类重新追加。结构变更具有持久效果，取消这两类动作不等于证明“零数据影响”，也不套用旧 v3 无持久效果资格。
- 仍在隔离环境使用独立结构和合成数据验证本次结构变更、兼容性、权限及直接受影响功能；不为结构迁移验证复制正式业务数据或执行全库 dump/restore。业务数据处理范围按[数据存储与迁移](数据存储与迁移.md)单独安排。
- 日常备份、既有恢复点的保护与保留、单独授权的备份或生产恢复继续独立管理。本约定不关闭备份调度、不删除已有恢复点，也不自动授权业务数据处理或生产恢复。
- 此约定适用于后续新发布；不通过文档修改追改在途或已封存批次的步骤、审计和结果，也不直接改变已安装工具门禁。新发布准备时应核对执行工具与此约定的一致性，提前处理旧工具仍强制全库备份/恢复的兼容问题，不能现场伪造证据、绕过门禁或静默补回已取消的默认步骤。

### 事实来源与五项独立判断

先绑定实际生产前驱 source-snapshot、最终组合源码的完整成员集合与所有增删改字节、运行依赖闭包及原前后 preparation receipt 的非源码输入，再独立复审真实构建、启动、部署、观察和消费链。main、分支名、文件名、HTTP GET 或“前端／筛选／只读”标签均不能替代这些证据。缺完整前驱、候选或部署输入时，写“无法据现有证据判定”，保留 full，不做纸面减免。

每个精确候选分别写明：验证强度、数据库保障、维护范围、切换方式、恢复边界。`release-impact.mjs` 的 `requirementsForImpact` 产生测试和验收要求；`recoveryDecision` 决定数据库动作。严格验证可以与经精确资格证明的无迁移闭包并存，维护保留 PostgreSQL 也不代表免备份。它们不得混成一个高／中／低风险标签。

[归档 Q11](历史记录/发布限定资格-20261022.md#q11)保留既有工具类别和历史资格的语义，不作为 AI 默认执行功能验证的清单；后续每次发布均优先遵守[发布检查与功能验收分工](#发布检查与功能验收分工)，只做必需代码检查，功能由用户上线后检测。结构迁移的数据库保障按上节处理；已有封存批次的精确检查和数据库操作合同不因文档更新被追改，已安装执行器也不被本次文档直接改写。

旧协议的展示/business/strict 分类及完整数据库资格见[Q11](历史记录/发布限定资格-20261022.md#q11)。26 小时、7 天、完整静态/副作用闭包等原条件仍逐项生效；未知效果保留 full，不以标签、布尔声明或维护参数减免。

<a id="ci门禁不进入发布链路"></a>

#### CI 门禁不进入发布链路

`.github/workflows/ci.yml` 的步骤是**合并前的仓库级检查**，不是发布执行路径的一环：发布器入口 `tools/publish-latest-main.mjs` 及其内部库 `tools/publish-prepared-main.mjs` 不调用任何 CI 步骤、不执行测试套件，`PrepareApp`/`VerifyPreparedApp` 只校验摘要链与文件指纹。所以 **CI 全绿不代表能发布，CI 红也不是发布被拒的原因**；发布的放行条件只有发布器与原生控制器内置的版本、制品完整性、身份、权限、互斥、排空、必要迁移及启动门禁。

反向同样成立：**修复 CI 门禁不等于解除发布阻塞**。两类阻塞各自独立，判断某次发布能否执行时只看发布器与控制器的实际断言，不以 CI 状态替代。

一个例外必须知道，否则会误判影响面：CI 所用的测试文件往往同时被 `tools/verify-release-candidate.mjs` 的 profile 引用——它全文引用 36 个不同 `.test.mjs`（另有少量 `.py` 检查器），单个 profile 一次就列十余个（如 `:574` 列 11 个、`:600` 列 10 个，两处都含 `tests/manual-maintenance-continuation.test.mjs`）。该工具用于合并前的候选兼容性验证，**本身没有生产调用方，也不被发布器调用**，但改动任何测试文件前都须核对它的 profile 清单，不能只看 CI 是否通过。

因此 `tools/manual-maintenance-continuation.mjs` 的 `piNativeCandidateControllerSha256` 一类**控制器字节资格化**属于发布链路（`maintenanceReadiness` 在写 STARTED 前即断言，失配直接拒绝发布），即使它同时被 CI 测试覆盖；而 `tools/check_schema_code_digest.py` 比对的 recipe/proof 摘要**无任何生产调用方**（全仓仅 CI 调用），只约束合并。两者都红时须分别处置，不可合并为“CI 问题”一并对待。

当前main继续适用本页首部的按真实改动范围最小充分验证及[开发与交付](开发与交付.md)原门禁。这里说明候选尚未交付，不是豁免子集实际需要的高级别、生命周期或数据验证；真实影响/依赖要求更强检查时必须在隔离环境完成，无法完成就保留对应候选，不凭拆分或命令名称减免。声明完整、SHA一致或草稿生成时间不证明执行、采用或现场就绪。每动作完整字节/物理路径、精确进程/权限、维护/排空及原新鲜窗口保持；watch只失效。离线报告始终`acceptancePassed:null`，保原失败、未测、未知及reconcile，不用最终成功追认旧exit0。

计时分别记录T1精确批准到完整交付、T2维护/进程停稳/HTTP与认证业务恢复、T3失败执行/未知补证/故障恢复/正常恢复验证/收尾。区间并集和父子关系防止重叠累加；离散采样空档不回填。未经同源码/载荷/门禁/负载配对测量，不承诺净省分钟数。

## 发布包与数据库备份保留

- 发布包保留最近 7×24 小时的完整包；当前运行版本、必要回滚版本及显式保护版本即使超过七天仍保留。历史启动校验依赖的 manifest、successor、activation fence、guard、authority 和审计凭证不按日期删除。仅清理经验证且无进程引用的精确旧包载荷，禁止整目录按时间通删。
- PostgreSQL 使用既有 `pg_dump` custom 格式与一致性快照备份，不新增备份密码或恢复密钥。一个恢复点包含 dump、manifest、SHA-256 校验文件；角色、权限和迁移证据继续按现有归档版本验证。数据库备份不代表已备份 R2 附件或整机配置。
- 备份脚本包含中文路径时使用 UTF-8 BOM，并同时验证 Windows PowerShell 5 和 PowerShell 7 的实际路径、根权限及子文件继承。E 盘归档根使用独立受限 DACL，不得绕过仅限 D 盘 runtime 的权限函数。备份后台启动 Windows PowerShell 5 时固定使用其系统内置模块目录并清除继承的 library-only 标志，不修改全局 `PSModulePath`。加载运维脚本库时隔离参数作用域，避免覆盖调用者的 `Execute`、`Json` 等变量；跨旧代码页传输路径时使用无损的 ASCII 转义 JSON。
- 正式数据库备份保存到 `E:\运营管理系统业务数据`，最多 3 个已验证恢复点；D 盘只作生成和导入校验的临时区。发布前后备份均占名额，必要的迁移前备份作为保护项占其中一个名额，其余按完成时间保留最新。新备份成功、E 盘归档复验完成后才淘汰旧份，过程中允许短暂第四份；失败不提前删旧，不因达到上限解除关键备份保护。保护项占满或证据异常时停止轮换并报告。
- 系统备份管理仅允许无数据范围限制的管理员使用，复用既有备份/Verify/隔离恢复工具。导出交付完整备份包；导入先上传、校验并在独立 PostgreSQL 环境恢复验证。上传或校验不等于生产恢复，恢复生产必须另获用户对精确恢复点、目标与维护窗口的明确确认。
- 发布流程以 `docs/运维/部署与启动/startup-release-optimization.md` 为准：开发、测试、生产构建及候选准备期间保持生产正常，不修改当前生效入口或运行包。正式切换可在用户批准的短时应用维护窗口进行；不得把在线准备描述为全程零停机。优先保留 PostgreSQL 的应用维护，沿用唯一生命周期引擎和全部原验证/恢复门禁。
- 备份、维护、切换与验证强度分别判断；旧批准批次和 WAL 不减免、不换绑。旧 v2/v3 见[Q11](历史记录/发布限定资格-20261022.md#q11)，v4 及原完整尾注见[Q12](历史记录/发布限定资格-20261022.md#q12)。部署入口内部的完整字节／路径／权限／进程／ready／互斥／排空及动作前验证保留；常规收尾按[发布完成的判定](#发布完成的判定)，真实业务补数另按独立授权任务处理。
