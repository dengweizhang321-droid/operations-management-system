# 开发与交付

路径约定：反引号中的代码、配置和工具路径均相对仓库根目录；Markdown 链接相对本文件。

## 任务开始与事实来源

1. 开始任何任务前，遵守当前用户指定的共享记忆任务启动协议，读取根目录 `AGENTS.md`、`README.md` 与本规范，再按任务范围加载相关专题。用户明确指令优先于历史文档和记忆。
2. 以当前代码、测试、数据库迁移、`README.md`、`AGENTS.md`、`docs/规范/` 和仍在生效的操作文档为事实来源。若文档与代码冲突，先验证当前行为，再更新过期文档，不能为了匹配旧文档回退正确实现。
3. 修改前先检查 `git status` 和相关差异。工作区中已有的改动默认属于用户；不得覆盖、格式化、暂存或提交无关文件。
4. 涉及当前运营数据的查询，必须先阅读并遵守 [docs/OPERATIONS_DATA_QUERY.md](../../docs/OPERATIONS_DATA_QUERY.md)。

## 开发隔离与合并流程

- 前端展示调整可在独立 worktree 使用 `npm run preview:isolated`，通过 3100 端口和独立合成 SQLite 数据先给用户观看；数据准备/快照和限制见 `docs/ISOLATED_PREVIEW.md`。不得向预览 worktree 复制生产 `.dev.vars`、密钥或数据库连接。演示验收不能替代 PostgreSQL/权限/写流程验收；测试与必要审查通过后及时合并；用户明确要求效果确认时先完成该确认，生产发布另须用户确认。

- 后续代码变更默认从最新 `main` 创建独立 `codex/*` 分支和独立 Git worktree，在该 worktree 内完成开发、测试、构建、迁移演练与复审；不得直接在生产运行目录或生产检出上开发、切分支、安装依赖、生成构建产物或运行会改变状态的脚本。
- 涉及数据库、导入、队列、缓存、对象存储或自动化的验证，默认使用与生产隔离的镜像库/镜像环境。镜像必须使用独立连接、凭据、端口和存储命名空间；任何写入、迁移、回填、清理、任务消费和回调都只能指向镜像，禁止把生产连接作为开发回退路径。
- 镜像数据只用于验证，需保留必要的业务口径和边界条件，并按最小范围处理敏感数据；测试邮件、机器人、Webhook、定时任务和浏览器自动化默认关闭或指向测试接收端，避免产生真实外部副作用。
- 只有在 worktree 内相关测试、构建、迁移 dry-run、数据回查、权限/审计检查及必要复审全部通过，且确认与最新 `main` 合并无冲突后，才允许合并到 `main`。检查失败、证据不完整或镜像与生产契约不一致时不得合并。
- 合并到 `main` 不等于生产发布。生产数据库迁移、服务重启、路由切换、自动化启用和数据写入仍须走对应模块的受控发布与回滚流程；未经用户明确授权，不得自动部署或改变生产环境状态。
- 每次系统调整完成后，均须以当前 `main` 为基准检查对应 `codex/*` 分支是否已合入；仅当分支已完整合入、对应 worktree 无未提交内容且未被其他任务使用时，移除该 worktree，并删除本地及同名远程分支。未合入、worktree 不干净或使用中的分支必须保留，并明确报告原因。

## Git 与交付


- 所有开发（包括文档与配置）在从最新 `main` 创建的独立 `codex/*` 分支及 worktree 完成。相关测试、审查与生产构建通过后，及时合并并推送 `main`，核验远端包含本次提交；合并不等于上线。完成生产候选构建/准备后等待用户对本次上线的明确确认，才执行维护、迁移、部署和生产验收。已合并分支及 worktree 在确认无构建、发布、进程或其他任务依赖、且必要材料已保全后及时清理；包括本次本地及同名远端开发分支。受管 worktree 使用应用归档工具。未合并、未验证或仍在使用的内容不得强制删除。
- 每次源码或项目配置修改完成后，创建一个聚焦、可审查的 Git 提交，并推送到已配置远端；文档/规范修改也属于项目配置修改。
- 只暂存本任务文件。推送前再次核验 `git diff --cached`，避免纳入用户已有改动、生成文件、下载文件、凭证或运行产物。
- 不使用破坏性 Git 命令清理工作区。没有明确要求时不改写历史、不强推、不切换或删除用户分支。
- 交付说明必须列出：变更内容、验证结果、提交与推送状态、未执行的部署/迁移/服务操作，以及仍需用户决定的风险。

### 本地 worktree 与分支清理

- 用户已长期授权清理本项目已停用的 worktree、已保全的本地开发分支及经核验的重复备份；由当前会话统一核查和收尾，无需原开发会话再次批准，也不要求用户回到原会话操作。目标是本地只保留 `main` 主工作区；不要为清理而继续旧任务、合并未验收功能或部署生产。
- 清理前核验精确路径、Git 状态、提交保全情况、正在运行的进程、自动化及正式启动绑定。未提交内容、未合并提交和有价值的忽略文件必须先形成可恢复且已验证的快照；远端同名提交或 Git bundle 可以保全提交，但不替代忽略文件保全。不得删除仍在使用或身份不明的目录，不以强制重置丢弃改动。
- 受管 worktree 使用应用提供的归档工具，保持聊天本身可用。为执行清理，用户已授权临时取消相关原开发聊天的置顶，完成后恢复原置顶顺序；需要原聊天调用其附件归档工具时，当前会话可以发送限定清理指令并核查结果，无需再次询问用户。此授权不包含恢复原开发、对外发消息或修改生产服务。
- 普通 Git worktree 与应用受管附件分别处理：核验 Git 管理目录、归属元数据及占用，确认未受应用管理、未锁定且内容已保全后，可以使用 Git 原生 `git worktree remove` 同步移除检出和登记，不需要原会话。不能只因缺少聊天归属就把普通 Git 工作树永久搁置，也不能伪造或移除受管归属来绕过归档保护。Git 登记移除后仍须检查目录；剩余 junction、空目录或其他文件单独列为残留，不跟随 junction 删除目标。
- 闲置的发布准备工作树仅在确认运行进程、日常启动及计划任务不依赖该检出后才能清理；已部署的不可变运行包及生产数据保持。下一次发布须先按发布工具要求重新准备来源，不得为省略准备步骤而放宽生产门禁。停止的隔离测试数据库及可再生缓存可随闲置检出清理，必要的独有脚本与验收材料应先校验保全，避免反复复制整套生成数据。
- 用户授权与工具能力分开判断：原会话不是审批门槛，但工具的附件范围、受管保护或系统权限仍须遵守。确实无法从当前工具完成时，记录精确路径与工具阻塞，不绕过保护直接删除，不把部分清理说成只剩 `main`。
- 历史清理只删除已解除 worktree 占用、提交已保全的本地分支；后续新开发按[开发与交付](开发与交付.md)清理本次已合并的本地及同名远端分支，恢复标签继续保留。重复备份必须先核验保留副本的完整文件清单、大小、SHA-256、备份 manifest 及可读取性，删除精确重复副本并留存审计；不得把唯一备份、生产数据或正式运行目录当作缓存。
- 结束时复查 `git worktree list`、本地分支、主工作区状态、保留副本和实际释放空间；明确区分已清理项目与尚存阻塞。该清理授权不扩展到停服、发布、迁移或业务补跑；远端删除只限[开发与交付](开发与交付.md)明确的本次已合并开发分支。

## 保护原有功能，优先复用代码

1. 开发前先了解相关代码和现有功能，优先复用已有模块、接口、组件及业务流程，避免重复开发。
2. 除本次需求明确要求修改的部分外，不得擅自删除、替换、简化或改变原有功能及业务规则。
3. 优先在原有代码上做最小必要的修复或扩展，不做无关重构，不因个人偏好重写代码或更换技术方案。
4. 如确实需要替换原有实现或改变原有功能，应先说明原因、影响范围和方案，经用户确认后执行；本次需求已明确授权的内容无需重复确认。
5. 修改完成后，验证本次需求和受影响的原有功能，确保原有能力未被意外破坏。

## 文档与长期信息维护

- 根 `AGENTS.md` 只保存稳定开发约定和路径索引。禁止追加每日开发内容、单次执行结果、发布流水、版本摘要或聊天收尾记录。
- `README.md` 面向使用者，维护当前能力、启动入口、使用方法及已确认限制。工程细则只链接到本目录，不再复制。
- 稳定业务口径、技术约束和协作流程在本目录对应专题维护；同一规则只保留一份正文，其他位置用链接引用。
- 每日开发、候选准备、生产采用与验收结果写入 `docs/<任务目录>/` 的专题报告和证据，并明确候选、已合并、已采用及适用范围。既有历史归档只供追溯，不继续充当每日记录入口。
- 任务结束时按当前用户要求，把可复用、非敏感结论写入共享记忆库相应主题；不确定事项进入 Inbox。仓库规范与运行证据仍分别以本目录和任务报告为准，历史记忆不能替代当前行为核验。
- 禁止记录密码、令牌、个人敏感信息或原始客户数据；没有长期价值的信息不为留痕而写入规范。
