# 导入、自动化与多店铺隔离

路径约定：反引号中的代码、配置和工具路径均相对仓库根目录；Markdown 链接相对本文件。

- 京东客服 `JdCustomerService2026` 固定志高商用设备旗舰店、上海09:00和截至昨天滚动30天。先在注册Default Profile的京麦首页确认会话，再进入ChatLog；身份只取唯一页头名称与title。首次缺账户组件的有界刷新不能用于已提交导出。Excel和LOG分别校验原storage目录，协议相对链接按固定HTTPS入口解析，旧下载只能为unbound。分天重解析必须与整段业务值完全等价，提交未决不重放，完整成功须精确批次、实际归属行数、日期和收尾通过。监控账本与故障边界见 `docs/JD_CUSTOMER_SERVICE_WORKFLOW.md`；历史零效果闭合回执不授权未来清理或重放。

- 所有导入必须保留来源、原文件 SHA-256、规范化业务内容指纹、业务范围、批次、店铺、数据集、覆盖日期、行数、告警和最终状态，并在返回成功前做落库回查。下载成功不等于导入成功，创建下载任务也不等于数据已经发布。
- 所有导入接口的重复判定统一为“业务域 + 精确业务范围 + 解析、清洗和业务过滤后的完整规范化内容”全部一致。行顺序、对象键顺序、文件名、原始行号和工作簿元数据等非业务差异不得触发新导入；通过校验的权威业务集合中任一业务字段、业务行数或业务范围变化都必须创建新批次。原文件哈希只用于签收、审计和原文件追踪，不能单独决定 `duplicate`，也不得用全局哈希把不同店铺、月份或数据集误判为重复。签名、解析、表头、范围或空数据等预校验拒绝只写尝试审计，不得创建业务内容指纹、抢占范围锁或改变范围状态；没有受控来源提供的权威空集合证明时，零行必须失败关闭，不能删除既有事实。分天数据的行身份仍必须包含数据集、业务日期和 SKU/SPU。
- SKU 快递费率导入固定读取名称精确为 `SKU累计` 的工作表，并以 B 列“代码”、M 列“实际金额”、Z 列“合计快递费”和 AA 列“快递费占比”为固定契约。规格代码是事实身份，快递费率必须由 `Z / M` 重算（M 为 0 时按 0）并与 AA 缓存值交叉核验；仅允许同费率或一条完整、一条空白的安全重复行折叠，冲突重复必须拒绝。每次通过校验的文件都是全量权威集合，须使用全局业务内容指纹、owner fencing、原子替换和落库行数回查；负值和超过 100% 的比率保留原值并告警，不得截断。商品经营明细只读取最新已完成批次，列位于退货率之后，未匹配规格显示 `—`。
- 同一月份、日期或快照的内容变化必须在精确业务范围内原子替换完整事实集合；被新版本移除的旧行不能残留，失败不得留下部分事实。大文件和分块上传要保留会话所有权、完成状态和可恢复性，过期 worker 或迟到响应不能覆盖新任务结果。
- 可能重叠的日期、月份或会话集合必须按稳定的业务基域串行抢占写锁，不能把整段范围集合本身当作互斥键；锁所有者必须是唯一导入尝试而不是确定性批次号。锁申请、处理中指纹和尝试审计要原子写入，完成与失败只能由同一尝试释放；事实已发布但响应丢失时，精确重试必须完成原尝试、推进范围状态令牌并另记本次 `duplicate` 尝试。粗范围状态令牌必须固定长度并从锁头 O(1) 读取，不能为每次导入扫描整个历史事实表；事实发布前要续验 owner，并在同一事实发布事务内安装 owner 提交栅栏。30 分钟无进展且状态令牌未变化的 `processing` 尝试才可原子接管，旧 owner 不得写事实、清理或完成新尝试；失败释放必须保留上一个已发布状态令牌。库存行身份使用稳定的“仓库 + 货品”业务键且拒绝同文件重复身份，不能把源行号写入事实键，也不能在 `duplicate` 路径补插事实。
- 多店铺京东任务按店铺串行执行，并使用 `config/jd-store-accounts.json` 中受控的 Chromium 可执行文件、独立 `profileName/profileDir`、调试端口和下载目录。允许四店共享同一 Chromium `userDataDir`，但启动参数必须同时传入 `--user-data-dir` 和唯一的 `--profile-directory`；商品主数据、商智 SKU/SPU 和市场榜单还必须共用一个带活进程校验的全局 Chromium 所有权锁，同一用户数据根目录不得并发启动。京东账号密码不得进入 n8n、注册表、环境变量、命令参数、日志或审计；仅注册表显式设置 `loginMode=windows_dpapi_credentials` 的受控店铺可由当前 Windows 用户绑定的 DPAPI 凭据库自动登录，在唯一账号密码表单中内存解密、填入并最多提交一次，且不得回读字段值。商品主数据导航若先停留在空白业务页、随后才跳转登录页，原首屏查询监听必须保持有效并把延迟跳转交给同一次 DPAPI 登录；登录成功却落到商家首页时，只允许在确认首轮未产生商品查询后单次返回目标商品页，不得再次提交凭据或补点“查询”。验证码、短信、滑块、安全验证、凭据缺失/损坏/拒绝、登录控件歧义或店铺身份不符都必须失败关闭并要求人工处理，不得绕过或在另一店 Profile 重试。京东商品主数据页面禁止使用带 `HeadlessChrome` 特征的模式，日常必须以普通有头 Chromium 后台运行；严格静默模式除离屏启动外，还必须按实际 browser PID 持续隐藏 Windows 顶层窗口，拒绝复用不受本轮窗口守护和执行所有权控制的既有实例。商智 SKU/SPU 分天可继续使用 `headless=new`；每个自动阶段只关闭自己启动的 Chromium，并在释放调试端口后才能进入下一阶段或切店。商品主数据自动流程必须从空白页启动，在唯一受控页面导航前监听首屏 `queryValidProductList`，以首屏响应和页面总数回显作为新鲜度证据；不得先打开未接管的重复商品页，不得在首屏查询后再次补点“查询”。普通流程在登录失效、验证码、安全验证、业务码 `601` 或店铺登录身份异常时，才允许关闭后台实例并打开当前店铺对应的可见 Chromium profile；Chromium 静默副本必须把 `silentNoWindow` 绑定进运行计划、runner 审计和所有子流程，异常时只失败关闭并保留证据，不得打开可见窗口。两种模式都必须保持原任务失败关闭、保留恢复清单并禁止自动重放业务点击；`601` 只能认定为京东服务端风控拒绝，不能仅凭无头、有头、CDP 或点击方式归因，更不能通过反检测或注入式系统输入绕过。发现同端口残留旧 `HeadlessChrome` 时，商品主数据步骤必须先关闭旧实例再启动后台有头实例；切换期间端口被其他进程接管则失败关闭。人工首次登录使用显式 `--interactive-login`。切店后必须验证当前账号/店铺身份；商智恢复清单、建立下载中心 baseline、确认创建任务和点击下载前必须从页头唯一商城链接精确核验 `shopName + shopId`，清单同时绑定 `storeKey + shopName + shopId`；不一致时失败关闭并保留/归档证据，不得接管、提交或下载另一店任务。商智公告必须等同一公告的唯一安全关闭控件连续稳定后才点击，首击无效仅可在公告身份不变时重试一次；跨日后昨天尚未开放时必须按来源未就绪失败关闭，不得缩短日期范围。不得共享会话、下载清单或恢复状态。
- 京准通 AI 推广自动化只允许显式白名单中的 `jd-yiyong-director`（“志高亿用-总监”/“志高商用设备旗舰店”/Default）和 `jd-maidehao-operator1`（“志高迈德豪-运营1”/“志高切肉机旗舰店”/Profile 2）；n8n A 节点必须通过受控请求头显式绑定店铺，后续 B/C 只能使用计划内身份，并与其他京东流程共用全局 Chromium 所有权锁。报表入口必须从当前账号的自定义报表列表按名称唯一选择“AI推广数据自动下载”，不得跨店复用另一账号的报表 ID；账号、报表名称和日期月份等异步渲染控件必须有界等待后精确读回。建立下载中心 baseline、生成任务、恢复任务和点击下载前都必须核验页面账号；只允许按报表名前缀、精确起止日期、创建时间和 baseline 之外的唯一任务接管，任务状态变化不得改变持久任务身份。CSV 必须为 UTF-8、非空、连续覆盖全部目标日且关键表头齐全；导入固定为 `source=jd_promotion`、`dataset=ad`、`platform=京东`，只有文件 SHA-256、行数、店铺、日期、零告警和精确 completed 批次全部回查一致才算完成。两店不得共享 profile、端口、下载目录、恢复清单或任务身份；生成点击未决、多个候选任务、登录或安全验证异常时保留恢复清单并失败关闭，不得重复生成或猜测历史下载。
- 天猫店铺使用共享 Chromium 用户数据根目录中的 Profile 时，注册表必须同时保存 `executablePath + userDataDir + profileName + profileDir`，且 `profileDir` 必须精确等于 `userDataDir/profileName`；启动时必须同时传入 `--user-data-dir` 与 `--profile-directory`。货品、商品日 Cookie 和推广阶段必须复用同一店铺注册项，不能回退到默认 Chrome 或旧的独立 `.runtime` profile。
- 天猫账号密码不得进入 n8n、注册表、环境变量、命令参数、日志或审计。允许的自动登录仅限注册表显式设置 `loginMode=windows_dpapi_credentials` 的受控店铺：凭据由操作者通过 `npm run tmall:credential:setup -- -StoreKey <店铺键>` 交互录入，仅以当前 Windows 用户绑定的 DPAPI 密文保存到 Git 已忽略的 `.runtime/tmall-credentials/`；A 节点只在唯一密码表单、无验证码/安全验证且店铺资源与执行所有权匹配时于内存解密、填入并最多提交一次，提交后不得回读字段值或记录明文。验证码、滑块、短信、安全验证、凭据缺失/损坏、登录按钮缺失/歧义或登录后店铺身份不符都必须失败关闭并要求人工处理，不得绕过、猜测或在其他店铺 Profile/凭据项重试。`saved_browser_credentials` 只作为兼容模式，仍只能检测并提交 Chromium 已自动填充字段，不得读取浏览器密码库。
- 天猫货品、生意参谋商品日和推广导入固定绑定 `platform=天猫`，`shop_name` 必须来自 `config/tmall-store-accounts.json` 中已启用的受控店铺；未提供店铺名时仅允许注册表恰有一个启用店铺的兼容路径，不得接受未注册或未启用店铺。每店使用独立 profile、调试端口、下载目录、签收单和恢复清单并串行运行，切店后必须核验页面可见店铺身份。商品日与推广日下载前必须分别核验当前店铺注册起始日至上海昨天的 Django/PostgreSQL 日期覆盖；按两类缺失日的并集从早到晚选择本轮目标日，保持每个完整 execution 最多一天。B/C 只补商品缺口，P 复核同日商品覆盖后只补推广缺口；已覆盖的无动作跳过不等于新批次导入完成。覆盖读取失败、旧活动清单冲突或空计划复核出现缺口时失败关闭，不得视为空库或清理证据；明确授权重采仍须走受控入口。实际导入的重复判定继续遵守完整业务内容指纹规则。采用与实测边界见 `docs/天猫商品与推广缺失日规划.md`。推广费率和推广成交占比只按两类报表的日期交集计算，商品访客只表达商品×日累计，不得估算为店铺去重 UV。阿里妈妈推广自动化只能在商品日签收导入成功后运行，入口固定为阿里妈妈“报表”→“商品报表”的受控路由；逐店精确核验页面身份与目标日期，营销场景必须全选并逐项回读货品全站推广、关键词推广、人群推广、店铺直达，维度必须同时选择并回读“商品、计划”。DPAPI 登录回跳或单页应用懒加载导致目标日期路由漂移/页面骨架不完整时，只允许一次无业务副作用的精确路由恢复；恢复后必须重新核验店铺身份、目标日期路由以及“商品报表/营销场景/商品数据明细”语义，全部确认前禁止任何报表业务点击，第二次仍未就绪即失败关闭。目标日期按升序逐日串行，每个报表起止日期必须为同一业务日，下载弹窗必须再次核对日期、时间粒度“分天”和“全部数据指标”。确认后只能点击同时包含“离线数据生成成功”和“下载任务管理”语境的成功提示内“立即前往/前往下载”，不得把广告或普通前往按钮当作下载入口；恢复已提交任务时才允许使用受控下载任务地址。下载中心必须按“商品报表”名称、唯一目标日、任务创建时间、成功状态和唯一下载动作锁定本轮任务，不得接管旧全站推或历史任务。ZIP 只有在单 CSV、商品主体、唯一目标日、店铺、大小、行数和哈希均通过后才可继续；商品+计划维度的多行必须先按“日期 + 商品”完整汇总为唯一商品日事实，再导入并完成精确批次和日期覆盖回查。旧协议活动清单一旦进入 `report_submitting`、`report_submitted`、`downloaded` 或 `importing`，新流程必须保留原证据并失败关闭，不得重置、覆盖或重复生成。
- 天猫 n8n execution 在 A 前通过原子协调门禁领取 helper execution owner，领取成功后固定按 A→B→C→P→M 串行；A/B/C/P 每日执行，M 终态入口每日调用，但只有店铺注册表 `productMasterCadence` 到期、存在未决货品活动清单或 n8n 手动完整运行显式发送强制标记时才允许产生货品导出与导入业务动作。六个已启用店铺当前均为每日到期，成功后从实际完成日顺延 1 个上海日历日；新代码只在原注册项通过校验后应用六店direct/daily策略，原注册表字节和浏览器资源保持。失败不得推进，下一次新的完整 workflow 自动补跑。定时未到期必须返回 `status=not_due`，不创建货品任务、不改节奏状态，但仍关闭本店 Chromium、释放 helper，并可作为该日 M 正常终态；不得使用日历取模 cron 或单独 M 工作流替代该持久门禁。节点之间保持该店独立 Chromium 打开，M 实际成功、`not_due` 或任一阶段失败后，helper 必须按受控店铺注册表中的调试端口关闭该实例，已关闭视为满足。M 失败不得回滚或重标已完成回查的商品日与推广事实，但整个 execution 必须失败并保留货品活动清单；`export_submitted`、`export_confirmed`、`downloaded` 等已发生业务点击的状态只能按原快照续接，不得重置或重复发送导出指令。不得扫描、复用或终止其他 Chromium 实例；关闭失败必须让 execution 失败关闭并保留业务清单和恢复证据。
- 天猫货品活动清单跨日时，`export_submitted`、`export_confirmed` 或 `downloaded` 必须先绑定原快照日续接，不得重新发送导出指令；`export_submitting` 继续失败关闭并要求人工核对，只有未发生业务点击的 `planned`、`browser_ready` 或已完成残留清单才可安全丢弃后开始新快照。

## 销售与快递费率的输入边界

- 销售明细导入以表单提交的开始/结束日期作为权威替换边界，不查询运营库推断缺失日；即使新文件最后一天没有记录，也要清除该边界内已从新版本消失的旧行。默认把该范围的销售台账视为完整业务集合；只导入部分店铺时，调用方必须提交非空、去重且纳入白名单的 `expectedChannels` JSON 字符串数组，文件渠道与声明完全一致，系统只原子替换“日期范围 + 精确渠道集合”。缺店、混入其他渠道或未注册渠道失败关闭。
- SKU 快递费率文件超过 2 MiB 时使用 1 MiB 分片，单文件最大 20 MiB；表头、内容校验和完整集合替换规则仍按本页原契约执行。

## 天猫逐日补缺候选与采用边界

六店当前默认检查截至上海昨天的最近七个完整日（不早于注册日），分别读取商品日/推广日权威覆盖，选择并集的最早缺失日，每轮最多一天；无缺口仍验证覆盖与未决任务。覆盖读取失败不视为缺数；每店原显式恢复日期及原重试锚点保持。六店P/M直连、每日持久货品节奏和实际验收状态见[生产记录](../tmall-seven-day-direct-20261007/PRODUCTION.md)；保留单日图，不带入下述历史循环模板。
