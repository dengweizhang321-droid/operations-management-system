## W5-R1 · P1：活动报告复用未持久绑定本次 clientRequestId

**位置：** [reports.create](../../backend/ai_assistant/reports.py#L87)，特别是 93–94 行活动命中直接返回；请求绑定查询在 61–65 行，只读取 `AiReportRun.client_request_id`。Worker [requestDjangoAi](../../lib/django/ai-service.ts#L115) 每次公开请求生成独立内部请求号，因此通用签名写回执不等于正文 `clientRequestId` 的持久绑定。

**触发和实测结果：**

1. 使用模型 A 和 `original-a` 创建报告；使用新号 `alias-request`、相同范围和模型 A，命中活动去重并返回原报告。该路径未创建 `alias-request` 的绑定记录。
2. 再使用相同 `alias-request` 改选模型 B。原请求查询找不到该号，B 的快照不匹配 A，实际返回 HTTP 200、新建模型 B 报告；应当拒绝同 ID 改换模型。
3. 独立第二个反例：第 1 步复用后，将原报告正常取消，再原样重试 `alias-request` 和模型 A。仍返回 HTTP 200 并创建第二份报告；同一请求号/正文随原报告状态变化产生不同结果。

**影响：** 本次“所选模型纳入 clientRequestId 请求绑定”仅覆盖首次实际创建者，未覆盖去重复用者；失去复用响应后的重试也可能重新排队并产生额外模型调用。反例未实际调用模型，只证实第二份持久任务已创建，不能声称已产生真实费用。

**原件：** 外置 `D:/codex-artifacts/ai-repair-batch2-20261108/w5/astra-review-source/backend/w5_alias_repro.py`，日志 `w5/astra-alias-repro-final.log`。从固定 Git 提交导出后端和必要仓库映射配置，使用隔离 SQLite、真实 Django 签名路由/领域事务与合成模型目录；两项测试通过表示**缺陷断言复现**，不是整改验收通过。第一轮因外置副本缺仓库映射配置在启动检查失败，原日志 `astra-alias-repro.log` 保留；补齐同提交配置后成功复现。未启动 PostgreSQL 或访问生产。
