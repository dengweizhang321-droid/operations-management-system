# 吉客云导入系统多 AI、多方法跑通测试（2026-08-06）

## 1. 结论

本轮业务目标固定为：**只有能够证明数据属于 2026-08-05 的历史快照，分仓库存和库龄才允许进入正式导入与发布。**

结论分为两层：

- 代码与工作流契约：已跑通“发现来源 → 设置并读回历史日期 → 本轮查询刷新 → 表格稳定 → 导出 → 精确下载 → 处理 → 导入 → 精确批次及当前事实归属回查”的失败关闭链路；定向负向测试通过。
- 当前吉客云账号的真实来源能力：只读检查未发现“历史库存”“库存变动”“进销存”等可用入口，当前分仓库存、库龄页面也没有可证明 2026-08-05 的历史日期控件。旧运行状态明确记录“无日期框（实时库存）”。因此本轮**没有执行真实导出、导入或重导**，也不能把旧文件、实时页面或调用方填写的 `snapshotDate` 宣称为 2026-08-05 历史快照。

这不是“任务已导入成功”，而是“系统已能在缺少历史来源时正确停止”。要完成真实 2026-08-05 发布，必须先由吉客云提供当前账号可访问、可按日查询且能精确读回 2026-08-05 的历史库存和历史库龄来源。

## 2. 方法组合

本轮按照同事提供的三份方法笔记组合执行：

| 方法 | 本轮用途 | 产出 |
|---|---|---|
| 结构化思维协议 | 意图、事实、假设、验证、自检分层 | 把“跑通”拆成来源证明、查询证明、文件绑定、导入回查和发布证明 |
| CoT 式分步验证 | 沿五类严格顺序检查每个状态转换 | 固化导航、查询、刷新、稳定、导出、下载、导入时间线 |
| ToT 多分支 | 并行比较页面下载、OSS 后备、旧文件复用、历史来源等路径 | 只保留可形成同一证据链的路径，剪除实时页伪装、共享目录扫描和固定文件名身份 |
| ReAct | 代码检查、自动化测试、现有 Chrome 只读观察交替进行 | 用真实页面能力和测试结果纠正仅凭文档作出的假设 |
| Self-Consistency / 多 AI | 三路独立审查后交叉复审 | 发现并修复无关 XHR/MiniUI 刷新误判、跨运行重放、prepared 升级、证据摘要不重算、旧库存批次冒充当前事实和批次未绑定输出文件等问题 |
| 对抗式负向测试 | 主动篡改日期、时间、运行身份、哈希、批次与归属 | 验证任何一处不一致都在导入或发布前失败关闭 |

## 3. 2026-08-05 历史快照的最小证明标准

库存和库龄必须同时满足：

1. 页面存在语义明确且唯一的历史日期控件；目标日和读回日均为 `2026-08-05`。
2. 日期读回发生在本轮导航之后、查询之前。
3. 查询刷新来源只能是本轮 XHR/Fetch，且请求 URL/载荷必须同时匹配当前模块和 `2026-08-05`，同一 requestId 必须收到 2xx 响应并完成；非 2xx、缺失响应状态、网络失败、任意 MiniUI grid lifecycle、页面 `documentURL`、通知请求和旧稳定表格都不是历史日期刷新证据。
4. `queryRefreshCompletedAt` 位于 `queryIntentAt` 与 `tableStableAt` 之间，之后才能导出。
5. schema v2 handoff 和下载 provenance 同时绑定 `RUN_ID + module + policyVersion`；下载完成时间与 handoff 完全一致。
6. 文件直接位于 `downloadDirectory/jackyun/<RUN_ID>/<module>/`，SHA-256 与字节数和 runner 实际读取值完全相等。OSS 数字对象名允许使用，文件名不再承担模块身份。
7. runner 将 handoff 时间线、历史快照证据、下载 provenance、文件哈希、业务日期和导入参数纳入完整输入证据摘要。
8. C 节点从归档审计重算摘要，并交叉核对规范路径下的原始 handoff、归档源/输出文件、清单、日运行契约和精确批次。
9. 四类非销售批次号必须由归档输出 SHA-256 确定性推导；库存批次还必须是系统当前实际选用的快照。销售回查的 `totals.rawFileHash` 必须等于本轮归档输出 SHA-256，存在 `systemCost.sourceBatchId` 时必须等于本轮库存批次，并按日期范围确认 `rowsNotOwnedByBatch=0`。
10. 任一条件缺失均不得返回完成；`prepared` 不得原地升级，completed 前缀和 duplicate 命中也必须先复验归档证据及原子 handoff。

## 4. 多 AI 交叉审查发现与处置

| 发现 | 风险 | 处置 |
|---|---|---|
| 页面 `documentURL` 可让无关 XHR 被误判为刷新 | 旧实时表格可能被标成历史快照 | 只匹配请求 URL/载荷；库存、库龄网络证据强制含目标日期 |
| 任意 MiniUI 网格共用刷新探针 | 仓库下拉等无关网格完成后可能接受旧库存表 | 库存、库龄历史证明只接受同时命中模块与目标日期的网络请求 |
| 日期匹配请求返回 4xx/5xx 后仍触发 loadingFinished | 失败查询可能让旧表格被当成新结果 | 同 requestId 必须先收到 2xx response，再完成加载；任一失败使本轮刷新永久失败 |
| handoff/provenance 缺少运行身份 | products、sales、combos 可跨运行重放 | schema v2 强制 `RUN_ID + module + policyVersion`，并约束本轮模块目录 |
| prepared 可被 direct runner 升级 | dry-run 可能伪装正式完成 | 同一 run id 永久禁止 prepared → formal |
| 合法 OSS 数字对象名被旧中文文件名正则拒绝 | 正常下载无法进入 B 阶段 | 取消文件名身份门禁，改用运行身份、目录、哈希和字节数 |
| C 节点只比较两个已保存哈希 | 审计被改写后不能独立发现 | 保存完整输入契约，C 从字段重算摘要并与原始 handoff 交叉核对 |
| `exportStart` 非法时 `Date.parse()` 产生 NaN | 时间边界可能 fail-open | 所有导航、查询、稳定、导出、下载时间先验证为有限时间戳 |
| 续跑和 duplicate 不复验已完成证据 | 损坏前缀后仍可能继续真实导入 | 续跑与 duplicate 前逐模块复验审计、文件、摘要、provenance、原子 handoff 和批次 |
| 库存旧批次仍保留行却已不是系统当前快照 | C 可能把历史残留行误报为当前发布 | 回查接口复用系统实际选择逻辑并强制 `isCurrent=true` |
| 自洽批次号未绑定归档输出文件 | 可用另一同样行数的批次冒充本轮结果 | 非销售按输出 SHA 推导批次号；销售核验 `rawFileHash` 与可选成本来源批次 |
| 直接续跑并发启动后才核验 completed 前缀 | 浏览器可能在发现损坏 handoff 前产生页面副作用 | 公共入口在启动任何 worker 前预检现有 contract、manifest、归档和原子 handoff；漏传 `--resume` 同样零启动拒绝 |
| n8n 外层丢失失败码和 stage | 无法定位日期/刷新/下载失败点 | 保留稳定 failure code，并在辅助服务响应中返回 `failureStage` |

## 5. 测试结果

- 历史日期、查询刷新、下载绑定、日 runner、直接 runner、n8n A/B/C、工作流 UI、辅助进程、续跑和精确批次定向测试：94/94 通过；项目完整单元测试：575/575 通过。
- 已覆盖的负向场景包括：无历史日期控件、日期读回不一致、刷新完成缺失、无关通知 XHR、无关 MiniUI 网格完成、刷新载荷缺少目标日、日期匹配请求返回 500、跨运行 handoff/provenance、错误策略版本、共享目录/错误运行目录、文件哈希或字节数不一致、非法导出时间、证据摘要篡改、原子 handoff 与审计不一致、completed 前缀缺失 handoff、直接续跑或漏传 `--resume` 时 worker 零启动、prepared 升级、外来批次号未绑定输出 SHA、库存批次不再是系统当前快照、销售原文件哈希或成本来源批次错位。
- 未执行生产构建：本项目 Worker 正在监听 `127.0.0.1:3000`，当前对话未授权停止或重启服务。
- 未执行真实吉客云导出、业务数据导入、重导、清理、远程迁移或部署。
