# Antigravity 系统理解与 2026-10-09 上线耗时复核

本轮由用户明确指定真正的 Antigravity（本机 agy CLI）作独立只读评估。核查范围为上海时间 2026-10-09 的上线记录与耗时，不包含生产维护、调度修改或新发布。源码观察冻结于远端 main `0308adb9f4ab37b5012ac36ea9e65dafcbe648d0`；昨天实际采用版本另按各批不可变包、原日志及报告识别。

结论：原严格保障有依据，三个成功批次均有必要验收闭合记录；从用户说“上线”到全部收尾，167～279 分钟的体验不适合作为日常小改动常态。主要改善方向是启动外围完成协议、验收误报与错误诊断、重复准入计算、发布队列和交付收尾组织。备份恢复与 Worker-only 的优化必须满足实际影响证明和现场资格，不能直接按“前端改动”减免。

## 系统理解

系统是 Windows 本机运行的电商运营平台。当前导航有 BI、市场、销售、网店、客服、商品经营、库存、运营事务、自动化中心、AI 助理、数据导入和系统设置 12 个模块，见 [导航定义](../../app/shell/navigation-catalog.ts)。业务包括跨店商品与推广数据、销售与毛利、库存与备货、客服会话、运营计划及新品跟进等。

- React/Next.js 组件约定配合 Vinext/Vite 构建交互界面；薄 Worker 提供公开 API、真实身份/范围检查、输入契约和签名转发，保留必要文件与边缘能力。
- Django 分业务域承担权威业务规则、读写服务、导入与审计，PostgreSQL 保存结构化业务事实。BI 只读聚合；AI 属于独立领域，通过受控工具访问业务能力。[当前 Django 路由](../../backend/teruisi_backend/urls.py)覆盖 12 个领域入口。
- R2 仅按领域边界保存适用的附件/图片，不能把数据库备份解释为已备份 R2 或整机。D1 留作退役证据，不进入当前正常业务或发布控制链。
- n8n 调度外部平台下载/导入，专用浏览器及 helper 处理登录、导出与下载，导入需按批次、店铺、日期覆盖回查。流程成功与真实业务完成分别证明。
- 正式启动汇聚到唯一 Worker 生命周期引擎，再验证 Django/PostgreSQL 与全部组件。Git main、准备目录、已采用 immutable Worker/Django 包是不同身份；实际有效版本由受保护 successor/effective-head 链确定。

依据：[README](../../README.md)、[系统架构](../规范/系统架构.md)、[验证与发布](../规范/验证与发布.md)。本轮是源码与历史证据理解，没有逐页测试整个系统，也没有测量当前生产性能。

## 上线时段与流程合理性

严格前后备份恢复、完整版本/权限/进程身份验证、任务排空和真实任务验收都有依据。首批涉及导入及生命周期，吉客云涉及自动化/helper；四项交互包含可执行行为，10 月 10 日新分类器对真实四文件差异仍判 strict。Django 包没有变化，单独不足以证明可获展示保障减免。

从总等待看，流程仍不适合频繁小改动：启动引擎主体与用户总等待相差很大，准入重复、失败诊断、排队和文档收尾应纳入流程目标。不能用“页面已恢复”提前宣布全部完成。

08:40 与 08:41 两批近同时批准，后批在同通道等待，且前批采用后必须重新绑定实际前驱。这是有证据的组织成本。晚间批首次维护与周报持同一互斥的记录支持调度冲突方向，但原 stderr 缺失，不能确定唯一根因。09:02:36 自然客服导入发生在旧基线后、维护前，说明验收基线还必须跟实际业务截点对齐。

没有按小时的用户访问、导入长尾和资源负载数据，不能认定上午、午休或夜间必然最佳。建议提前公布窗口，在入场前核对原任务实际在途状态、下一轮 cron、共享互斥及预计排空/切换/验收预算；剩余窗口不足就重新安排。不得为了发布擅自停用工作流或修改调度。
