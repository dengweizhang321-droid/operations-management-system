# 京东四店首屏查询超时：候选修正

日期：2026-10-04。范围：商品主数据首屏查询与登录恢复，不修改导出任务、日数据日期口径、导入接口、n8n 定义或调度。

## 已确认的证据与限制

- 原 execution 5900 在第一店 `jd-yiyong-director` 的 `verify_product_query` 阶段等待 60 秒后失败，没有创建商品导出任务；后续三店和 SKU/SPU 日数据未执行。四店 SKU/SPU 的 9 月 30 日至 10 月 2 日缺口仍须独立覆盖验证。
- 旧观察器的 60 秒期限从目标页导航之前开始，包含页面启动、登录表单等待和登录恢复。登录器本身允许表单等待及登录后等待，因此网络缓慢或登录恢复可能耗尽响应期限。
- 旧竞速分支只观察主页面 URL，可能漏掉延迟出现的登录 iframe。隔离 Chromium 夹具实际复现了“主页面商品管理、子 frame 登录”的拓扑及旧 URL 观察器漏检。
- 本机对公开京东商品页引用的应用脚本曾出现直接连接超时。这只证明该次本机直接请求失败，不能证明生产浏览器的同一次故障源于 CDN，也不能推断 API 签名变化。
- 10 月 4 日 00:55 的持久维护记录为 `EnterMaintenance`、`keepPostgres=true`、`drainedStopped=true`；随后只读组合状态为 Stopped。没有启动诊断浏览器，没有解除维护或重启服务。

## 修正后的行为

1. 在唯一目标导航前安装 request/response 观察器。响应须绑定本次实际观察到的同一 Request，继续使用原精确查询 API 白名单。
2. 查询响应的 60 秒从实际请求发出时开始。页面启动另有 60 秒预算，一次有界登录期间暂停启动预算；整体最多 200 秒，未知情况继续失败关闭。
3. 用既有 frame 分类器持续观察主页面及子 frame。验证码、密码拒绝、锁定立即停止；同一登录恢复 Promise 仅执行一次，响应先到仍等待恢复完成。
4. 原请求已发出后禁止登录恢复再次导航商品页。额外匹配请求在进入导出前拒绝，保留原任务恢复清单和全局串行锁。
5. 审计仅新增枚举、布尔值、请求次数与失败脚本计数，不保存 URL、正文、账号或凭据。
6. 新 `--inspect-query-only` 使用已有登录态、禁止自动凭据读取、可见失败重开、导出和导入；完成状态为 `inspected`，没有业务成功 sentinel。

## 验证与采用边界

验证记录见同目录工作树的 `outputs/jd-query-recovery/`：相关单测与真实隔离 Chromium 夹具、全量单测、页面契约、lint、生产构建、helper 构建、diff 检查与单店安全 dry-run。dry-run 三阶段均为 planned、completed 为零。首次全量测试缺少隔离 Python 环境的七项失败已补齐环境后复验；随后全库复跑 3,216 项通过、21 项跳过、失败零，其中已在首轮完整通过且未改动的 `worker-local-release-rotation.test.ts` 不重复执行。页面契约 20 项通过；lint 零错误、14 条未改动文件提示；全库 TypeScript 检查仍有未改动文件诊断，改动文件无诊断。

隔离浏览器使用临时 profile、路由夹具和独立拒绝代理，没有触达真实京东导出/导入，也不能当作真实四店验收。

正式 helper 从受保护主工作区启动商品导出子 CLI。因此把这三个工具文件直接写入主工作区会改变下一次真实执行；候选先保留在隔离分支，不以普通源码更新绕过采用门禁。当前另有持久维护在途，不能将该状态当成本任务的上线许可。

采用前须协调现有维护归属、核验正式状态及原发布绑定；仅在本次明确批准的窗口采用候选，沿用原备份、唯一生命周期引擎与验证门禁。先做一店只读查询诊断，再从原 n8n 完整入口执行既有补缺计划，逐批回查四店 SKU/SPU 日期；成功执行或下载文件不能替代覆盖验证。任何已提交任务保持精确复用，不清除登录态、任务 manifest 或旧失败记录。
