### 4.10 [medium][race] 迟到销售分片可把 completed 会话重新打开

**title**：迟到的销售分片 PUT 会把已完成上传会话重新改回 uploading/ready

**file**：`lib/sales/chunked-upload.ts:138-209`

**detail**：

1. `lib/sales/chunked-upload.ts:107-111` 让同一 fingerprint 的多个客户端复用一个活动会话；`app/api/imports/sales/chunks/route.ts:44-77` 允许 PUT 与 complete 并发。
2. PUT 在 `lib/sales/chunked-upload.ts:145-148` 只检查一次状态，随后 `:155-157` 写 R2，形成 TOCTOU 窗口。
3. `:159-169` 无条件 UPSERT 分片元数据，并以 `WHERE id=?` 把父会话写回 uploading/ready，没有 status、expiry 或 owner CAS。
4. complete 在 `:175-206` 没有 ready→processing claim，完成时删除 R2/分片并把父会话置 completed。
5. 可达交错：迟到 PUT 先读 ready 后暂停 → complete 完成并置 completed → PUT 恢复，重新写分片并把 completed 改回 uploading/ready。

**verdict**：

- `real: true`。
- 证伪检查：分片唯一约束在 finish 删除元数据后不再阻挡 INSERT；R2 put 在 finish 前后两种顺序都会留下“对象或元数据缺一/重生”的状态；D1 batch 只保证各自原子；单客户端顺序执行不能覆盖两个复用 fingerprint 的官方调用方并发。
- 最小修复：同构 `lib/inventory/chunked-upload.ts:174-318`：R2 写入后二次校验活动状态并检查 D1 changes；增加 ready→processing CAS、仅 processing 可 assemble、仅 processing→completed 或 processing→ready；complete 持久化终态后再清理对象。补可控 R2 Promise 的迟到 PUT、双客户端和重复 complete 交错测试。

## 7. 可复用审查模板

### 7.1 阶段零：冻结基线

记录以下信息：

- 当前分支、HEAD、`git status --short`；
- 用户已有改动及归属；
- 业务板块、写入口、持久缓存/派生表、长任务和外部副作用清单；
- 允许执行的只读测试，以及明确禁止的真实任务、部署和数据写入。

### 7.2 阶段一：单 lens 攻击

每个 agent 只能使用一个 lens；不得把测试缺失本身当成 bug。输出：

```json
{
  "title": "可证伪的缺陷标题",
  "file": "path/to/file.ts:line",
  "detail": "完整行号链；用户操作序列；预期 vs 实际；影响时长/范围；已检查但不能缓解的机制",
  "severity": "high|medium|low",
  "lens": "invalidation|race|boundary|transaction|contract"
}
```

同时输出 `coverage`，列出已审板块、写路径和明确未覆盖范围。禁止使用“可能”“或许”作为结论。

### 7.3 阶段二：独立证伪

每条候选交给未提出该主张的 verifier。verifier 必须重新读取最终源码，并主动检查：

- 路径是否真实可达，角色、状态、字段类型和时间前提是否成立；
- 是否存在全局中间件、下游强校验、数据库约束、CAS/租约或其他触发器；
- “碰巧缓解”是否覆盖所有合法写法，还是只覆盖插入新行、变更身份等子集；
- 仓库是否已有同类问题的正确修复模式；
- 最小修复是否同时覆盖运行时兼容、前向迁移和负向测试。

输出：

```json
{
  "verdict": {
    "real": true,
    "reason": "重新核实的文件行号链及主动反例检查",
    "fix": "仅 real=true；具体到文件和行号级别的最小方案"
  }
}
```

`real=false` 时省略 `fix`，并把证伪理由保留到 refuted，避免下轮重复出题。

### 7.4 阶段三：汇总门禁

- confirmed 只包含 `real=true`，按 severity 降序。
- 每条保留 `title/file/detail/verdict`，不能只留下修复建议。
- refuted 单列并保留证伪理由。
- 统计必须满足：`出题数 = 确认数 + 证伪数`。
- 报告验证应至少包含相关单测、lint、`git diff --check`；构建、真实 dry-run、生产迁移和外部任务须遵守项目服务与授权边界。
