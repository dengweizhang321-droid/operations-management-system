# 客服自动 AI 分析：最新优先、跳过无聊天记录（2026-11-17）

分支 `codex/cs-analysis-newest-first-20261117`，基点 `main` e3ecd40b。Opus 策划与反审，Sonnet 实现。
范围：Django `backend/customer_service/query.py` 候选选取 + 测试；Worker 侧只改页面提示文案与一处注释。**无迁移，不改每日上限（480）与每批条数（8）。**

## 问题

`auto_analysis_candidates` 原先在「72 小时内完成的导入批次」里用 `order_by("?")` 随机取 8 条。由于每天重导最近 30 天，窗口实际覆盖 30 天，待分析约 2.3 万条，额度被随机撒在旧会话上；其中约 15% 的候选没有聊天记录。

## 生产只读核实（2026-11-17 18:10，客服 reader 账号、只读事务）

- `messages` 100% 为 JSON 数组，元素键恒为 sender/sentAt/content。
- 空数组 `[]` 共 11,070 行，恰等于 `match_status = session_only` 的全部行；其他状态没有空数组；不存在「非空但内容全空白」的数组。故判据定为 `messages == []`（按数据判，不按 match_status）。
- 待分析 23,225 条，其中无聊天记录 3,517 条；咨询时间 10-16 至 11-16。
- 11-16 自动分析 480 条，其中 80 条（17%）无聊天记录；11-17 的 480 条额度在 00–02 点用完。
- `consulted_at` 全部为 19 位 `YYYY-MM-DD HH:MM:SS`，字典序即时间序。

## 改动

- 候选排除 `messages == []`；`pendingCount` 同口径，不再计入无聊天记录会话。
- 先按 `consulted_at` 倒序、`id` 倒序取最新 64 条作池，再从池中随机抽 8 条，按最新在前返回。
  - 为什么不严格取最新 8 条：模型对某些内容固定出错时整批不写回，严格排序会每分钟重选同一批并持续消耗模型派发额度；池内抽样让卡住的会话每轮只有约 1/8 概率被选中，新数据进来后旧会话自然滑出池。
- 保留：只选 `analysis_source == ""`（不覆盖人工标注；7255fbca 重导清空 AI 标注后的行仍会重新成为候选）、completed 且 72 小时内批次的窗口、`analyzedToday` 口径、返回字段集合。
- 页面提示改为「优先分析最新且有聊天记录的会话，每分钟最多 8 条，每日上限 N 条」。

## 验证

- `manage.py test customer_service`（SQLite）：26 个测试全部通过；新增 4 个测试：无聊天记录排除、最新池且倒序（真实随机 20 轮）、同时间按 id 倒序、少于 limit 全返回。
- 反审注入 5 种错误实现（去掉排除、恢复全表随机、去掉 id 次序、严格取最新 8 条、返回随机顺序），每种都至少有 1 个测试失败；恢复后文件哈希一致、测试全部通过。
- 生产只读 EXPLAIN ANALYZE（与 ORM 相同的 `IN (子查询)` 写法）：池查询 3.5 ms（走 `consulted_at` 索引倒序扫描）；计数 0.3–0.8 秒，与原随机查询同一量级；均低于 reader 7 秒超时与 Worker 5 秒取候选超时。

## 已知取舍

每天带聊天记录的新会话约 650–860 条，多于 480 条额度。最新优先意味着每天只覆盖前一日较晚时段的会话（当前池覆盖 11-16 21:25–23:37），较早时段的会话会被次日新数据挤出，基本不会被自动分析。若希望每日样本覆盖全天，可改为「最新一天内随机」，需另行决定。
