# 京东推广深度诊断六天首版候选

## 范围与验收口径

用户确认首份报告固定为京东「志高商用设备旗舰店」2026-09-20 至 2026-09-25，前等长周期为 2026-09-14 至 2026-09-19。09-26 不在首报范围内。首版复用现有网店推广页面、权限、京准通导入事实和 XLSX 写入能力，生成总览、趋势、计划、跟单 SKU、关键词、搜索词、词货、计划关联 SKU、计划关联关键词、搜索词关联 SKU、人工行动建议和来源口径十二张表。HTML 可离线搜索、排序、分页、按结论/行动定位精确对象、沿同一来源行查看关系并导出当前表 CSV；XLSX 的表格数值与 HTML 来源一致，并带标题行、冻结行和筛选。

确定性报告的分析类型为 `deterministic_review_draft`：规则生成待人工复核的判断，不自动修改投放，也不把京准通归因额称为店铺净销售、利润或增量效果。可选单模型解读单独标为“AI解读（人工复核）”，只解释已计算对象，必须引用可回查的证据 ID；来源身份未核实前禁止派发。用户选择沿用现有默认模型的 65,536 最大输出 Token、按实际计费；本入口仅手动触发且失败不自动重试，不更改全局模型配置。原五阶段候选中的影子库、五 Agent 签发链和额外协议不作为首版依赖。

## 系统接线

- Django 只读 `GET /api/netshop/promotion-diagnostic`：管理员、京东平台、精确店铺复合键和最多 31 天范围；按原始 `NetshopRow` 的已导入推广事实汇总，逐日对平 `NetshopPromotionShopDaily`；缺日、缺指标、未知分组身份明确返回；八种分组是同一来源行的替代视角或真实关系，不跨表相加；超行数/分组数/响应大小拒绝截断。
- Next 同名 API：沿用应用身份与店铺授权，严格过滤查询参数并代理到 Django reader。
- 推广分析页：仅在目标店铺及 1—7 日已选周期显示“生成当前周期诊断”；前等长周期单独读取，缺失或修订变化时环比留空；切换范围会中止旧请求。来源不完整时只展示缺口，不开放完整报告导出。
- 报告生成器：HTML 和 XLSX 使用同一组表格单元格；来源修订、日期覆盖、主对象分组与关系分组总行数校验失败时拒绝生成。计划按稳定 ID 汇总，未知计划不参加集中度排名；无关键词/搜索词的投放单列，不当作词效果。四类对象按稳定身份显示本期/前期/变化，新增、消失、缺身份或缺基期保留独立状态，不补零制造增幅。
- 可选 `POST /api/netshop/promotion-diagnostic/interpret`：服务端重新读取同一店铺、期间和修订，只选择有界的精确对象证据；先核来源账户昵称归属，再复用现有 `analysis-reply` 单模型入口。模型回复必须为有限结构化 JSON，全部证据 ID 在本次白名单内，每项含精确对象引用；数值仍来自确定性表，模型文字与规则分表。当前账户别名未获权威核验，因此不会调用模型。

## 实际来源的只读预核对

本机 2026-09-20 至 25 六份京准通 CSV 为 UTF-8 BOM，共 61,311 行；每份仅含一个目标业务日。六天合计花费 9,363.22 元、展现 100,460、点击 4,591、平台归因订单行 134、归因总订单金额 105,118.75 元；与当前系统推广页四舍五入后展示一致。计划 ID/名称、跟单 SKU ID 和五项核心指标在这六份文件中均有值；关键词仅在 22.22% 来源行出现，其空值行占花费约 83.27%，搜索词在 84.99% 来源行出现。六天可识别计划 27 个、跟单 SKU 581 个、有值关键词 124 个、有值搜索词 7,790 个、关键词×SKU 分组连空值桶共 1,560 个。CSV 所在账号目录与权威店铺身份的映射来自 `config/jd-store-accounts.json`，CSV 自身不提供店铺 ID；CSV 内原始账户昵称与登记账号标签不同，可能是子账号，正式采用前需对照导入批次和店铺映射核实。

前等长周期六份 CSV 的同五项合计为花费 9,809.37 元、展现 97,094、点击 4,291、归因订单行 151、归因总订单金额 121,753.05 元。两期核心表头相同；前期另有一个不可用的乱码扩展表头，不参与比较。十二个原文件摘要、日期/行数和正式 completed/零告警精确批次已只读回查，正式推广概览的十二日五项逐日聚合与 CSV 独立汇总 60/60 差值均为零。此对账不能证明原始账户昵称属于登记店铺；新诊断接口仍待正式发布后验收。

## 明确边界与剩余验收

首版暂无同店同日期的品类/SPU 映射、市场、店铺净销售、B 端销售及同比的已验收关联；报告会显示缺口，不补造这些结论。归因窗口成熟度与因果效果未独立核实。61,311 行本地内存读侧演练含三种真实关系约 9.84 MB JSON，低于 12 MiB 响应上限，但不含生产数据库 I/O。

已用十二份已完成导入清单及其原始 CSV 生成本期/前期真实数据的离线试用件，保存于 `outputs/01a0a909-291e-7c21-bd8b-9a8363c3177f/`，文件名标注“真实来源待身份核验”。这不是已发布系统的下载回执：本地合同使用 `offline-manifest-v1`，正式新 reader 当前返回 404；尚需生产查询耗时、精确批次和系统“选择周期→生成→查看→下载”验收。离线 HTML 约 5.23 MB，Chrome 本地打开、十二表切换、精确行动定位及无外网请求通过；XLSX 约 2.03 MB，十二工作表、数值、来源日期与 23,195 行搜索词×SKU 表由独立读取器复核。账户昵称到受控店铺的官方归属关系是生产采用前的剩余身份门槛。后续受控发布不触发新下载、导入或迁移。

定向验证：Django 接口权限、店铺隔离、缺日、聚合差异、响应超限；TS 报告六天日期、对象级比较、新增/消失、关系守恒、精确定位、AI 证据/回包校验、HTML 脚本语法、XLSX 同值、匿名计划防误判；现有 XLSX 读取用例回归及 `vinext build`。截至本文候选状态，生产环境未改变，真实付费模型未调用。

## 本 MVP 受控采用顺序

1. 先取得京准通账号管理的权威昵称到受控账号/店铺映射，核对店铺 ID 701455，再把精确昵称加入首版允许名单；不能用本地目录、文件名或金额一致替代该证据。重做身份门禁、两期报告与定向测试。
2. 更新到最新主线并固定候选源码，在线预置 Django 应用和 Worker successor；检查当时的 n8n/helper 与导入任务已排空。制作发布前 PostgreSQL 一致性备份，在独立端口完成恢复内容复核，并核对 E 盘归档逐文件摘要。
3. 用已部署的唯一 Worker 生命周期入口进入保留 PostgreSQL 的持久维护。按原受控 `DeployApp`/`HardenAcl`、Worker successor apply、精确退出维护及唯一 `Start` 顺序采用；不改迁移清单、n8n 工作流定义或业务数据。
4. 验 12 组件、Ready/exact_release、启动绑定、守护与既有渠道。再从正式 reader 读取本期和前期两次诊断，量取查询耗时、逐日批次/账户覆盖、五项指标、关系分组与修订一致性；页面选择六天、生成、定位对象、沿关系查看、下载 HTML/XLSX，并用独立读取器与正式响应对平。来源身份和配置均确认后才手动触发一次单模型解读，校验引用和独立 AI 表。
5. 完成发布后备份、复验及 E 盘归档。任一来源、权限、超时、产物或版本门禁失败时保留现场并按原回退流程处理，不把旧离线件冒充在线终验，也不手动补跑下载/导入。
