## 修订后的最小方案

### A：先修预算结构，不直接缩短单服务期限

保留现有6并发，单服务请求从真正发出开始计时，并保留现有4秒上限。独立设置整轮总预算，结合23项分四批及外层HTTP期限一起校准，给排队与解析留余量；不能只改内层而让外层先超时。具体总预算须由有限的慢响应夹具及现有测量确定，本轮不把猜测数值作为已验证配置。

独立方案曾建议3/13/15秒，主负责人未采纳其3秒单服务值：这会使早排的合法3.5秒响应从原先可通过变为失败，历史样本不足支持缩短。保留4秒的同时也不承诺任何高负载都能通过；整轮耗尽未发出的项目标记“未完成探测”，不能伪装成服务自身报错。

### B：只在原发布内做一次有界等待

原Start及VerifyStartup完成后，暂定总计最多120秒、失败后约5秒串行只读重查，所有请求/等待都继承父deadline并用单调时间计算。首个合法`200 + ok=true + status=ready`立即结束，不固定多等、不增连续成功门槛。最终参数与A一起验证，不能多层各自重复120秒。

合法聚合503、连接拒绝/重置及超时可在总期限内重查。认证/授权拒绝、404、重定向、不合法JSON/响应契约、明确配置/角色失败应直接拒绝；当前只有不可用服务名时不能凭名称猜其原因。持续失败仍保留FAILED，不放行到SUCCESS，也不重放Deploy/Start/迁移或自动补账。

### C：保留少量、足够定位的证据

有界解析预期JSON后再判状态。发布层记录尝试次数、总耗时、HTTP状态、固定失败类别和白名单服务名；聚合层记录排队/实际请求耗时，并区分请求超时、整轮预算耗尽、未完成探测及明确not_ready。不记录URL、SQL、任意异常文本、业务正文或凭据。

### 实施与采用范围

只改就绪探测、发布末端等待及上述有限诊断，不重做已有权限/ACL/业务探测分离，不增加自动重启或通用记账框架。有限隔离检查覆盖四批慢响应、永不响应、503→200、持续503、非法响应、父取消、总预算，以及失败不写SUCCESS/不重放生命周期动作。
