| --- | ---: | ---: | --- |

空正文的 B 样本记录：`finish_reason=length`，320 个完成 token 全部为 reasoning token，正文长度为 0。当前 B 请求最多 320 token；配置页面保存的 65,536 不会直接成为这条标注路径的输出上限。因此 HTTP 200 不能作为识别成功依据。

OpenCode 官方要求稳定的会话标识和客户端名称，并将 Go 定位为编码代理服务；长期批量业务调用的渠道适配也应据此评估。[OpenCode Go 官方说明](https://opencode.ai/v2/docs/console/go/#where-can-i-use-it)。DeepSeek 原厂文档说明默认开启思考。[思考模式说明](https://api-docs.deepseek.com/guides/thinking_mode/)。这里的“格式不可用”仅为本渠道本组请求的事实，不泛化成所有路由都不支持严格 JSON。

现有 Django AI 助理的 `provider.py` 已补 OpenCode 会话头，而市场视觉路径在 Worker 中自行拼装请求，遗漏了相同适配。这也说明，通用模型配置测试成功不能替代市场视觉适配器验证。

## 每一步是否合理以及更优方式

| 环节 | 当前事实与判断 | 建议 |
| --- | --- | --- |
| 分类标准与 Prompt | 净水 Prompt 正文描述 25 种开水器、直饮机等规则，输出却受另一套 11 类约束。技术上能返回合法枚举，业务分类仍有冲突 | 先确认采用的业务字典，再统一规则；激活前校验枚举、占位符和样本。不要以语法通过替代业务正确 |
| 候选筛选 | 按业务身份、图片和已有结果过滤，方向合理。页面全库指标与当前计划候选不是同一范围 | 明确显示本次任务范围、A/B 数量、阻塞项与复用项 |
| 创建计划 | 12 条用了 83 次 SQL；200 条约 929 次，1,000 条约 4,531 次，存在逐条读取快照、缓存与历史记录的开销 | 用集合查询或有界批量预取生成计划；保留完整身份、规则版本和来源一致性校验 |
| A/B 划分 | A 一次调用取得分类和价格，B 固定分类仅补价格；本次 12 条领取顺序符合要求 | 保留该业务设计，两类共用预算；无需把 A 再强制拆成两次模型调用 |
| 开始与恢复 | 先隔离过期领取、再恢复剩余项，保护方向合理 | “接受启动”“等待派发”“正在识别”“暂停”必须分开记录；恢复不应重置未知结果 |
| 调度 | 已取消每轮固定空等，并保留有界时间片；这只能改善派发，不能修复后续协议和数据库问题 | 保留持续补位与维护排空，先修复实际阻断，不再只扩大派发窗口 |
| 领取查询 | 生产只读等价查询约 23.6 秒；错误基数估计导致重复扫描 | 先处理统计信息与领取查询计划，保证在途身份判断有界；验证同一真实规模分布，不全局禁用 nested loop |
| 锁与回写预算 | 领取和完成使用同模型事务锁；慢领取使完成请求也等待。领取默认 30 秒，回写每次 5 秒、共 2 次 | 缩短持锁事务，避免领取堆积挤占回写能力；以预算协调和短事务解决，不单纯增加线程或延长签名时限 |
| 租约时间 | 领取的 now 在等待模型锁之前采样，拥堵会消耗发出时的有效租约预算 | 获锁及实际发出前重新核验剩余期限；结果迟到继续按既有 fencing 拒绝 |
| 图片读取 | 同哈希缓存复用与校验合理；本次能正常取到样本 | 继续优先缓存，保留哈希变化拒绝和安全回退。未证明图片处理是本次主瓶颈，不先降低价格小字清晰度 |
| 模型协议 | 市场路径缺少 OpenCode 会话头，造成明确的 HTTP 400 | 统一供应商传输适配，使用真实稳定的任务会话和诚实客户端名称；连接测试必须覆盖实际市场路径 |
| 思考与输出 | 自动思考与 320/600 token 标注预算不协调，出现空正文 | 为市场分类抽取设置独立参数；本组“会话头＋非思考”已通过。AI 助理复杂推理参数保持独立 |
| 响应解析 | 严格 JSON、分类枚举、价格类型与空值校验是必要保护 | 保留；增加 finish reason、正文是否为空、输出是否耗尽等判断，避免把 HTTP 200 当成功 |
| 错误分类 | 缺会话头的 400 最终变成通用 annotation_failed，原始供应商原因丢失，失败耗时没有完整持久化 | 配置或协议错误应立即停止新派发；保存脱敏 HTTP 状态、供应商错误码、阶段和耗时，避免消耗每张图的尝试次数 |
| 回写与幂等 | 隔离链路的结果回写、重复入库回执均正确；生产堵塞会让有效机制无法及时完成 | 保留固定请求身份及原子落库；重试存储只能重用原结果，不重新调用模型 |
| 复核与入库 | 分类和正式价格可以独立确认；无价保持 null，入库仍需人工 | 保留人工复核。明确无价、看不清、未处理及执行失败不得混用 |
| 进度与运行证据 | 新页面已区分历史复用与模型新完成，这是正确改进；原日志仍不能逐张追踪失败 | 建立任务、领取尝试、模型请求和回写之间的关联记录；单条失败应能直接定位所属阶段 |

## 数据库对照如何解释

之前生产只读对照的 23.62 秒与 36.88 毫秒来自先后两个活跃快照，候选分别为 8,486 和 8,485 条；它们没有行锁，也没有模型或写入，不能当作严格冻结的整链路基准。

本次补充了两轮隔离实验：先构建 54 个历史任务共 27,000 条合成记录，生成统计信息，再插入一个 8,558 条的新任务，刻意保留旧分布。前两项在同一个 Repeatable Read、Read Only 快照中执行；第三项在同一不再变化的数据集上仅刷新隔离库统计信息。

| 查询条件 | 第一轮 | 第二轮 |
| --- | ---: | ---: |
| 旧统计信息，默认计划 | 13,701 ms | 14,177 ms |
| 仅当前只读事务使用 Hash Anti Join | 22.71 ms | 21.57 ms |
| 刷新隔离库统计信息，恢复默认优化器 | 21.06 ms | 20.25 ms |

每轮三种方式选中的合成候选完全相同。隔离 ANALYZE 本身约 163–187 ms。**这支持先修复统计估计与查询结构，而不是在生产全局关闭 nested loop。**是否仅靠一次统计维护就能长期稳定，仍应以真实任务分布、索引和并发回写复验判断。

## 建议的修复顺序

1. **先修必须闭合的三项**：领取查询和锁内耗时；OpenCode 请求适配；市场标注专用的思考与输出参数。修复协议错误的分类，避免继续逐张失败。
2. **再用同一记录方法验证组合效果**：计划创建、A/B 领取、12 路执行、逐条回写、失败暂停、幂等和最终回读。模型返回结果与生产采用分别判定。
3. **随后减少稳定开销**：创建计划改为集合查询；模式等频繁读取状态使用适合查询的数据结构，审计保留证据职责；统一供应商能力适配，减少多个调用实现之间的遗漏。
4. **最后再评估并发或模型替换**：以新完成/分钟、正确率、限流和失败率比较，而非只看配置值。Go 的业务用途与吞吐保障需单独评估，不能靠伪装客户端解决。

正式任务中的未知结果继续隔离，不因本次样本成功而自动重置。生产统计维护、修复部署和正式识别恢复均未在本次执行。
