# 网店真实启动与业务就绪验收

本工具用于发布前捕获启动环境遗漏，以及发布后识别“结构Ready但业务读取失败”。它不改变现有liveness、`/health/ready`、看门狗或自动重启规则，也不直接执行生产生命周期、导入或通知。

两项检查分别产生可审查结果。启动检查通过不代表业务验收通过，HTTP200也不代表全景的每一路来源成功。最终生产采用仍要复核原候选/前驱/运行版本绑定，沿用原维护、备份及恢复流程。

## 启动链的实际执行范围

`tools/verify-netshop-startup-chain.ps1` 只读指定候选目录，核对已审的启动器SHA，随后在新建私有目录中调用候选本身的 `Invoke-WithDjangoEnvironment` 和 `Start-ManagedProcess`。它启动真实Python子进程、Waitress和候选Django WSGI，读取动态回环端口的 `/health/live`，核验角色、只读属性和三路reader地址确实传入子进程。

Windows虚拟环境的Python可能有启动转发进程，工具按真实父子PID和nonce核验归属。正常发出本次私有退出信号并等待；超时时仅回收自己已经核验的私有进程，报告失败。不会按端口或进程名终止生产服务。

候选应用要求production数据库配置固定5432，因此子进程仅使用合成数据库身份，并在导入候选前封闭psycopg连接入口；不会连接生产数据库。该检查验证真实环境/进程/WSGI链路和liveness，不声称已经执行原完整Start引擎、数据库恢复或跨域业务读取。跨域真实读取由下一项检查负责。

调用示例，路径和摘要须取本次已核实候选，不能照抄旧记录：

```powershell
powershell.exe -NoProfile -File tools/verify-netshop-startup-chain.ps1 `
  -CandidateRoot '<已准备且经原清单验证的候选目录>' `
  -PythonPath '<按候选requirements安装的独立venv>\Scripts\python.exe' `
  -ExpectedPythonVersion '<目标运行环境的精确Python版本>' `
  -ExpectedLauncherSha256 '<已审tools/django-local-service.ps1的SHA256>' `
  -EvidenceDirectory '<候选目录之外的新证据目录>'
```

使用实际计划运行的PowerShell和Python版本验收，子进程核验Python版本及候选requirements中的精确包版本。环境函数兼容5/7时，两版本均验；不能用一版结果代替另一版。证据目录必须不存在、不得位于生产runtime或候选内。工具不安装依赖，不加载生产DPAPI凭据，也不将调用者环境中的业务变量透传给私有子进程。

输出 `startup.json` 包含候选启动器及WSGI摘要、PowerShell版本、子进程归属、三路配置存在/精确匹配、liveness及退出结果；不输出数据库密码、令牌或全环境。退出0仅表示本启动合同通过，退出2表示门禁失败。脚本执行异常非0同样失败。

## 独立业务就绪检查

在与当前候选对应的已启动隔离栈中先验；生产采用后可由原发布负责人显式进行同一组只读检查。先通过原部署工具核实运行身份，不将其他环境的成功结果绑定到当前候选。

```powershell
node --import tsx tools/netshop-business-readiness.ts `
  --base-url http://127.0.0.1:3000 `
  --platform 京东 --shop '<当前账号获准的精确店名>' `
  --start '<YYYY-MM-DD>' --end '<YYYY-MM-DD>' `
  --output '<新建的业务就绪报告.json>'
```

工具只允许明确的127.0.0.1 HTTP端口、一个精确店铺、1至7个自然日。API路径固定，全部GET；不允许外部地址、重定向、自定义接口、请求正文或任意请求头。沿用目标Worker已有真实鉴权，401/403直接失败，不注入伪principal、不加载或输出凭据。若目标环境要求浏览器登录，本CLI不会绕过该要求。

检查顺序为liveness、结构readiness、总览、商品、推广、全景、对比。复用已有完整业务DTO解码器，验证请求范围、来源版本与字段合同，不另写简化的“200就算成功”。全景进一步检查全部六来源（特别是销售、财务、经营事件），对比检查ERP和推广来源；嵌套来源错误同样不能掩盖。

| 结果 | 含义 |
| --- | --- |
| passed | 本检查真实读取和合同通过；仍可能有合法数据缺口 |
| degraded | HTTP、权限、传输、超时、格式或嵌套业务来源失败 |
| unverified | 未运行、总预算耗尽，或依赖因为无映射/未接入等原因未实际验证 |

`businessReady=true`要求所有检查通过。`dataGaps`单独统计已验证指标的缺数原因，不将缺字段/缺日改成0，也不把传输失败标为缺数。选择的店铺若不能实际行经某个必需来源，报告unverified；须由负责人选择合法且有对应映射的测试范围，不能删除该来源检查。

默认每请求最多20秒、整次最多120秒、响应最多2MiB，顺序执行、无自动重试。超时或撤权后不继续发更多查询；未知/未执行项目保留unverified。没有放宽业务API原预算，也不声称HTTP取消会杀死数据库SQL。该时间门槛用于发布冒烟，超时可能是查询慢，需要原负责人检查，不能直接判为数据库坏或启动重启。

输出只保存探测状态、HTTP状态、耗时、字节数、来源状态和缺数计数；店铺以请求scope摘要绑定，不保存业务明细、原始异常或客户资料。退出0表示本次业务检查通过，2表示未通过，1表示参数或报告写入异常。报告文件create-only，禁止覆盖旧证据。

## 纳入原发布流程

1. 候选准备后，先按原规则核验完整包，再运行启动链检查；缺依赖配置不得进入“可采用”状态。
2. 在对应隔离栈完成业务检查及原M7必要验收，保存准确来源版本、scope和运行身份。启动测试本身的私有liveness进程不能被当作业务栈。
3. 获批采用后，保持原维护与恢复流程。先取得原结构就绪和启动绑定，再运行限量业务检查。结构Ready、业务degraded应分别报告，不能宣称五栏目全部可用。
4. 有任一必需检查未通过时不签发本次业务验收完成；按原负责人决策处理最小修复或恢复，不由本工具改数据、清队列或重启。
5. 不把检查挂进每分钟看门狗反复执行重型查询，也不创建新的定时任务。常态低成本观测如需扩展，另行定义采样与预算。

## 本轮验证边界

Windows PowerShell5和PowerShell7分别对真实准备候选与未含peer注入的主线基线执行原启动函数/原受管进程、Waitress/Django WSGI。两种来源的liveness均通过，但旧基线在两版本中都因三路配置缺失明确失败；修复候选通过。该正反例能够重现本次“进程可用但依赖配置缺失”的遗漏。

业务工具使用现有独立PostgreSQL生成的完整六来源捕获，经原解码器核验，再通过独立动态端口HTTP验证运输、内部失败和脱敏。另测403、重定向、非法UTF8、超长响应、真实慢HTTP超时、取消和不完整DTO。它们证明工具行为，不冒充新的生产经营数据或全栈生产验收。

本轮不修改正式控制器/公共路由，三peer配置补丁仍由原总控独立维护；本工具不能替代其审查或授权。本轮也未修复业务SQL超时，配置、传输和查询问题分别记录。
