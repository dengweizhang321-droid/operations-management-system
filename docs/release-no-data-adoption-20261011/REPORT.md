# 无数据发布规则：首次采用准备与独立复审

本轮补齐真正采用新规则所需的源码绑定、配套 Django 工具、限定迁移闭包验证和现场准入时效修正。C 按用户选择只准备、复审，统一安排发布。源码合并、候选准备与生产采用分开记录；此文件不构成生产批准。

## 规则及适用范围

| 判断 | 原流程 | 新流程 |
| --- | --- | --- |
| 已证明本次及部署无持久业务数据影响 | full/reuse；复用资格不足回到两次备份、两次演练 | v3 封存为 not-required，数据库 operationIds 为空；保留源码/制品完整校验、排空、原切换、权限及实际功能验收 |
| 写逻辑变化、结构兼容 | 完整保护流程 | 首轮仍完整流程；未来按具体写风险设计恢复点、隔离写验证与旧版兼容，不在本轮自动化复杂类别 |
| 迁移、批量修正、存储或恢复机制改变 | 完整保护流程 | 保留严格流程，单独制定本次保护与恢复验证方案 |
| 日常备份或演练异常 | 容易与每次功能发布捆绑 | 独立呈现健康、影响与处理路径；在途操作与所有权正常阻断 |
| 本次新机制首次采用 | 尚未采用 | strict/full，四数据库阶段保持，精确范围另批 |

首轮支持同结构 CSS 展示值及满足被动字面量边界的 TSX；全前驱到候选差异、调用/副作用、启动/构建输入、独立 effects 复审与固定操作词汇必须闭合。不能按目录、GET、Django 摘要或人工布尔值判断。经审查的只读展示若尚未落入机器支持范围，明确缺口并使用严格流程。无数据描述针对发布引起的影响，不要求整个业务数据库在上线期间停止正常变化。

## 本轮必要实现

- 原准备器支持精确、完整 SourceBinding 信封；源码路径、原始身份、真实前驱及 chain-state 与原 manifest/plan/receipt/batch 一致。固定其他任务来源目录不改，来源选择失败不回退另一目录。
- 配套 Django 保持全部业务/config/drizzle/依赖和原维护、服务工具；只更新同字节 verifier/rotation。原 PrepareApp 实际产生第三个 CF 缓存差异，单独按精确原始 hash、六个传输 leaf 与全部其他字段不变封存；不设置通用缓存忽略或 TTL 字节放行。
- tools-no-migration-v1 限定 v3 strict/full、十控制文件完整差异与实际执行字节、前后两份完整 Django 清单/库存及现场重读。只把测试类别 migration-rehearsal 换为 migration-closure，不免除四生产数据库阶段，不伪造 PG 恢复已执行。
- 将慢核放在末尾动态采样之前，末核 chain/head/path、Django 和 WAL；保留真实 native 返回时间，5 秒以外、倒退及无效时钟拒绝。旧 helper 无新 DTO/export，故仅在 collector 内做既定白名单投影和原失败记录持久化，不引入第十一工具或额外健康探针。
- 真观察器原把回执写入 numbered WAL 子目录，导致下次读 WAL 失败；改为同级 _observations，真实 wrapper 的失败存证后回读测试覆盖该缺口。
