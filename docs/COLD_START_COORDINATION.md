# 开机后首次打开的并发启动等待

## 现场原因

2026-09-21 22:18 重启后，登录 Django 守护于 22:20:19 开始恢复后端，22:21:40 完成，耗时约 81 秒。第一次桌面请求随后进入同一 Django 生命周期锁，从 22:20:39 等到 22:21:09，触发原固定 30 秒等待期限。总控返回 failed/StatusError，后台原启动却仍继续。22:21:25 发起的第二次桌面请求最终于 22:23:58 成功。

这与此前 `f1fdafb2` 的共享回执读取错误不同：新现场有明确的后端锁等待失败回执。服务已运行时的打开测试不足以验收开机冷启动。

## 候选变更

- Django 仅完整 `Start` 在锁争用时最多等待 900 秒。取得锁后先复验维护状态、有效且匹配本控制器的 running 意图；守护请求仍须通过原始精确意图摘要核验。随后执行原幂等启动和全部域就绪检查。Stop、Deploy 及其他操作的原 30 秒锁等待不变。
- Worker 仅 `Start` 在生命周期锁忙时最多等待 900 秒。加入已有操作后只读取结果：精确 Worker/helper 身份、全部后端就绪、首页 HTTP 200 和 helper 健康均通过才返回 already_running。原操作若停止了服务、留下不明状态或后端未就绪，后来的请求报错，不启动或重启任何组件，不重新派发钉钉渠道。
- Worker 其他变更操作仍非阻塞拒绝竞争。连续持锁、同线程重入、不可变版本及端口身份门禁保持原有协议。
- 桌面收到总控 start_in_progress 后继续检查就绪，等待期限由 3 分钟改为 15 分钟；提示冷启动可能需要几分钟。窗口关闭后不再由该等待分支打开浏览器，超时仍失败。桌面主动派发的既有 `Start -Open` 行为保持不变。

900 秒是各等待边界的上限，不是完整启动耗时承诺，也不是无限重试。重复请求仅在合法运行意图和原安全检查通过时推进；没有绕过迁移、权限、ACL、维护、release 或 readiness 检查。

正式采用需在本轮获准的维护窗口，按 `STARTUP_RELEASE_OPTIMIZATION.md` 的候选准备、备份及独立恢复、排空、持久维护、版本切换和完整就绪回查流程部署两个控制器，再安装桌面启动器。不得重启 n8n、手动补跑数据工作流或发测试消息来验收本修复。
