# 发布交付流程简化

2026-10-13；开发基线 `4807ac54b5fecde767ff61500fcbd51dfd132a7f`。

## 用户要求与最终流程

用户要求从第 4 步起只保留“验证修改功能、合并同时生成制品、发布”。范围识别及组件选择保持既有方式，后续流程如下：

4. 验证本次修改功能及直接受影响路径，不默认运行全量单测、全仓 lint 或无关模块验收。
5. 验证通过后，在同一次连续交付中合并、推送并从最终合并提交生成受影响组件的制品。构建包含在制品准备中，只执行一次；纯文档、测试或离线工具且应用载荷未变化时不生成应用包。
6. 已获本次上线授权且制品就绪后发布，只检查版本、必需服务就绪及本次修改功能，随交付完成记录和清理。

完整正文见[验证与发布](../规范/验证与发布.md#常规发布的三个交付步骤)，开发交付见[开发与交付](../规范/开发与交付.md)，批次衔接见[发布批次协议](../RELEASE_BATCH_WORKFLOW.md)。根 AGENTS 只更新稳定约定。

## 工具变更

`tools/release-scope-plan.mjs` 输出协议升级为 `teruisi-scoped-release-plan-v2`，增加按 4、5、6 步排列的 `workflow` 清单。普通前端只要求修改功能测试；普通后端不再固定加入迁移 dry-run 或系统检查；迁移检查只在 migration 变化时加入，共享或未知影响保留受影响集成路径验证。生产构建归入既有对应制品准备，不重复列在功能验证阶段。

此工具只生成计划，不执行合并、构建、生产写入或服务操作。原组件分类、数据库保护、迁移部署动作保持；既有批次合同及已安装运行包未更改。原 v1 计划不能冒充新 v2，摘要同时绑定流程和提交。
