# 五阶段经营分析：剩余开发与验收顺序

核对日期：2026-09-17。范围是当前独立候选工作区，包括正在集成的商品关联报告与工作台代码；不是 main、生产 release 或正式数据库的状态证明。本次只读代码与项目文档，没有读取生产数据、启动服务或调用模型。本文不改写历史批次记录。

## 判断口径

用户目标是让系统按不同经营问题，结合店铺、市场、店铺销售和 B 端销售，由多个 Agent 协作产生可追溯诊断、调整规划及工程级 HTML/XLSX。两个参考文件是质量样本，不是固定模板。原五阶段仍是「数据与计算基础 → 多 Agent 闭环 → 完整诊断与规划 → 工程级文件与规模 → 工作台与正式验收」，开发批次数不是阶段数。

候选已具备主要工程链路，不能再将预算、持久多卷或商品关联全部列为尚未开发；也不能据此宣称五阶段全部验收。用户已授权持续开发，下面的普通开发、合成测试与独立复审可以连续推进，无需逐批询问。真实付费运行、生产采用及服务维护按现有授权与项目流程处理；不要把这些验收边界变成日常开发的反复确认。

四种状态必须分开：

| 状态 | 含义 |
| --- | --- |
| 已实现候选 | 实际代码存在，并有对应测试；不等于该版本全部回归已通过或已上线 |
| 真正未开发 | 当前链路没有该能力，必须增加协议、实现或产品交互 |
| 合成待验 | 能力已有，但仍需在最终组合版本执行特定测试；测试文件存在不等于已运行通过 |
| 真实验收 | 需要真实来源、真实模型判断或受控采用才能完成；不得用 mock、合成金额或截图替代 |

## 可执行的后续顺序

### 1. 当前关联工作台链路（候选合成已验，真实验收仍缺）

已有固定 `mappingPlan`、独立执行 profile、数据库绑定、工具证明及完整映射文件；[集成报告测试](../backend/ai_assistant/test_business_integrated_reports.py)和[映射文件测试](../backend/ai_assistant/test_business_mapped_export.py)已覆盖有/无预算的合成路径。工作台父级集成仍应以最终冻结版本的结果为准，不能用独立组件通过代替父级通过。

最小下一步：完成「已封存来源 → 显式选择本期/环比/同比关联 → 无预算/有预算两条报告创建 → 五 Agent → 人工复核 → 多卷下载」组合验收。增加重读失败后不静默降级无关联报告、同任务版本变化、账号切换、提交未知刷新后同 UUID/同 body、目录不足/映射歧义、映射与预算并存的断言；最终构建、旧 catalog 摘要、迁移/备份恢复一起核验。旧参数/旧文件/旧 profile 字节保持是回归条件，不是新增功能。

进度更新：第二十七、二十八批已完成上述后端五 Agent、文件与工作台的合成组合验证；第二十九批又复验了五份独立读取证明和文件交付。具体通过项与首次失败、最终复测分别保存在 [集成报告证据](evidence/ai-business-integrated-report-candidate.json)、[工作台证据](evidence/ai-business-mapping-workbench-candidate.json) 和 [复用证据](evidence/ai-business-content-reuse-candidate.json)。后续变更按影响范围回归，不能把此前合成通过称为真实模型或生产采用通过。

### 2. 权威身份选择，再做自然语言范围建议（部分候选实现）

[预览服务](../backend/ai_assistant/business_planning.py)明确不读取事实；[规划器](../backend/business_analysis/planning.py)接受用户填写的精确平台、店铺、渠道、市场条件和日期；工作台仍是问题文本加显式表单。`canCollect` 是支持性与表示容量检查，不是店铺存在、历史齐全或模型已经理解问题的证明。

最小切片先做有界、只读的权威身份/来源可用性选择器：由各 owning reader 返回精确店铺、渠道、市场条件、来源及可用日期边界，显示无数据与无权限的区别；选择结果绑定身份版本，不通过名称猜 ERP 渠道。接着增加「问题 → 候选分析目的、日期和来源建议 → 展示匹配理由与歧义 → 用户确认精确范围」步骤。可以先使用确定性日期/目的解析；模型只提出候选，不能自行制造或替换真实身份，也不能自动开始付费分析。

验收：同名跨平台、别名冲突、渠道空值、输入未知店铺、去年同期/闰日、缺源、问题与表单冲突、49 来源完整拒绝、权限变化、源文本提示注入。没有可靠匹配时保留待选状态。原手工入口和未知提交的冻结 body 保持兼容。

进度更新：第三十批已实现网店精确来源元数据 GET 和签名分页，后端新旧接口 21 项测试通过；未接 UI，也未实现 ERP/市场独立选项。历史导入日期明确不证明事实完整，见 [选项证据](evidence/ai-business-source-options-candidate.json)。

### 3. 补店铺独立总览，并核清跨源指标（真正未开发 + 真实来源验收）

[网店适配器的 SOURCES](../backend/netshop/analysis.py)只有 promotion/sku/spu/b2b/master；`productDayVisitors` 已正确标为商品×日累计，不能作为店铺去重 UV。现有 `dimension=shop` 是所选事实的店铺聚合，不是独立的店铺总览来源。系统其他页面可能有统计，但本经营证据协议尚未接入可证明区间去重的店铺 UV。

最小下一步：先确定平台提供的是日去重 UV 还是所选整个区间去重 UV，以及成交、订单、退款的真实口径；日 UV 也不能相加冒充区间去重。建立独立源/字段/覆盖/版本合同，接入 owning reader、规划、封存、分析表与文件。拿不到区间去重源则明确返回不可用，不能反推。增加推广归因成交、平台销售、ERP 净销售/成本/毛利、B 端金额并排对账，注明包含关系，禁止直接求和。

验收：真实平台导出与系统汇总对照、跨商品/跨日重复访问、跨店、缺日、退款和补差、B 端与总销售是否重叠。ERP 当前主数据映射不能证明历史归属，映射毛利不能推成关键词利润；这两项限制保留。

### 4. 派生结果复用与长期采集恢复（单次复核复用已有，持久复用与续签仍缺）

**派生复用。** [普通分析分页](../backend/ai_assistant/business_evidence.py)的 `analysis_table()` 每次从证据块重新 `build_table()`；[映射分页](../backend/ai_assistant/business_mapped_analysis.py)每次重新建立临时分区。当前的请求内缓存、临时 SQLite、同一次导出的 spool 不等于跨 Agent/跨请求的持久派生结果复用。

进度更新：第二十九批在集成报告一次完整 `content()` 范围内复用规范分析页及预算，保持每 Agent 独立证明与实时授权；映射页重算由 3 次降至 1 次、预算由 6 次降至 1 次。下一次复核仍重新计算，不能将此结果计为跨请求分页或持久派生存储已实现。

最小切片：按 owner/scope、证据版本/封存摘要、完整查询、维度/比较窗口、固定映射计划和算法版本生成派生键；完整核验一次后原子发布只读分区，后续有界分页。读取仍重新授权，计算失败不发布部分分区。新增存储必须有独立字节/行数/任务配额、并发构建幂等、清理与恢复政策；不能把缓存做成无界第二事实源。验收重复多页/多 Agent 读不重复扫描、失效与篡改拒绝、权限撤销、并发、磁盘满和独立恢复。

**过期游标恢复。** [网店](../backend/netshop/analysis.py)、[ERP](../backend/sales/analysis.py)、[市场](../backend/market/analysis.py)的签名游标均 `max_age=3600`。[采集器](../backend/ai_assistant/business_collection.py)已有暂停/恢复和有限只读重试，但未实现过期游标受控续签；长时间暂停仍可能需要新建采集任务。

最小切片：仅由 owning reader 在原 query、源 revision、sourceRef、页长、lastId 与持久检查点一致时换发下一游标；固定窗口不变。源已变化则停止，提供明确的新任务重采入口并关联旧任务，保留旧页，不能从首页与旧页拼接。验收过期但版本不变、版本变化、取消竞态、重复续签、篡改 lastId 和跨店/跨 owner。模型未知结果不因取数恢复而重放。

### 5. 建立诊断质量及多店多期验收集（质量门禁尚缺，不是重写已有 Agent）

[诊断校验](../backend/ai_assistant/business_diagnosis.py)已强制对象、改动、前提、指标、观察期、回退、责任角色、优先级和预算影响；它核对引用数值，不能证明文字因果或建议有效。[集成读取证明](../backend/ai_assistant/business_integrated_receipts.py)保证各 Agent 的目录、必要预算及映射页读取；至少一页映射也不等于读完整事实。完整明细文件可取得与模型已全面诊断必须分别陈述。

最小下一步：建立版本化问题集、人工可复算的关键事实和建议评分表。先用合成源验证事实/缺口/动作结构，再在许可的真实问题上验收专业 Agent、独立复核和整合稿，记录漏项、矛盾、错误归因与修改。若报告需要声称「全量异常筛查」，先增加确定性的全量扫描摘要/异常候选及覆盖证明，再让模型解释，不能因读完目录就给全量结论。

首组问题覆盖：费用上升销售不升、某 SKU 退款侵蚀毛利、B 端与零售结构变化、市场入榜/出榜变化、跨店同 SKU 表现分化、同比缺日/缺店/负基期、预算不可行及参数不完整。至少两个店铺、current/previous/yearAgo、多个渠道，分别有完整来源与缺源版本。近期/中期规划须有明确观察期和优先次序；预算情景只表达固定假设，不保证收入。按证据准确性、完整性披露、原因可信度、动作可执行性及风险回退评分，保留不合格样例用于回归。

### 6. 验证实际规模与参考文件质量，再决定容量变更（合成待验 + 真实验收）

[19 来源全链路](../backend/ai_assistant/test_business_workbench_catalog_acceptance.py)及[156 表导出](../backend/ai_assistant/test_business_export_catalog_acceptance.py)已提供工程合成基线。48 来源是目录上限，不保证每份事实能装入 64 MiB/2000 页，也不保证每个模型可容纳该任务；[模型预检](../backend/ai_assistant/business_integrated_preflight.py)继续决定能否运行。单表 100 万行、单文件 256 MiB、每任务文件总额 1 GiB 等边界不能靠界面承诺扩大。

最小下一步：选一套完整多店多期、接近用户参考文件规模的可复现实例，记录事实字节/页数、分组数、临时盘、峰值内存、耗时、模型输入/调用/费用和完整表数。超限必须完整解释并拒绝，不能裁掉来源或明细。当前按表/行规划多卷，字节超限整批拒绝；若真实样例需要按字节动态拆卷，再作为明确新功能实现，不宣称已有。

双格式逐指标/缺失/比较/映射/预算一致；HTML 搜索排序分页与移动显示，XLSX 数字类型、冻结、公式、预算联动和打开复算分别验收。参考报告还需人工对照诊断深度、可读性和调整计划，不只比较扩展名、工作表数量或样式。本次审查没有重新打开用户两份原始参考文件，不把视觉/业务质量对照记为已完成。

### 7. 真实端到端与受控采用（外部条件验收）

按前述最小集合核验真实来源身份、日期覆盖、金额和历史；只读查询计划/超时必须在实际数据分布下验证，合成规模测试不替代正式执行计划。真实多 Agent 验收须明确使用的模型、成本上限和完整问题范围，保留实际调用与独立复核结果，不以 dryRun 或 provider 替身宣称模型效果通过。

源码、全部定向回归、升级/旧记录摘要、最小角色、备份独立恢复及回退条件通过后，再按项目既有受控流程采用。采用后核验身份权限、精确 release、工作台、任务恢复、已复核文件下载和真实业务结果；通知/投流修改不是本目标的默认动作。最终交付记录要区分「候选通过」「真实业务通过」「已采用」，并逐项关闭原五阶段放行条件。

## 文档与交接约束

[主说明](AI_BUSINESS_ANALYSIS.md)混合了历史批次状态：早期的「没有诊断协议」「预算未接入」「关联仅内部」不能作为当前全部代码状态；现候选已有上述实现。反过来，新的测试/组件存在也不能自动覆盖主线程尚未完成的组合验证。本文件只给剩余执行顺序，不在本次改写旧文档或提前宣告最新候选发布。

可并行的下一轮分工：一人完成当前入口组合验收；一人做权威身份/范围建议；一人做店铺总览源合同；一人独立复核。派生复用与游标续签再按所有权拆开实施，共享迁移、PG、整体构建和提交仍由主线程串行协调。每项用代码证据、实际测试和剩余限制收口，不再用「新增一批」代替阶段完成情况。
