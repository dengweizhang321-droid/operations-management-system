# TERUISI 运营管理系统 AI 能力重构：1—3 层推进文档

> 创建日期：2026-07-29
> 参考资料：`LLM与Agent框架图-2026-07-29(2).html` 仅用于分层与风险检查，不复制其中的 Django、Celery、钉钉身份或接口设计。
> 实施基线：仓库 `main`，起始提交 `d556676`。
> 本阶段范围：①入口层、②问答管线、③模型接入层；中央工具注册表及业务工具实现保持唯一事实源。

## 1. 目标与完成定义

本轮不是另建一套 Agent 框架，而是把系统已有 AI 能力整理成一条可测试、可取消、可审计、可继续扩展的主管线：

```text
已认证入口
  → 入口上下文（真实 principal / surface / requestId / AbortSignal）
  → 问答 Workflow（校验 → 短路 → 历史边界 → 模型路由 → 工具循环 → 持久化/审计）
  → 模型网关（OpenAI compatible / Anthropic）
  → lib/ai/tool-registry.ts（唯一工具注册表）
  → 有界业务 handler + D1/R2
```

以下条件全部满足才算 1—3 层完成：

1. 网页对话不再自行拼接模型、权限和工具参数，而是创建统一入口上下文后交给问答 Workflow。
2. 用户身份与角色只来自 `requireAppPrincipal()`；模型参数中不得出现可覆盖身份、角色或数据范围的字段。
3. 问答 Workflow 能执行无需模型的短路分支，支持上下文断点，并为模型分支统一拼装系统规则、有效历史和工具执行上下文。
4. 浏览器停止请求时，同一个 `AbortSignal` 贯穿模型请求、轮次边界和工具执行前后。
5. 新旧会话均可显式选择已启用的文本或视觉模型；已有会话切换后从下一条消息生效，未指定时才回退默认文本模型。
6. OpenAI compatible 与 Anthropic 的请求、超时、输出限制、工具协议和错误处理收敛到模型网关；客服文本 AI 复用同一网关。
7. 每个文本模型的超时、最大输出、温度、工具轮数和总工具调用数均有服务端边界，不能由客户端或模型任意放大。
8. 工具仍只在 `lib/ai/tool-registry.ts` 注册一次；角色过滤、scope、审计和 handler 边界不出现第二套实现。
9. 数据库迁移、运行时旧库补列、API、页面和测试同步完成；不停止或重启正在运行的本地 Worker。

## 2. 现状盘点（以本仓库为准）

### 2.1 已具备的基础

- 网页入口：`app/api/ai/chat/route.ts` 使用 `requireAppPrincipal()`，analyst/operator/admin 可提问。
- 对话数据：`ai_conversations` 与 `ai_conversation_messages` 已持久化。
- 模型配置：`ai_models` 已加密保存 API Key，支持 `openai_compatible`、`anthropic`、text、vision。
- 模型安全：模型端点限制、禁止重定向、响应体 2 MiB 上限和总超时已实现。
- 工具总线：`lib/ai/tool-registry.ts` 是单一注册表，生成 OpenAI/Anthropic schema，并在真实 principal 下做角色、scope、参数和审计校验。
- 外部入口：MCP 已直接复用中央工具注册表；企业微信回调仅验签、解密和去重，不会自动执行消息内容。
- 页面内旁路：市场视觉标注和客服批量标注有独立业务引擎。

### 2.2 当前缺口

| 层 | 缺口 | 风险/影响 |
| --- | --- | --- |
| 入口层 | 网页路由直接负责会话、模型、消息和生成；没有标准入口上下文 | 新增入口容易复制权限与审计逻辑 |
| 入口层 | 页面没有“新对话 + 模型选择”；发送只能阻塞等待 | `ai_conversations.model_id` 形同虚设，用户无法停止长请求 |
| 问答管线 | 没有独立 Workflow；所有问题直接烧模型 | 帮助、新话题等确定性请求浪费 token |
| 问答管线 | 历史只是最近 24 条，没有上下文断点 | 用户无法可靠开启新话题 |
| 问答管线 | 请求取消没有贯穿 fetch 和工具循环 | 浏览器停止后后端可能继续调用模型/工具 |
| 模型层 | provider 调用散落在 `assistant-service.ts` | 配置测试、聊天、客服 AI 容易产生不一致 |
| 模型层 | 超时、输出、温度和工具预算是代码常量 | 不同模型无法安全调优 |
| 模型层 | 已有会话仍每次解析默认模型 | 模型切换后，同一会话上下文与模型不稳定 |

## 3. 本系统的三层目标架构

### 3.1 第一层：入口层

新增入口契约，至少包含：

```ts
type AiEntryContext = {
  principal: AppPrincipal;        // 仅服务端认证产生
  source: "web_chat";             // 本阶段真正接入问答主管线的入口
  surface: "ai_chat";             // 进入中央工具审计
  requestId: string;              // 接受合法 x-request-id，否则服务端生成
  signal?: AbortSignal;           // 浏览器断开/停止时协作取消
};
```

入口矩阵：

| 入口 | 本阶段处理 | 身份边界 |
| --- | --- | --- |
| 网页“小特对话” | 接入统一问答 Workflow | `requireAppPrincipal()` |
| MCP | 维持直接调用中央工具，不绕到自然语言管线 | MCP 认证映射出的真实 principal |
| 企业微信/钉钉回调 | 继续只验签与防重，不把消息自动交给模型 | 尚无应用用户映射，禁止冒充站内用户 |
| 客服 AI | 维持业务批处理入口，文本生成改为复用模型网关 | 站内 principal + 专用 surface |
| 市场视觉 AI | 维持视觉任务引擎；本轮不强行改成文本问答 | 管理员 + 任务模型 ID |
| 定时问答/报告 | 不伪造入口；待有持久化调度身份和配额后单独实施 | 必须绑定真实创建者与可撤销授权 |

本阶段不把外部聊天回调直接变成经营问答入口，因为当前数据库没有 `staffId/openId → app_users` 的唯一、可撤销映射；直接接入会破坏中央权限原则。

### 3.2 第二层：问答管线

Workflow 固定顺序如下：

```text
W0 验证入口与消息长度
W1 定位/创建会话，并校验会话所有权
W2 短路判定
   ├ 新话题：写 context_reset 断点，直接返回
   └ 帮助/能力：读取当前角色可见工具目录，直接返回
W3 持久化用户消息
W4 解析会话当前模型或用户为新旧会话显式指定的模型
W5 读取“最后一个 context_reset 之后”的有界历史
W6 拼装系统规则 + 入口/角色/scope 说明
W7 模型 ↔ 中央工具循环
W8 保存助手回复
W9 记录聊天级成功/失败/取消审计
```

管线原则：

- 短路优先，但不实现关键词黑名单或自定义业务回复管理页；仓库目前没有真实需求、管理数据模型或审批口径，不能照参考文件虚构。
- “新话题”不删除历史，只写入 `context_reset` 消息类型；审计与对话可追溯，模型只读取断点之后的消息。
- 帮助回复只展示调用者当前角色和 scope 真正可见的中央工具，不泄漏管理员工具。
- 工具返回的文本永远按数据处理，不拼进 system prompt。
- 对当前运营数据的问答继续强制先调用 `get_data_freshness`，最终答案必须说明截止日期、筛选、金额口径和截断状态。
- 取消采用协作式 `AbortSignal`；在模型尚未返回时没有伪造“部分答案”，失败/取消审计不保存密钥或完整原问题。

### 3.3 第三层：模型接入层

新增统一模型网关，提供两种调用：

```ts
completeText({ model, messages, systemPrompt?, signal? })
completeWithTools({ model, messages, systemPrompt, tools, executeTool, signal? })
```

模型记录仍使用现有 `ai_models`，不照搬参考文件的平台/条目双表。当前系统的一条配置本来就对应一个可用端点 + 一个具体模型，强行拆表只会增加迁移与密钥继承复杂度。

新增的逐文本模型服务端参数：

| 字段 | 默认 | 服务端允许范围 | 用途 |
| --- | ---: | ---: | --- |
| `timeout_ms` | 20,000 | 3,000—120,000 | 覆盖响应头和完整响应体 |
| `max_tokens` | 1,024 | 128—8,192 | 最大模型输出 |
| `temperature_milli` | 200 | 0—1,000 | 以千分数存储，避免 SQLite 浮点口径漂移 |
| `max_tool_rounds` | 6 | 1—62 | 模型工具循环轮数；0043 将已有文本模型增加 50 |
| `max_total_tool_calls` | 12 | 1—74 | 单次问答总工具调用数；0043 将已有文本模型增加 50 |

协议适配：

- OpenAI compatible：`POST /chat/completions`，Bearer Key，OpenAI function tools。
- Anthropic：`POST /messages`，`x-api-key` + 固定 `anthropic-version`，`tool_use/tool_result`。
- 两种协议共用端点安全、重定向拒绝、完整响应超时、2 MiB 上限、取消信号和脱敏错误。
- 本轮不开放供应商任意 `extra_body`，避免客户端绕过服务端预算。
- vision 保留现有专用适配器；文本问答、模型文本测试、客服文本分析统一进入新网关。

## 4. 数据与接口变更

### 4.1 D1 迁移

新增前向迁移 `0039_ai_question_pipeline.sql`：

- `ai_models` 增加五个有界运行参数。
- `ai_conversation_messages` 增加 `message_kind`，取值由服务端控制为 `message` 或 `context_reset`。
- 增加 `(conversation_id, message_kind, created_at)` 索引以读取有效历史。
- 运行时 `ensureAiAssistantSchema()` 对 0013 老库按 PRAGMA 补列，保证本机与未完整迁移环境安全启动。

### 4.2 API

| API | 变更 |
| --- | --- |
| `GET /api/ai/conversations` | 返回调用者对话和可选的启用文本/视觉模型摘要，不含端点/密钥 |
| `PATCH /api/ai/conversations` | 校验对话访问权与模型状态后切换后续消息使用的模型 |
| `DELETE /api/ai/conversations?id=...` | 删除调用者可访问的对话、消息和数据产物，保留投递审计 |
| `POST /api/ai/chat` | 接受可选 `modelId`，统一进入 Workflow；保留 JSON 响应兼容现有页面 |
| `GET /api/ai/chat` | 保持按会话读取消息，返回 `messageKind` |
| `POST /api/ai/models` | 管理员可保存有界模型运行参数 |

本轮不新增一个“看起来是流式、实际仍整段等待”的 SSE 接口。现有供应商响应继续整段、有界读取；页面停止按钮通过 AbortController 中断同一请求。以后若引入真正 token streaming，必须同时实现流式字节上限、重定向拒绝、工具调用增量拼装和取消测试。

## 6. 测试矩阵

### 6.1 入口与权限

- payload 即使携带 `role/admin/principal` 也不会被读取。
- viewer 仍不能发送，analyst/operator/admin 可发送；读取对话遵循本人或 admin。
- 普通用户获得的模型摘要不包含 `baseUrl`、API Key 或测试原始响应。
- 会话指定的模型必须是 enabled + text；vision/disabled/不存在均拒绝或按明确规则回退。

### 6.2 Workflow

- “新话题/清空上下文”写断点并直接返回，模型 request 函数调用次数为 0。
- “帮助/你能做什么”只列当前 principal 可见工具，模型 request 调用次数为 0。
- 最后一个断点以前的消息不进入模型历史。
- 普通问题按顺序写 user → assistant；模型失败只保留用户问题并写失败审计。
- AbortSignal 在轮次开始、模型请求、工具执行前后均生效，取消后不会启动下一工具。

### 6.3 模型网关

- OpenAI tool_call ID、Anthropic tool_use ID 原样回传。
- 每模型 timeout/max_tokens/temperature/tool budget 进入实际请求。
- 超时、重定向、超限、无效 JSON 和协议缺字段均返回脱敏错误。
- 模型测试、客服文本 AI 和网页对话使用同一文本调用实现。

### 6.4 数据库与前端

- 0013 基线应用 0039 后字段默认值正确，历史消息均为 `message`。
- 页面具备“新对话”、新旧会话模型选择、对话删除和“停止生成”；文本与视觉模型均可用于纯文本对话。
- 管理模型表单可编辑五个参数，服务端再次夹取范围，不能只依赖 HTML 控件。

## 7. 回滚与兼容

- `/api/ai/chat` 保留原 JSON 形状 `{ conversationId, reply }`，新增字段只做向后兼容扩展。
- 原 `ai_models`、`ai_conversations`、`ai_conversation_messages` 不删除、不改主键；0039 仅加列和索引。
- 旧会话 `model_id` 为空或指向不可用模型时，明确回退默认启用文本模型；用户也可为已有会话显式切换已启用的文本或视觉模型。
- 新参数均有数据库默认值，旧模型无需重新保存即可运行。
- 不停止、重启或覆盖当前本地 Worker 的 `dist`；构建验证若需要，使用不干扰运行实例的安全路径。

## 8. 明确不在本轮范围

- 把企业微信/钉钉回调消息自动交给模型。
- 定时任务、报告长任务、写操作确认、长期记忆/RAG、代码执行沙箱。
- 任意 SQL、任意 API、任意 R2 文件读取能力。
- 把市场视觉任务强行改造成对话 Agent。
- 生产 D1 迁移、生产发布或本地服务重启。

这些能力必须在身份映射、持久化任务、配额、审批或数据口径准备好后单独立项，不能因参考图中存在就宣称本系统已经具备。
