# 具体问题、修复方向与回归范围

受审源码与生产绑定见 [总报告](REPORT.md)。以下“高可信”是代码和本轮证据吻合；“条件性”表示只在明确合成前提下复现，生产影响尚未量化。所有方向均为建议，未实施。P1/P2/P3 定义沿用总报告。

## A. 已复现 bug

### B01 · P1 · 自定义日期尚未确认就生效，取消后不恢复

- **页面/操作**：公共统计周期；以销售本月入口为例。进入→统计周期→自定义→不点确认→取消→刷新。
- **预期/实际及负担**：预期取消保留原本月范围且不发新业务查询；实际由 `2026-10-01—10-08` 立即变成 `09-09—10-08`，发出 core/full，取消仍保留新范围，而 URL 没变；刷新又回到本月。用户可能把取消后的数值当作原范围，必须重选日期才能恢复。
- **证据**：[public-interactions.json](evidence/public-interactions.json) `custom-date-cancel`：确认前两请求、取消前后标题/日期/URL、刷新对照；[截图](evidence/date-cancel-synthetic.png)。真实 Home+合成后端，生产同文件字节。
- **根因/可信度**：高。`app/page.tsx:595–618` 先 `setRange(nextRange)`，`:224–227` 用它组成全局范围，`:655` 的取消只关面板；已应用日期与编辑意图混在一起。
- **最小修复**：打开自定义仅创建 picker 草稿；确认时原子提交 range/from/to/intent 与 URL；取消/外点/Escape 只销毁草稿。复用现有 picker，不改日期业务口径。
- **回归**：全部使用周期的模块，本月/去年同期/月度/自定义互切；取消、Escape、外点、刷新、前进后退；在途旧结果、未确认货品文本、日期边界及 366 天限制。

- **操作**：客服已加载合成店 A→选择店 B；分别令 B 列表迟到 2.5 秒或返回 503→点击仍显示的 A 会话。
- **预期/实际**：旧行应明确标作上次结果并禁止作为新范围操作，或清除/分区显示；实际筛选已经 B，列表还是 A，行“查看会话”、三个标注下拉、AI分析均 enabled、无 inert/旧范围标记；GET `id=101` 可以打开 A 详情。失败后同样成立。**未点击真实写入或模型任务，不声称已经误写数据或越权。**
- **证据**：[7组客服/备份真实Home合成结果](evidence/customer-backup-1791469618600/result.json) 的 `customer-stale-pending` / `customer-stale-failure`，含请求、控件状态和合成截图。正常生产开关客服详情另通过。

- **回归**：店/日期/货品快速变化，旧请求迟到、失败重试、列表在途打开详情、标注入口、批量AI取数；真正权限变化另需隔离账号验证。

### B03 · P2 · 全局搜索取消后回到同一词，永久停在忙碌态

- **操作**：在实际 Home 打开搜索，输入“审查A”；其请求在途时，56ms 内加 B 再删回 A；等待超过原 1200ms 合成响应延迟。

- **证据**：[public-interactions.json](evidence/public-interactions.json) `global-search-return-to-pending-query`、[截图](evidence/search-stuck-synthetic.png)。搜索入口通过真实 shell 键盘 handler，数据响应为明确合成值。

- **最小修复**：把查询代次/取消后需重订阅纳入请求状态机，或让 effect 独占取消与 busy 生命周期；同词返回须有活动请求或已验证成功结果，不能仅设 busy。不要无条件自动重试网络失败。

## B. 有测量证据的性能瓶颈或重复等待

### P01 · P2 · 库存/商品不同范围共用慢计算锁

**操作/影响**：一个未缓存key开始慢loader，同时读取另一个已缓存key。应独立返回已有有效值，实际跟着等待200ms；持锁直到后者结束时，后者约5000ms后503。生产没有制造并发，也没有据此解释所有慢样本。

**证据/根因**：当前真实class的[首轮实验](evidence/cache-lock-probe.json)和[UTF8复跑](evidence/cache-lock-probe-utf8.json)分别保留；`backend/inventory/read_cache.py:22–60` 与 `backend/products/summary_cache.py:13–49` 单个进程级锁包住loader/校验/序列化与热命中。缓存key身份隔离存在，但锁隔离不存在。高可信，生产触发率未知。

**最小方案/回归**：短元数据锁管理有界LRU/在途表，同key合并、不同key独立；保留scope/principal/DB角色/authority/revision、事务绕过、版本前后复验、容量字节/TTL、异常清理、等待剩余期限。回归热/冷、多key/同key、版本变化/批次交错、oversize、取消/失败；库存regional/base/广东嵌套调用必须保留可重入且不能自锁，延续`backend/inventory/tests/test_read_cache.py:41–53`的保障。禁止扩大5秒超时掩盖。

### P03 · P2 · BI及部分网店/市场读取真实等待偏长，服务端阶段未知

**样本/影响**：BI主请求10.766/14.591/9.224秒，另等flow；网店平台对比10.790秒、商品表现12.644秒、推广4.241秒；市场榜单5.830秒、行业3.789秒。表体不大也要等待，不能凭源码大小或多fetch归因。详见 [PERFORMANCE.md](PERFORMANCE.md)，单样本栏目不称P95。

**根因可信度**：等待实证高；具体SQL/锁/CPU归因未定。可达结构：`backend/bi/cockpit.py:125–171` 销售后才并行其他源，最终等慢来源，前端`:53–77` 主结果后才启动flow；`backend/netshop/store_overview.py:229–294,389–430`每次完整聚合再切页；市场full在 `backend/market/query.py:238–291,437–505,1171–1210` 有全量物化/串行消费者。**均衡总览本次301/177ms及翻页229/102ms，不能把其结构风险写成这次12秒网店商品表现的已证根因。**

**最小方案/回归**：先在原read-only链加请求ID及阶段耗时，隔离固定规模做 SQL计划/聚合次数；BI考虑独立区域但仍保留范围和来源一致性、缺源未知；网店仅复用被证实重复的公共计算；市场分清ranking和full。单/多店、小/大日期、来源缺失、冷/暖、版本变化、完整数值深等价是准入，不缩小统计范围或提高上限/超时。

### P04 · P2 · BI一次刷新发两次相同flow

**复现/实际**：正常生产本月点击刷新，cockpit9224ms，`/api/bi/flow?range=month&deferFlow=1` 两个200分别1715/1631ms、各3824B；应只读取本轮必要flow一次，实际多一轮同范围服务工作。[证据](evidence/production-chains-summary.json)。

**根因/方向**：高。`app/bi-cockpit-view.tsx:63–75` effect同时依赖refresh与data：refresh立即用旧data启动flow，新主data回来再启动一次。按本轮主成功代次驱动一次，局部flow筛选独立读取；主失败应保留明确旧状态及局部重试。不简单删掉refresh让flow永不更新。

**回归**：首次、同范围刷新、主/flow先回或失败、快速平台/店变化、来源缺失、日期校验及取消。未测两个请求各自SQL成本，不相加声称节省3.3秒CPU；未见跨权限串数据。
