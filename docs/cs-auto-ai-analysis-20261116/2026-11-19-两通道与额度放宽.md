# 客服自动分析：两通道与额度放宽（2026-11-19）

分支 `codex/cs-analysis-capacity-20261119`，基点 main `1f0c83d7`。**无迁移。**

## 背景

导入会刷新老会话的 `last_import_batch_id`，72 小时窗口里积着约 1.9 万条，凌晨 00:00–06:30 就用完 480 条日额度，当天 09–10 点导入的真正新会话轮不到。历史从未分析且有聊天内容的会话约 6.8 万条。

## 变更

### 两条通道（`backend/customer_service/query.py::auto_analysis_candidates`）

| 通道 | 选择条件 | 每日上限 |
| --- | --- | --- |
| new（新增） | `analysis_source=""`、`messages != []`、`created_at`（首次入库）在 72 小时内 | `CUSTOMER_SERVICE_AUTO_ANALYSIS_DAILY_LIMIT`，默认 **800**（原 480） |
| backlog（积压） | `analysis_source=""`、`messages != []`，且不属于 new（`created_at` 早于 72 小时） | `CUSTOMER_SERVICE_BACKLOG_ANALYSIS_DAILY_LIMIT`，默认 **6000** |

- 两通道都按 `consulted_at` 新到旧取 64 条池、池内随机抽 ≤8 条（防卡死设计不变）。new 不再看 `last_import_batch_id`。
- 计额：当天 `analysis_source="ai"` 且 `analyzed_at` 在上海今日 0 点后的会话，`created_at` 在 72 小时内计入 new，其余计入 backlog（含手动按钮的 AI 分析）。无新增字段。
- 接口 `GET /api/customer-service/conversations/auto-analysis` 新增可选参数 `lane=new|backlog`（默认 new，缺省时查询串与旧版一致）。返回 `ids`（所请求通道）、`lane`、`analyzedTodayNew/Backlog`、`pendingCountNew/Backlog`（封顶计数）；旧字段 `pendingCount`/`analyzedToday` 恒表示 new 通道。

### 调度（`lib/customer-service/auto-analysis-scheduled.ts`）

每个 tick **只派发一批（≤8 条）**：先查 new；new 无候选或已达 new 上限时才查 backlog。`CUSTOMER_SERVICE_AUTO_ANALYSIS=off` 同时关闭两条通道；`CUSTOMER_SERVICE_BACKLOG_ANALYSIS=off/false/0` 只关积压通道（默认开启）。每分钟 1 批 × 8 = 每日最多 11,520 条，足够覆盖 800 + 3000。

### 派发配额来源（`backend/ai_assistant/dispatch_limits.py`，由 `chat.py::dispatch_budget` 每次调用时读取）

原写死的 1000 / 120 / 500 改读环境变量（仅改数值来源，不改计数口径）。**不进 Django settings**：`backend/teruisi_backend/settings.py` 的字节被三份结构证据绑定，改动会迫使重做 PG 演练。

| 环境变量 | 含义 | 默认（原值） |
| --- | --- | --- |
| `TERUISI_AI_DISPATCH_DAILY_LIMIT_GLOBAL` | 全局每日派发 | 4000（1000） |
| `TERUISI_AI_DISPATCH_DAILY_LIMIT_PER_OWNER` | 单账号每日派发 | 2500（120） |
| `TERUISI_AI_DISPATCH_DAILY_LIMIT_PER_MODEL` | 单模型每日派发 | 4000（500） |

取值范围 1–100000。空值视为未设置；非整数或越界时不让进程失败，回落默认值并记一次 warning。图片派发（`space.py::image_dispatch_budget`）不在此列。

### 页面

`GET /api/customer-service/analyze` 的 `autoAnalysis` 增加 `backlogEnabled`、`backlogDailyLimit`（旧字段保留）；客服分析页提示显示两个上限。

## 估算

每日新增有效会话约 450–860 条，平均约 650，800 的 new 上限可覆盖。积压按 6000/天约 11–12 天清完 6.8 万条。(800+6000)/8 ≈ 850 次派发/天，长会话还会拆分，故派发上限默认取 4000/2500/4000。

## 补充：analysis-reply 请求预算 120 秒 → 240 秒

生产 `django-ai-writer` 在 started 后约 2 分钟记录 `Service Unavailable: /api/ai/consumer`：`views.dispatch` 对 consumer 一律套 `request_budget(120)`，模型调用超过该总预算时 `remaining_budget` 抛 `provider_timeout`（503），而 `analysis-reply` 只在调用前写 started，失败不写任何审计，于是表现为“只有 started”。现把 `analysis-reply` 单独放宽到 `ANALYSIS_REPLY_BUDGET_SECONDS = 240`（低于 writer 的 channel-timeout 320 秒），Worker 侧 `lib/django/ai-service.ts` 对该操作的 fetch 超时由 130 秒放宽到 250 秒。影响面：所有 `analysis-reply` 调用方（客服手动/自动分析、市场 AI、网店诊断解读）失败前最多多等约 2 分钟，占用的 writer 线程也相应更久；`analysis-plan`、`pandas-analysis` 及其它 consumer 操作仍是 120 秒。
