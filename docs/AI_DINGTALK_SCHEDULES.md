# AI 助理 → AI定时任务

2026-09-12 已在本机生产采用：Worker/helper `20260912T085820Z-cde69efbfa6cb274`，AI `0010` 迁移与 reader/writer 最小权限已应用，Stream 接收器已连接。正式列表及新增窗口、整栈就绪、发布前备份独立恢复和发布后备份复验通过；未创建任务或执行真实投递验收。完整记录见 [发布证据](evidence/ai-scheduled-production-20260912.json)。

定时任务现为 AI 助理下的独立子模块，位于“AI 管理”右侧，名称为“AI定时任务”。直达地址为 `/?module=ai&view=scheduled`，刷新后保持当前子模块；沿用无数据范围限制的管理员权限。新增、编辑、执行与记录列表集中在此页。

管理员可创建、编辑、启停和手动入队任务；每天、每周、每月 1–28 日按 `Asia/Shanghai` 执行。内容可选 AI 只读问数文字、指定页面截图或已复核 Excel 报告，新增任务默认停用。任务最多 100 个，文字执行内容最多 4000 字。

目标分为已绑定员工的本人私聊，以及已在“AI 对话群设置”批准启用的群。配置时填写执行账号的钉钉 `staffId`，群任务按该绑定账号的实时角色与数据范围执行；个人任务只允许同一个 `staffId` 作为接收人。管理页面不会暴露完整绑定目录，错误的 `staffId` 会在实际执行前失败关闭。管理员可以编辑任务，但无法用页面改变群审批或员工绑定。模型工具入口仍为 `dingtalk_chat` 中逐项开放的只读工具，不能借定时任务调用写工具。

任务定义和每个执行槽保存在 AI PostgreSQL 域的 `ai_dingtalk_schedules`、`ai_dingtalk_schedule_runs`。`0010_dingtalk_schedules` 添加迁移、角色最小权限、fence、readiness 和备份清单；历史备份依据其中记录的 migration 版本继续按旧表数验证。执行器复用已经受控启动的钉钉 Stream 接收器，不创建浏览器或新的外部定时器。接收器未运行时页面仍可保存、入队，但不会主动执行。

普通定时槽只在计划时间后 5 分钟内认领。接收器停机或 AI 群开关关闭期间错过的旧槽跳过，不追发历史报表；手动入队超过 5 分钟也标记为错过。执行前及模型处理期间重新验证任务版本、创建管理员身份、绑定员工身份/权限、AI 群策略；发送前还按已有钉钉通道核验应用、群名、精确群 ID 和机器人安装。任务编辑/停用会撤销旧版本的待执行项。外部发送前持久预留 `sending`；中断或超时无法确认的调用只记 `unknown`，不得自动调用付费模型或外发第二次。`sent` 表示 DWS 确认受理，不保证终端已读。

## 接收器随系统自动启动

2026-09-13 已在本机受控发布并启用。源码 `8b25c7005b6d6af4e04ee75937f2496b257ebf0e`，Worker/helper `20260912T234549Z-017f8196dda91b2b`，Django manifest SHA `8c87f48c44b850baa0c426d00ef26970db671d656ebdb7ffd1d558e88d0beaa5`。实际从停止状态启动 Worker 后，系统自行拉起接收器并记录 `connected`；再次系统启动返回 `already_running`，接收器 PID、创建时间与运行回执保持一致。启动项绑定回读通过；本次未重启 Windows，不能把系统启动验证称为整机重启验收。完整证据见 [正式发布记录](evidence/dingtalk-receiver-autostart-production-20260913.json)。

接收器可通过系统启动配置，在 Windows 登录后的既有启动链或手动启动运营系统时自动开启，无需保留 PowerShell 窗口。它在数据库、各域服务和 Worker 就绪之后启动；对已运行的系统再次执行“启动”也会检查接收器。仍复用现有受控 AI operator、进程回执和 PostgreSQL 单例锁，不创建第二个定时任务执行器。

此功能新安装时默认关闭，本机已启用。其他环境须先受控发布配套 `django-ai.ps1` 和 `worker-local-service.ps1`，再执行以下配置：

```powershell
$aiController = "D:\teruisi-runtime\django-sales\app\tools\django-ai.ps1"
& $aiController -Action EnableDingTalkStartup
```

启用时只核验现有身份和授权，不发送消息，也不立即启动进程；配置成功后通过系统正常“启动”入口生效。配置存于受保护 runtime 的 `config/dingtalk-startup.json`，绑定接收器配置摘要和 AI authority，配置文件变化需重新核验启用。网页 AI 对话开关、任务开关、绑定权限和群审批仍在实际处理前实时核验。

`DisableDingTalkStartup` 关闭以后随系统自动启动，保持当前接收器运行；`StopDingTalk` 则同时关闭自动启动并停止当前接收器。整套系统正常停止保留自动启动配置，下次系统启动会再次带起。`StartDingTalk` 仍仅为单次手动启动，不撤销持久停用设置。`Status` 增加 `DingTalkStartup` 和 `DingTalkReceiver`，进程 `running` 不等于平台连接确认，连接仍须核验本轮日志的 `connected`。

自动启动失败会明确报告接收器失败，已就绪的业务服务不因此被停止。本次仅接入系统启动链，不新增接收器自身的无限重启或认证重试；连续建联失败退出后仍需排障并重新启动系统入口。当前 Windows 启动链要求登录原用户（DPAPI 身份），不支持重启后无人登录即运行。超过 5 分钟的旧执行槽仍不补发。

管理员可为一条定时任务选择三种互斥内容：原有只读 AI 文字、指定运营管理系统页面截图、已复核的 Excel 报告。截图仅开放 BI 总览、网店分析/商品/推广、销售总览、库存总览/广东仓和市场榜单这八个固定页面，不接受任意 URL、路径或 Windows 桌面。报告只能选择当前管理员本人已完成复核的既有报告，执行时重新校验报告归属与权限，从原持久证据生成 XLSX；不会重新取数或调用模型。媒体任务要求执行 staffId 实时绑定到同一个无数据范围限制的管理员，任务默认停用。

页面截图需要专用 Chrome 登录目录，固定为 `D:\teruisi-runtime\django-sales-screenshot-profile\Chrome`，不复用操作者日常 Chrome。Chrome 会在缓存项上添加自身沙箱 ACL，因此其目录必须位于 Django 受保护 runtime 树之外；独立父目录禁用上级 ACL 继承，只允许当前 Windows 运行账号、SYSTEM 和 Administrators 完全控制，Chrome 目录根继承这三项。接收器每次启动和配置核验时复查这两个目录的路径、实体身份和根 ACL，不满足即拒绝启用截图。初次使用须在当前 Windows 运行账号下用此目录打开 `http://127.0.0.1:3000` 并完成系统登录，然后关闭专用浏览器窗口。后续接收器启动时若目录存在，会带入精确的 `--screenshot-profile` 参数；若目录不存在，文字和报告任务仍可运行，截图任务会明确失败。截图时使用独立无界面 Chrome、固定回环 URL，截取 1440×1000 的当前可见区域，并调用 `/api/ai/screenshot-identity` 核对当前登录账号与任务创建人一致且仍为无范围限制管理员。登录过期、目录占用、页面未就绪、截图超过 2 MiB 或身份变化时不发送。专用目录含登录状态，不得复制到仓库、测试镜像、日志或备份附件。
