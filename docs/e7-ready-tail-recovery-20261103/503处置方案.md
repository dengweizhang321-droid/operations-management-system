# 发布末端503：证据与最小修复方案

本页回答本轮“503的问题，怎么样解决”。状态：机制诊断和建议，未改生产代码或放宽就绪门禁；本次应用已就绪，发布记账已另获授权完成受限收尾。

## 已知事实与不能推断的部分

- 19:48:02原VerifyStartup通过，随后发布末端ready503；19:49:31只读观察仍503/degraded，19:50:00已200/ready，19:52及恢复现场原门禁也通过。
- 原发布器 `tools/publish-prepared-main.mjs:130` 的ready函数只发一次GET；非200先assert，未解析响应JSON便退出。因此原FAILED仅留下`503 !== 200`，没有具体`unavailableServices`。
- `lib/django/backend-readiness.ts` 检查23个Django reader/writer，6路并发，共享最多4000毫秒的整轮预算。任一配置、HTTP、响应契约、数据库/角色不就绪、请求超时或排队超过整轮预算都加入unavailableServices，聚合返回503；这些原因当前不分码输出。

上述代码说明启动后短时未就绪或预算耗尽**可能**造成一次503，且现行发布器会立即终止。但没有当时23个子检查的响应/耗时证据，不能把4秒预算、某一个具体服务或启动热身认定为已证实唯一根因，也不能用后续200否认原503。

## 建议的最小持久修复

1. **发布末端有界等待。** 只对既有ready GET增加总计例如120秒的单调时间预算、约5秒间隔和每次原有请求期限；实际参数在隔离边界核验后确定。任何一轮仍须严格满足HTTP200、ok=true、status=ready才完成。有效就绪即结束，不固定额外等待。总期限用尽仍失败关闭，不把503当成功。
2. **保留可定位的原生证据。** 每次观察保存时间、耗时、HTTP状态、固定原因码和经过白名单校验的不可用服务名；非200也应有界读取预期JSON字段，读取失败另记解析/网络错误。日志不得保存原始响应、凭据、业务数据或任意后端异常文本。最终FAILED携带这份有限观察记录的位置和摘要。
3. **只在证据支持时调整子检查预算。** 如果后续证据证实23服务共享4秒是瓶颈，再评估整轮预算与并发分配；若是某个服务稳定未就绪，应修该服务。当前不直接增大健康接口超时，不剔除慢服务，也不重启掩盖原因。

等待只重复只读健康GET，**不重复DeployApp、WorkerApply、Start、迁移或业务请求**。持续503应准确保留失败和已完成步骤；不能靠另一个SUCCESS或手写catalog假装原流程成功。

本次“记账修复”只修正已经完成应用切换后的记录一致性，并不包含以上防复发代码。后续实施应从最新main独立分支做聚焦修改，验证首次就绪、几次503后恢复、持续失败、超时/非JSON及总预算边界，独审后按正常合并和发布授权交付。
