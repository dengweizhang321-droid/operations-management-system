## 已完成的改动

1. **统一恢复闭合。** `healthy`（自然恢复）与 `recovered`（自动恢复成功）都保存恢复确认，并为可能已收到故障通知的事件建立独立恢复待发送记录，再关闭主故障事件。原故障通知 unknown 不重发。待发送记录与主状态使用不同文件，避免旧恢复通知覆盖新故障。
2. **通知失败不丢记录。** 身份预检失败沿用每 15 分钟、最多 3 次的有界预检重试；sending/sent/unknown 均不重放。每轮最多进行一次新的身份/投递准入。终态转到恢复完成记录，通知审计继续保留。延迟恢复消息明确确认时间；当前另有异常时提示查看最新提醒。
3. **安装先校验后修改。** 新 `PlanInstall` 只读绑定候选内容、旧安装清单字节和旧计划任务定义摘要。`Install` 要求精确 planId，并在与 Check 相同的系统互斥内校验任务归属、运行状态、原文件、候选和当前完整健康，再次复验前驱。忙、未知或漂移均在生产写入前拒绝。
4. **固定版本路径和恢复事务。** 脚本/helper/安装库/无控制台 launcher/诊断包装放入内容绑定的版本目录；旧入口文件保持。只在校验后切换安装清单与任务引用。失败恢复旧清单的原字节和任务定义，保留通知流水。陌生任务或陌生清单变化拒绝强行回滚，留下 rollback_unconfirmed。正常一分钟/登录触发器接手第一次检查，安装期间不手工启动检查子进程。
5. **完整诊断可在独立监控包中采用。** `prepare-watchdog-status-driver.mjs` 以现场实际控制器、Worker service、Django service 和实际控制器 helper 的字节为前驱，生成只允许 Status/AggregateStatus 的只读包装。后端包装以 library-only 加载已安装服务库，仅替换原核心 Status 的同等检查实现，增加原两秒 HTTP 检查的分类和耗时；领域聚合与 Worker 原状态门禁继续复用。原生产文件不覆盖，不发布应用、不迁移、不重启、不增加业务 SQL。前驱变化后退回当前原控制器并明确诊断需刷新，原健康/身份检查继续生效。
6. **减少独立 HTTP 等待。** 四条现有 HTTP 健康探针并发，禁止代理/重定向、正文上限与严格布尔/对象/标记检查保持。每条仍受五秒上限及原整轮六十秒期限约束。按完成顺序消费，取消和未消费响应有独立释放，不跨轮缓存健康。
