## 1. 总体判断

**架构主方向和原有发布保护适合本系统；原方案不能原样实施。**

Worker 薄适配、Django/PostgreSQL 业务权威、领域读写隔离、不可变制品、在线准备、按组件发布及唯一生命周期入口，与目前 Windows 单机内部运营系统相符。没有证据支持为本次提速而重写架构、合并业务事实源、减少权限隔离或新建发布平台。

建议保留现有保护，优先解决**维护前材料齐备、周报与发布竞争、失败阶段可解释、相同证据重复生成**。备份体系建设、CI、常驻 staging、HA、SBOM 等分别评估，不与每次发布绑定。

## 3. 关键证据与需要更正的事实

### 3.1 两项建议与当前用户规则直接冲突

[验证与发布](../规范/验证与发布.md#发布检查与功能验收分工)第5–12行明确：AI只检查构建、部署、启动必需程序代码；功能及业务行为由用户上线后检测，成功后依原生回执报告，不新增业务接口或独立健康验收。[后续结构迁移约定](../规范/验证与发布.md#后续结构迁移的备份与恢复约定)第146–151行明确取消迁移前后全库备份和全库隔离恢复。

这两项取舍存在业务回归及恢复能力方面的剩余风险，应如实说明；风险本身不等于重新取得增加检查、备份或数据写入的授权。对结构变化继续检查实际构建部署启动兼容、有限安装器及原生门禁，不能宣称取消备份就证明“无数据影响”。

### 3.2 51分钟是失败到续接的间隔，尚不是持续锁占用根因

已确认的日志事实：21:35:31.780发起Stop，21:36:02.015因另一Django操作持锁失败；22:27:46.767有新Stop开始。首次Stop约30.235秒，之后约51分45秒是失败到下一次Stop的间隔。

该间隔没有完整锁持有者/释放轨迹，不能全部记为同一锁持续等待、人工等待或可消除的耗时，更不能当作连续停机时间。原报告约63/66分钟只能作为其选定事件间的跨度，原始上线授权时刻及全部交付收尾仍缺失。

原报告另将22:29:48列为DeployApp完成；原日志第1064行是22:29:48.477开始，第1072行22:30:49.839记录部署完成，第1073行22:30:49.843才是该操作成功结束。后续计时应采用对应原生完成边界。

源码 `tools/django-local-service.ps1:5239` 的等待策略是：Start最多900秒、指定发布过渡120秒、其他Action30秒，并受继承deadline约束；原文把它概括为“120秒等待”不准确。已有等待机制应先诊断，再决定哪一阶段需要改动。

因此可提出“发布启动中仍阻止新业务”的设计目标，但必须同时处理受控启动许可、watchdog/调度准入、reader/writer及Worker就绪、失败后部分进程和原owner；这属于后续独立协议改动。本次不建议把这个较大改动列为首项提速工程，也不自动重新进入维护或Stop未知身份的进程。

### 3.4 自动准备和发布编排已有采用证据

当前 `D:\codex-isolated\main-manual-release-20261016\CONTROL-INSTALLATION.json` 为v3、`status=adopted`；固定Git hook绑定同一不可变bundle。规范第69–82行和 `tools/main-prebuild-task.mjs`、`tools/publish-prepared-main.mjs` 也已规定普通用户准备、冻结目标、PREPARED与STARTED分离、deploy-only和未知不重放。

原报告将通用 `release-batch` 的候选状态延伸到整个固定发布链，不够准确。后续改动应先列清“源码已合并／控制入口已采用／制品已就绪／应用已上线”四种事实；新控制源码合main并不会自行替换已安装bundle。

本轮观察还显示：LATEST-PREPARED为新目标的`request-frozen`，不能称已准备；全局PUBLISHED-MAIN仍指旧b2，而实际Django部署清单来源为e969发布树。这里只证明摘要入口不能单独作为当前完整发布结论，**不据此宣告服务故障或自动补发**。应关联对应原生成功/有限恢复回执及两组件实际身份，缺证据显示待核实。

### 3.5 新品周报是已证实的具体竞争点

`tools/django-workflow-service.ps1:714` 在全局Django服务mutex内运行周报；`:590`开始的函数先做完整runtime/ACL和数据库准入，没有在业务执行前检查维护/drain。这个入口与实际安装副本SHA一致。

维护gate生效后，日志仍有周报按约5分钟节奏进入并做完整ACL；22:30也有周报取得mutex失败。它支持“周报与维护竞争”的判断，但不能证明首次Stop的持锁者一定是周报，或解释全部51分钟。

`backend/workflow/management/commands/new_product_weekly_report.py:230`先调用学习同步，`:232`生成含上传图片的周报，`:255`才判断非强制发送是否到期。因而“本轮不发送”仍可能做大量准备，不能假定整个非到期轮次没有业务副作用。

优先方案是在原互斥内、昂贵检查和业务作用之前，按已有维护/drain状态返回明确的延后状态，并让对应调度器理解该状态；不抢锁、不改全局等待。进一步把到期判断前移前，先确认学习同步是否有独立职责，保留dry-run、force、时区及投递账本语义。仅在确认未产生作用且原协议允许时延后同一任务；发送已开始、结果未知不得自动重发。

### 3.6 “只在有migration变化时迁移”与Start实现需分清

`tools/django-local-service.ps1:4311`每次完整Start都调用`Invoke-DjangoMigrations`；该函数不仅包含Django migrate，也做保护检查、数据库集成准入及权限处理。原报告选定的Start样本中：

| 原生日志阶段 | 耗时 |
| --- | ---: |
| `django-migrate` | 1.865秒 |
| `Invoke-DjangoMigrations`整体 | 11.188秒 |
| 核心`Start-ServiceStack` | 42.091秒 |
| 本次Django Start开始至action_completed | 约99.555秒 |

这些是嵌套阶段，不能相加。调用migrate不代表本次实际应用了新结构；同样，范围计划migrate=false也不证明内部没有调用。若后续优化无结构变化的启动，应先区分“实际待应用迁移、结构代际检查、角色权限恢复”三类，保留原保护，不能整体删掉该函数。这个样本的migrate本体只占约1.9秒，不应凭函数名把它当作本轮最大提速来源。

### 3.7 数据安全结论应写成边界，不写未经证实的上限

本轮只读看到`postgresql.conf`归档项为注释默认示例，以及E盘三个恢复点目录；没有查询生产实际生效参数、验证归档链或搜索所有外部备份位置。因此“已确认无PITR／仅有本机备份”仍需限定证据范围。

“最多损失24小时”不是由每日计划自动保证的上限：失败或暂停会扩大窗口，须以最后成功且可恢复的快照为准。原文建议的≤24小时与现有旧reuse资格的26小时也不是同一规则，不应另立竞争门槛。

Django在PostgreSQL上默认按单个migration事务执行；不能笼统推断所有DDL失败都留下半个结构。已提交的前序migration、非原子迁移、自定义SQL及不可逆数据操作仍须分别考虑，整轮发布不因此原子化。[Django 5.2官方说明](https://docs.djangoproject.com/en/5.2/topics/migrations/#transactions)

PITR需配套物理基础备份和连续WAL链；逻辑pg_dump不能直接用作该连续归档基础备份，单开归档参数不够。若要建设，还需归档成功监测、存储容量/保留、恢复目标及隔离恢复证明，适合作为独立运维方案。[PostgreSQL 17官方说明](https://www.postgresql.org/docs/17/continuous-archiving.html)

## 4. 补充后的优化路线

### 第一批：围绕实际等待，复用现有发布链

| 次序 | 优化项与最小实施范围 | 预期价值 | 必要交付依据与边界 |
| --- | --- | --- | --- |
| 1 | 新品周报维护准入和非到期准备成本；仅改对应入口及调度处理 | 减少周期性抢占服务mutex和无效准备 | 原锁内先判维护/drain、结构化延后；确认学习职责、force/dry-run和发送账本不被破坏。此审查不授权实际发送或任务补跑 |
| 2 | 完善现有就绪摘要，把已安装控制器兼容、真实前驱、依赖/有限迁移材料、恢复入口在维护前齐备 | 减少停服后补材料和修入口 | 原生PREPARED绑定最终来源与制品；尚未准备好就在维护前拒绝。普通权限准备、发布授权及deploy-only保留 |

| 5 | 用现有离线收尾统计正确记录总等待、准备、就绪后发布跨度及有证据的维护区间 | 确定最大可消除成本，避免虚报提速 | 授权时间缺失即注明；父子不重复相加、并行取并集，未采样空档不归因。15分钟为既有优化目标，不是强制终止时限或性能承诺 |

第1项已有具体源码与日志支撑，宜优先；第2–5项多为现有能力补齐，应先找真实缺口，已采用且有效的部分不重做。每项按实际构建部署启动影响完成必要代码检查，不扩大为功能测试、业务演练或多轮例行复审。

### 第二批：测量支持后再选一项

1. **无迁移Start的受控精简**：仅在分段数据表明确有收益时，分离迁移执行、结构准入和权限恢复；本样本不支持“大幅节省迁移时间”的承诺。
2. **完整树/ACL检查的实现成本**：本次日志ACL对象约29.2万，已超过文档中约9.4万对象的旧测量。先记录扫描范围和子树成本，解释增长后再取舍；不能为提速直接排除目录、用mtime缓存权限或删除保留材料。
3. **按组件生产基线清楚表达**：Worker-only和Django-only会让组件来源不同。范围与恢复材料应分别绑定实际前驱，不能只看一个main SHA或历史成功指针；先核现有汇总规则，不据此宣称已发现错误部署。
4. **启动阶段准入改进**：若明确需要启动期间保持业务关闭，再独立设计受控启动状态，不简单把gate清除后移。正常路径、失败部分启动、旧监控和调度兼容须同一方案处理。

常驻staging、全仓CI、HA、异地备份/PITR、供应链报告、机器重建手册均可单独立项；根据实际损失容忍度、频率和工程投入取舍，不设为下一次普通发布的前提。
