# 发布等待四项定向优化

## 范围与状态

用户只授权：新品周报与发布的锁竞争、维护前材料、锁等待诊断、有效检查结果复用。基线为`8e1411cc`；其他复审建议不实施。本任务没有应用上线、生产维护、迁移、调度停用或外部发送授权。

本报告随候选交付，最终必要代码检查及制品状态在收尾材料中记录。源码合并、原生制品准备和实际上线分别判断。

## 改动

1. `django-workflow-service.ps1`：三个周报入口在原服务mutex内，进入完整runtime检查前调用原维护/drain读取器。有效gate返回单一`deferred`结果和`sent=false`；坏gate保留原异常。学习同步、报表生成、到期判断、force/dry-run参数和发送账本原字节保持，n8n不改。控制边界与逆投影见[周报说明](WEEKLY-ADMISSION.md)。
2. `publish-prepared-main.mjs`：将原请求、真实入口/transport摘要及维护admission所需材料提前组装，在`STARTED`前发现缺件；只在之后补本次STARTED摘要和新鲜admission时间。每次生成说明性材料清单，引用原生PREPARED、两组件前驱和制品，不创建第二套批准。已知维护前失败可重新核同一原请求；已有STARTED无SUCCESS仍拒绝重放。原双锁中Check、现场身份、权限、前驱和排空检查保持。
3. `manual-maintenance-lock.psm1`：在原Worker→Django锁等待前后输出结构化stderr诊断，记录锁类别、阶段、共同预算、耗时和剩余预算；可向本轮目录原子写一个只用于显示的诊断文件。写入失败不授予锁权、不改变原异常。waiting诊断之后紧邻WaitOne重新计算原Stopwatch余额，保留共同预算、abandoned拒绝和调用原Worker前释放Django锁的顺序。`manual-maintenance-start.ps1`只增加该显示文件路径。
4. `publish-main-progress.mjs`：原子写本轮阶段、开始时间、原生动作和日志路径。心跳仅展示本步骤时间范围内、字段有效且有界的锁诊断记录，注明记录时刻，不猜owner；它不是锁当前状态或恢复许可。stderr完整记录在原操作结束后留存。正常准备或无发布返回时close写closed，保留已有成功/失败终态，不能把准备完成显示为部署成功。
5. `frozen-main-source.mjs`：每个原有现场检查点都保留；将同轮三次rev-parse合并为一次多对象读取，再做原来的干净状态检查。每次由4个Git子进程降为2个，不新增跨调用缓存，不省略外层加载原生工具之前的源码检查，也不复用陈旧权限或进程状态。不承诺节省固定分钟数。

## 必需程序代码检查

新增有限发布兼容资格，只接收本任务工具集合，核验周报逆投影、锁和维护入口的诊断增量、原Start/Stop及周报Python字节保持，并走既有私有发布参数/包完整性检查。检查只覆盖构建、部署和启动控制所需代码与工具边界，不运行业务功能、业务接口、权限业务场景或发送验收。

现行main尚含151→152的Pi结构交付，其代码绑定包含publisher。只更新对应recipe到本任务新生成的必需代码检查材料；原迁移文件、代际、安装策略及历史证明不改。本任务没有新增migration，不执行生产结构安装或隔离数据库演练。新材料明确`functionalValidationPerformed=false`，不把重绑当作业务验收。

## 保留边界

- 已经持锁运行的周报不强制中断；本次只减少维护期间新一轮周报的昂贵工作。锁外不新增信任链，极小竞争窗口仍按原有等待处理。
- deferred表示这次轮询未执行，不新增补发队列或修改原发送时间窗；维护跨过原发送窗口时不会擅自补发。
- 诊断文件可能滞后，展示注明记录时间；不用于判断锁所有者、解除维护、抢锁或unknown重试。等待时限不代表所有同步系统调用有硬实时上限。
- 原生Worker/Django制品完整性、VerifyPreparedApp/DeployApp、apply和现场动态门禁不减免；数据库迁移及权限恢复逻辑不改。
- 没有默认功能冒烟、固定观察期、全仓检查或恢复已取消的结构迁移前后全库备份/恢复。生产上线仍等待用户明确指令。
