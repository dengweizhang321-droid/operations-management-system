## 要做的事

**1. 新增一种 decision**（暂名 `superseded-by-later-publication`），与既有 decision 并列。

**既有 decision 的任何一条 assert 不得放宽。**

成立条件必须同时满足且可验证：

| 条件 | 内容 |
|---|---|
| a | `maintenanceStarted === false` —— 维护从未由它开始 |
| b | `selectedTarget` 已被一次成功部署覆盖：`PUBLISHED-MAIN.mainCommit === selectedTarget` 且 status 为已就绪终态 |
| c | 覆盖它的那次部署有可核验回执（receipt 路径 + sha256 与记录一致） |
| d | 该 dispatch 的准备产物与那次部署的消费关系可被证据链证明（**不能只凭"目标相等"就放行**） |

**2. 复用既有三段式**：写 `REQUEST-<phase>.json` → 独立只读观察者（`cleaned-preparation-observer.mjs`）产出 `OBSERVATION-<phase>.json` → 再提交。

不得新增旁路、不得手写 resolution 文件、不得跳过 epoch/nonce/deadline/CAS。

**3. 关键 — 必须提供可执行入口。**

现状：`preparation-resolution.mjs` 只导出函数，没有 CLI。

要求：提供受控 CLI，或在 REPORT 里写清既有驱动方式，并给出「收敛某张 unknown dispatch」的**完整可复制命令**（含观察者启动方式）。

**没有可用入口 = 本单未完成。** S03 依赖这条命令。

**4. 历史一致性必须同步。**

`preparation-resolution-history.mjs` 与 `readHistoricalResolution` 必须能容纳新 decision。否则下次 adopt 重建 bundle 后历史校验会失败，等于把问题推到下一轮。

加测试：写一条新 decision 的 resolution 后，能从历史目录读回并通过校验。

**5. 队列侧**只让该 dispatch 被正确识别为已收敛，**不得改动其他判定语义**。
