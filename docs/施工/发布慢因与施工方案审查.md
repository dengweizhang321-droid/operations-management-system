# 发布慢因与施工方案审查

日期：2026-10-23 审查，2026-10-24 落盘。范围为发布上线流程及本目录施工方案的只读审查：未改代码、队列、控制包或生产状态。本文是审查意见，不改变[看板](BOARD.md)及各单状态，不授予控制采用、队列协调或发布权限；第 4 节重排须经用户决定后再同步看板与对应单据。

## 结论

发布慢的主因不是编译，也不是 Django/Worker 业务架构，而是发布/部署架构导致队列频繁卡死、文件被反复校验。现有施工方案方向基本对，但漏掉了收益最大的一项，需要重排：S05d 从“救 a3d53227”改为“准备阶段 unknown 不再阻塞队列”。

## 1. 架构与发布流程

- 业务：React/Next 页面跑在本机 Miniflare/workerd 模拟的薄 Cloudflare Worker；后端 12 个 Django 域，多数分读写服务，共 23 个进程（端口 8001–8112）；PostgreSQL 17 + R2；全部在一台 Windows 主机（`D:\teruisi-runtime`）。
- 发布流程：
  1. 合并 main，Git 钩子生成票，进入串行后台队列（`D:\codex-isolated\main-manual-release-20261016\prebuild-queue-v2`）。
  2. 后台准备：冻结源码，生成 Worker 不可变包（`plan --prepare-online`）及 Django `PrepareApp`，得到 PREPARED。
  3. 用户双击“发布main.bat”：复验前端包、复验后台包、进入维护、部署后台、应用权限、切换前端、退出维护、启动、确认版本。
  4. 成功依据原生 SUCCESS 回执。

## 2. 慢的原因

### 2.1 最大原因：队列频繁被 unknown 卡住

统计 `prebuild-queue-v2/results` 10-18 至 10-22 全部 85 张票：

| 结果 | 张数 | 占比 |
| --- | --- | --- |
| prepared | 19 | 22% |
| blocked | 50 | 59% |
| unknown | 10 | 12% |
| failed / non-production | 6（failed 2、non-production 4） | 7% |

任一 unknown 会拦住后续所有票，直到人工证明安全：00385709 约 10.5 小时、拦 18 张；e786 约 19 小时；a3d53227 自 10-22 15:30 起，检查时仍未解除。

10 张 unknown 中 3 张是确定性前置拒绝，未动生产却记为 unknown：

- “依赖锁已变化，需要先准备对应离线依赖；本次未部署”
- “最新main含新增或改写迁移，尚无对应结构发布包；本次未部署”
- “结构发布材料校验失败：Bound mandatory code checks do not cover these exact installer bytes”

其余多为“本次目标发布未完成，退出码：1”，执行器拿不到结构化终态。准备阶段只写新目录、不碰生产，却与上线阶段 unknown 用同一套严格规则。

### 2.2 第二原因：发布工具改得太频繁

6 天内控制包 30 个版本（`control-bundles` 目录 30 个），配置 sha 变化 4 次；10-21 02:35 有 4 张票因 `incompatible-generation-before-dispatch-v1` 被拦。发布工具与应用同仓同包：51e242da 只改 2 个文件（tests 1、tools 1，`tools/manual-maintenance-continuation.mjs`），仍跑了约 27 分钟完整准备。

### 2.3 第三原因：同批文件被反复全量校验

准备约 28 分钟，其中前端 1455.567 秒，Vinext 编译所在区间 ≤27.340 秒。

发布包源码快照（4059afea）约 3.7 万文件、约 850MB：

| 目录 | 文件数 | 大小 |
| --- | --- | --- |
| node_modules | 31418 | 708.9MB |
| docs | 4999 | 68.7MB |
| tests | 1239 | 31.1MB |
| demos | 106 | 11.2MB |

`tools/worker-local-release.mjs` 有 7 处 `hashTree(` 调用。

51e 前端分项（秒）：源码快照及两次复制 50.957、依赖所在区间 132.862、封包复验 161.589、候选复验 242.007、尾段 384.287（未细分）、首段 339.210（未细分）。

| --- | --- |
| 复验前端 | 282.436 |
| 复验后台 | 63.529 |
| 进入维护 | 207.215 |
| 部署后台 | 57.748 |

正常路径合并到上线约 50 分钟（准备约 28 分钟 + 发布约 20 分钟）；4059 首次尝试到最终成功 65 分钟。

### 2.4 是否架构问题

是，但在发布/部署架构，不在业务架构：

1. 准备与上线共用“unknown 即全局阻塞”规则，而准备本可丢弃重来。
2. 每道关口全量重哈希，而非封存一次、只认封存清单；在 Windows NTFS 大量小文件上代价高。
3. 发布工具与应用同包，工具一改整包重做。

编译与业务拆分不是瓶颈；启动 320 秒与 23 个进程有关，但只占一小部分。

## 3. 施工方案审查

合理处：热点判断准确（校验链而非编译）；同包复用已生效，未重复计收益；蓝绿与预热放最后且为可选；未虚构 ROI。

主要问题：

1. S05c 样本偏差：只统计 10-22 一天 9 张票，得出“1 个 unknown”，低估频率（5 天 10 次），致使 S05d 被写成 a3d53227 个案修复。
2. 依赖链过长：S05d → S05b → S05 → S17；S16 可隔离开发，但上线须等 S05b，而 S05b 要证明 a3d53227 无副作用，本质难证，一卡全停。
3. 缺“终态结构化”：未把前置拒绝由 unknown 改为 failed（确认无生产作用）。
4. 缺“发布工具冻结/与应用解耦”：S08 触及但范围窄。
5. S16 先测后改偏慢，有明显收益的改动可先核实。
