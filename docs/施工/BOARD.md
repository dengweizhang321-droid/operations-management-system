### 准备侧：已确认不可削（结论，不是待办）

2026-10-26 那次真实准备 1455 秒的去向：「前驱完整自校验」五次合计 **609 秒、占 42%**。三个削减方向**全部关闭**：

1. **缓存自校验结果**——不行。`rotation.mjs:1155` 在首段之后**主动释放服务锁**（注释写明不阻塞构建期间的服务恢复），锁释放期间别的进程可改变 worker 状态，所以三次回调是**重新取证**而非重复取证。缓存会掩盖这五次校验本要防的东西。
2. **减少校验次数**——#1 与 #2 之间隔整个构建、都必要；#2 与 #3 窗口最短但只省 96 秒、论证成本更高。
3. **缩小哈希范围**——不行。`node_modules` 全树哈希是该目录完整性的**唯一**证据（`validateTree` 重算全树而非读 manifest），`dist` 仅 187 个文件而 `node_modules` 有 31418 个、`workerd.exe` 在后者内，两者是独立输入。

**609 秒是这套 immutable release 设计的固有成本。** 要降只有两条非「削减」路径：缩小 release 本体（发布架构改动），或换硬件（当前 6–11 MB/s、IOPS 受限，换 NVMe 零代码风险）。

### 发布侧：唯一剩余目标，数据未产出

「切换前端」两次实测 **202 秒**和 **213 秒**，与发布范围无关，整个耗在 `publish-main.mjs` 的单次 `applyApprovedRotationPlan` 调用里。第三步已补上 JSON 回执通道。

**数据何时产出（勿简化为「下一次发布」）**：`apply-timing.json` 在**目标提交包含第三步改动**的那次发布产出。发布执行器每次从**冻结源码**取当次目标提交的字节（`publish-latest-main.mjs` 的 `runPublisher` spawn `path.join(source,'tools/publish-main.mjs')`，`source` 经 `assertFrozenSource` 校验 HEAD/tree/干净度），已观测到冻结源码中该文件字节等于其目标提交。所以不存在「代码已在、通道未生效」的中间态；拿不到回执时应查**运行的是哪个控制代际/目标提交**，而不是怀疑通道需要额外一轮发布。

待确认项：已安装控制目录中存在一份与 `main` 不同的 `publish-main.mjs`（`1e21fde7…` vs `a5a1ea7f…`）。常规发布路径不使用它，但其来源与用途未核实；`publish-main.mjs:13-14` 显示 resume 模式下 `source = knownResume.source` 是另一条路径，是否也该带该改动需核 resume 调用链。

## 已知的门禁稳定性问题（独立待办，不属任何 S 单）

固定验证入口 `verify-release-candidate.mjs` 的 `preparation-queue-control` 这一 check 在本机命中率约四成：C 项三步至今十次门禁、**四次**败在 `tests/main-control-upgrade.test.mjs` 同一处，另有一次 pwsh 别名 EACCES、一次 base 落后。两类形态：

- `:175` `assert.equal(manual.status,1)` 得 `null`——`:43` 的 `cli` 助手 `timeout:20000` 给子进程，而该用例实测耗时 46–91 秒，高负载下真的超
- `:87` `release-root` 子用例 `EPERM: operation not permitted, rename`（errno -4048）——Windows 句柄占用，可能需 retry 或改临时目录策略

同一份已提交字节连跑三次得 35/1、34/2、36/0，非确定性已证。**处理原则：原样重跑，不改超时值、不改测试。** 该问题影响所有后续发布的门禁稳定性，须单独评估、审查、登记。

另一个工具陷阱（已实测，两次踩中）：核差异用 `git -c core.quotepath=false`（否则中文路径被转义，`grep -v "^docs/"` 误判）；核远端用完整 ref `git ls-remote origin refs/heads/main`（否则子串匹配会先命中 `refs/heads/codex/cloud-heads-20261023/main`）。
