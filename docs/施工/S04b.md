> 本单只处理一件事：让「维护前只读检查」能核验 Pi worker 的身份。
> **不改代码、不改配置、不手改任何回执格式**。

## 为什么要这一单

S04 重跑失败（`publish-4059afea8841/preparation/FAILED-54042fa3-….json`）：

```
phase              = 维护前只读检查
maintenanceStarted  = false     ← 维护从未开启，停机 0 分钟
exit                = 1，耗时 1332ms
stderr             = Original Pi process identity is unknown or changed
```

前面六步都已经过了（**包括 S04a 修的那道门，这次 0 秒放行**）：

```
[步骤 1] 准备本次最新main      17 秒（复用已准备包，未重新打包）
[步骤 2] 核对维护前驱资格       0 秒  ← S04a 生效
[步骤 3] 复验已准备前端        286 秒
[步骤 4] 复验已准备后台         65 秒  → {"status":"prepared_verified"}
[步骤 5] 维护前只读检查         ✗ 1332ms 失败
```

根因在 `tools/manual-maintenance-process.psm1:53-60`（`Assert-MaintenanceReadiness`）：
按 `run\django-ai-pi-worker.pid.json` 里记录的 PID 重新 `Get-CimInstance`，
要求 creationDate / executablePath / commandLine **逐字相同**，否则抛错。

**而那份回执已经陈旧：**

| 文件 | mtime | 内容 | 事实 |
|---|---|---|---|
| `django-ai-pi-worker.pid.json` | 2026-10-21 18:59:13 | `processId: 34836` | **该 PID 已不存在（count=0）** |
| `django-ai-pi-worker.control.json` | 2026-10-21 18:59:11 | `intent: "running"` | 与事实矛盾 |
| `django-ai-pi-worker.control.json.stopped` | 2026-10-21 **20:02:37** | `status: "stopped"` | worker 已正常停止 |

**全机没有任何 `python -m ai_assistant.pi_worker` 进程。**

即：worker 在 10-21 20:02:37 被停下（并且是**干净地**写了 `.stopped`），
但 `pid.json` 与 `control.json` 没被清理，于是维护前的身份核验永远失败。

## 步骤 2 · 选择恢复方式（**必须先把结论报给用户，等明确指示**）

两条路，**不得自行选**：

### 方案 A（推荐）：正规重启 Pi worker

- 找到该系统启动 Pi worker 的正规入口（脚本或既有命令），按它的方式启动
- 启动后 `pid.json` / `control.json` 会由 worker 自己刷新
- 再用步骤 1 的方法核验：新 PID 存在、creationDate/commandLine 与回执逐字一致
- **优点**：恢复它本该有的运行态（`control.json` 的 intent 一直是 `running`）
- **风险**：会真的启动一个后台 worker，需要确认它是不是本来就该在跑

#### ⚠ 方案 A 的硬前提：先处理掉旧的 `.stopped` 收据

`backend/ai_assistant/pi_worker.py` 的 `main()` 里，收据是**独占创建**的：

```python
finally:
    stopped.set()
    ...
    if args.control_file:
        done = Path(str(path)+".stopped")
        with done.open("x", encoding="utf-8") as file:   # 'x' = 已存在就抛 FileExistsError
            file.write(json.dumps({... "status": "stopped"}))
```

旧的 `django-ai-pi-worker.control.json.stopped`（10-21 20:02:37）**仍在原位**。
若直接重启，下一次正常关闭时 `open("x")` 会抛 `FileExistsError`，收据机制就坏了。

所以：

1. 先确认**启动入口自己会不会清理 `.stopped`**（读启动脚本，不要假设）
2. 若不会清理：把旧 `.stopped` **复制一份到证据目录**，再把原件**移走**（`-f` 移动到 `…\evidence\`，不删除、不改字节）
3. 再启动

#### 说明：`.stopped` 存在 ≠ "本该停止"

它是在 `finally` 里写的**关闭完成收据**，正常停止 / 未捕获异常退出**都会写**。
只有"线程没能在 5 秒内结束"时才**不写**（改抛 `SystemExit("Pi worker shutdown is unresolved; no stopped receipt was issued")`）。

因此 `.stopped` 在位只证明「关闭过程干净完成」，**不证明**这是操作员授权的停止 ——
`control.json` 的 `intent` 全程是 `running`，正说明**不是**通过控制文件正常关停的。


### 方案 B：清掉陈旧回执

- 只有在结论是"这个 Pi worker 本就不该运行"时才可考虑
- 做法：把 `pid.json` 移到证据目录（**移动而非删除**，字节不动），
  并把 `control.json` 的 `intent` 与 `.stopped` 对齐
- **风险**：这是在抹平运行态证据；必须用户明确授权，且必须在 BOARD 记明原因

**禁止**：用任何一种"改 `manual-maintenance-process.psm1` 让它容忍脏回执"的方式绕过。
那是把门禁改松，属于禁止动作。
